## 一、引言与导读

### 1.1 为什么需要单独一篇"实体创建与迁移"专题

在 BigWorld Engine 14.4.1 中,实体(Entity)是游戏世界的最小逻辑单元。一个玩家角色、一只 NPC、一辆载具、一个可拾取物品,甚至一个不可见的"管理型"实体(如 `SpawnPoint`、`ZoneManager`),都是一个 Entity。与 Unity ECS 或 Unreal Actor 不同,BigWorld 的实体并不是单进程对象,而是**分布式的三方存在**:

- **Base**:位于 BaseApp,持久化数据、跨区协调、客户端通信
- **Cell**:位于 CellApp,空间逻辑、AOI、物理模拟、Ghost 维护
- **Client**:位于客户端进程,渲染、玩家输入

这种三方存在的设计带来了巨大的灵活性,但也带来了巨大的复杂性:
1. 三方创建的**原子性**如何保证?Base 创建成功但 Cell 失败怎么办?
2. 实体的**Mailbox**如何在三方之间寻址?实体迁移后旧 Mailbox 怎么办?
3. 当 CellApp 过载时,如何把 Real 实体**跨进程迁移**到另一台 CellApp?迁移过程中消息会不会丢?
4. 当 BaseApp 即将退役时,如何把所有 Base 实体**offload**到其他 BaseApp?客户端连接如何无缝切换?
5. 服务器启动时,如何**自动加载**数百万持久化实体而不卡死?

这些问题的答案构成了 BigWorld Engine 的实体生命周期子系统,也是本专题的核心内容。本专题将**穷尽细节**地剖析这一子系统,从 Python 脚本接口到 C++ 底层实现,从数据结构到状态机,从正常流程到边界情况,从单组件行为到全集群协作。

## 二、实体三方存在的设计哲学

### 2.1 三方存在的本质

在传统 MMOG 架构中,一个"游戏对象"通常对应一个内存对象,所有逻辑都在同一个进程内运行。这种模型简单直观,但无法横向扩展:

```
传统架构:
┌─────────────────────────────────────┐
│         单一游戏进程                  │
│  ┌──────┐ ┌──────┐ ┌──────┐         │
│  │Player│ │ NPC  │ │ Item │  ...    │
│  └──────┘ └──────┘ └──────┘         │
│  AOI、物理、AI、网络、持久化 全在一起  │
└─────────────────────────────────────┘
```

BigWorld 的设计哲学是:**把一个逻辑实体拆分为三个物理实体**,分别承担不同的职责。三个部分通过 Mailbox 相互通信,呈现给脚本的是一个统一的逻辑实体。

```
                  ┌─────────────────┐
                  │     Client      │
                  │   渲染/输入      │
                  └────────┬────────┘
                           │ (客户端 Mailbox)
                           ▼
┌────────────────┐  ┌─────────────────┐  ┌────────────────┐
│  CellApp       │  │     BaseApp     │  │     DBApp      │
│  Cell Entity   │◄─┤   Base Entity   ├─►│   Database    │
│  AOI/物理/Ghost│  │ 持久化/网络/协调 │  │                │
└────────────────┘  └─────────────────┘  └────────────────┘
   (空间逻辑)         (逻辑控制)            (持久化)
```

### 2.2 三方的职责划分

| 维度 | Base | Cell | Client |
|------|------|------|--------|
| **所在进程** | BaseApp | CellApp | 玩家客户端 |
| **生命周期** | 长期(可持久化) | 跟随 Base,可被 offload | 跟随玩家会话 |
| **属性集** | BASE_DATA | CELL_DATA + GHOST_DATA | CLIENT_DATA |
| **网络位置** | `BaseApp addr` | `CellApp addr` | `client addr` |
| **持久化** | 是(写 DB) | 否(可备份) | 否 |
| **Mailbox 类型** | `BASE` | `CELL` | `CLIENT` |
| **可独立创建** | 是 | 否(必须有 Base) | 否(必须有 Base) |
| **可被 offload** | 是(跨 BaseApp) | 是(跨 CellApp) | 否(随 Base 迁移) |
| **可被销毁** | 是(destroy) | 是(destroyCellEntity) | 是(断开连接) |

### 2.3 三方 Mailbox 引用关系

每个部分都持有一个指向"另一方"的 Mailbox,使得脚本可以透明地调用另一方的方法:

```
   Base 持有:
     ├─ pCellEntityMailBox_  ──► Cell Entity (CellApp)
     └─ pClientMailBox_      ──► Client Entity (仅 Proxy 有)

   Cell Entity 持有:
     ├─ baseAddr_            ──► Base Entity (BaseApp)
     └─ (通过 Witness)       ──► Client Entity

   Client Entity 持有:
     └─ (通过客户端 Mailbox)  ──► Base Entity
```

### 2.4 三方创建的原子性挑战

由于三方位于不同进程,创建过程必然不是原子的。BigWorld 采用**最终一致性**模型:

1. **Base 先创建**:Base 是实体的"根",没有 Base 就没有 Cell
2. **Cell 后创建**:Base 创建成功后,通过 `createCellEntity` 请求 CellApp 创建 Cell
3. **Client 最后创建**:对于玩家实体,Base 在确认 Cell 创建后通知客户端

中间任一环节失败,系统通过**回调**与**超时**进行恢复:
- Cell 创建失败 → `Base.onCreateCellFailure` 回调
- CellApp 死亡 → `Base::restoreTo` 在新 CellApp 重建
- BaseApp 死亡 → Backup 接管,Cell 通过 `onBaseOffloadedForGhost` 更新 `baseAddr_`

### 2.5 与传统 MMOG 实体创建对比

| 特性 | 传统 MMOG | BigWorld |
|------|----------|----------|
| 实体存在位置 | 单进程 | 三方分布式 |
| 创建原子性 | 进程内原子 | 最终一致 |
| 跨区迁移 | 下线/重登 | 透明 offload |
| 玩家感知 | 明显切换 | 无感知 |
| 持久化时机 | 显式调用 | 自动备份 + 归档 |
| 失败恢复 | 全量重启 | Backup 接管 |

## 三、实体创建概述与触发点

### 3.1 创建触发点全景

实体创建不是单一入口,而是多个触发点的集合。每个触发点对应不同的初始化路径:

```
┌──────────────────────────────────────────────────────────────────┐
│                       实体创建触发点                              │
├──────────────────────────────────────────────────────────────────┤
│                                                                  │
│  1. 玩家登录                                                     │
│     LoginApp ─► BaseAppMgr::createEntity ─► BaseApp::createBase │
│                                                                  │
│  2. NPC 自动加载(服务器启动)                                      │
│     DBApp::EntityAutoLoader ─► BaseAppMgr ─► BaseApp            │
│                                                                  │
│  3. 脚本调用 BigWorld.createBase*                                 │
│     Python ─► EntityCreator::createBase{Locally,Remotely,Any...} │
│                                                                  │
│  4. 脚本调用 BigWorld.createBaseFromDB*                          │
│     Python ─► DBApp::loadEntity ─► BaseApp                     │
│                                                                  │
│  5. 脚本调用 BigWorld.createBaseFromTemplate                     │
│     Python ─► EntityCreator::createBaseFromTemplate             │
│                                                                  │
│  6. 故障恢复                                                      │
│     CellApp death ─► Base::restoreTo                            │
│     BaseApp death ─► BackedUpEntities::restore                  │
│                                                                  │
│  7. 客户端创建 cell entity(由 Base 触发)                          │
│     Base::createCellEntity ─► CellAppMgr::createEntity          │
│                                                                  │
└──────────────────────────────────────────────────────────────────┘
```

### 3.2 七大触发点详解

#### 触发点 1:玩家登录

**入口**:`BaseAppMgr::createEntity`(由 DBApp 触发,详见 `server/baseappmgr/baseappmgr.cpp:923`)

玩家登录是最常见的创建场景。流程如下:

```
LoginApp ─► DBApp::lookUpEntity
              └─► DBApp::loadEntity ─► BaseAppMgr::createEntity
                                          └─► 找到最空闲 BaseApp
                                          └─► BaseApp::createBaseWithCellData
                                                └─► EntityCreator::createBaseFromStream
```

**关键代码**(`server/baseappmgr/baseappmgr.cpp:923-985`):

```cpp
void BaseAppMgr::createEntity( const Mercury::Address & srcAddr,
        const Mercury::UnpackedMessageHeader & header,
        BinaryIStream & data )
{
    BaseApp * pBest = baseApps_.findLeastLoadedApp();  // 负载均衡
    if (pBest == NULL) { ... 错误处理 ... }

    bool areBaseAppsOverloaded = (pBest->load() >
                                LoginConditionsConfig::minLoad());
    if (this->calculateOverloaded( areBaseAppsOverloaded )) { ... 拒绝 ... }

    baseAppAddr = pBest->externalAddr();
    CreateBaseReplyHandler * pHandler =
        new CreateBaseReplyHandler( srcAddr, header.replyID, baseAppAddr );

    Mercury::Bundle & bundle = pBest->bundle();
    bundle.startRequest( BaseAppIntInterface::createBaseWithCellData, pHandler );
    bundle.transfer( data, data.remainingLength() );
    pBest->send();

    pBest->addEntity();  // 更新负载估计
}
```

注意 `BaseAppMgr` 用 `findLeastLoadedApp()` 而不是 `findBestCellApp`,这是因为 Base 实体的负载主要看 BaseApp 的整体 CPU 与内存,而非空间分布。

#### 触发点 2:服务器启动时 NPC 自动加载

**入口**:`DBApp::EntityAutoLoader::start`(详见 `server/dbapp/entity_auto_loader.cpp:213`)

服务器启动后,DBApp 会扫描数据库中所有标记为 `AutoLoad=true` 的实体,通过滑动窗口并行加载。这部分将在第 9 章详细剖析。

#### 触发点 3:脚本调用 `BigWorld.createBase*`

**入口**:`EntityCreator::createBase{Locally,Remotely,Anywhere}`(详见 `server/baseapp/entity_creator.cpp`)

Python 脚本可以通过三种方式创建 Base:

| API | 含义 | 决策逻辑 |
|-----|------|---------|
| `BigWorld.createBaseLocally(type, ...)` | 在当前 BaseApp 创建 | 强制本地 |
| `BigWorld.createBaseRemotely(type, dest, ...)` | 在指定 BaseApp 创建 | 显式指定 |
| `BigWorld.createBaseAnywhere(type, ...)` | 系统自动选择 | 看负载 |

`createBaseAnywhere` 的决策逻辑见 `entity_creator.cpp:1451-1455`:

```cpp
bool EntityCreator::shouldCreateLocally() const
{
    return (this->getLoad() < BaseAppConfig::createBaseElsewhereThreshold()) &&
        !BaseApp::instance().isServiceApp();
}
```

- 如果本 BaseApp 负载低于 `createBaseElsewhereThreshold`(默认 0.0,即只要非 0 就转移),则本地创建
- 否则,从 `destinationBaseApps_` 列表(由 BaseAppMgr 周期性下发)中按负载加权随机选一个

#### 触发点 4:从数据库加载实体

**入口**:`EntityCreator::createBaseFromDB`(详见 `entity_creator.cpp:780-870`)

两种重载:
- `createBaseFromDB(entityType, name, callback)`:按名字查找
- `createBaseFromDB(entityType, dbID, callback)`:按数据库 ID 查找

注意:按名字查找要求实体类型有 `Identifier` 字段(通常是 `playerName`),否则报错。

#### 触发点 5:从模板创建

**入口**:`EntityCreator::createBaseLocallyFromTemplate` 等

模板创建是一种优化路径,允许通过预定义的模板 ID 创建实体,避免每次都序列化完整属性字典。模板创建走 `BaseAppIntInterface::createBaseFromTemplate` 消息。

#### 触发点 6:故障恢复

详见第 20 章。两种恢复路径:
- **CellApp 死亡**:`Base::restoreTo` 在新 CellApp 重建 Cell
- **BaseApp 死亡**:`BackedUpEntities::restore` 在 Backup BaseApp 重建 Base

#### 触发点 7:Cell 实体创建(由 Base 触发)

**入口**:`Base::createCellEntity`(`server/baseapp/base.cpp:3321`)

Base 创建后,脚本通过 `Base.createCellEntity()` 显式请求创建对应的 Cell 实体。这是 BigWorld 的一个独特设计——Cell 创建是**显式**的,而不是 Base 创建时自动触发。这给脚本最大的灵活性:
- 某些纯逻辑型 Base(如全局管理器)不需要 Cell
- 玩家可以在创建 Base 后先做一些初始化,再创建 Cell

### 4.2 5 种创建路径

EntityCreator 提供了 5 类创建路径,每类有 Local/Remote/Anywhere 三个变体:

| 路径 | Local | Remote | Anywhere |
|------|-------|--------|----------|
| **从字典创建** | `createBaseLocally` | `createBaseRemotely` | `createBaseAnywhere` |
| **从模板创建** | `createBaseLocallyFromTemplate` | `createBaseRemotelyFromTemplate` | `createBaseAnywhereFromTemplate` |
| **从 DB 创建** | `createBaseFromDB` | `createRemoteBaseFromDB` | (内部根据 shouldCreateLocally 决定) |

### 4.3 IDClient:实体 ID 分配器

每个 BaseApp 都有一个 `IDClient` 实例(通过 `idClient_` 成员),负责从 DBApp 批量获取实体 ID。这是一个**分层 ID 池**设计:

```
              DBApp(全局 ID 池)
                  │
                  │ getIDs(n) / putIDs(n)
                  ▼
       BaseApp::idClient_(本地 ID 池)
            ├─ readyIDs_   (可用 ID 队列)
            ├─ lockedIDs_  (待回收 ID 队列)
            └─ pendingRequest_ (是否已发送请求)
                  │
                  │ getID() / putUsedID()
                  ▼
              实体创建/销毁
```

#### 4.3.1 IDClient 数据结构

`IDClient` 的核心数据结构(`lib/server/id_client.hpp:40-99`):

```cpp
class IDClient : private Mercury::ShutdownSafeReplyMessageHandler
{
protected:
    typedef std::queue<EntityID> IDQueue;
    IDQueue readyIDs_;        // 可立即分配的 ID
private:
    struct LockedID
    {
        LockedID( EntityID id );
        uint64 unlockTime_;   // 解锁时间戳
        EntityID id_;

    Mercury::ChannelOwner * pChannelOwner_;
    size_t highSize_;        // 超过此数量则返还给父节点
    size_t desiredSize_;     // 期望持有的数量
    size_t lowSize_;         // 低于此数量则请求更多
    size_t criticallyLowSize_;  // 紧急阈值
    bool pendingRequest_;    // 是否已发送 getMoreIDs 请求
    bool inEmergency_;        // 是否处于紧急模式
};
```

#### 4.3.2 ID 分配算法

`getID()` 算法(`lib/server/id_client.cpp:117-135`):

```cpp
EntityID IDClient::getID()
{
    if (readyIDs_.empty())
    {
        this->performUpdates( true );  // 紧急请求
        if (readyIDs_.empty())
        {
            ERROR_MSG("IDClient::getID: no id's left (really bad)\n");
            return 0;  // 无法分配
        }
    }
    EntityID id = readyIDs_.front();
    readyIDs_.pop();
    this->performUpdates( false );
    return id;
```

`performUpdates()` 是核心维护逻辑(`id_client.cpp:165-221`):

```cpp
void IDClient::performUpdates( bool isEmergency )
{
    isEmergency = isEmergency || readyIDs_.size() < criticallyLowSize_;

    // 紧急情况下,自动扩大池子大小
    if (isEmergency && !inEmergency_)
    {
        if (desiredSize_ < MAX_AUTO_INCREMENT_DESIRED_SIZE/2)
        {
            highSize_ *= 2;
            desiredSize_ *= 2;
            lowSize_ *= 2;
        }
        else { ... 达到上限警告 ... }
        inEmergency_ = true;
    }

    // 解锁已到期的 ID
    while (lockedIDs_.size() &&
            (lockedIDs_.front().unlockTime_ < now || isEmergency))
    {
        readyIDs_.push( lockedIDs_.front().id_ );
        lockedIDs_.pop();
    }

    // 池子太多,归还一些
    if (readyIDs_.size() > highSize_ && !inEmergency_)
        this->putBackIDs();
    // 池子太少,请求更多
    else if (((readyIDs_.size() <= lowSize_) || inEmergency_) &&
            !pendingRequest_)
    {
        this->getMoreIDs();
    }
}
```

#### 4.3.3 ID 回收的"锁定"机制

注意 `LockedID` 的 `unlockTime_` 默认是 `timestamp() + 10 * stampsPerSecond()`,即 10 秒后才解锁。这是为了防止 ID 重用导致的问题:

```cpp
IDClient::LockedID::LockedID( EntityID id )
{
    id_ = id;
    unlockTime_ = timestamp() + uint64(10) * stampsPerSecond();
}
```

**为什么需要锁定?** 考虑以下场景:
1. 实体 #100 被销毁,ID 100 回收到池
2. 立即创建新实体,分配到 ID 100
3. 网络中还有发给"旧 #100"的消息延迟到达
4. 新 #100 错误地处理了这些消息

10 秒的锁定窗口足以让绝大多数延迟消息到达并丢弃。

#### 4.3.4 ID 回收开关

注意 `id_client.cpp:101-110`:

```cpp

{
```

`MF_ID_RECYCLING` 宏默认**未定义**,意味着 ID 回收在默认配置下是关闭的!这是因为:
- 回收可能导致 ID 重用问题
- 数据库的自增 ID 不会回退,但实体 ID 是另一回事
- 系统保守地选择"用完即弃"

如果开启,系统会回收 ID。但如果某处保留了已销毁实体的引用,可能会"复活"它。所以官方注释:

### 4.5 加权随机的目标选择

当 `shouldCreateLocally()` 返回 false 时,EntityCreator 调用 `getAddressFromDestinationBaseApps()` 选择目标。这是一个**反向加权随机**算法(`entity_creator.cpp:1463-1512`):

```cpp
const Mercury::Address & EntityCreator::getAddressFromDestinationBaseApps()
{
    if (destinationBaseApps_.empty())
        return intInterface_.address();  // 退化为本地

    double totalWeight = 0;
    double maxLoad = 0;

    // 第一步:找出最大负载,计算总负载
    for (auto & entry : destinationBaseApps_)
    {
        if (entry.load_ > maxLoad) maxLoad = entry.load_;
        totalWeight += entry.load_;
    }
    maxLoad += 0.01;  // 避免零权重
    // 关键:权重 = (maxLoad - load_),负载越低权重越高
    totalWeight = maxLoad * destinationBaseApps_.size() - totalWeight;

    double randPick = ((double)rand() / (double)RAND_MAX) * totalWeight;
    double curr = 0;

    for (auto & entry : destinationBaseApps_)
    {
        curr += maxLoad - entry.load_;
        if (curr >= randPick)
        {
            entry.load_ += 0.01;  // 微调,避免连续选中同一个
            return entry.addr_;
        }
    }
    // 兜底:随机选一个
    int randIndex = rand() % destinationBaseApps_.size();
    return destinationBaseApps_[ randIndex ].addr_;
}
```

#### 4.5.1 算法分析

设 N 个 BaseApp,负载为 $L_1, L_2, ..., L_N$,最大负载 $L_{max} = \max(L_i)$。

每个 BaseApp 的权重为 $w_i = L_{max} - L_i + 0.01$。

- 负载最低的 BaseApp 权重最高(约 $L_{max} - L_{min}$)
- 负载最高的 BaseApp 权重最低(0.01)
- 总权重 $W = N \cdot L_{max} - \sum L_i + 0.01N$

每次选中后,把目标 BaseApp 的 `load_` 增加 0.01,实现"软粘性"——避免短时间内连续选中同一个。

#### 4.5.2 算法局限

1. **本地负载信息滞后**:`destinationBaseApps_` 中的 load 是 BaseAppMgr 周期下发的快照,不是实时的
2. **无历史感知**:算法不记录"上次选了谁",只通过 load_ += 0.01 实现弱粘性
3. **负载估计粗糙**:只用 CPU load,不考虑实体数量、内存占用等

## 五、Base 实体创建流程详解

### 5.1 createBase 内部实现

无论从哪个入口,最终都会调用 `EntityCreator::createBase`(`entity_creator.cpp:272-297`):

```cpp
PyObject * EntityCreator::createBase( EntityType * pType,
    PyObject * pDict, PyObject * pCellData ) const
{
    EntityID id = const_cast< IDClient & >( idClient_ ).getID();

    if (id == 0)
    {
        ERROR_MSG( "EntityCreator::createBase: Unable to allocate id.\n" );
        PyErr_SetString( PyExc_RuntimeError, "Unable to allocate id" );
        return NULL;
    }

    Base * pNewBase = pType->newEntityBase( id, DatabaseID(0) );

    if (pNewBase)
    {
        // We increment before calling init() as init() may release a reference
        // if the object self-destroys in script __init__()
        Py_INCREF( pNewBase );

        pNewBase->init( pDict, pCellData, NULL );
    }

    return pNewBase;
}
```

注意几个细节:
1. **ID 先于对象分配**:先获取 ID,再创建对象,这保证 ID 一定不会重复
2. **Py_INCREF 在 init 之前**:`init()` 可能调用脚本的 `__init__()`,如果脚本中自杀,引用计数会归零导致 use-after-free。提前 INCREF 是防御性编程
3. **`pCellData` 是 PyCellData 对象**:包含 `position`、`direction`、`spaceID`,这些信息会传给 Cell 创建流程

### 5.4 createBaseWithCellData:消息接收端

`createBaseWithCellData`(`entity_creator.cpp:1120-1179`)是 BaseApp 接收 `createBase` 请求的入口。它不仅创建 Base,还处理 proxy 的登录流程:

```cpp
    BasePtr pBase = this->createBaseFromStream( data, &clientAddr, &encryptionKey );

        return;

    // 成功,返回 base mailbox
    ref = pBase->baseEntityMailBoxRef();
    sender.bundle() << ref;

    // 如果是 proxy 且有 client 地址,准备登录
    if (pBase->isProxy() && clientAddr != Mercury::Address::NONE)
    {
        Proxy * pProxy = (Proxy*)pBase.get();
        SessionKey loginKey = pProxy->prepareForLogin( clientAddr );
        sender.bundle() << loginKey;

        if (!encryptionKey.empty())
            pProxy->encryptionKey( encryptionKey );
    }
}
```

### 6.2 三种创建路径

`sendCreateCellEntityToMailBox`(`base.cpp:3428-3458`)根据 nearby mailbox 的类型分发:

```cpp
bool Base::sendCreateCellEntityToMailBox(
    Mercury::ReplyMessageHandler * pHandler,
    const ServerEntityMailBox & mailBox,
    const char * errorPrefix )
{
    EntityMailBoxRef::Component component = mailBox.component();

    if ((component == EntityMailBoxRef::CELL) ||
            (component == EntityMailBoxRef::BASE_VIA_CELL))
    {
        // 路径 1:直接发给 Cell
        if (!this->sendCreateCellEntity( pHandler, mailBox.id(),
                mailBox.address(), errorPrefix ))
            return false;

    else if ((component == EntityMailBoxRef::BASE) ||
            (component == EntityMailBoxRef::CELL_VIA_BASE))

                mailBox.address(), errorPrefix ))
            return false;

    else
    {
        PyErr_Format( PyExc_TypeError, "%sCannot use a %s mailbox",
            errorPrefix, mailBox.componentName() );
        return false;
    }
    return true;
}
```

`Cell::createEntityInternal`(`server/cellapp/cell.cpp:292-393`)是 Cell 实体真正被创建的地方:

```cpp
EntityPtr Cell::createEntityInternal( BinaryIStream & data,
    const ScriptDict & properties,
    bool isRestore, Mercury::ChannelVersion channelVersion,
    EntityPtr pNearbyEntity )
{
    AUTO_SCOPED_PROFILE( "createEntity" );

    EntityID id;
    EntityTypeID entityTypeID;
    data >> id >> entityTypeID;

    // ID 为 0 时本地分配
    bool shouldAllocateID = (id == 0);
    if (shouldAllocateID)
    {
        id = CellApp::instance().idClient().getID();
        if (id == 0) { ERROR_MSG( "No free IDs!\n" ); return NULL; }
    }

    // 检查实体是否已存在
    EntityPopulation::const_iterator found = Entity::population().find( id );
    if (found != Entity::population().end() && !found->second->isDestroyed())
    {
        EntityPtr pExisting = found->second;

        // 如果是 restore 且存在 zombie ghost,先杀掉
        if (!pExisting->isReal() && isRestore)
        {
            WARNING_MSG( "Destroying zombie ghost %u ...\n", pExisting->id() );
            while (!pExisting->isDestroyed())
                pExisting->destroyZombie();
        }
        else
        {
            WARNING_MSG( "%s %u already exists!\n", ... );
            MF_ASSERT( !isRestore );
            data.finish();
            return found->second;
        }
    }

    // 创建 Entity 对象
    EntityPtr pNewEntity = space_.newEntity( id, entityTypeID );
    if (!pNewEntity) return NULL;

    Entity::callbacksPermitted( false );

    // 初始化 Real 部分
    if (!pNewEntity->initReal( data, properties, isRestore, channelVersion,
                pNearbyEntity ))
    {
        pNewEntity->setShouldReturnID( shouldAllocateID );
        pNewEntity->decRef();
        Entity::callbacksPermitted( true );
        return NULL;
    }

    // 加入 realEntities_ 列表
    // 注意 shouldSendNow=false,延迟发送 currentCell 消息,
    // 与 backup 数据一起发送,确保无窗口期
    this->addRealEntity( pNewEntity.get(), /*shouldSendNow:*/false );

    Entity::callbacksPermitted( true );

    // 触发 onEnteredCell 脚本回调
    pNewEntity->callback( "onEnteredCell" );

    return pNewEntity;
}
```

### 6.7 shouldSendNow 的设计意图

注意 `addRealEntity` 中 `shouldSendNow=false` 的设计意图(`cell.cpp:393` 的注释):

```cpp
// Delay sending the currentCell message to the base so that it will be on
// the same bundle as the backup. This guarantees that there is no window
// between losing cellData and getting the first backup data.
this->addRealEntity( pNewEntity.get(), /*shouldSendNow:*/false );
```

如果立即发送 `currentCell`,而 backup 数据晚一点才到,会有一个**窗口期**:
- Base 已知道新 Cell 的地址,但还没有 backup 数据
- 此时如果 Cell 立刻崩溃,Base 没法 restore

延迟发送让 `currentCell` 与第一条 backup 数据捆在同一 bundle,保证原子性。

## 七、Client 实体创建流程详解

### 7.1 Client 实体的特殊性

Client 实体是玩家客户端进程中的实体对象。它的特殊性在于:
1. **不在服务器集群中**:跨互联网,网络延迟大、可能丢包
2. **不可信**:客户端可能被篡改,服务器不能信任客户端状态
3. **跟随玩家会话**:玩家断线即销毁
4. **只有 Proxy 类型才有 Client 实体**:NPC 没有 Client

### 7.2 Client 实体的创建时机

Client 实体的创建不是 Base 创建时立即触发的,而是经过几个阶段:

```
1. 玩家登录到 LoginApp
2. LoginApp 鉴权,转发到 BaseAppMgr
3. BaseAppMgr 选择 BaseApp,触发 createBaseWithCellData
4. BaseApp 创建 Proxy Base
5. Proxy 调用 prepareForLogin(clientAddr)
6. 客户端拿到 loginKey,直接连接 BaseApp
7. BaseApp::acceptClient 处理客户端连接
8. Proxy 创建 Cell Entity
9. 客户端开始接收实体创建消息
```

### 7.3 prepareForLogin

`Proxy::prepareForLogin` 在 `createBaseWithCellData` 中被调用(`entity_creator.cpp:1168-1178`):

```cpp

{

    SessionKey loginKey = pProxy->prepareForLogin( clientAddr );
    sender.bundle() << loginKey;

        pProxy->encryptionKey( encryptionKey );
```

`prepareForLogin` 做的事:
1. 记录客户端地址
2. 生成一个 `SessionKey`(随机数)
3. 把 key 与 clientAddr 关联,存入 `LoginHandler`
4. 客户端用这个 key 来连接 BaseApp

### 7.4 客户端连接 acceptClient

客户端拿到 `loginKey` 后,通过 `BaseAppExtInterface::baseAppLogin` 消息连接 BaseApp。BaseApp 收到后调用 `acceptClient`(`baseapp.cpp:2148-2173`):

```cpp
void BaseApp::acceptClient( const Mercury::Address & srcAddr, ... )
{
    EntityID entityID;
    data >> entityID;

    Base * pBase = bases_.findEntity( entityID );
    if (!pBase || !pBase->isProxy())
    {
        NOTICE_MSG( "BaseApp::acceptClient: called for proxy %d that doesn't exist", entityID );
        data.finish();
        // 回复失败
        Mercury::UDPChannel & channel = BaseApp::getChannel( srcAddr );
        Mercury::Bundle & bundle = channel.bundle();
        bundle.startReply( header.replyID );
        bundle << false;
        channel.send();
    }
    else
    {
        static_cast< Proxy * >( pBase )->acceptClient( srcAddr, header, data );
    }
}
```

`Proxy::acceptClient` 完成:
1. 验证 `loginKey`
2. 创建客户端 Mailbox
3. 建立实体通道(Entity Channel)
4. 触发 `Proxy.onLogOn` 脚本回调

### 7.5 Client 实体的初始化

Client 实体在客户端进程中被 `BigWorld.player()` 触发创建。客户端通过 entity channel 接收:
- 实体创建消息(包含初始属性)
- 属性更新消息(volatile 与 non-volatile)
- 方法调用消息

详细机制超出本专题范围,可参考 Mercury 网络协议(专题7)与 AOI/Witness(专题6)。

### 8.2 失败回滚机制

BigWorld 的三方创建**没有跨进程事务**,而是通过以下机制实现最终一致性:

#### 8.2.1 Base 创建失败

如果 `createBaseFromStream` 失败(如 ID 冲突、类型无效),返回空 ref。`createBaseWithCellData` 把空 ref 回复给调用方。调用方知道失败,可以重试。

#### 8.2.2 Cell 创建失败

如果 `Cell::createEntityInternal` 失败,CellAppMgr 通过 `CreateEntityReplyHandler` 把失败传回。Base 端 `CreateCellEntityHandler::handleMessage`(`create_cell_entity_handler.cpp:31-55`)处理:

```cpp

{

    data >> entityID;

    if (entityID == pBase_->id())
    {
        pBase_->cellCreationResult( true );
    }
    else
    {
        WARNING_MSG( "Failed to create associated cell entity for %u.\n"
                "\tResponse was entity id %u\n", pBase_->id(), entityID );
        pBase_->cellCreationResult( false );
    }
    delete this;
}
```

`cellCreationResult(false)`(`base.cpp:3750-3783`)触发 `onCreateCellFailure` 脚本回调,脚本可以选择重试或销毁 Base:

```cpp
void Base::cellCreationResult( bool success )
{
    if (isDestroyed_) return;

    if (!isCreateCellPending_) { ... 异常情况 ... return; }

    isCreateCellPending_ = false;

    if (!success)
    {
        isGetCellPending_ = false;
        Script::call( PyObject_GetAttrString( this, "onCreateCellFailure" ),
                PyTuple_New( 0 ), "onCreateCellFailure", true );
    }
}
```

#### 8.2.3 网络异常

如果 `createCellEntity` 请求在网络上丢失(罕见,因为 Mercury 用可靠通道),`Mercury::NubException` 会被 `CreateCellEntityHandler::handleException` 处理:

```cpp

        const Mercury::NubException & exception, void * arg )
{
    ERROR_MSG( "Failed to create associated cell entity for %u.\n"
            "\tNub exception was %s\n",
        pBase_->id(), Mercury::reasonToString( exception.reason() ) );

    pBase_->cellCreationResult( false );
    delete this;
}
```

注意这个 handler 是 `ShutdownSafeReplyMessageHandler`,意味着即使 BaseApp 正在关闭,也能正确处理(避免泄漏)。

### 8.3 创建的幂等性

BigWorld 在创建流程中嵌入了**幂等性检查**:

1. **ID 冲突检测**(`createBaseFromStream` 中的 `findEntity` 检查)
2. **已存在实体检测**(`createEntityInternal` 中的 `population().find` 检查)
3. **重复销毁检测**(`inDestroy_` 标志)

这些检查防止网络重传导致的重复创建。

## 九、EntityAutoLoader 自动加载机制

### 9.1 设计目标

服务器启动时,需要把所有标记为 `AutoLoad=true` 的持久化实体从数据库加载到 BaseApp。这通常包括:
- 全局管理实体(如 `WorldManager`)
- 重要 NPC(如 `Banker`、`QuestGiver`)
- 静态场景实体(如 `Door`、`Chest`)

如果有数百万这样的实体,**串行加载**会耗时数小时;**全部并行加载**又会瞬间打爆 DBApp 与 BaseApp。`EntityAutoLoader` 采用**滑动窗口**机制平衡两者。

### 9.2 EntityAutoLoader 类

`server/dbapp/entity_auto_loader.hpp:16-43`:


### 9.3 滑动窗口算法

`maxOutstanding_` 由 `DBAppConfig::maxConcurrentEntityLoaders()` 控制,默认 5(`server/dbapp/dbapp_config.cpp:22`):


`start()` 启动 `maxOutstanding_` 个并发加载(`entity_auto_loader.cpp:213-227`):


每个加载请求由 `AutoLoadingEntityHandler` 处理,它是一个状态机(`entity_auto_loader.cpp:55-67`):

```
    │   │
    │   ▼

    │   ▼

    │   ▼
```

### 9.5 与 BaseAppMgr 协作

### 9.6 setBaseEntityLocation 的作用

`setBaseEntityLocation` 是 DBApp 维护"实体当前在哪个 BaseApp 上"的元数据。三阶段状态:
1. **StateInit**:实体在 DB 中
2. **LoggingOn**:实体正在被加载,即将"上线"
3. **Final**:实体已成功在某个 BaseApp 上

这个状态机防止了:
- 多个 DBApp 并发加载同一个实体(通过 LoggingOn 锁)
- 实体加载失败后状态不一致(通过 Final 阶段确认)

## 十一、实体迁移概述

### 11.1 为什么需要迁移

实体迁移(Migration)是 BigWorld 区别于其他 MMOG 引擎的核心特性之一。它指的是:在不销毁实体、不重连客户端的前提下,把实体从一个进程迁移到另一个进程。

迁移的两大动因:

#### 11.1.1 负载均衡

```
       CellApp A (load=0.9)            CellApp B (load=0.2)
       ┌──────────────────┐            ┌──────────────────┐
       │ Real: Player1     │            │                  │
       │ Real: Player2     │            │                  │
       │ Real: Player3     │   迁移     │                  │
       │ Real: NPC1        │ ────────► │                  │
       │ Real: NPC2        │            │ Real: Player3    │
       └──────────────────┘            │ Real: NPC1        │
                                       │ Real: NPC2        │
                                       └──────────────────┘
       (迁移后:load=0.4)                (迁移后:load=0.7)
```

#### 11.1.2 跨区域移动

当实体物理移动跨越 Cell 边界时,需要把 Real 迁移到目标 Cell 所在的 CellApp,以保持权威性:

```
       Cell A (CellApp 1)              Cell B (CellApp 2)
       ┌────────┬──────────┐          ┌──────────┬────────┐
       │        │          │          │          │        │
       │   *P   │          │          │          │        │
       │        │          │          │          │        │
       └────────┴──────────┘          └──────────┴────────┘
                │
                │ Player P 移动
                ▼
       ┌────────┬──────────┐          ┌──────────┬────────┐
       │        │          │          │          │        │
       │        │          │          │     *P   │        │
       │        │          │          │          │        │
       └────────┴──────────┘          └──────────┴────────┘
                                        ▲
                                        │
                                  Real 迁移到 CellApp 2
```

### 11.2 迁移的类型

BigWorld 的迁移分为三个层次:

| 类型 | 名称 | 跨越 | 触发 | 频率 |
|------|------|------|------|------|
| **Cell 内迁移** | Offload | CellApp 内 Cell 间 | OffloadChecker 周期触发 | 高频 |
| **跨 CellApp 迁移** | Offload | CellApp 间 | CellAppMgr 决策 + 实体移动 | 中频 |
| **跨 BaseApp 迁移** | Retirement Offload | BaseApp 间 | BaseApp 退役 | 低频 |

### 11.3 迁移的核心挑战

1. **状态保持**:实体的所有属性、控制器、AOI 状态必须完整转移
2. **消息顺序**:迁移过程中消息不能丢失,也不能乱序
3. **Mailbox 重定向**:迁移后,持有该实体 Mailbox 的所有方都要更新地址
4. **客户端透明**:玩家不应感知到迁移
5. **Haunt 通道**:Real 的所有 Ghost 都通过 Haunt 通道与 Real 通信,迁移时需要更新
6. **原子性**:迁移过程中的任一阶段失败,系统必须能恢复

### 11.4 迁移涉及的子系统

迁移是 BigWorld 中最复杂的操作之一,涉及:

- **Ghost 同步系统**(专题1):Real/Ghost 切换
- **Mailbox 系统**(专题5):地址重定向
- **负载均衡系统**(专题2):触发决策
- **Mercury 网络**(专题7):通道版本、消息路由
- **AOI/Witness**(专题6):视野切换
- **Backup 系统**(专题3):状态保存

## 十二、Cell 内迁移(同 CellApp 跨 Cell)

### 12.1 触发场景

同一个 CellApp 上可能承载多个 Cell(同一 Space 的不同区域,或不同 Space 的 Cell)。当实体物理移动跨 Cell 边界时,需要把 Real 从一个 Cell 迁移到另一个 Cell。

注意:这种迁移**不会跨进程**,但会涉及 Real/Ghost 角色转换。

### 12.2 与跨 CellApp 迁移的关系

Cell 内迁移实际上是跨 CellApp 迁移的简化版本。在 `Cell::offloadEntity`(`cell.cpp:183-217`)中,无论是 Cell 内还是跨 CellApp,都走相同的代码路径:

```cpp
void Cell::offloadEntity( Entity * pEntity, CellAppChannel * pChannel,
   bool isTeleport )
{
    AUTO_SCOPED_PROFILE( "offloadEntity" );
    SCOPED_PROFILE( TRANSIENT_LOAD_PROFILE );

    MF_ASSERT( pEntity->pReal() != NULL );

    EntityPtr pCopy = pEntity;  // 防止零引用计数

    if (!isTeleport)
    {
        pEntity->callback( "onLeavingCell" );
    }

    if (pEntity->isReal())
    {
        if (pReplayData_ && isTeleport)
            pReplayData_->deleteEntity( pEntity->id() );

        realEntities_.remove( pEntity );
        pEntity->offload( pChannel, isTeleport );
        pEntity->callback( "onLeftCell" );
    }
}
```

`pChannel` 是 `CellAppChannel`,既可能指向本 CellApp 的另一个 Cell(同一 CellApp 内迁移),也可能指向另一个 CellApp。从代码角度看,两者完全相同——因为目标都是"通过通道发送 onload 消息"。

### 12.3 Cell 内迁移的特殊性

虽然代码路径相同,Cell 内迁移有一些隐含的优势:
1. **网络零开销**:消息在本进程内传递,不经过网络
2. **无 Mailbox 重定向**:Base 仍指向同一个 CellApp,只是 Cell 不同
3. **无 Haunt 通道重建**:同进程内,Ghost 之间的 haunt 通道不变

但 Real/Ghost 切换仍然发生,因为不同 Cell 的 Real 必须是唯一的。

### 13.2 run() 主循环

```cpp
void OffloadChecker::run()
{
    // 空间正在关闭,不迁移
    if (cell_.space().isShuttingDown())
        return;

    static ProfileVal localProfile( "boundaryCheck" );
    START_PROFILE( localProfile );

    // 遍历所有 Real 实体
    Cell::Entities::iterator iEntity = cell_.realEntities().begin();
    while (iEntity != cell_.realEntities().end())
    {
        EntityPtr pEntity = *iEntity;
        MF_ASSERT( &cell_ == &(pEntity->cell()) );

        // EntityGhostMaintainer 同时处理两件事:
        // 1. 检查实体是否跨过 Cell 边界,需要 offload
        // 2. 检查附近的 Cell 是否需要 Ghost
        EntityGhostMaintainer entityGhostMaintainer( *this, pEntity );
        entityGhostMaintainer.check();
        ++iEntity;
    }

    this->sendOffloads();  // 发送所有待 offload 的实体

    STOP_PROFILE_WITH_DATA( localProfile, offloadList_.size() );
}
```

### 13.7 convertRealToGhost:Real → Ghost 转换

`convertRealToGhost`(`entity.cpp:2005-2061`)是 Real/Ghost 切换的关键:

```cpp
void Entity::convertRealToGhost( BinaryOStream * pStream,
        CellAppChannel * pChannel, bool isTeleport )
{
    MF_ASSERT( this->isReal() );
    MF_ASSERT( !pRealChannel_ );

    Entity::callbacksPermitted( false );

    // 1. 先把 Witness 数据刷给客户端
    Witness * pWitness = this->pReal()->pWitness();
    if (pWitness != NULL)
        pWitness->flushToClient();

    if (pChannel != NULL)
    {
        // 2. 把 Real 数据写入流(发往目标 CellApp)
        MF_ASSERT( pStream != NULL );
        this->writeRealDataToStream( *pStream, isTeleport );

        // 3. 设置 RealChannel 指向新 Real
        pRealChannel_ = pChannel;

        // 4. 通知 Haunts:Real 的新地址
        // 一旦目标 CellApp 创建 Real,它会发送 ghostSetReal 回来,
        // 我们要准备好接收
        nextRealAddr_ = pRealChannel_->addr();

        // 5. 销毁本地的 Real 部分(通知 Haunts 新地址)
        this->offloadReal();
    }
    else
    {
        // 实体被销毁
        this->destroyReal();
    }
    MF_ASSERT( !this->isReal() );

    // 6. 删除 Real-only 的属性(Ghost 不需要的)
    MF_ASSERT( properties_.size() == pEntityType_->propCountGhostPlusReal() );
    for (uint i = pEntityType_->propCountGhost(); i < properties_.size(); ++i)
    {
        if (properties_[i])
            pEntityType_->propIndex(i)->dataType()->detach( properties_[i] );
    }
    properties_.erase( properties_.begin() + pEntityType_->propCountGhost(),
        properties_.end() );

    this->relocated();

    Entity::callbacksPermitted( true );
}
```

### 13.9 onload:目标 CellApp 接收

目标 CellApp 收到 `CellAppInterface::onload` 消息,调用 `Entity::onload`(`entity.cpp:4560-4640`):

```cpp
void Entity::onload( const Mercury::Address & srcAddr,
        const Mercury::UnpackedMessageHeader & header,
        BinaryIStream & data )
{
    static ProfileVal localProfile( "onloadEntity" );
    SCOPED_PROFILE( TRANSIENT_LOAD_PROFILE );
    START_PROFILE( localProfile );

    bool teleportFailure = false;
    data >> teleportFailure;

    int dataSize = data.remainingLength();

    MF_ASSERT( !this->isReal() );  // 接收端必须是 Ghost

    this->callback( "onEnteringCell" );

    this->convertGhostToReal( data, teleportFailure ? &srcAddr : NULL );

    STOP_PROFILE( localProfile );

    // 性能告警
    uint64 duration = localProfile.lastTime();
    if (duration > g_profileOnloadTimeLevel)
        outputEntityPerfWarning( "Profile onload/timeWarningLevel exceeded",
                *this, stampsToSeconds( duration ), dataSize );
    else if (dataSize > g_profileOnloadSizeLevel)
        outputEntityPerfWarning( "Profile onload/sizeWarningLevel exceeded",
                *this, stampsToSeconds( duration ), dataSize );

    if (teleportFailure)
    {
        // teleport 失败,清理失败的 haunt
        RealEntity::Haunts::iterator iHaunt = pReal_->hauntsBegin();
        while (iHaunt != pReal_->hauntsEnd())
        {
            if (iHaunt->channel().addr() == srcAddr)
            {
                pReal_->delHaunt( iHaunt );
                break;
            }
            ++iHaunt;
        }

        if (this->cell().pReplayData())
            this->cell().pReplayData()->addEntityState( *this );

        this->callback( "onTeleportFailure" );
    }
}
```

### 13.10 convertGhostToReal:Ghost → Real 转换

`convertGhostToReal`(`entity.cpp:4657-4703`)是 onload 的核心:


### 13.11 迁移过程的 Mailbox 更新

迁移过程中,Mailbox 的更新分两部分:

#### 13.11.1 Base 端的更新

`Cell::addRealEntity` 调用 `Entity::informBaseOfAddress`,发送 `currentCell` 消息给 Base,告知新 Cell 的地址。Base 收到后调用 `setCurrentCell`,更新 `pCellEntityMailBox_`。

#### 13.11.2 Ghost 端的更新

旧的 Real(已变 Ghost)的 `pRealChannel_` 指向新 Real。所有发给这个 Ghost 的 Real-bound 消息会自动转发到新 Real。

新 Real 创建后,会发送 `ghostSetReal` 消息回旧 CellApp,通知"我已经是 Real 了"。这是为了处理可能的"双 Real"问题。

### 13.12 迁移的原子性保证

迁移过程中的原子性通过以下机制保证:

1. **Real 数据完整序列化**:`writeRealDataToStream` 写入所有 Real 属性、控制器、witness 状态
2. **通道版本同步**:Base 在 `sendCreateCellEntity` 中传递 `channel().version()`,新 Real 用这个版本号继续接收消息
3. **Haunt 通道保持**:旧 Real 的所有 Haunt 在 `offloadReal` 中被通知 `nextRealAddr_`,它们直接指向新 Real
4. **Ghost 缓冲消息**(详见专题1):在 Real/Ghost 切换瞬间,到达的消息被缓冲,切换完成后回放

### 13.13 客户端透明性

迁移对客户端完全透明:
1. 客户端只与 Base 通信(通过 entity channel)
2. Base 的 `pCellEntityMailBox_` 指向新 CellApp,但客户端不知道
3. Cell 内部的事(空间逻辑、AOI)对客户端不可见
4. Witness 在迁移前 `flushToClient()`,确保客户端状态一致

## 十四、跨 BaseApp 迁移(retirement offload)

### 14.1 Retirement 触发场景

BaseApp **退役(retirement)**是 BigWorld 的运维特性,允许在不停止服务的情况下移除一个 BaseApp。触发场景:
1. 运维需要重启 BaseApp(更新代码、修复 bug)
2. 节点缩容(减少 BaseApp 数量)
3. 节点故障前主动退役

### 14.2 Retirement 流程概述

```
1. BaseAppMgr 发送 requestRetirement 给目标 BaseApp
2. BaseApp::requestRetirement()
   - 标记 isRetiring_ = true
   - 记录 retireStartTime_
3. BaseAppMgr 通知所有 BaseApp:这个 BaseApp 即将退役
4. BaseAppMgr 等待 backup hash 切换确认
5. 目标 BaseApp 调用 startOffloading()
   - 销毁本地 Service Fragments
   - 开始把所有 Base offload 到其他 BaseApp
6. BackupSender::tick() 周期性 offload
   - 每个 tick offload 一批
   - 等待客户端连接(对于 proxy)
7. 所有 Base offload 完成后,BaseApp 退出
```

### 14.5 BackupSender::tick 的 offload 逻辑

`BackupSender::tick`(`backup_sender.cpp:98-182`)在每个 tick 处理 offload:

```cpp
void BackupSender::tick( const Bases & bases,
                         Mercury::NetworkInterface & networkInterface )
{
    int periodInTicks = BaseAppConfig::backupPeriodInTicks();
    if (periodInTicks == 0) return;
    if (!isUsingNewBackup_ && entityToAppHash_.empty()) return;

    Mercury::BundleSendingMap bundles( networkInterface );

    // 计算这个 tick 要 backup/offload 多少个
    float numToBackUpFloat =
        float(bases.size())/periodInTicks + backupRemainder_;
    int numToBackUp = int(numToBackUpFloat);
    backupRemainder_ = numToBackUpFloat - numToBackUp;

    // offload 模式下,数量只增不减
    if (isOffloading_)
    {
        if (offloadPerTick_ < numToBackUp)
        {
            offloadPerTick_ = numToBackUp;
            INFO_MSG( "BaseApp is retiring, offloading at %d entities per tick\n",
                offloadPerTick_ );
        }
        else
            numToBackUp = offloadPerTick_;
    }

    if (basesToBackUp_.empty())
        this->restartBackupCycle( bases );

    bool madeProgress = false;
    while ((numToBackUp > 0) && !basesToBackUp_.empty())
    {
        Base * pBase = bases.findEntity( basesToBackUp_.back() );
        basesToBackUp_.pop_back();

        if (pBase && this->autoBackupBase( *pBase, bundles ) )
        {
            madeProgress = true;
            --numToBackUp;
        }
    }

    if (madeProgress)
    {
        bundles.sendAll();
        ticksSinceLastSuccessfulOffload_ = 0;
    }
    else
    {
        // 没进度,可能等待客户端连接
        if (isOffloading_ && !bases.empty())
        {
            ++ticksSinceLastSuccessfulOffload_;
            // 每秒日志一次
            const std::div_t sec = std::div( ticksSinceLastSuccessfulOffload_,
                BaseAppConfig::updateHertz() );
            if (sec.rem == 0)
            {
                INFO_MSG( "unable to offload %" PRIzu
                        " entities during last %d seconds (possibly waiting "
                        "for client connection)\n", bases.size(), sec.quot );
            }
        }
    }
    ...
}
```

```cpp
void BackedUpEntities::restoreRemotely( const Mercury::Address & deadAddr, 
        const BackupHashChain & backedUpHashChain )
{
    INFO_MSG( "Offloading %" PRIzu " restored entities\n", data_.size() );

    Mercury::BundleSendingMap bundles( BaseApp::instance().intInterface() );

    Container::iterator iter = data_.begin();
    while (iter != data_.end())
    {
        const EntityID & id = iter->first;
        BW::string & backupData = iter->second;

        MemoryIStream stream( const_cast< char * >( backupData.data() ), 
            backupData.size() );
        // 通过 hash chain 找到新的目标 BaseApp
        Mercury::Address destBaseAppAddr = backedUpHashChain.addressFor( 
            deadAddr, id );

        Mercury::Bundle & bundle = bundles[destBaseAppAddr];
        bundle.startMessage( BaseAppIntInterface::backupBaseEntity );

        bundle << true;     // isOffload
        bundle << id;
        bundle.transfer( stream, stream.remainingLength() );

        ++iter;
    }
}
```

## 十五、Mailbox 重定向机制

### 15.1 Mailbox 在迁移中的挑战

实体的 Mailbox 被许多地方持有:
- 其他 Base 实体的属性中
- Cell 实体的 `baseAddr_` 中
- 客户端的实体对象中
- 脚本的全局变量中

迁移后,旧 Mailbox 的地址失效。如果继续用旧地址,消息会丢失。BigWorld 的解决方案是**多层重定向**。

### 15.2 三层重定向机制

#### 15.2.1 第一层:Base 端的 setCurrentCell

Cell 实体迁移后,新 CellApp 通过 `currentCell` 消息通知 Base,Base 调用 `setCurrentCell` 更新 `pCellEntityMailBox_`。

#### 15.2.2 第二层:Cell 端的 pRealChannel_

Ghost 的 `pRealChannel_` 指向当前 Real 所在的 CellAppChannel。Real 迁移时,旧 Real 变 Ghost,其 `pRealChannel_` 设置为新 Real 的通道。

#### 15.2.3 第三层:CellAppMgr 的路由

某些情况下,Mailbox 没有及时更新,CellAppMgr 充当**最后兜底**的路由器。CellAppMgr 知道每个 space 的所有 cell 分布,可以把消息转发到正确的 CellApp。

### 15.3 BackupHashChain:BaseApp 死亡后的 Mailbox 重定向

`BackupHashChain`(`lib/server/backup_hash_chain.hpp:14-33`)是一个**历史哈希链**,记录 BaseApp 死亡时的 backup 关系:

```cpp
class BackupHashChain
{
public:
    BackupHashChain();
    ~BackupHashChain();

    void adjustForDeadBaseApp( const Mercury::Address & deadApp, 
                               const BackupHash & hash );
    Mercury::Address addressFor( const Mercury::Address & address,
                                 EntityID entityID ) const;

private:
    typedef BW::map< Mercury::Address, BackupHash > History;
    History history_;
};
```

`addressFor(deadAddr, entityID)` 的算法:
1. 查找 `history_` 中是否有 `deadAddr` 的记录
2. 如果有,用当时的 `BackupHash` 计算 `entityID` 哈希到哪个 BaseApp
3. 如果那个 BaseApp 也死了,递归查找
4. 返回最终有效的 BaseApp 地址

这保证了即使多个 BaseApp 连续死亡,Mailbox 也能找到正确的目标。

### 15.4 消息丢失防护

迁移过程中可能的消息丢失场景与防护:

#### 15.4.1 Real 迁移瞬间

**场景**:Real 正在迁移,消息到达旧 CellApp
**防护**:旧 Real 已变 Ghost,`pRealChannel_` 指向新 Real,消息自动转发

#### 15.4.2 Base offload 瞬间

**场景**:Base 正在 offload,消息到达原 BaseApp
**防护**:`BaseMessageForwarder` 转发到新 BaseApp

#### 15.4.3 CellApp 死亡

**场景**:CellApp 死亡,消息到达 CellAppMgr
**防护**:CellAppMgr 路由到新 CellApp,或回复错误让 Base 触发 restoreTo

#### 15.4.4 BaseApp 死亡

**场景**:BaseApp 死亡,消息发往死亡地址
**防护**:`BackupHashChain` 找到 backup BaseApp,Mercury 通道自动重连

### 15.5 ServerEntityMailBox::adjustForDeadBaseApp

`BaseApp::handleBaseAppDeath` 中调用(`baseapp.cpp:2710-2711`):

```cpp

    *pBackupHashChain_ );
```

这会遍历所有现存的 `ServerEntityMailBox`,把指向死亡 BaseApp 的引用重定向到 backup。这是一个**全局扫描**,在大量 Mailbox 时可能耗时。

## 十六、Real/Ghost 切换详解

### 16.1 Real 与 Ghost 的本质区别

| 维度 | Real | Ghost |
|------|------|-------|
| **存在位置** | 权威 CellApp | 其他 CellApp |
| **属性集** | Ghost + Real 属性 | 仅 Ghost 属性 |
| **pReal_** | 非 NULL | NULL |
| **pRealChannel_** | NULL | 非 NULL |
| **可调用 Real-only 方法** | 是 | 否 |
| **可触发客户端事件** | 是 | 否 |
| **可写 DB** | 是(通过 Base) | 否 |
| **数量** | 一个实体只有一个 Real | 可有多个 Ghost |
| **生命周期** | 跟随 Base | 跟随 Real / 边界检查 |

### 16.2 Real → Ghost 的转换

参见第 13.7 节的 `convertRealToGhost`。转换步骤:

1. **Witness flush**:把客户端待发数据全部发出
2. **写 Real 数据到流**:序列化所有 Real 属性、控制器、witness
3. **设置 pRealChannel_**:指向新 Real
4. **设置 nextRealAddr_**:通知 Haunts 新地址
5. **offloadReal()**:销毁本地 RealEntity 对象
6. **删除 Real-only 属性**:`properties_` 数组截断到 `propCountGhost()`
7. **relocated()**:通知 EntityDelegate 位置变化

### 16.3 Ghost → Real 的转换

参见第 13.10 节的 `convertGhostToReal`。转换步骤:

1. **清除 pRealChannel_**:不再是 Ghost
2. **从流读取 Real 数据**:反序列化所有 Real 属性、控制器、witness
3. **加入 realEntities_**:通知 Base 新地址
4. **relocated()**:通知 EntityDelegate
5. **触发 onEnteredCell**:高优先级回调

### 16.4 转换时的状态保存与恢复

#### 16.4.1 属性保存

Real 属性存储在 `properties_[propCountGhost()..propCountGhostPlusReal()-1]` 索引范围内。Real → Ghost 时,这些属性被 `detach` 并从 `properties_` 中删除。Ghost → Real 时,从流中重新创建。

#### 16.4.2 控制器保存

控制器(如移动控制器、AI 控制器)存储在 `RealEntity` 中,通过 `writeOffloadData` 序列化。Ghost 没有 `RealEntity`,所以没有控制器。

#### 16.4.3 Witness 保存

Witness(玩家视野)是 Real 才有的。Witness 状态通过 `writeOffloadData` 序列化,包括:
- 当前 AOI 范围
- 视野中的实体列表
- 客户端通道状态

#### 16.4.4 Haunt 通道处理

`offloadReal()` 调用 `RealEntity::destroy(&nextRealAddr_)`,在销毁 RealEntity 前通知所有 Haunts:"新 Real 在 `nextRealAddr_`"。Haunts 收到后,把它们的 `pRealChannel_` 更新为新地址。

### 16.5 numTimesRealOffloaded_ 统计

注意 `convertGhostToReal` 中的 `++numTimesRealOffloaded_`(`entity.cpp:4660`),这是一个统计计数器,记录实体被 offload 了多少次。可用于:
- 调试:判断实体是否在频繁迁移
- 性能分析:找出热点区域

### 16.6 与 Ghost 同步的协作

Real/Ghost 切换与 Ghost 同步(详见专题1)的协作点:

1. **Ghost 创建**:Real 在新 CellApp 上线后,会通过 `EntityGhostMaintainer` 在周边 CellApp 创建 Ghost
2. **Ghost 销毁**:Real 迁移后,旧位置的 Ghost 不再需要,会被 `OffloadChecker` 删除
3. **Ghost 数据同步**:Real → Ghost 转换时,Real 已经把最新数据写入流,Ghost 从流中读取,保证数据一致

## 十七、Haunt 通道在迁移中的处理

### 17.1 Haunt 通道回顾

Haunt 是 Real 与其 Ghost 之间的通信通道。每个 Ghost 在 Real 上对应一个 Haunt,每个 Real 在 Ghost 上对应一个 `pRealChannel_`。

### 17.2 迁移时的 Haunt 更新

Real 迁移时,所有 Haunt 都需要更新指向新 Real 的地址。这通过 `offloadReal()` 完成:

`Entity::offloadReal`(`entity.cpp:3046-3058`):

```cpp
void Entity::offloadReal()
{
    // 这是唯一一次同时有 pRealChannel_ 和 pReal_ 的情况
    MF_ASSERT( pReal_ != NULL && pRealChannel_ != NULL );
    pReal_->destroy( &(nextRealAddr_) );  // 通知 Haunts 新地址
    // RealEntity::destroy 调用 'delete this'
    pReal_ = NULL;
    ...
}
```

`RealEntity::destroy(&nextRealAddr_)` 在销毁前遍历所有 Haunts,发送 `ghostSetReal` 消息,告知新 Real 地址。

### 17.3 ghostSetReal 消息

`ghostSetReal` 消息让 Ghost 知道"我的 Real 现在在 `nextRealAddr_`"。Ghost 收到后:
1. 更新自己的 `pRealChannel_` 指向新 Real
2. 后续的 Real-bound 消息(如属性更新)会发往新 Real

### 17.4 旧通道的断开

旧 CellApp 上的 Real 销毁后,与之相关的 Haunt 通道断开。但这不会影响 Ghost 的存在——Ghost 仍然在,只是它的 Real 在别处。

### 17.5 新通道的建立

新 Real 在新 CellApp 上线后:
1. 通过 `EntityGhostMaintainer` 重新检查周边 Cell,创建必要的 Ghost
2. 新 Ghost 与新 Real 之间建立 Haunt 通道
3. 旧位置的 Ghost(如果还存在)通过 `ghostSetReal` 重定向到新 Real

### 17.6 消息顺序保证

迁移过程中,消息顺序通过以下机制保证:

1. **通道版本**:Base 发送给 Cell 的消息带有 `channel().version()`,Cell 端按版本号处理,过期版本的消息被丢弃
2. **Buffered Ghost Messages**:Real/Ghost 切换瞬间到达的消息被缓冲,切换完成后回放(详见专题1)
3. **Mercury 可靠通道**:所有跨进程消息走可靠通道,保证不丢失

### 18.1 Teleport 与 Offload 的区别

```cpp
    entity_.writeGhostDataToStream( ghostDataStream );

    bundle.startMessage( CellAppInterface::onloadTeleportedEntity );
    bundle << nearbyMBRef.id;
    bundle << uint32( ghostDataStream.remainingLength() );
    bundle.transfer( ghostDataStream, ghostDataStream.remainingLength() );

    // 11. 调用 offloadEntity,触发 Real → Ghost
    EntityPtr pThisEntity = &entity_;
    pThisEntity->population().rememberBaseChannel( *pThisEntity, pChannel->addr() );
    pThisEntity->cell().offloadEntity( pThisEntity.get(), pChannel,
            /* isTeleport: */ true );

    // 12. 恢复旧位置
    pThisEntity->localPosition_ = oldPos;
    pThisEntity->localDirection_ = oldDir;

    return true;
}
```

## 二十、实体恢复流程

### 20.1 恢复触发场景

实体恢复发生在故障后:

| 故障 | 恢复谁 | 触发 |
|------|--------|------|
| CellApp 死亡 | Cell 实体 | `BaseApp::handleCellAppDeath` |
| BaseApp 死亡 | Base 实体 | Backup BaseApp 接管 |
| BaseApp 退役中死亡 | Base 实体 | `OffloadedBackups::handleBaseAppDeath` |

### 20.2 CellApp 死亡后的恢复

CellApp 死亡后的恢复由 `BaseApp::handleCellAppDeath` 触发,这是最常见也最关键的恢复路径。其核心思路是:**BaseApp 上保留了每个 Cell 实体的备份数据(`cellBackupData_`),在 CellApp 死亡后将这些备份发送到新的 CellApp 重新创建 Cell 实体**。

#### 20.2.1 handleCellAppDeath 入口

```cpp

    NOTICE_MSG( "BaseApp::handleCellAppDeath: CellApp %s is dead\n",

```

消息数据流格式:

```
+---------------------+----------------------------------+
| Mercury::Address    | 死亡的 CellApp 地址              |
+---------------------+----------------------------------+
| (SpaceID, Address)* | 每个 Space 的替代 CellApp 地址对 |
+---------------------+----------------------------------+
```

`CellAppMgr` 在检测到 CellApp 死亡后,会为该 CellApp 上每个 Space 选出一个替代 CellApp,然后将 `<SpaceID, newCellAppAddr>` 列表广播给所有 BaseApp。BaseApp 收到后:

1. 调用 `DeadCellApps::addApp` 记录死亡信息和替代地址映射
2. 立即调用 `tick` 启动恢复流程

#### 20.2.2 DeadCellApps 与 DyingCellApp 双层管理

`DeadCellApps` 维护两类信息:

| 类 | 用途 | 生命周期 |
|----|------|----------|
| `DeadCellApp` | 标记"最近死亡"的 CellApp,用于过滤紧急消息 | 10 秒(`MAX_AGE`) |
| `DyingCellApp` | 待恢复的 CellApp,持有替代地址映射 | 直到所有实体恢复完成 |

```cpp
// programming/bigworld/server/baseapp/dead_cell_apps.cpp:111

{

            shared_ptr< DyingCellApp >( new DyingCellApp( addr, data ) ) );

```

`DeadCellApp` 的 10 秒保留期用于处理"brown-out"(半死)场景:CellApp 死亡消息可能比 `emergencySetCurrentCell` 请求更早到达某些 BaseApp,此时需要识别死亡地址并触发立即恢复。

#### 20.2.3 DyingCellApp::tick 恢复主循环

```cpp
// programming/bigworld/server/baseapp/dead_cell_apps.cpp:234
bool DyingCellApp::tick( const Bases & bases )
{
    int numRestored = 0;
    Bases::const_iterator iter = bases.begin();

    while (iter != bases.end())
    {
        Base * pBase = iter->second;
        ++iter; // 提前递增,可能丢弃实体

        if (pBase->cellAddr() == addr_)
        {
            ++numRestored;
            Mercury::Address newDest = this->destinationFor( pBase );

            if (newDest == Mercury::Address::NONE)
            {
                ERROR_MSG( "BaseApp::handleCellAppDeath: "
                        "No alternate CellApp for %u (on space %u)\n",
                    pBase->id(), pBase->spaceID() );
            }

            if (BaseApp::instance().isRecentlyDeadCellApp( newDest ))
            {
                newDest = Mercury::Address::NONE;
            }

            if (newDestinations_.empty())
            {
                ++numDiscarded_;
                pBase->discard();
            }
            else if (!pBase->restoreTo( pBase->spaceID(), newDest ))
            {
                CRITICAL_MSG( "BaseApp::handleCellAppDeath: "
                              "%u could not be restored to space %u\n",
                              pBase->id(), pBase->spaceID() );
            }
            else if (pBase->isProxy())
            {
                ((Proxy*)pBase)->restoreClient();
            }

            if (BaseApp::instance().nextTickPending())
            {
                WARNING_MSG( "DyingCellApp::tick: "
                                "Next tick pending after restoring %d\n",
                            numRestored );
                return false;
            }
        }
    }

    return true;
}
```

关键设计点:

1. **遍历所有 Base 实体**:对每个 `cellAddr_ == 死亡地址` 的 Base 触发恢复
2. **时间片保护**:每次恢复后检查 `nextTickPending()`,若下一 tick 即将到来则暂停,等下次 tick 继续
3. **替代地址查询**:`destinationFor` 根据实体的 `spaceID` 查 `newDestinations_` 映射
4. **死亡链过滤**:若替代 CellApp 也已死亡,将 `newDest` 置为 `NONE`
5. **空映射丢弃**:若 `newDestinations_` 为空(无任何替代信息),调用 `pBase->discard()` 直接销毁
6. **Proxy 特殊处理**:Proxy(玩家)实体需要额外通知客户端

`Base::restoreTo` 是单个实体恢复的核心方法:


### 20.3 BaseApp 死亡后的恢复

BaseApp 死亡的恢复比 CellApp 死亡复杂得多,因为 Base 实体是实体的"主体"(Real),包含持久化数据和客户端连接。恢复的核心机制是 **BackupHash 哈希分配 + BackupHashChain 历史链**。

#### 20.3.1 恢复触发与 handleBaseAppDeath

当 BaseAppMgr 检测到某 BaseApp 死亡后,会向所有 BaseApp 广播 `handleBaseAppDeath` 消息:

```cpp
// programming/bigworld/server/baseapp/baseapp.cpp:2670
void BaseApp::handleBaseAppDeath( const Mercury::Address & srcAddr,
        const Mercury::UnpackedMessageHeader & header,
        BinaryIStream & data )
{
    Mercury::Address deadBaseAppAddr;
    uint8 isService = 0;
    data >> deadBaseAppAddr >> isService;

    baseAppExtAddresses_.erase( deadBaseAppAddr );

    BackupHash backedUpHash;
    data >> backedUpHash;

    if (backedUpHash.empty())
    {
        WARNING_MSG( "BaseApp::handleBaseAppDeath: "
                    "Unable to recover from BaseApp death.\n" );
        return;
    }

    // 1. IDClient 调整(防止 ID 重复分配)
    pEntityCreator_->handleBaseAppDeath( deadBaseAppAddr );

    // 2. 恢复本地备份(本 BaseApp 备份了死亡 BaseApp 的实体)
    pBackedUpBaseApps_->handleBaseAppDeath( deadBaseAppAddr );

    // 3. 全局 Base 服务地址更新
    pGlobalBases_->handleBaseAppDeath( deadBaseAppAddr );

    // 4. 更新备份哈希链
    pBackupHashChain_->adjustForDeadBaseApp( deadBaseAppAddr, backedUpHash );

    // 5. 处理已 offload 到死亡 BaseApp 的备份
    pOffloadedBackups_->handleBaseAppDeath( deadBaseAppAddr,
        *pBackupHashChain_ );

    // 6. 服务碎片清理
    this->servicesMap().removeFragmentsForAddress( deadBaseAppAddr );

    // 7. 重定向 Mailbox
    ServerEntityMailBox::adjustForDeadBaseApp( deadBaseAppAddr,
        *pBackupHashChain_ );

    // 8. 解决失效 Mailbox
    pGlobalBases_->resolveInvalidMailboxes();

    // 9. 通道死亡通知
    this->intInterface().onAddressDead( deadBaseAppAddr );

    // 10. 备份与归档调整
    pBackupSender_->handleBaseAppDeath( deadBaseAppAddr );
    pArchiver_->handleBaseAppDeath( deadBaseAppAddr, bases_, pSqliteDB_ );

    // 11. 触发脚本事件
    this->scriptEvents().triggerEvent(
        (isService ? "onServiceAppDeath" : "onBaseAppDeath"),
        Py_BuildValue( "((sH))",
            deadBaseAppAddr.ipAsString(),
            ntohs( deadBaseAppAddr.port ) ) );
}
```

11 步恢复流程,每一步都至关重要:

| 步骤 | 操作 | 目的 |
|------|------|------|
| 1 | `IDClient::handleBaseAppDeath` | 死亡 BaseApp 持有的 ID 池失效,避免重复分配 |
| 2 | `BackedUpBaseApps::handleBaseAppDeath` | 本地恢复备份的实体(若哈希映射到我) |
| 3 | `GlobalBases::handleBaseAppDeath` | 全局 Base 服务地址迁移 |
| 4 | `BackupHashChain::adjustForDeadBaseApp` | 历史哈希链追加新哈希,用于查找旧备份 |
| 5 | `OffloadedBackups::handleBaseAppDeath` | 处理退役时 offload 出去的备份 |
| 6 | `servicesMap().removeFragmentsForAddress` | 清理服务碎片 |
| 7 | `ServerEntityMailBox::adjustForDeadBaseApp` | 重定向指向死亡 BaseApp 的 Mailbox |
| 8 | `resolveInvalidMailboxes` | 解决因迁移产生的失效 Mailbox |
| 9 | `intInterface().onAddressDead` | 通道层通知,condemn 死亡通道 |
| 10 | `BackupSender/Archiver` | 备份/归档机制自身的清理 |
| 11 | `onBaseAppDeath` 脚本事件 | 业务层处理(如踢玩家、日志) |

#### 20.3.2 BackupHash 哈希分配原理

BigWorld 使用一致性哈希的变体分配实体到 BaseApp。每个实体 ID 通过 `MiniBackupHash::hashFor` 计算其所属的 BaseApp 索引:

```cpp
// programming/bigworld/lib/server/backup_hash.hpp
class MiniBackupHash
{
    uint32 hashFor( EntityID id ) const
    {
        return addressFor( id ).addr;
    }
    // ...
};
```

哈希函数基于素数取模:`(id * prime) % numApps`,其中 `prime` 通过 `choosePrime` 根据当前 BaseApp 数量动态选择,保证分布均匀。

当 BaseApp 数量变化时,只会有约 `1/N` 的实体需要重新映射,这就是一致性哈希的核心优势。

#### 20.3.3 BackupHashChain 历史链

```cpp
// programming/bigworld/lib/server/backup_hash_chain.hpp
class BackupHashChain
{
    struct HashEntry
    {
        BackupHash hash;
        Mercury::Address deadAddr;
    };
    BW::list<HashEntry> entries_;
public:
    Mercury::Address addressFor( const Mercury::Address & deadAddr,
        EntityID id ) const;
    void adjustForDeadBaseApp( const Mercury::Address & deadAddr,
        const BackupHash & newHash );
};
```

哈希链的设计目的:**当一个 BaseApp 死亡时,其上的实体需要迁移到新 BaseApp。但有些实体的备份可能在死亡 BaseApp 死亡之前已被 offload 到其他 BaseApp(退役流程),需要通过历史哈希链找到这些备份的当前位置**。

`addressFor` 方法遍历哈希链:从最新到最旧,依次尝试用每个历史哈希计算实体 ID 的目标地址,返回第一个非死亡地址。

```cpp
Mercury::Address BackupHashChain::addressFor(
    const Mercury::Address & deadAddr, EntityID id ) const
{
    // 从最新到最旧遍历
    for (auto it = entries_.rbegin(); it != entries_.rend(); ++it)
    {
        Mercury::Address addr = it->hash.addressFor( id );
        if (addr != deadAddr)
        {
            return addr;
        }
    }
    return Mercury::Address::NONE;
}
```

#### 20.3.4 BackedUpBaseApps::handleBaseAppDeath

每个 BaseApp 都在为其他 BaseApp 备份实体(基于哈希分配)。当某 BaseApp 死亡时,所有持有其备份的 BaseApp 都会恢复:

```cpp
// programming/bigworld/server/baseapp/backed_up_base_app.cpp:160
void BackedUpBaseApp::restore()
{
    if (usingNew_)
    {
        WARNING_MSG( "BackedUpBaseApp::restore: Restoring while using new.\n" );
        this->discardNewBackup();
    }
    currentBackup_.restore();
}

// programming/bigworld/server/baseapp/backed_up_base_app.cpp:176
void BackedUpEntities::restore()
{
    INFO_MSG( "Restoring %" PRIzu " entities\n", data_.size() );

    Container::iterator iter = data_.begin();
    while (iter != data_.end())
    {
        MemoryIStream stream(
            const_cast< char * >( iter->second.data() ), iter->second.size() );

        BaseApp::instance().createBaseFromStream( iter->first, stream );
        ++iter;
    }
}
```

`createBaseFromStream` 使用与正常创建相同的流程,从备份流中重建 Base 实体。这意味着恢复的实体也会触发 `onCreate` 脚本回调,业务层需要处理"恢复"与"新建"的区别(通过参数或状态标记)。

#### 20.3.5 restoreRemotely:远端恢复

死亡 BaseApp 上有些实体可能已被 offload 到其他 BaseApp(退役流程)。这些备份需要被重新 offload 到新的备份 BaseApp:

```cpp
// programming/bigworld/server/baseapp/backed_up_base_app.cpp:203
void BackedUpEntities::restoreRemotely( const Mercury::Address & deadAddr,
        const BackupHashChain & backedUpHashChain )
{
    INFO_MSG( "Offloading %" PRIzu " restored entities\n", data_.size() );

    Mercury::BundleSendingMap bundles( BaseApp::instance().intInterface() );

    Container::iterator iter = data_.begin();
    while (iter != data_.end())
    {
        const EntityID & id = iter->first;
        BW::string & backupData = iter->second;

        MemoryIStream stream( const_cast< char * >( backupData.data() ),
            backupData.size() );
        // 通过历史哈希链找到当前应存放的 BaseApp
        Mercury::Address destBaseAppAddr = backedUpHashChain.addressFor(
            deadAddr, id );

        Mercury::Bundle & bundle = bundles[destBaseAppAddr];
        bundle.startMessage( BaseAppIntInterface::backupBaseEntity );

        bundle << true;       // isOffload
        bundle << id;
        bundle.transfer( stream, stream.remainingLength() );

        ++iter;
    }
}
```

关键点:
- `BundleSendingMap` 合并发往同一 BaseApp 的多个 backupBaseEntity 消息,减少网络开销
- `isOffload=true` 标记这是 offload(不是 backup),接收方需放入 `OffloadedBackups`
- 通过 `backedUpHashChain.addressFor` 找到的目标可能是任意 BaseApp(取决于哈希)

#### 20.3.6 恢复时序图

```
BaseAppMgr        BackupBaseApp          死亡BaseApp        Offload目标

    | death detected   |                      | (已死)           |
    |----------------->|                      |                  |

    |                  |                      |                  |

```


### 20.4 OffloadedBackups 恢复流程

`OffloadedBackups` 处理的是**退役(BaseApp Retirement)过程中**的特殊恢复场景。当一个 BaseApp 正在退役,它已经把部分实体的备份 offload 到了其他 BaseApp。如果此时该死亡 BaseApp 真的死亡,这些已 offload 的备份需要被重新路由。

#### 20.4.1 OffloadedBackups 数据结构

```cpp
// programming/bigworld/server/baseapp/offloaded_backups.hpp
class OffloadedBackups
{
    // 按源地址(原属主 BaseApp)分组的备份
    typedef BW::map< Mercury::Address, BackedUpEntities > Container;
    Container apps_;
public:
    void backUpEntity( const Mercury::Address & srcAddr, BinaryIStream & data );
    void handleBaseAppDeath( const Mercury::Address & deadAddr,
        const BackupHashChain & backedUpHash );
    bool wasOffloaded( EntityID entityID ) const;
    void stopBackingUpEntity( EntityID entityID );
};
```

与 `BackedUpBaseApps` 的区别:

| 属性 | BackedUpBaseApps | OffloadedBackups |
|------|-----------------|------------------|
| 触发场景 | 周期性备份 | 退役时 offload |
| 数据来源 | 哈希分配的常规备份 | 主动 offload |
| 是否有哈希 | 有(`BackedUpEntitiesWithHash`) | 无(纯按源地址分组) |
| 恢复方式 | `restore()` 本地恢复 | `restoreRemotely()` 远端路由 |
| 清理时机 | `switchToNewBackup` | 接到 `stopBackingUpEntity` |

#### 20.4.2 backUpEntity 接收备份

```cpp
// programming/bigworld/server/baseapp/offloaded_backups.cpp:25
void OffloadedBackups::backUpEntity( const Mercury::Address & srcAddr,
                                     BinaryIStream & data )
{
    EntityID entityID;
    data >> entityID;

    BW::string & backupData = apps_[ srcAddr ].getDataFor( entityID );
    int dataSize = data.remainingLength();
    backupData.assign( (char *)data.retrieve( dataSize ), dataSize );
}
```

收到 `backupBaseEntity(isOffload=true)` 消息时,数据按**源地址**(原属主 BaseApp)分组存储。这个分组对后续恢复至关重要:恢复时需要知道备份的"原属主"是谁,以便通过 `BackupHashChain` 查找新目标。

#### 20.4.3 handleBaseAppDeath 远端恢复

```cpp
// programming/bigworld/server/baseapp/offloaded_backups.cpp:42
void OffloadedBackups::handleBaseAppDeath( const Mercury::Address & deadAddr,
       const BackupHashChain & backedUpHash )
{
    apps_[ deadAddr ].restoreRemotely( deadAddr, backedUpHash );

    // Once the cluster has recovered from one death, it cannot recover from
    // another. Thus, clear the backups completely to tie up any loose ends
    // regarding offload confirmation.
    apps_.clear();
}
```

调用 `restoreRemotely` 后**清空所有 OffloadedBackups**,注释明确指出:

> 一旦集群从一次死亡恢复后,无法再从下一次死亡恢复。这是为了避免 offload 确认的混乱。

这是一个重要的限制:**BigWorld 不支持连续的 BaseApp 死亡恢复**。设计取舍是简化协议,牺牲容错能力。如果业务需要更强容错,需要使用归档(Archive)机制作为最后兜底。

#### 20.4.4 stopBackingUpEntity 清理

```cpp
// programming/bigworld/server/baseapp/offloaded_backups.cpp:76
void OffloadedBackups::stopBackingUpEntity( EntityID entityID )
{
    Container::iterator iApp = apps_.begin();
    Container::iterator iLastApp;
    while (iApp != apps_.end())
    {
        iLastApp = iApp;
        iApp++;
        iLastApp->second.erase( entityID );
        if (iLastApp->second.empty())
        {
            apps_.erase( iLastApp );
        }
    }
}
```

当新属主 BaseApp 确认接管实体后,会发送 `stopBackingUpEntity` 让旧备份方清理。这避免了同一实体存在多份备份造成混乱。

#### 20.4.5 三层备份体系对比

| 层级 | 机制 | 触发 | 数据位置 | 恢复优先级 |
|------|------|------|----------|------------|
| L1 | **Backup**(周期备份) | `backupPeriod` 定时器 | 哈希分配的备份 BaseApp | 高 |
| L2 | **Offload**(退役迁移) | BaseApp 退役流程 | 新属主 BaseApp | 中 |
| L3 | **Archive**(归档) | `archivePeriod` 定时器 | DBApp / SQLite | 兜底 |

三层互相补充:
- L1 应对突发 BaseApp 死亡,数据最新(秒级延迟)
- L2 应对计划内退役,数据完整转移
- L3 应对集群级故障(如机房断电),数据可能滞后(分钟级)

#### 21.1.2 实体创建相关参数详解

| 参数 | 类型 | 默认值 | 含义 | 影响 |
|------|------|--------|------|------|
| `createBaseElsewhereThreshold` | float | 0.1 | 远程创建 Base 的负载阈值 | 当本地负载超过此值,新实体倾向远程创建 |
| `shouldResolveMailBoxes` | bool | false | 是否解析 Mailbox 到具体地址 | true 会让脚本误判实体位置,生产环境应 false |
| `warnOnNoDef` | bool | true | 缺少 .def 文件时告警 | 推荐开启,避免脚本错误调用 |
| `backUpUndefinedProperties` | bool | false | 是否备份未定义属性 | 调试用,生产关闭以减小备份体积 |
| `loadSmoothingBias` | float | 0.05 | 负载平滑系数 | 越大响应越快但波动大 |

**createBaseElsewhereThreshold 详解**:

当 `BaseAppMgr::createEntity` 决定在哪个 BaseApp 创建实体时,会查询本地负载。若当前 BaseApp 的负载超过 `createBaseElsewhereThreshold`(0-1 之间),会优先选择其他负载较低的 BaseApp。这个参数控制了**实体创建的负载均衡敏感度**:

- 值越小(如 0.05):越敏感,稍有负载就转移,适合大量小实体场景
- 值越大(如 0.5):越宽松,允许本地负载较高才转移,适合需要局部性的场景

#### 21.1.3 备份相关参数详解

| 参数 | 类型 | 默认值 | 含义 | 调优建议 |
|------|------|--------|------|----------|
| `backupPeriod` | float | 10.0 秒 | 备份周期 | 越小数据越新但网络开销大 |
| `backupPeriodInTicks` | int | 派生 | 备份周期(tick 数) | 由 `backupPeriod * updateHertz` 计算 |
| `backupSizeWarningLevel` | int | 1024*1024 | 备份大小告警阈值 | 单实体备份超过此值告警 |
| `shouldLogBackups` | bool | false | 是否记录备份日志 | 调试开启,生产关闭 |

`backupPeriod` 是 L1 备份的关键参数。它决定了 RTO(Recovery Time Objective):

```
RTO ≈ backupPeriod + 检测延迟 + 恢复时间
   ≈ 10s + 5s + 5s = 20s (默认配置)
```

若业务对数据丢失敏感,可以减小到 5s 甚至 1s,但要注意网络开销随周期减小线性增加。

#### 21.1.4 归档相关参数

| 参数 | 类型 | 默认值 | 含义 |
|------|------|--------|------|
| `archivePeriod` | float | 300 秒 | 归档周期(5 分钟) |
| `archivePeriodInTicks` | int | 派生 | 归档周期(tick 数) |
| `archiveEmergencyThreshold` | float | 0.95 | 紧急归档触发阈值 |

归档是 L3 兜底机制,周期较长(默认 5 分钟)。当 BaseApp 负载超过 `archiveEmergencyThreshold` 时,会触发紧急归档,避免内存耗尽。

| `defaultAoIRadius` | float | 100.0 | 默认 AoI 半径 | 实体未指定时使用 |
| `checkOffloadsPeriod` | float | 0.5 秒 | Offload 检查周期 | 越小迁移越及时但 CPU 高 |
| `checkOffloadsPeriodInTicks` | int | 派生 | Offload 检查周期(tick) | 由 `checkOffloadsPeriod * updateHertz` |
| `backupPeriod` | float | 10.0 秒 | Cell 实体备份周期 | 数据备份到 BaseApp |
| `maxGhostsToDelete` | uint | 100 | 单 tick 最大删除 Ghost 数 | 限流,避免 Ghost 风暴 |
| `minGhostLifespan` | float | 0.5 秒 | Ghost 最小生命周期 | 避免 Ghost 抖动 |
| `minGhostLifespanInTicks` | int | 派生 | Ghost 最小生命周期(tick) | 派生自 `minGhostLifespan` |

**ghostDistance 详解**:

`ghostDistance` 决定了 Cell 边界处 Ghost 实体的传播距离。例如 Cell A 与 Cell B 相邻,Cell A 中的实体若距边界小于 `ghostDistance`,会在 Cell B 中创建 Ghost 副本。

```
   Cell A          |          Cell B
                   |
   [实体1]  200m   |   <-边界
                   |
   [实体2]  500m   |  ghostDistance=500
                   |  实体2 距边界500m,临界
   [实体3]  800m   |  实体3 距边界800m,不创建Ghost
```

调优权衡:
- **增大** `ghostDistance`:Ghost 更多,跨 Cell 交互更流畅,但内存与同步开销增加
- **减小** `ghostDistance`:Ghost 更少,资源占用低,但跨边界交互可能出现延迟

**checkOffloadsPeriod 详解**:

`checkOffloadsPeriod` 控制 `OffloadChecker` 的执行频率。每个 Cell 周期性检查实体是否越界,若越界则触发 offload。默认 0.5 秒检查一次,意味着实体可能"越界 0.5 秒后"才被 offload。期间 Cell 边界检查依赖 Ghost 机制保证可见性。

#### 21.2.3 Ghost 更新相关参数

| 参数 | 类型 | 默认值 | 含义 |
|------|------|--------|------|
| `ghostUpdateHertz` | int | 10 | Ghost 更新频率(Hz) |
| `maxGhostsToDelete` | uint | 100 | 单 tick 最大 Ghost 删除数 |
| `minGhostLifespan` | float | 0.5 | Ghost 最小存活时间(秒) |
| `enforceGhostDecorators` | bool | true | 是否强制 Ghost 装饰器 |
| `treatAllOtherEntitiesAsGhosts` | bool | false | 调试:把所有其他实体当 Ghost |

`ghostUpdateHertz` 默认 10Hz,即每 100ms 更新一次 Ghost 状态。这个频率独立于游戏 tick(通常 10-30Hz),允许 Ghost 用更低频率同步以节省带宽。

#### 21.2.4 控制器限制参数

| 参数 | 类型 | 默认值 | 含义 |
|------|------|--------|------|
| `expectedMaxControllers` | int | 6 | 预期最大控制器数 |
| `absoluteMaxControllers` | int | 16 | 绝对最大控制器数 |

控制器(Controller)是 Cell 实体的运动/状态控制机制。每个实体可以有多个控制器,但总和受此限制。超过 `expectedMaxControllers` 触发警告,超过 `absoluteMaxControllers` 触发错误。

### 21.3 DBApp 配置参数

## 二十二、性能分析

本章从吞吐量、延迟、内存、网络四个维度分析实体创建与迁移的性能特征。

### 22.1 实体创建性能

#### 22.1.1 创建路径性能对比

| 创建路径 | 主要开销 | 典型耗时 | 吞吐量 |
|----------|----------|----------|--------|
| `createEntityLocal` | 内存分配+脚本初始化 | <1ms | ~10000/s |
| `createEntityRemote` | 网络 RTT + 远端初始化 | 5-20ms | ~500/s |
| `createEntityAnywhere` | ID 申请 + 远端创建 | 10-30ms | ~300/s |
| `createEntityFromDB` | DB 查询 + 反序列化 | 50-200ms | ~50/s |
| `createEntityFromTemplate` | 模板拷贝 + 远端创建 | 5-15ms | ~500/s |

#### 22.1.2 createEntityLocal 性能剖析

```cpp
// 本地创建的主要开销
Base::createEntityLocal(...)
{
    // 1. 分配 EntityID(从 readyIDs_ 取,O(1))
    EntityID id = pEntityCreator_->getID();
    // ~10ns

    // 2. 构造 Base 对象
    Base * pBase = new Base( ... );
    // 包含 ScriptObject 构造,~50us

    // 3. 调用脚本 onCreate
    pBase->pType()->description().callMethod( "onCreate", ... );
    // 取决于脚本复杂度,典型 100us-1ms

    // 4. 注册到 bases_ 哈希表
    bases_.addBase( pBase );
    // ~100ns

    // 5. (可选)createCellEntity
    pBase->createCellEntity( ... );
    // 异步,不计入本地耗时
}
```

典型本地创建耗时:**100us - 1ms**(主要取决于脚本 `onCreate` 复杂度)。

#### 22.1.3 createEntityFromDB 性能剖析

DB 创建是最慢的路径,主要瓶颈在 DBApp:

```
BaseApp            BaseAppMgr         DBApp              DB
  |                   |                  |                  |
  | 1. createEntity   |                  |                  |
  |------------------>|                  |                  |
  |                   | 2. loadEntity    |                  |
  |                   |----------------->|                  |
  |                   |                  | 3. SELECT       |
  |                   |                  |----------------->|
  |                   |                  | 4. ~50-100ms    |
  |                   |                  |<-----------------|
  |                   |                  | 5. 反序列化     |
  |                   |                  | ~1-5ms          |
  |                   | 6. 回流           |                  |
  |                   |<-----------------|                  |
  | 7. createBaseFromStream               |                  |
  |<------------------|                  |                  |
  | 8. ~5-10ms        |                  |                  |
```

DB 创建的关键瓶颈:
1. **DB 查询**:50-100ms(MySQL,单实体)
2. **反序列化**:1-5ms(取决于属性数量)
3. **回流传输**:1-2ms(典型实体 1-10KB)

#### 22.1.4 EntityAutoLoader 性能

`EntityAutoLoader` 滑动窗口的吞吐量受限于:

```
吞吐量 = min(maxOutstanding_, maxConcurrentEntityLoaders_) / 单次加载耗时
       = min(5, 5) / 0.1s
       = 50 个/秒
```

调优建议:
- 若 DBApp CPU 闲置:增大 `maxConcurrentEntityLoaders`(到 10-20)
- 若 DB I/O 瓶颈:不变(并发不会加速磁盘)
- 若 BaseApp 网络空闲:增大 `maxOutstanding_`(与上面匹配)
- 默认 5/5 适合 100-200 个实体的小场景

### 22.2 实体迁移性能

#### 22.2.1 Offload 性能

单次 offload 耗时:

```
1. 触发检查:           ~10us  (OffloadChecker::tick)
2. 写流到 stream:      ~50us  (writeRealDataToStream,1KB-100KB)
3. 发送消息:            ~1ms   (Mercury 单包 RTT)
4. 远端 onload:         ~100us (反序列化+初始化)
5. 通知 Base:           ~1ms   (Mercury 单包 RTT)
6. 本地 convertRealToGhost: ~50us

总计:~2-3ms
```

但 `OffloadChecker` 是**周期性**触发,实际延迟受 `checkOffloadsPeriod` 影响:

```
最坏情况延迟 = checkOffloadsPeriod + 上述耗时
            = 0.5s + 3ms ≈ 0.5s
```

#### 22.2.2 Teleport 性能

Teleport 是最重的迁移操作,涉及 12 个步骤:

```
1. 准备阶段:           ~1ms   (写流,准备参数)
2. 通知 CellAppMgr:    ~5ms   (网络 RTT)
3. CellAppMgr 查找:    ~1ms   (BSP 树查找)
4. 通知目标 CellApp:   ~5ms   (网络 RTT)
5. 目标 Cell 创建:      ~5ms   (createEntityInternal)
6. 通知源 Cell:         ~5ms   (网络 RTT)
7. 源 Cell 销毁:        ~1ms   (销毁 Real)
8. Base 更新:           ~1ms   (更新引用)
9. Ghost 同步:          ~10ms  (向邻居广播新位置)

总计:~30-50ms
```

#### 22.2.3 性能瓶颈分析

```
        吞吐量        延迟      CPU开销     内存开销    网络开销
Offload  ~100/s       3ms      低         低          低
Teleport ~30/s        50ms     中         中          中
Ghost更新  ~1000/s     10ms     低         中          中
创建实体  ~5000/s      1ms      高         高          低
销毁实体  ~10000/s     0.5ms    中         -           低
```

### 22.3 内存分析

#### 22.3.1 实体内存占用估算

每个实体类型的内存占用差异较大,典型值:

| 实体类型 | Base 内存 | Cell 内存 | Ghost 内存 | 总计 |
|----------|-----------|-----------|------------|------|
| 简单 NPC | 1KB | 2KB | 0.5KB | 3.5KB |
| 玩家 Proxy | 5KB | 10KB | 1KB | 16KB |
| 复杂怪物 | 2KB | 5KB | 1KB | 8KB |
| 静态物件 | 0.5KB | 1KB | 0.3KB | 1.8KB |

#### 22.3.2 Ghost 内存放大

Ghost 数量取决于 `ghostDistance` 和实体密度。假设:
- Cell 大小 500m × 500m
- `ghostDistance` = 500m
- 实体密度 = 1 个/100m²

每个 Cell 中实体数 ≈ 25 个,Ghost 数 ≈ 25 × 4(四个方向邻居)= 100 个。

Ghost 总内存 = 100 × 0.5KB × 100 Cells = 5MB(可接受)。

若 `ghostDistance` = 1000m,Ghost 数翻 4 倍到 400 个,内存 20MB。

### 22.4 网络分析

#### 22.4.1 备份网络开销

每 `backupPeriod` 周期,BaseApp 发送所有实体的备份:

```
备份流量 = (实体数 × 平均备份大小) / backupPeriod
        = (10000 × 5KB) / 10s
        = 5 MB/s = 40 Mbps
```

这对千兆网络可接受,但若实体数到 100000:

```
备份流量 = 50 MB/s = 400 Mbps  ← 接近千兆上限
```

需要增大 `backupPeriod` 或减小备份大小。

#### 22.4.2 Offload 网络开销

Offload 是**事件驱动**的,只在实体越界时触发。假设每秒有 100 个实体越界:

```
Offload 流量 = 100 × 10KB = 1 MB/s = 8 Mbps
```

可接受。但若大量实体同时越界(如玩家集体迁移),会形成突发流量,可能短时打满网络。

### 22.5 CPU 分析

#### 22.5.1 tick 时间预算

游戏 tick 通常 10Hz,每 tick 100ms。CPU 时间分配:

| 任务 | 占比 | 耗时 |
|------|------|------|
| 实体 tick | 30% | 30ms |
| Ghost 更新 | 10% | 10ms |
| 网络处理 | 20% | 20ms |
| 备份/Offload | 5% | 5ms |
| 脚本执行 | 30% | 30ms |
| 保留 | 5% | 5ms |

`reservedTickFraction` 默认 0.5,即 tick 时间内 50% 给业务,50% 保留给系统(网络、备份等)。若超时,触发 `nextTickPending` 警告。

#### 22.5.2 性能告警

关键性能告警阈值:

| 告警 | 阈值 | 含义 |
|------|------|------|
| `tickTimeExceeded` | tick > 100ms | tick 超时 |
| `sendWindowOverflow` | 通道发送窗口溢出 | 网络拥塞 |
| `entitySpam` | 实体超过 `entitySpamSize` | 实体过多 |
| `backupSizeWarning` | 备份 > `backupSizeWarningLevel` | 单实体过大 |

## 二十三、边界情况与故障处理

### 23.1 实体创建边界情况

#### 23.1.1 ID 耗尽

`IDClient` 的 ID 池有限。当所有 BaseApp 同时大量创建实体时,可能耗尽 `readyIDs_`:

```cpp
// programming/bigworld/lib/server/id_client.cpp
EntityID IDClient::getID()
{
    if (readyIDs_.empty())
    {
        if (pendingRequest_)  // 已有请求在途
        {
            // 触发警告,返回 0(无效 ID)
            WARNING_MSG( "IDClient::getID: No IDs available\n" );
            return 0;
        }
        this->requestIDs();  // 发起新请求
        return 0;
    }
    // ...
}
```

业务层需检查返回值:

```python
id = BigWorld.createEntity(...)
if id == 0:
    # ID 耗尽,重试或告警
    pass
```

#### 23.1.2 重复创建

若脚本错误地对同一模板多次创建,会生成多个实体。BigWorld 不做去重,业务需自行管理:

```python
# 错误:可能创建多个
def spawn():
    BigWorld.createEntity("NPC", spaceID, position)

# 正确:使用全局注册表
spawned = {}
def spawn():
    if "NPC" not in spawned:
        spawned["NPC"] = BigWorld.createEntity("NPC", spaceID, position)
```

#### 23.1.3 创建失败处理

`createEntity` 可能失败的场景:

| 场景 | 失败原因 | 处理 |
|------|----------|------|
| BaseAppMgr 不可达 | 网络故障 | 重试或回滚 |
| 目标 BaseApp 死亡 | 创建中崩溃 | 触发 `handleBaseAppDeath` |
| DB 查询失败 | DB 不可用 | 回调返回失败 |
| 脚本 `onCreate` 异常 | 业务错误 | 实体已创建但状态异常 |

### 23.2 实体迁移边界情况

#### 23.2.1 Teleport 失败

`RealEntity::teleport` 12 步流程中任何一步失败:

```
步骤1: 准备数据     ─┐
步骤2: 通知Mgr     ─┤
步骤3: Mgr查找     ─┤  任何失败 → 回滚(实体保持原位)
步骤4: 通知目标     ─┤
步骤5: 目标创建     ─┘
步骤6: 通知源       ─┐  失败 → 实体已在目标,但源未销毁 → 双重存在!
步骤7: 源销毁       ─┘
```

第 6-7 步失败最危险:目标已创建实体,但源未销毁。BigWorld 通过**通道版本号**和**心跳检测**处理:
- 源 Cell 上的实体会因版本号不匹配拒绝消息
- 最终源 Cell 会因心跳超时检测到 Base 失联,触发销毁

#### 23.2.2 Offload 与销毁竞态

实体越界触发 offload 的同时,可能被销毁:

```
线程1: OffloadChecker::tick → 触发 offload
线程2: Base::destroy → 销毁实体

竞态:offload 消息已发出,但实体已销毁
```

BigWorld 通过**单线程 tick** 避免此问题:所有 Cell 实体操作在同一个 tick 内串行执行。但跨进程消息仍可能竞态,接收方需处理"未知实体 ID"消息。

#### 23.2.3 Ghost 抖动

实体在 Cell 边界来回运动,会导致 Ghost 反复创建/销毁:

```
t=0: 实体在 CellA,Ghost 在 CellB
t=1: 实体越界到 CellB,Ghost 在 CellA
t=2: 实体回到 CellA,Ghost 在 CellB
...
```

通过 `minGhostLifespan` 缓解:Ghost 至少存活 0.5 秒,避免立即销毁。

### 23.3 故障恢复边界

#### 23.3.1 双重死亡

两个 BaseApp 同时死亡:BigWorld **不支持**。`OffloadedBackups::handleBaseAppDeath` 注释明确:

> Once the cluster has recovered from one death, it cannot recover from another.

业务需通过监控避免此场景,或依赖归档恢复。

#### 23.3.2 网络分区

CellApp 与 BaseApp 网络不通但都活着:Mercury 通道超时后视为死亡,触发 `handleCellAppDeath`。但实际上 CellApp 仍在运行,可能产生"分裂脑"(Split-Brain):

- Base 在新 CellApp 创建新 Cell 实体
- 旧 CellApp 上的 Cell 实体仍在运行

BigWorld 通过**通道 condemn** 处理:旧 CellApp 上的实体会因通道失效而停止接收消息,最终被 GC。

#### 23.3.3 资源耗尽

- **内存耗尽**:CellApp OOM 时,触发 fastShutdown,所有实体丢失,需从备份恢复
- **DB 连接耗尽**:DBApp 拒绝新查询,`createEntityFromDB` 失败
- **CPU 过载**:tick 超时,`nextTickPending` 触发,offload/恢复暂停

### 23.4 数据一致性边界

#### 23.4.1 备份滞后

实体最新状态可能在内存中已变,但备份尚未发出:

```
t=0: 实体 HP=100
t=1: 备份发出 (HP=100)
t=2: HP 改为 80
t=3: BaseApp 死亡 → 恢复后 HP=100,丢失 t=2 的修改
```

业务需设计为**幂等**或**事件溯源**,避免依赖最新内存状态。

#### 23.4.2 Mailbox 失效

Mailbox 指向死亡 BaseApp 时:

```python
# 错误:可能崩溃
mailbox.method()

# 正确:检查有效性
if mailbox.isValid():
    mailbox.method()
else:
    # 处理失效
```

BigWorld 提供 `shouldResolveMailBoxes` 配置,生产环境应保持 false(不解析到具体地址),让 Mailbox 通过哈希自动重定向。

| 创建 | 跨进程 ID 分配 | `SpawnActor` |
| 持久化 | DBApp | SaveGame 对象 |

Unreal Actor 的网络复制是**单服务器多客户端**,适合中小型游戏。BigWorld 是**多服务器多客户端**,适合大型 MMO。

### 24.3 与 Photon Server 对比

| 维度 | BigWorld | Photon Server |
|------|----------|---------------|
| 架构 | BaseApp/CellApp/DBApp | Application/Server |
| 状态分区 | Space + Cell BSP | Room 模型 |
| 跨服务器迁移 | offload/teleport | 切换 Room |
| 持久化 | DBApp + MySQL | 业务自定义 |
| 负载均衡 | 反向加权随机 | 手动分配 Room |

Photon 的 Room 模型更适合**对战类**游戏(小规模独立场景),BigWorld 的 Space/Cell 更适合**开放世界**(大规模连续场景)。

### 24.4 架构对比总结

```
                单进程                  多进程
                +-----+                +-----+
                | ECS |                | MMO |
                +-----+                +-----+
                  |                      |
            +-----+-----+          +-----+-----+
            |           |          |           |
        Unity ECS   Unreal     BigWorld     Photon
        (single)   Actor      (multi)      (Room)
                    (single)
```

BigWorld 的独特价值:
1. **Space/Cell 自动分区**:无需业务关心服务器边界
2. **Ghost 透明跨边界**:跨 Cell 交互无需特殊代码
3. **三方架构**:Base(持久)/Cell(空间)/Client(渲染)职责清晰
4. **多级容灾**:L1 备份 + L2 offload + L3 归档

## 二十六、总结与最佳实践

### 26.1 核心设计回顾

BigWorld 实体系统的核心设计:

1. **三方架构**:Base/Cell/Client 职责分离,持久化/空间/渲染解耦
2. **Space/Cell 分区**:空间自动按 BSP 树切分,跨服务器透明
3. **Ghost 边界副本**:跨 Cell 可见性通过 Ghost 实现,业务无感
4. **多级容灾**:L1 备份 + L2 offload + L3 归档,层层兜底
5. **哈希分配**:实体到 BaseApp/备份 BaseApp 通过一致性哈希,扩缩容代价低

### 26.2 最佳实践

#### 26.2.1 实体创建

```python
# 1. 批量创建用 EntityAutoLoader
loader = BigWorld.createAutoLoader()
for id in ids:
    loader.load(id)
loader.wait()  # 等待所有加载完成

# 2. 单个创建用 createEntityAnywhere
BigWorld.createEntity("NPC", spaceID, pos, {})

# 3. 玩家登录用 createEntityFromDB
BigWorld.lookUpEntity(playerID, callback)

# 4. 避免在 onCreate 中做重活
def onCreate(self):
    # 轻量初始化,重活延后
    self.addTimer(0.1, 0, 0)  # 100ms 后再处理

# 5. 区分"恢复"与"新建"
def onCreate(self):
    if self.wasRestored:
        # 恢复逻辑
    else:
        # 新建逻辑
```

#### 26.2.2 实体迁移

```python
# 1. Teleport 是重操作,避免频繁调用
# 错误:每帧 teleport
def onUpdate(self, dt):
    self.teleport(self.position + delta)  # 别这样!

# 正确:用 setPosition + controllers
def move(self, target):
    self.setMoveController(target)  # 内部优化

# 2. 监听 onTeleportSuccess
def onTeleportSuccess(self):
    # 迁移完成,可恢复业务
    pass

# 3. 处理 onCellAppDeath
def onCellAppDeath(self, addr):
    if addr == self.cellAddr:
        # 我的 Cell 死了,等 Base 触发恢复
        pass
```

#### 26.2.3 Mailbox 使用

```python
# 1. 总是检查有效性
def callRemote(self, mailbox):
    if mailbox and mailbox.isValid():
        mailbox.method()
    else:
        # 处理失效
        self.cleanupMailbox(mailbox)

# 2. 不要缓存 Mailbox 地址
# 错误:缓存的地址可能失效
addr = mailbox.addr
# ... 一段时间后 ...
sendToAddr(addr)  # 可能已失效!

# 正确:每次通过 Mailbox 对象
mailbox.method()  # 内部自动重定向

# 3. 用 ServerEntityMailBox 而非 ClientEntityMailBox
# Server 版会自动处理 BaseApp 死亡重定向
```

### 26.3 反模式

#### 26.3.1 错误:在 Cell 实体上做持久化

```python
# 错误:Cell 实体可能被 offload 或销毁,数据丢失
class MyCell(CellEntity):
    def save(self):
        db.save(self.importantData)  # 别在 Cell 上做!

# 正确:在 Base 实体上持久化
class MyBase(BaseEntity):
    def save(self):
        db.save(self.importantData)
```

#### 26.3.2 错误:跨 Cell 直接通信

```python
# 错误:绕过 Mailbox 直接调用
cellA_entity.method_on_cellB_entity()  # 不存在这种调用!

# 正确:通过 Mailbox
mailbox_to_b.method()
```

#### 26.3.3 错误:依赖 Ghost 状态

```python
# 错误:Ghost 数据可能滞后
def check(self):
    if other.position.x > 100:  # other 可能是 Ghost,位置旧
        ...

# 正确:用 ServerEntityMailBox 获取最新状态
# 或:接受 Ghost 滞后,设计容错逻辑
```

### 26.4 性能优化清单

- [ ] `backupPeriod` 不小于 5s(避免网络压力)
- [ ] `ghostDistance` 不大于 Cell 对角线(避免无谓 Ghost)
- [ ] `checkOffloadsPeriod` 不小于 0.2s(避免 CPU 浪费)
- [ ] 单实体备份大小 < 100KB(`backupSizeWarningLevel`)
- [ ] 单 Cell 实体数 < 1000(避免单 Cell 过载)
- [ ] `maxOutstanding_` 与 `maxConcurrentEntityLoaders` 匹配
- [ ] 监控 `tickTime` < 100ms
- [ ] 监控 `numGhosts` < 实体数 × 10

### 26.5 演进建议

BigWorld 的设计已有 20+ 年历史,现代 MMO 可能的演进方向:

1. **ECS 化**:将 Component 模型引入,提升数据局部性
2. **Actor 模型**:用更现代的 Actor 框架(如 Akka)替代 Mercury
3. **容器化**:BaseApp/CellApp 容器化,支持弹性扩缩容
4. **云原生**:利用 K8s 健康检查替代心跳,自动恢复
5. **无状态化**:更多状态推到 DB,简化容灾

但 BigWorld 的核心思想——**Space/Cell 分区、Ghost 透明、三方架构**——依然是大型 MMO 的最佳实践。
