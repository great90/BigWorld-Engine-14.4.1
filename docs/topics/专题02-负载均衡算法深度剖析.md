## 一、负载均衡概述

### 1.1 为什么 MMOG 需要负载均衡

大型多人在线游戏(MMOG)的核心挑战之一是**单机性能瓶颈**。一台服务器进程能承载的实体数量、tick 频率、网络吞吐都是有上限的。当玩家数量达到单机上限时,必须把世界拆分到多台机器上,同时还要让玩家感觉不到拆分边界——这就是负载均衡的本质任务。

BigWorld Engine 是面向 MMOG 的开源引擎,负载均衡是其三大特色之一(另外两个是 Ghost 同步和容灾备份)。BigWorld 把负载均衡做到运行时动态调整,不需要停服,这是它和早期分区分服 MMOG 的根本区别。

#### 1.1.1 单机性能瓶颈的来源

```
┌────────────────────────────────────────────────────────────────┐
│                       单台 CellApp 进程的瓶颈                  │
├────────────────────────────────────────────────────────────────┤
│ 1. CPU:每个 tick (100ms) 内必须处理所有实体的 AI、物理、属性同步│
│ 2. 内存:每个实体平均占用 2~10 KB,5 万实体就是 100~500 MB      │
│ 3. 网络:每秒需向所有 Witness 推送 AOI 内实体状态,带宽爆炸    │
│ 4. 集合点:某个集市聚集 1 万玩家,单机完全无法承载              │
└────────────────────────────────────────────────────────────────┘
```

### 1.2 BigWorld 两层负载均衡体系

BigWorld 把负载均衡分为两层,分别针对空间子系统和代理子系统:

```
┌─────────────────────────────────────────────────────────────────┐
│                    BigWorld 负载均衡两层架构                     │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│   第1层:Cell 层(空间负载均衡)                                  │
│   ┌────────────────────────────────────────────────┐             │
│   │ CellAppMgr ──── BSP 树分割 ──── Cell 边界移动  │             │
│   │  触发:每 1 秒 (loadBalancePeriod)              │             │
│   │  粒度:Cell 边界 (BSP 切分线)                  │             │
│   │  作用:在 Space 内部移动 Cell 边界平衡负载     │             │
│   └────────────────────────────────────────────────┘             │
│                            ↓ 协作                                │
│   第2层:Meta 层(跨 CellAppGroup 负载均衡)                     │
│   ┌────────────────────────────────────────────────┐             │
│   │ CellAppMgr ──── CellAppGroup ──── 新建/退役 Cell│             │
│   │  触发:每 3 秒 (metaLoadBalancePeriod)          │             │
│   │  粒度:CellApp (整进程级)                      │             │
│   │  作用:跨 CellApp 转移 Cell,平衡 CellApp 负载  │             │
│   └────────────────────────────────────────────────┘             │
│                                                                  │
│   第3层:Base 层(代理负载均衡)                                 │
│   ┌────────────────────────────────────────────────┐             │
│   │ BaseAppMgr ──── findLeastLoadedApp ──── 迁移   │             │
│   │  触发:每个 tick / 周期更新                     │             │
│   │  粒度:Base 实体 (代理)                        │             │
│   │  作用:登录与创建 Base 时分配最空闲的 BaseApp   │             │
│   └────────────────────────────────────────────────┘             │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

| 层次 | 进程 | 周期 | 粒度 | 操作 | 是否触发实体迁移 |
|------|------|------|------|------|------------------|
| Cell 层 | CellAppMgr | 1s | Cell 边界 | 移动 BSP 切分线 | 否(只调边界) |
| Meta 层 | CellAppMgr | 3s | CellApp | 新建/退役 Cell | 是(整个 Cell 切换所属) |
| Base 层 | BaseAppMgr | 周期 | Base 实体 | offload/登录分配 | 是(Base 实体迁移) |

### 1.3 动态迁移的本质

BigWorld 的负载均衡本质上是**运行时重新分配负载**。这与传统 MMOG 的"分区分服"截然不同:

1. **传统方式**:把世界按区域预先切成多个区,每个区一台服务器,玩家跨区时显式切换服务器。
2. **BigWorld 方式**:世界是一个连续空间,由 BSP 树动态分割成多个 Cell,Cell 在 CellApp 间动态迁移;玩家无感跨 Cell 边界(由 Ghost 机制保证)。

动态迁移的关键挑战:

- **空间局部性**:负载迁移不能打散玩家聚集的区域(Ghost 通信代价大),要保持空间连续性。
- **客户端透明**:玩家不会看到 Cell 边界切换,只看到连续世界。
- **原子性**:迁移过程中实体要么在源 Cell,要么在目标 Cell,不能同时存在两份。
- **可逆性**:过载时迁移走,空闲时再迁移回来,平滑可逆。

### 1.4 与其他 MMOG 的负载均衡对比

| 引擎/产品 | 负载均衡粒度 | 触发时机 | 空间连续性 | 客户端可见性 |
|-----------|--------------|----------|------------|--------------|
| BigWorld | Cell(矩形子区域) | 周期+过载 | BSP 树保持连续 | 透明 |
| 传统分区分服 | 整个区 | 静态 | 区域边界明显 | 需切服 |
| 动态 sharding | shard(哈希分片) | 阈值触发 | 哈希离散 | 部分透明 |
| Actor model | 单个 actor | 消息驱动 | 无空间概念 | 完全透明 |
| Spatial sharding | 网格 shard | 周期 | 网格连续 | 透明 |

BigWorld 的特色在于:
1. **BSP 树**保证空间连续性,不破坏局部性。
2. **Ghost 机制**让玩家跨 Cell 边界时无需切换服务器代理。
3. **两层触发**兼顾精细调整(1s)和粗粒度迁移(3s)。

### 2.3 loadBalance 与 metaLoadBalance 两层触发

#### 2.3.1 第1层 loadBalance(Space 内部)

`cellappmgr.cpp:795-819`:

```cpp
void CellAppMgr::loadBalance()
{
    // Balance all spaces
    {
        Spaces::iterator iter = spaces_.begin();

        while (iter != spaces_.end())
        {
            if (g_shouldLoadBalance)
            {
                iter->second->loadBalance();   // 委托给 Space::loadBalance
            }
            else
            {
                iter->second->informCellAppsOfGeometry( /*shouldSend*/ false );
            }

            iter++;
        }
    }

    // 在所有 Space 平衡后,把消息聚合发送给所有 CellApp
    cellApps_.sendToAll();
}
```

**关键点**:
- 遍历所有 Space,调用 `Space::loadBalance()`,后者会调整 BSP 树的切分线位置。
- `g_shouldLoadBalance` 是匿名命名空间内的全局变量(`cellappmgr.cpp:70`),可通过 watcher `debugging/shouldLoadBalance` 动态开关,便于调试。
- 所有 Space 平衡完后,通过 `cellApps_.sendToAll()` 把每个 CellApp 的 bundle 一次性发出。这避免了每个 Space 平衡就触发一次 send,提高网络效率。

`Space::loadBalance()` 的实现(`space.cpp:201-272`):

```cpp
void Space::loadBalance()
{
#ifndef BW_EVALUATION
    if (isBalancing_)                              // 防止递归
    {
        WARNING_MSG( "Space::loadBalance( %d ): Called recursively.\n", id_ );
        return;
    }

    if (pRoot_ == NULL)                            // BSP 树为空,无可平衡
    {
        INFO_MSG( "Space::loadBalance( %d ): Called with pRoot_ == NULL.\n",
                id_ );
        return;
    }

    isBalancing_ = true;

    pRoot_->updateLoad();                          // 自底向上更新所有节点的负载

    BW::Rect rect(                                // 根 range 是无限大矩形
        -std::numeric_limits< float >::max(),
        -std::numeric_limits< float >::max(),
        std::numeric_limits< float >::max(),
        std::numeric_limits< float >::max() );

    // 计算安全边界,防止过载 CellApp 接受更多负载
    // safetyBound 是绝对上限,safetyRatio * avgSmoothedLoad 是相对上限
    // 取两者较大值,确保不会让原本就过载的 CellApp 接收更多
    float loadSafetyBound = std::max( CellAppLoadConfig::safetyBound(),
            pRoot_->avgSmoothedLoad() * CellAppLoadConfig::safetyRatio() );

    bool wasLoaded = this->hasLoadedRequiredChunks();
    pRoot_->balance( rect, loadSafetyBound );      // 递归平衡 BSP 树
    pRoot_->updateLoad();                          // 平衡后重新更新负载
    // ...

    this->informCellAppsOfGeometry( /* shouldSend */ false );

    // 删除 balance 中标记的待删除 Cell(空 Cell)
    {
        CellsToDelete copyOfCellsToDelete;
        copyOfCellsToDelete.swap( cellsToDelete_ );

        CellsToDelete::iterator iter = copyOfCellsToDelete.begin();
        while (iter != copyOfCellsToDelete.end())
        {
            (*iter)->removeSelf();
            ++iter;
        }
    }

    this->checkCellsHaveLoadedMappedGeometry();
    isBalancing_ = false;
#endif
}
```

**算法步骤**:
1. **递归保护**:用 `isBalancing_` 防止递归调用。
2. **负载更新**:`pRoot_->updateLoad()` 自底向上汇总每个节点的负载。
3. **计算安全边界**:`max(safetyBound, avgSmoothedLoad * safetyRatio)` —— 默认 `safetyBound=0.85`,`safetyRatio=1.1`,意味着要么绝对上限 0.85,要么当前平均的 1.1 倍(取大值)。
4. **递归平衡**:`pRoot_->balance(rect, loadSafetyBound)` —— 从根开始递归,每个内部节点决定向左还是向右移动切分线。
5. **二次更新**:平衡后再更新一次负载,反映新边界下的负载分布。
6. **通知 CellApp**:`informCellAppsOfGeometry(false)` —— 把新的 BSP 树序列化发给每个 CellApp,但暂不发送(等 loadBalance 末尾统一 sendToAll)。
7. **清理空 Cell**:遍历 `cellsToDelete_`,删除被标记的空 Cell。
8. **几何加载检查**:`checkCellsHaveLoadedMappedGeometry()` 通知 CellApp 几何已加载。

#### 2.3.2 第2层 metaLoadBalance(跨 CellAppGroup)

`cellappmgr.cpp:768-789`:

```cpp
void CellAppMgr::metaLoadBalance()
{
    // 1. 重新识别 CellApp 分组(洪水填充)
    CellAppGroups appGroups( cellApps_ );

    // 2. 计算合并阈值:平均负载 + 容忍度
    const float mergeThreshold =
        this->avgCellAppLoad() + CellAppMgrConfig::metaLoadBalanceTolerance();

    // 3. 检查过载的组:过载则加 Cell
    appGroups.checkForOverloaded( mergeThreshold );

    // 4. 检查加载中的 Space:需要更多加载 Cell
    bool hasLoadingSpaces = this->checkLoadingSpaces();

    // 5. 检查空闲的组:空闲则退役 Cell
    if (!hasLoadingSpaces)
    {
        appGroups.checkForUnderloaded( CellAppLoadConfig::lowerBound() );
    }
}
```

**算法步骤**:
1. **分组识别**:`CellAppGroups appGroups(cellApps_)` —— 构造函数内部调用 `cellApps_.identifyGroups(list_)`,通过洪水填充把互相连通的 CellApp 分到同一组(详见第十章)。
2. **阈值计算**:`avgCellAppLoad() + metaLoadBalanceTolerance` —— 默认 `metaLoadBalanceTolerance=0.05`,意味着组的平均负载超过全局平均 5% 就算过载。
3. **过载处理**:`checkForOverloaded(mergeThreshold)` —— 遍历所有组,对每个过载组添加一个 Cell。
4. **加载中 Space**:`checkLoadingSpaces()` —— 如果有 Space 还在加载几何,可能需要更多 Cell 帮助加载(避免单个 Cell 加载过慢)。
5. **空闲处理**:`checkForUnderloaded(lowerBound)` —— 没有加载中的 Space 时,检查空闲组,退役最空闲 CellApp 的所有 Cell。

## 三、Cell 评分体系

Cell 评分体系是 metaLoadBalance 决策"哪个 CellApp 应该接收新 Cell"的核心机制。它由 `CellAppComparer` 类实现,定义在 `programming/bigworld/server/cellappmgr/cellapp_comparer.hpp` 与 `cellapp_comparer.cpp`。

### 3.1 CellAppComparer 概览

`cellapp_comparer.hpp:22-42`:


`CellAppComparer` 是一个**多评分项比较器**:
- 内部维护一个 `attributes_` 向量,按优先级顺序存放多个 `CellAppScorer`。
- 比较两个 CellApp 时,**按顺序遍历评分项**,第一个能区分出高低的评分项决定结果(类似字典序比较)。
- 这种设计允许灵活配置:不同的评分项组合产生不同的策略。

#### 3.2.1 CellAppLoadScorer —— 自身负载

`cellapp_comparer.cpp:251-255`:


**评分公式**:`score = -estimatedLoad`

```cpp

    Cells::const_iterator iter = cells_.begin();

        ++iter;
    }
    return count;

```

**直觉**:同一 Space 的多个 Cell 如果在同一台机器上,它们之间的 Ghost 通信走 loopback,代价远低于跨机器。所以这个评分项鼓励"把新 Cell 放到已有同 Space Cell 的同机器上"。

#### 3.2.4 BaseCellTrafficScorer —— Base-Cell 通信代价


### 3.4 评分计算公式

`cellapp_comparer.cpp:189-218`:

```cpp
bool CellAppComparer::isABetterCellApp(
        const CellApp * pOld, const CellApp * pNew, const Space * pSpace ) const
{
    if (pOld == NULL)
    {
        return true;   // 第一个总是被接受
    }

    Scorers::const_iterator iter = attributes_.begin();

    while (iter != attributes_.end())
    {
        const CellAppScorer & attribute = **iter;

        float result = attribute.compareCellApps( pOld, pNew, pSpace );

        if (result < 0.f)
        {
            return false;   // 新的更差
        }
        else if (result > 0.f)
        {
            return true;    // 新的更好
        }
        // result == 0,平手,继续看下一项

        ++iter;
    }

    return false;  // 全部平手,默认不替换
}
```

每个评分器的 `compareCellApps`(`cellapp_comparer.cpp:227-244`):

```cpp
float CellAppScorer::compareCellApps(
        const CellApp * pOld, const CellApp * pNew, const Space * pSpace ) const
{
    float oldScore = this->getScore( pOld, pSpace );
    float newScore = this->getScore( pNew, pSpace );

    if (CellAppMgrConfig::shouldShowMetaLoadBalanceDebug())
    {
        DEBUG_MSG( "CellAppScorer::compareCellApps( %s ): "
                        "Old (App %d. Score %f). New (App %d. Score %f)\n",
                    this->name(),
                    pOld->id(), oldScore,
                    pNew->id(), newScore );
    }

    return newScore - oldScore;   // 新减旧,正数表示新更好
}
```

**最终比较公式**:

```
对每个评分项 s_i(按优先级顺序):
    diff_i = score_i(new) - score_i(old)
    if diff_i > 0: 新更好
    if diff_i < 0: 旧更好
    if diff_i == 0: 继续看下一项

全部平手 → 不替换(返回 false)
```

### 3.5 findBestCellApp 选择算法

`cellapps.cpp:415-440`:

```cpp
CellApp * CellApps::findBestCellApp( const Space * pSpace,
        const CellAppGroup * pExcludedGroup ) const
{
    MF_ASSERT( pSpace );
    CellApp * pBest = NULL;
    Map::const_iterator iter = map_.begin();

    while (iter != map_.end())
    {
        CellApp * pApp = iter->second;

        // 排除同组的 CellApp(因为新 Cell 必须放到不同组才能扩大连通域)
        if (((pExcludedGroup == NULL) || (pApp->pGroup() != pExcludedGroup)) &&
                !pApp->isRetiring())
        {
            // 必须先通过有效性检查,再进行打分比较
            if (cellAppComparer_.isValidApp( pApp, pSpace ) &&
                cellAppComparer_.isABetterCellApp( pBest, pApp, pSpace ))
            {
                pBest = pApp;
            }
        }

        ++iter;
    }

    return pBest;
}
```

**算法步骤**:
1. **遍历所有 CellApp**:O(N),N 是 CellApp 总数。
2. **过滤排除组**:新 Cell 必须放到与当前 Space 所在组不同的 CellApp 上,这样添加后才能把两个组连成一个(扩大连通域)。
3. **过滤正在退休的 CellApp**:`!pApp->isRetiring()`。
4. **有效性检查**:`isValidApp` 调用每个评分器的 `hasValidScore`(目前只有 `LimitedSpacesScorer` 实现了非默认逻辑)。
5. **比较替换**:用 `isABetterCellApp` 比较当前最佳与新候选,如果新的更好就替换。

**复杂度**:O(N * S),其中 N 是 CellApp 数,S 是评分项数(通常 5)。在大规模集群(N=100+)中,这个线性扫描是可接受的。

```cpp

{
    totalLoad_ = pLeft_->updateLoad() + pRight_->updateLoad();

    totalSmoothedLoad_ =
        pLeft_->totalSmoothedLoad() + pRight_->totalSmoothedLoad();

    numRetiring_ = pLeft_->numRetiring() + pRight_->numRetiring();

    areaNotLoaded_ = pLeft_->areaNotLoaded() + pRight_->areaNotLoaded();

    minLoad_ = std::min( pLeft_->minLoad(), pRight_->minLoad() );
    maxLoad_ = std::max( pLeft_->maxLoad(), pRight_->maxLoad() );

    // 合并左右子树的实体边界级别
    entityBoundLevels_.merge( pLeft_->entityBoundLevels(),
                            pRight_->entityBoundLevels(),
                            isHorizontal_, position_ );

    // 合并左右子树的 chunk 边界
    const BW::Rect & lBounds = pLeft_->balanceChunkBounds();
    const BW::Rect & rBounds = pRight_->balanceChunkBounds();

    if (isHorizontal_)
    {
        chunkBounds_.yMin_ = lBounds.yMin_;
        chunkBounds_.yMax_ = rBounds.yMax_;
        chunkBounds_.xMin_ = std::max( lBounds.xMin_, rBounds.xMin_ );
        chunkBounds_.xMax_ = std::min( lBounds.xMax_, rBounds.xMax_ );
    }
    else
    {
        chunkBounds_.xMin_ = lBounds.xMin_;
        chunkBounds_.xMax_ = rBounds.xMax_;
        chunkBounds_.yMin_ = std::max( lBounds.yMin_, rBounds.yMin_ );
        chunkBounds_.yMax_ = std::min( lBounds.yMax_, rBounds.yMax_ );
    }

    leftCount_ = pLeft_->cellCount();
    rightCount_ = pRight_->cellCount();

    return totalLoad_;
}
```

**关键点**:
- **后序遍历**:先递归更新子节点,再汇总到当前节点。
- **负载汇总**:总负载是左右之和,最小是左右最小,最大是左右最大。
- **chunk 边界合并**:对于水平切分(沿 Y 轴),chunk 的 Y 范围是左.yMin 到右.yMax(覆盖两侧),X 范围是左右 X 范围的交集(因为两侧 X 相同)。这反映了"chunk 边界是子节点已加载 chunk 的并集在切分轴方向上"。
- **EntityBoundLevels 合并**:把左右子树的实体边界按切分线合并,这是计算平衡时"实体在哪里"的关键数据。

### 4.4 BSP 树的构建

BSP 树的构建通过 `addCell` 方法完成,有几种情况:

#### 4.4.1 CellData::addCell —— 叶子节点添加新 Cell

`cell_data.cpp:355-370`:

```cpp
CM::BSPNode * CellData::addCell( CellData * pCell, bool isHorizontal )
{
    const float partitionPt = range_.range1D( isHorizontal ).max_;
    BW::Rect newRange = range_;
    newRange.range1D( isHorizontal ).min_ = partitionPt;
    newRange.range1D( isHorizontal ).max_ = partitionPt;
    pCell->setRange( newRange );

    // 新 Cell 总是加到右侧(或上侧)
    return new CM::InternalNode( this, pCell,
            isHorizontal, range_, partitionPt );
}
```

**算法**:
1. 切分点取当前 range 在切分轴上的最大值(即右边界/上边界)。
2. 新 Cell 的 range 是"零宽度"的(在切分轴上 min=max=partitionPt)。这是初始状态,后续 loadBalance 会扩展它。
3. 创建新的 `InternalNode`,左右子分别是当前 CellData 和新 CellData。

**注意**:新 Cell 的初始 range 是零宽度的,这意味着它一开始不覆盖任何空间,直到 loadBalance 把切分线移动给它一些空间。

#### 4.4.2 InternalNode::addCell —— 内部节点添加新 Cell

`internal_node.cpp:100-125`:

```cpp
BSPNode * InternalNode::addCell( CellData * pCell, bool isHorizontal )
{
    bool addToLeft = false;

    if (leftCount_ < rightCount_)
    {
        addToLeft = true;   // 左子树 Cell 少,加到左
    }
    else if (leftCount_ == rightCount_)
    {
        // 数量相等,根据切分线在中点哪侧决定
        float value = range_.range1D( isHorizontal_ ).midPoint();
        addToLeft = (position_ < value);
    }

    if (addToLeft && !pLeft_->isRetiring())
    {
        pLeft_ = pLeft_->addCell( pCell, !isHorizontal_ );  // 翻转切分方向
    }
    else
    {
        pRight_ = pRight_->addCell( pCell, !isHorizontal_ );
    }

    return this;
}
```

**算法**:
1. **平衡子树大小**:优先加到 Cell 数较少的一侧。
2. **数量相等**:根据切分线在中点哪侧,加到另一侧(让切分线尽量居中)。
3. **避免加到正在退休的子树**:如果选中左但左在退休,改加到右。
4. **翻转切分方向**:递归调用子树时,切分方向取反。这是 BSP 树的关键特性:**层次交替切分方向**。例如根是水平切分,第二层是垂直切分,第三层又是水平切分,如此交替。

这种交替切分保证了 BSP 树的空间划分是**二维均衡**的,而不是只在一个方向上无限切分。

### 4.5 分割平面选择

BigWorld BSP 的分割平面有两个特点:

1. **方向交替**:每深一层,切分方向翻转一次。这保证了二维空间被均衡切分。
2. **位置可移动**:内部节点的 `position_` 不是固定的,每次 `balance` 都会根据负载差异调整。

#### 4.5.1 初始分割位置

`cell_data.cpp:355-370` 中,新 Cell 的切分点是 `range_.range1D(isHorizontal).max_`(右/上边界)。这意味着新 Cell 一开始占据零宽度,所有空间仍归原 Cell。后续 `balance` 会把切分线左移,把空间逐渐转移给新 Cell。

#### 4.5.2 平衡时的位置调整

`internal_node.cpp:358-438` 的 `doBalance` 是核心:

```cpp
InternalNode::BalanceDirection InternalNode::doBalance( float loadSafetyBound )
{
    bool shouldLimitToChunks =
        CellAppMgrConfig::shouldLimitBalanceToChunks();
    const bool isRetiring = pLeft_->isRetiring() || pRight_->isRetiring();

    float loadDiff = 0.f;

    // 必须等左右子 Cell 都已创建(避免 CellApp 还没准备好)
    const bool childrenCreated = pLeft_->hasBeenCreated() &&
        pRight_->hasBeenCreated();

    if (!isRetiring)
    {
        // 还有 chunk 没加载完
        if (!this->hasLoadedRequiredChunks())
        {
            shouldLimitToChunks = false;
            if ((this->maxLoad() < loadSafetyBound) &&
                CellAppMgrConfig::shouldBalanceUnloadedChunks())
            {
                // 基于"未加载 chunk 面积"来平衡,而不是负载
                return childrenCreated ?
                    this->balanceOnUnloadedChunks( loadSafetyBound ) :
                    BALANCE_NONE;
            }
        }

        // 计算负载差异(从平均值的偏离)
        const float leftAvgLoad = pLeft_->avgLoad();
        const float rightAvgLoad = pRight_->avgLoad();
        const float nodeAvgLoad = this->avgLoad();

        if (leftAvgLoad > rightAvgLoad)
        {
            loadDiff = fabs( leftAvgLoad - nodeAvgLoad );
        }
        else
        {
            loadDiff = -fabs( rightAvgLoad - nodeAvgLoad );
        }
    }
    else
    {
        // 退休时,固定方向(向退休方移动)
        loadDiff = pLeft_->isRetiring() ? 1.f : -1.f;
    }

    BalanceDirection balanceDir = this->dirFromLoadDiff( loadDiff );

    BSPNode * pFromNode = this->growingChild( balanceDir );

    // 检查是否应该移动:方向非空,子节点已创建,源节点未过载
    const bool shouldMove = (balanceDir != BALANCE_NONE) &&
        childrenCreated &&
        (pFromNode->maxLoad() < loadSafetyBound);

    float newPos = position_;

    if (shouldMove)
    {
        // 计算实体边界限制(防止把实体切到错误的 Cell)
        float entityLimit = this->entityLimitInDirection( balanceDir,
                loadDiff * balanceAggression_ );
        // 计算 chunk 边界限制(防止切到未加载的 chunk)
        float chunkLimit = shouldLimitToChunks ?
            this->chunkLimitInDirection( balanceDir ) : entityLimit;

        // 取 entityLimit 和 chunkLimit 中"更保守"的
        newPos = this->closestLimit( position_,
                    entityLimit, chunkLimit, balanceDir );
    }
    else
    {
        balanceDir = BALANCE_NONE;
    }

    position_ = newPos;

    this->adjustAggression( balanceDir );

    return balanceDir;
}
```

**算法详解**:

**Step 1: 判断是否需要特殊平衡**

```cpp
if (!this->hasLoadedRequiredChunks())
{
    if ((this->maxLoad() < loadSafetyBound) &&
        CellAppMgrConfig::shouldBalanceUnloadedChunks())
    {
        return this->balanceOnUnloadedChunks( loadSafetyBound );
    }
}
```

如果该 Space 还有 chunk 没加载完,并且当前未过载,使用基于"未加载面积"的平衡策略(让 chunk 加载更均匀)。

**Step 2: 计算负载差异**

```cpp
const float leftAvgLoad = pLeft_->avgLoad();
const float rightAvgLoad = pRight_->avgLoad();
const float nodeAvgLoad = this->avgLoad();

if (leftAvgLoad > rightAvgLoad)
{
    loadDiff = fabs( leftAvgLoad - nodeAvgLoad );   // 正数,左重
}
else
{
    loadDiff = -fabs( rightAvgLoad - nodeAvgLoad );  // 负数,右重
}
```

`loadDiff` 是**带符号的负载差异**:正数表示左子树重,需要把切分线左移(给左子树减负);负数表示右子树重,需要把切分线右移。

**Step 3: 决定方向**

```cpp
BalanceDirection InternalNode::dirFromLoadDiff( float loadDiff )
{
    return
        (loadDiff > 0.f) ? BALANCE_LEFT :
        (loadDiff < 0.f) ? BALANCE_RIGHT : BALANCE_NONE;
}
```

注意命名:`BALANCE_LEFT` 意思是"向左平衡",即使左子树缩小、右子树增大(切分线左移)。这与直觉相反,需要小心。

**Step 4: 检查可移动性**

```cpp
const bool shouldMove = (balanceDir != BALANCE_NONE) &&
    childrenCreated &&
    (pFromNode->maxLoad() < loadSafetyBound);
```

`pFromNode = growingChild(balanceDir)`:如果方向是 LEFT(左重),`growingChild` 返回 `pRight_`(右子树将增大)。检查 `pFromNode->maxLoad() < loadSafetyBound` 是确保"接收负载的子树当前未过载"——否则会让它更过载。

**Step 5: 计算新位置**

```cpp
float entityLimit = this->entityLimitInDirection( balanceDir,
        loadDiff * balanceAggression_ );
float chunkLimit = shouldLimitToChunks ?
    this->chunkLimitInDirection( balanceDir ) : entityLimit;
newPos = this->closestLimit( position_,
            entityLimit, chunkLimit, balanceDir );
```

- `entityLimit`:基于实体边界的限制,表示"最多移动到哪里,不会把太多实体切到对侧"。
- `chunkLimit`:基于 chunk 边界的限制,表示"最多移动到哪里,不会切到未加载的 chunk"(避免触发额外 chunk 加载)。
- `balanceAggression_`:侵略性,决定一次移动多少。`loadDiff * balanceAggression_` 是"想要迁移的负载量"。
- `closestLimit`:在两个限制中取更保守的(更接近当前位置)。

#### 4.5.3 closestLimit 函数

`internal_node.hpp:104-110`:

```cpp
static float closestLimit( float position, float limit1, float limit2,
        BalanceDirection direction )
{
    return (direction == BALANCE_LEFT) ?
        std::min( position, std::max( limit1, limit2 ) ) :
        std::max( position, std::min( limit1, limit2 ) );
}
```

- 向左平衡(BALANCE_LEFT):新位置 = min(当前位置, max(entityLimit, chunkLimit)) —— 即"不超过较保守的限制"。
- 向右平衡(BALANCE_RIGHT):新位置 = max(当前位置, min(entityLimit, chunkLimit))。
- 不平衡(BALANCE_NONE):不会进入此函数。

`max/min` 的选择反映"两个限制中谁更保守":向左移时,较小值更保守(移动更少);向右移时,较大值更保守。

### 4.6 空间局部性原理

BSP 树保证了空间局部性:相邻的 Cell 在 BSP 树中也是邻居关系。这点对 Ghost 通信至关重要。

#### 4.6.1 pCellAt 定位

`internal_node.cpp:220-225`:

```cpp

{
    bool isLeft = isHorizontal_ ? (y < position_) : (x < position_);
    return isLeft ? pLeft_->pCellAt( x, y ) : pRight_->pCellAt( x, y );
}
```

定位一个点所在的 Cell:从根开始,根据切分线决定走左还是右,直到叶子。复杂度 O(log N),N 是 Cell 数。

#### 4.6.2 邻居 Cell 的快速查找

由于 BSP 树的空间局部性,查询某 Cell 的邻居只需在 BSP 树中查找边界相邻的叶子。这在 Ghost 通信中很重要:Ghost 主要在邻居 Cell 之间传播,所以邻居关系的快速查找能显著降低开销。

#### 4.6.3 切分方向交替的意义

如果只在一个方向切分,BSP 树会退化成"条带"——空间被切成 1D 的条带,跨条带边界的实体非常密集。交替切分避免了这个问题,让 Cell 形状接近正方形,降低 Ghost 通信量(正方形的周长面积比最小)。

### 4.7 BSP 树的动态调整

BSP 树不是静态的,它在每次 `balance` 时都会调整切分线位置。动态调整的核心是 `adjustAggression`(侵略性自适应)。

#### 4.7.1 balanceAggression 自适应

`internal_node.cpp:445-464`:

```cpp
void InternalNode::adjustAggression( InternalNode::BalanceDirection balanceDir )
{
    const int hasReversedDirection =
        ((balanceDir == BALANCE_LEFT) && (prevBalanceDir_ == BALANCE_RIGHT)) ||
        ((balanceDir == BALANCE_RIGHT) && (prevBalanceDir_ == BALANCE_LEFT));

    if (hasReversedDirection)
    {
        // 方向反转,降低侵略性
        balanceAggression_ *= BalanceConfig::aggressionDecrease();
    }
    else
    {
        // 同向或静止,提高侵略性
        balanceAggression_ *= BalanceConfig::aggressionIncrease();
    }

    balanceAggression_ = BalanceConfig::clampedAggression( balanceAggression_ );
    prevBalanceDir_ = balanceDir;
}
```

**算法**:
- **方向反转**:本次方向与上次相反(上次左移,这次右移),说明上次移过头了,降低侵略性。`aggressionDecrease` 默认 0.5,即侵略性减半。
- **同向/静止**:本次方向与上次相同或上次静止,提高侵略性。`aggressionIncrease` 是计算出来的值,使得在 `aggressionIncreasePeriod`(默认 10s)内能恢复到降低前的水平。

#### 4.7.2 侵略性边界

`balance_config.cpp:94-111`:

```cpp
bool BalanceConfig::postInit( float balancePeriod )
{
    const float numDecreaseSteps =
        maxAggressionIncreasePeriod()/aggressionIncreasePeriod();
    float minToMaxRatio = powf( aggressionDecrease(), numDecreaseSteps );
    minAggression.set( maxAggression() * minToMaxRatio );

    // 计算每个 tick 应该增加多少,才能在 aggressionIncreasePeriod 内恢复
    float ticksToReclaim = aggressionIncreasePeriod()/balancePeriod;
    float reclaimAmount = 1.f/aggressionDecrease();

    aggressionIncrease.set( expf( logf( reclaimAmount )/ticksToReclaim ) );

    minCPUOffload.set( cpuOffloadForLevel( numCPUOffloadLevels() - 1 ) );

    return true;
}
```

**默认值计算**(假设 `loadBalancePeriod=1s`):
- `numDecreaseSteps = maxAggressionIncreasePeriod / aggressionIncreasePeriod = 40 / 10 = 4`
- `minToMaxRatio = 0.5^4 = 0.0625`
- `minAggression = 1.0 * 0.0625 = 0.0625`(最大侵略性是 1,最小是 0.0625)
- `ticksToReclaim = 10 / 1 = 10`
- `aggressionIncrease = exp(log(2)/10) ≈ 1.0718`(每秒增长约 7%)

这意味着:
- **最大侵略性 1.0**:第一次平衡时,如果方向不变,可以迁移 100% 的目标负载量。
- **最小侵略性 0.0625**:经过多次方向反转后,侵略性降到 1/16,只迁移 6.25% 的目标负载。
- **恢复周期**:从最小恢复到最大需要 `log(16)/log(1.0718) ≈ 40s`(即 `maxAggressionIncreasePeriod`)。

这种自适应机制防止了"负载在两个 Cell 之间反复振荡",让平衡过程收敛。

#### 4.8.2 级别的含义

`balance_config.hpp:21`:`numCPUOffloadLevels = 5`(默认 5 级)。

`balance_config.cpp:43-48`:

```cpp

{
    // 每个级别 offload 的量是上一级的一半,最后一级 offload maxCPUOffload
    return maxCPUOffload() * powf( LEVEL_STEP, level );
}
```

`LEVEL_STEP = 0.5`,`maxCPUOffload = 0.02`(默认)。

所以各级别 offload 量为:

| Level | offload 量 | 含义 |
|-------|-----------|------|
| 0 | 0.02 | 最多(2% CPU) |
| 1 | 0.01 | 1% CPU |
| 2 | 0.005 | 0.5% CPU |
| 3 | 0.0025 | 0.25% CPU |
| 4 | 0.00125 | 最少(0.125% CPU) |

`entityBounds_[level]` 表示"如果想要 offload `cpuOffloadForLevel(level)` 的负载,需要把切分线移到哪里"。level 越小,offload 量越大,边界越远。

#### 4.8.3 合并算法

`entity_bound_levels.cpp:35-56`:

```cpp
void EntityBoundLevels::merge( const EntityBoundLevels & left,
        const EntityBoundLevels & right,
        bool isHorizontal, float partitionPosition )
{
    if (isHorizontal)
    {
        this->mergeTwoBranches( left, right, false, false );
        this->mergeTwoBranches( left, right, false, true );
        this->takeSingleBranch( left, true, false, partitionPosition );
        this->takeSingleBranch( right, true, true, partitionPosition );
    }
    else
    {
        this->mergeTwoBranches( left, right, true, false );
        this->mergeTwoBranches( left, right, true, true );
        this->takeSingleBranch( left, false, false, partitionPosition );
        this->takeSingleBranch( right, false, true, partitionPosition );
    }
}
```

**合并逻辑**:
- 切分轴方向(Y 或 X):合并左右两子树的级别数据(`mergeTwoBranches`)。
- 垂直切分轴方向:直接取对应子树的数据(`takeSingleBranch`),因为切分不影响该方向。

`takeSingleBranch`(`entity_bound_levels.cpp:62-82`)会把子树的边界限制在切分线一侧(防止越界)。

`mergeTwoBranches`(`entity_bound_levels.cpp:88-179`)是一个**双指针合并**算法,从两个子树各自的最大级别开始,按边界位置排序合并,直到填满本节点的级别数组。每个合并后的级别,其负载是左右两侧在该边界位置的最大负载。

#### 4.8.4 查询最佳边界

`entity_bound_levels.cpp:219-235`:

```cpp
float EntityBoundLevels::entityBoundForLoadDiff( float loadDiff,
        bool isHorizontal, bool isMax, float defaultPosition ) const
{
    const float absLoadDiff = fabs( loadDiff );
    for (int level = 0;
            level < (int)entityLoads_.size();
            ++level)
    {
        if (entityLoads_[ level ].range1D(
                isHorizontal )[ isMax ] <= absLoadDiff)
        {
            return entityBounds_[ level ].range1D( isHorizontal )[ isMax ];
        }
    }

    return defaultPosition;
}
```

**算法**:
- 遍历 level 从小到大(即 offload 量从大到小)。
- 找到第一个 `load >= absLoadDiff` 的 level,返回对应的边界位置。
- 如果没有(目标 offload 量太大),返回 `defaultPosition`(即当前位置,不移动)。

这是 BSP 平衡时决定"切分线移到哪里"的核心查询。

## 五、Cell 分裂算法

Cell 分裂是指在已有 Cell 旁边添加新 Cell,共享原 Cell 的 range,然后通过负载均衡把空间和实体逐渐转移到新 Cell。

### 5.1 触发条件

Cell 分裂由 `metaLoadBalance` 间接触发,具体路径:

1. `CellAppMgr::metaLoadBalance`(`cellappmgr.cpp:768-789`)调用 `appGroups.checkForOverloaded(mergeThreshold)`。
2. `CellAppGroups::checkForOverloaded`(`cell_app_groups.cpp:66-85`)对每个过载组调用 `group.addCell()`。
3. `CellAppGroup::addCell`(`cell_app_group.cpp:465-483`)选择一个 Space,在其上添加 Cell。
4. `Space::addCell()`(`space.cpp:442-456`)选择合适的 CellApp,调用 `Space::addCell(CellApp&)`(`space.cpp:368-435`)。

#### 5.1.1 过载检测

`cell_app_groups.cpp:66-85`:


### 5.3 实体迁移

实体迁移不是显式的"搬数据",而是通过**调整 BSP 切分线**隐式完成。

#### 5.3.1 隐式迁移原理

```
平衡前:
                切分线
                  ↓
  ┌───────────────┼───────────────┐
  │   Cell A      │   Cell B      │
  │   load=0.8    │   load=0.2    │
  │  实体: ●●●●● │  实体: ●     │
  └───────────────┼───────────────┘

平衡后(切分线右移):
                       切分线
                         ↓
  ┌──────────────────────┼──────────┐
  │   Cell A             │  Cell B  │
  │   load=0.5           │  load=0.5│
  │  实体: ●●●         │ 实体:●●● │
  └──────────────────────┼──────────┘
```

切分线右移后,原本属于 A 的实体(在新切分线右侧的)现在属于 B。这些实体的 Real 状态会通过 Ghost 机制从 A 迁移到 B(详见专题1 Ghost 同步机制)。

#### 5.3.2 实体迁移的 Ghost 协议

当切分线移动后,CellApp 之间的实体 Real/Ghost 状态会重新协商:
1. **新归属方**:Cell B 发现自己范围内有"应该是 Real 但当前是 Ghost"的实体(因为它们原本属于 A),触发 Ghost-to-Real 转换。
2. **旧归属方**:Cell A 发现自己范围内的实体"应该是 Ghost 但当前是 Real",触发 Real-to-Ghost 转换。
3. **状态同步**:转换过程中,旧 Real 把最新状态发给新 Real,新 Real 接管权威。

这套机制由 `EntityGhostMaintainer` 在 CellApp 端自动完成,CellAppMgr 不参与细节。

### 5.4 BSP 树更新

BSP 树的更新通过 `balance` 递归完成。每次 `loadBalance` 调用 `pRoot_->balance(rect, loadSafetyBound)`,从根开始递归:

1. **InternalNode::balance**:计算方向,移动切分线,递归 balance 子节点。
2. **CellData::balance**(`cell_data.cpp:618-636`):更新 range,检查是否应该删除(空 Cell)。

```cpp
void CellData::balance( const BW::Rect & range,
        float loadSafetyBound, bool isShrinking )
{
    MF_ASSERT( hasBeenCreated_ || !isShrinking );

    range_ = range;
    isOverloaded_ = (this->cellApp().smoothedLoad() > loadSafetyBound);

    bool hasArea = (range.xMin() < range.xMax()) &&
            (range.yMin() < range.yMax());

    // 当 Cell 没有面积,且正在缩小或退休,且没有实体时,标记删除
    if (!hasArea && (isShrinking || numRetiring_) && (this->numEntities() == 0))
    {
        Space::addCellToDelete( this );
    }
}
```

**关键**:
- `range_ = range`:更新本 Cell 的 range。
- `isOverloaded_`:标记本 Cell 所属 CellApp 是否过载(用于 watcher 显示)。
- **删除条件**:Cell 没有面积(`xMin >= xMax` 或 `yMin >= yMax`) + 正在缩小或退休 + 没有实体,则添加到 `cellsToDelete_` 集合,稍后删除。

## 六、Cell 合并算法

Cell 合并是 Cell 分裂的逆过程:当某个 Cell 的 range 缩小到没有面积且没有实体时,它会被自动删除,其原所属的 InternalNode 会被替换为另一个子节点。

### 6.1 触发条件

Cell 合并没有显式的"合并算法",而是**通过 balance 自然完成**。当一个 Cell 持续缩小(因为它的负载低,被对侧"挤压"),最终 range 变为零面积,就会被 `CellData::balance` 标记删除。

#### 6.1.1 自然合并 vs 显式合并

BigWorld 不做显式的"把两个 Cell 合并成一个"操作,因为:
1. **CellData 是无状态的**:CellAppMgr 端的 CellData 不持有实体,只是 BSP 叶子。删除一个叶子,其空间自动归并到对侧叶子。
2. **实体由 Ghost 机制处理**:Cell 删除后,其范围内的实体的 Real 状态自动迁移到对侧 Cell(通过 Ghost 机制)。

### 6.2 合并流程

```cpp
{
    CM::BSPNode * pResult = this;

    if (pLeft_ == pCell)
    {
        // 左子是要删的,右子替代本节点
        pResult = pRight_;
        pLeft_ = pRight_ = NULL;
        delete this;
    }
    else if (pRight_ == pCell)
    {
        // 右子是要删的,左子替代本节点
        pResult = pLeft_;
        pLeft_ = pRight_ = NULL;
        delete this;
    }
    else
    {
        // 递归到子树
        pLeft_ = pLeft_->removeCell( pCell );
        pRight_ = pRight_->removeCell( pCell );
    }

    return pResult;
}
```

**关键**:当某个内部节点的子节点是要删除的叶子时,**用另一个子节点替换本内部节点**(并 delete 本内部节点)。这相当于"把内部节点提升为它的另一个子节点",BSP 树的高度减 1。

注释提到:
```
// Note: This may promote an internal node so that we have two
// consecutive partitions that are in the same direction.
```

也就是说,删除后可能出现"两个连续的同方向切分"。这不会引起错误,但会让 BSP 树略微"不平衡"。后续 `addCell` 时会通过 `!isHorizontal_` 翻转方向来纠正。

### 6.3 实体合并

实体合并不是显式操作,而是通过 Ghost 机制自然完成:
1. Cell A 的 range 缩小,某些实体不再属于 A。
2. 这些实体在 A 端 Real-to-Ghost 转换。
3. 它们的 Real 状态转移到对侧 Cell B(通过 Ghost-to-Real 转换)。
4. Cell A 被删除时,所有剩余实体(理论上 numEntities==0 才能删除)都已转移完毕。

注意 `CellData::balance` 的删除条件包含 `this->numEntities() == 0`,所以**只有空 Cell 才能被删除**。这保证了不会丢失实体。

## 七、Cell 退休算法

Cell 退休是一种**显式标记 + 渐进清空**的机制。当某个 CellApp 过载或需要下线时,可以标记它的 Cell 为"退休",系统会逐渐把它的负载转移到其他 Cell。

### 7.1 触发条件

Cell 退休主要由 `metaLoadBalance` 的 `checkForUnderloaded` 触发。

`CellAppGroup::checkForUnderloaded`(`cell_app_group.cpp:490-521`):

```cpp
void CellAppGroup::checkForUnderloaded( float loadLowerBound )
{
    // 如果少一个 CellApp 后平均负载仍低于阈值,退役最空闲的
    if (this->avgLoad( 1 ) < loadLowerBound)
    {
        CellApp * pLeastLoaded = NULL;
        float leastLoad = FLT_MAX;

        iterator iter = this->begin();
        while (iter != this->end())
        {
            CellApp * pApp = *iter;
            if ((!pApp->hasOnlyRetiringCells() &&
                pApp->smoothedLoad() < leastLoad))
            {
                pLeastLoaded = *iter;
                leastLoad = pLeastLoaded->smoothedLoad();
            }
            ++iter;
        }

        if (pLeastLoaded)
        {
            pLeastLoaded->retireAllCells();
        }
    }
}
```

**算法**:
1. **预测**:计算"如果组内少一个 CellApp,平均负载是多少"(`avgLoad(1)`)。
2. **决策**:如果预测平均负载仍低于 `loadLowerBound`(默认 0.02),说明组内 CellApp 过多,可以退役一个。
3. **选择**:找出组内**最空闲且不全是退休 Cell** 的 CellApp。
4. **退役**:调用 `pLeastLoaded->retireAllCells()`,把它的所有 Cell 标记为退休。

`avgLoad(1)` 的实现(`cell_app_group.cpp:346-367`):

```cpp
float CellAppGroup::avgLoad( int ifNumRemoved ) const
{
    int count = -ifNumRemoved;  // 减去预想的退役数
    float totalLoad = 0.f;

    CellAppGroup::iterator iter = this->begin();
    while (iter != this->end())
    {
        CellApp * pApp = *iter;
        totalLoad += pApp->smoothedLoad();

        if (!pApp->hasOnlyRetiringCells())
        {
            ++count;
        }
        ++iter;
    }

    return (count > 0) ? totalLoad/count : FLT_MAX;
}
```

注意 `count` 的计算:已经在退役(`hasOnlyRetiringCells`)的 CellApp 不计入分母,但其负载仍计入分子。这让"全部 Cell 都在退役的 CellApp"的负载被分摊给其他人,反映退役完成后的真实情况。

## 八、Cell 迁移流程详解

Cell 迁移是指把一个 Cell 从一个 CellApp 转移到另一个 CellApp。这在 BigWorld 中并不显式发生——Cell 不"搬家",而是**通过"添加新 Cell + 退休旧 Cell"组合实现**。

### 8.1 CellAppMgr 决策

当需要把某 Cell 从 CellApp A 迁移到 CellApp B 时:
1. 在 CellApp B 上创建一个新 Cell(可能通过 `addCellTo` 分裂原 Cell)。
2. 标记原 Cell(在 A 上)为退休。
3. BSP 平衡把切分线向退休方移动,实体自然从 A 迁移到 B。
4. 退休 Cell 清空后,被删除。

这种"伪迁移"的好处是**渐进性**:不需要一次性把所有实体搬到目标,而是通过负载均衡平滑过渡。

### 8.2 通知源 CellApp 与目标 CellApp

#### 8.2.1 通知目标 CellApp

通过 `CellAppInterface::addCell` 请求(`space.cpp:407`),目标 CellApp 收到:
- Space ID
- BSP 树序列化
- 是否是第一个 Cell
- 是否从 DB 恢复
- 所有 Space Data

目标 CellApp 据此创建本地 `Cell` 实例,设置 HBF(Haunt Boundary),初始化 Ghost 表。

#### 8.2.2 通知源 CellApp

通过 `CellAppInterface::retireCell` 通知(`cell_data.cpp:172-185`):


源 CellApp 收到 `retireCell` 后,本地的 Cell 进入退休状态:
- 停止接受新 Real 实体(新实体应该到对侧 Cell)。
- 加速 Real-to-Ghost 转换,把 Real 状态推给对侧。

### 8.3 实体状态转移

#### 8.3.1 Real → Ghost 转换

在源 Cell A 上,原本是 Real 的实体随着切分线移动,落入 B 的 range。CellApp A 端检测到该实体的位置不再属于自己,触发 `convertRealToGhost`:
1. 把实体当前状态(属性、AOI 列表)序列化发给 B。
2. 把本地实体改为 Ghost(清空 Witness、停止 AI、释放大部分内存)。
3. 在 B 上,`convertGhostToReal` 把对应 Ghost 升级为 Real,接收 A 发来的状态。

#### 8.3.2 Ghost → Real 转换

在目标 Cell B 上,原本是 Ghost 的实体(因为 A 是 Real)现在应该变成 Real(因为 A 把它变成了 Ghost)。CellApp B 端检测到这种情况,触发 `convertGhostToReal`:
1. 通知 A:"我要变成 Real 了"。
2. A 把最新状态发给 B。
3. B 升级 Ghost 为 Real,启用 AI、Witness 等。

#### 8.3.3 双方握手

实体状态转移是**双方握手**的:A 不能单方面"扔掉" Real 状态,必须等 B 确认接管后才能降级为 Ghost。这保证了任何时刻都至少有一个 Cell 持有 Real 状态,不会丢失。

详细协议见专题1(Ghost 同步机制)。

### 8.4 客户端透明性

客户端**完全不知道** Cell 边界的存在,这通过两层机制保证:

#### 8.4.1 Mailbox 重定向

每个实体有一个 `Mailbox`,客户端通过 Mailbox 与实体通信。当 Real 实体从一个 Cell 迁移到另一个 Cell:
1. 新 Real 接管后,会通过 BaseApp 更新自己的 Mailbox 路由。
2. 客户端的请求会被路由到新 Real,客户端无感。

#### 8.4.2 Witness 不变

Witness 是玩家观察世界的代理。Witness 跟随玩家移动,但 Witness 所在的 Cell 不一定是玩家实体 Real 所在的 Cell。当玩家跨 Cell 边界时:
- 玩家实体 Real 状态可能迁移到新 Cell。
- Witness 仍在原 Cell(只要原 Cell 还存在)。
- 客户端看到的世界是 Witness 通过 AOI 收集的实体状态,与 Real 在哪个 Cell 无关。

这种解耦让客户端**完全感知不到** Cell 边界变化。

### 8.5 迁移的原子性保证

#### 8.5.1 Real/Ghost 切换的原子性

BigWorld 通过**两阶段提交**保证 Real 状态的原子转移:
1. **阶段1**:新 Cell 创建 Ghost 副本(还没升级为 Real),旧 Cell 仍是 Real。
2. **阶段2**:旧 Cell 把最新状态发给新 Cell,新 Cell 升级为 Real,旧 Cell 降级为 Ghost。

任何时刻,Real 状态都唯一存在,不会同时出现在两个 Cell 上。

#### 8.5.2 BSP 切分线的原子更新

BSP 切分线的更新是 CellAppMgr 单方面决定的,但实体的归属变化是 CellApp 端基于切分线**逐渐**完成的:
1. CellAppMgr 更新切分线,通过 `informCellAppsOfGeometry` 发给所有 CellApp。
2. CellApp 收到新 BSP 树后,本地的 EntityGhostMaintainer 检测哪些实体的归属应该变化。
3. 触发相应的 Real/Ghost 转换。

这种"决策集中、执行分布"的架构保证了切分线更新的一致性,同时让实体转换可以异步进行。

```cpp
BaseApp * ManagedAppSubSet::findLeastLoadedApp() const
{
    BaseApp * pBest = NULL;

    float lowestLoad = 0.f;
    BaseAppsIterator iter = this->iterator();

    while (BaseApp * pCurr = iter.next().get())
    {
        const float currLoad = pCurr->load();

        if (!pCurr->isRetiring())
        {

                pBest = pCurr;
```

**关键检查**:
1. **backup hash 必须有效**:offload 过程中不能切换 backup hash,否则实体位置可能错乱。
2. **不能在 hash 切换中**:必须等切换完成。
3. **避免循环依赖**:如果 A 在 backing up B,而 B 还没开始 offloading,就可能出现"B 恢复后又 offload 给 A"的循环。所以必须等所有 backing up target 都进入 offloading 状态。

只有以上检查全部通过,才设置 `isOffloading_=true`,通知 BaseApp 开始 offload 实体。

#### 9.3.3 offload 过程

一旦 `isOffloading_=true`,BaseApp 开始:
1. **选择实体**:按顺序选择 Base 实体 offload。
2. **确定目标**:根据 backup hash 找到该实体的备份 BaseApp,作为 offload 目标。
3. **发送状态**:把实体的完整状态(属性、定时器、内部数据)发给目标。
4. **目标接管**:目标 BaseApp 创建对应 Base 实体,接管权威。
5. **重定向 Mailbox**:通过 BaseAppMgr 通知所有引用此实体的 Mailbox,重定向到新地址。
6. **本地销毁**:源 BaseApp 销毁本地副本。

整个过程是**流式**的,实体逐个迁移,避免一次性阻塞。

```cpp

{
```

```cpp
    // 当前实现相比初始方案略高级。 balancing 主要来自登录登出,
    // 总是分配到最空闲的 BaseApp。
    //
    // 当前方案:每个 BaseApp 有一个目标 BaseApp 列表(应该创建 Base 实体到这些 BaseApp)。

    BW::vector<BaseAppAddrLoadPair> infoPairs;

    BaseAppsIterator iter = this->iterator();

    {
        infoPairs.push_back( BaseAppAddrLoadPair( pCurr->addr(), pCurr->load() ) );

    {
        destSize = Config::maxDestinationsInCreateBaseInfo();
        // 部分排序,把最空闲的 destSize 个移到前面
        std::partial_sort(
            infoPairs.begin(), infoPairs.begin() + destSize, infoPairs.end(),
            std::bind( std::less<float>(),
                       std::bind( &BaseAppAddrLoadPair::load, _1 ),
                       std::bind( &BaseAppAddrLoadPair::load, _2 ) ) );
        infoPairs.erase( infoPairs.begin() + destSize, infoPairs.end() );
    }
    // ...

    // 3. 序列化发给所有 BaseApp
    MemoryOStream infoStream( infoPairs.size() * sizeof(BaseAppAddrLoadPair) +
                                sizeof(uint32) );
    infoStream << infoPairs;
    sendToBaseApps( BaseAppIntInterface::setCreateBaseInfo, infoStream,
                    BaseAppsIterator( apps_ ) );
}
```

**算法**:
1. **收集**:把所有 BaseApp 的地址和负载组成列表。
2. **裁剪**:如果超过 `maxDestinationsInCreateBaseInfo`(默认 250),用 `partial_sort` 找出最空闲的 250 个,丢弃其他。这是为了控制每个 BaseApp 维护的目标列表大小(避免大规模集群时列表过大)。
3. **下发**:把列表发给所有 BaseApp。

BaseApp 收到后,在创建 Base 实体时,根据列表中每个 BaseApp 的负载**反比加权随机**选择目标。负载越低,被选中概率越高。这种**随机加权**避免了"所有创建都涌向最空闲的 BaseApp"的雷同效应,让负载分布更平滑。

更新周期默认 5s(`updateCreateBaseInfoPeriod=5`)。

CellAppGroup 是 metaLoadBalance 的核心抽象:它表示**一组可以通过普通负载均衡互相平衡的 CellApp**。同一组内的 CellApp 通过共享 Space(多 Cell Space)相连。

#### 10.1.1 组的定义

两个 CellApp 在同一组,当且仅当存在一个 Space,它在这两个 CellApp 上都有 Cell。换句话说,组是"通过多 Cell Space 连通的 CellApp 集合"。

#### 10.1.2 组的意义

只有同一组的 CellApp 才能**通过普通 loadBalance 互相平衡负载**(因为 loadBalance 只在 Space 内部移动切分线,而 Space 跨越的 CellApp 才能受益)。所以:
- 同组 CellApp 之间可以通过普通 loadBalance 平衡。
- 跨组 CellApp 必须**通过 metaLoadBalance 添加新 Cell**来建立连接,才能开始普通平衡。

#### 10.2.1 markGroup 洪水填充

`cellapp.cpp:536-568`:

```cpp
void CellApp::markGroup( CellAppGroup * pGroup )
{
    pGroup->insert( this );

    // Flood fill all connected CellApps.
    // 1. 遍历本 CellApp 的所有 Space
    Cells::iterator fromAppIter = cells_.begin();
    while (fromAppIter != cells_.end())
    {
        Space * pSpace = (*fromAppIter)->getSpace();

        // 2. 遍历该 Space 的所有 Cell
        Cells::const_iterator fromSpaceIter = pSpace->cells().begin();
        while (fromSpaceIter != pSpace->cells().end())
        {
            CellApp * pNewApp = (*fromSpaceIter)->pCellApp();

            // 3. 如果该 Cell 的 CellApp 还没分组,递归 markGroup
            if (pNewApp->pGroup() != pGroup)
            {
                MF_ASSERT( pNewApp->pGroup() == NULL );
                pNewApp->markGroup( pGroup );
            }

            ++fromSpaceIter;
        }

        ++fromAppIter;
    }
}
```

**洪水填充算法**:
1. 把当前 CellApp 加入组。
2. 遍历该 CellApp 的所有 Cell(从而所有 Space)。
3. 对每个 Space,遍历其所有 Cell,找到对应的 CellApp。
4. 如果该 CellApp 还没分组,递归 `markGroup`。

这是一个标准的**深度优先搜索(DFS)**,复杂度 O(V+E),V 是 CellApp 数,E 是"CellApp-Space-CellApp"边数。

```cpp
class HybridSpaceChooser: public SpaceChooser
{
public:
    HybridSpaceChooser();
    virtual void onSpace( const Space & space );

    bool hasLargestSpace() const { return minCells_ == 0; }

private:
    int minCells_;
    float maxLoad_;
};

void HybridSpaceChooser::onSpace( const Space & space )
{
    float currentLoad = space.avgLoad();

    if (space.isLarge())
    {
        // 大 Space:选负载最高的
        if ((currentLoad > maxLoad_) || !this->hasLargestSpace())
        {
            pSpace_ = &space;
            maxLoad_ = currentLoad;
            minCells_ = 0;  // 不再考虑 minCells
        }
    }

    // 小 Space:选 Cell 最少的(并列时选负载高的)
    if ((space.numCells() < minCells_) ||
            ((space.numCells() == minCells_) && (currentLoad > maxLoad_)))
    {
        pSpace_ = &space;
        minCells_ = space.numCells();
        maxLoad_ = currentLoad;
    }
}
```

混合策略:
- **大 Space**(多 Cell 且至少有一个 CellApp 只在这一个 Space 上):选负载最高的,因为它最需要平衡。
- **小 Space**:选 Cell 最少的,并列时选负载高的(负载高说明每个 Cell 都很忙,需要更多 Cell 分担)。

**注意**:级别是倒序的——**级别 0 是最高级**(卸载 `maxCPUOffload * 0.5^0 = 0.02`),级别 4 是最低级(卸载 `0.02 * 0.5^4 = 0.00125`)。这是有意为之:CellApp 上报的"边界级别"中,级别数字越大表示边界越宽松(越不需要卸载),所以最低级别的卸载量也最小。

#### 11.3.3 反向计算:levelForCPUOffload

`balance_config.cpp:55-70` 提供了反向函数:已知需要卸载的负载量,反推应该使用的级别。

```cpp
// balance_config.cpp:55-70
int BalanceConfig::levelForCPUOffload( float loadToOffload )
{
    if (loadToOffload <= 0.0001f)  // 太小不卸载
        return 0;

    float offloadFraction = loadToOffload / maxCPUOffload();
    // Find 0.5^x = offloadFraction
    float numHalves = logf( offloadFraction ) / logf( LEVEL_STEP );
    int level = int( ceilf( numHalves ) );

    return BalanceConfig::clampedOffloadLevel( level );
}

// balance_config.cpp:76-79
int BalanceConfig::clampedOffloadLevel( int level )
{
    return Math::clamp( 0, level, numCPUOffloadLevels() - 1 );
}
```

**算法步骤**:
1. 计算比例 `offloadFraction = loadToOffload / 0.02`
2. 解方程 `0.5^x = offloadFraction`,得 `x = log(offloadFraction) / log(0.5)`
3. 向上取整得到级别
4. 用 `Math::clamp` 限制在 `[0, 4]` 范围内

**举例**:
- `loadToOffload = 0.02`(2% CPU)→ `offloadFraction = 1.0` → `x = 0` → level = 0(最高级)
- `loadToOffload = 0.01`(1% CPU)→ `offloadFraction = 0.5` → `x = 1` → level = 1
- `loadToOffload = 0.005` → `offloadFraction = 0.25` → `x = 2` → level = 2
- `loadToOffload = 0.00125` → `offloadFraction = 0.0625` → `x = 4` → level = 4(最低级)

#### 11.3.4 侵略性参数的派生

侵略性参数 `aggressionDecrease`/`aggressionIncrease` 通过 `postInit` 派生出 `minAggression`/`aggressionIncrease`/`minCPUOffload`:

```cpp
// balance_config.cpp:94-111
bool BalanceConfig::postInit( float balancePeriod )
{
    // 1. 计算 minAggression:maxAggression 经过 N 步 0.5 衰减后的值
    const float numDecreaseSteps =
        maxAggressionIncreasePeriod() / aggressionIncreasePeriod();
    float minToMaxRatio = powf( aggressionDecrease(), numDecreaseSteps );
    minAggression.set( maxAggression() * minToMaxRatio );

    // 2. 计算 aggressionIncrease:每 tick 增长系数
    float ticksToReclaim = aggressionIncreasePeriod() / balancePeriod;
    float reclaimAmount = 1.f / aggressionDecrease();   // 反向:从 0.5 恢复到 1.0 需要乘 2
    aggressionIncrease.set( expf( logf( reclaimAmount ) / ticksToReclaim ) );

    // 3. 计算 minCPUOffload:最低级别的卸载量
    minCPUOffload.set( cpuOffloadForLevel( numCPUOffloadLevels() - 1 ) );

    return true;
}
```

**算法解析**:

1. **minAggression 计算**:假设 `maxAggressionIncreasePeriod = 40`、`aggressionIncreasePeriod = 10`,则 `numDecreaseSteps = 40/10 = 4`。意思是"经过 4 次连续衰减,从 maxAggression 跌到 minAggression"。`minToMaxRatio = 0.5^4 = 0.0625`,所以 `minAggression = 1.0 * 0.0625 = 0.0625`。

2. **aggressionIncrease 计算**:`reclaimAmount = 1/0.5 = 2`,意思是"从最低值恢复到最高值需要乘 2"。要在 `aggressionIncreasePeriod / balancePeriod` 个 tick 内完成这个增长,所以每 tick 增长系数为 `exp(log(2) / ticksToReclaim)`。若 `balancePeriod = 0.1s`、`aggressionIncreasePeriod = 10s`,则 `ticksToReclaim = 100`,`aggressionIncrease = exp(log(2)/100) ≈ 1.00696`。即每秒增长约 7%。

3. **minCPUOffload 计算**:`cpuOffloadForLevel(numCPUOffloadLevels - 1) = cpuOffloadForLevel(4) = 0.02 * 0.5^4 = 0.00125`。

#### 11.3.5 侵略性参数语义

侵略性(aggression)是 EntityApp 内部一个自适应参数,控制卸载时机的激进程度:

- **高侵略性(接近 1.0)**:积极卸载,容易触发实体迁移
- **低侵略性(接近 0.0625)**:保守,只在严重过载时才卸载

**自适应逻辑**(概念,具体在 CellApp/BaseApp 内部):
- 当 EntityApp 决定卸载一个实体时,`aggression *= aggressionDecrease(0.5)`,即侵略性减半
- 每个 tick,`aggression *= aggressionIncrease(约 1.007)`,缓慢恢复
- 经过 `aggressionIncreasePeriod(10s)` 即 100 ticks 后,侵略性恢复到原来的 2 倍(因为衰减时减半了)

这种"惩罚 + 缓慢恢复"机制防止了"抖动":刚卸载完不会立即又触发卸载,给系统时间稳定下来。

### 11.4 动态调整

BigWorld 负载均衡的动态调整涉及多个层次:

#### 11.4.1 负载平滑(EWMA)

`cellapp.cpp` 的 `informOfLoad` 使用指数加权移动平均(EWMA)平滑负载:

```cpp
// cellapp.cpp:72-90
void CellApp::informOfLoad( float currLoad, float extraLoad )
{
    currLoad_ = currLoad;
    smoothedLoad_ = (currLoad * (1.f - LOAD_SMOOTHING_BIAS)) +
                    (smoothedLoad_ * LOAD_SMOOTHING_BIAS);
    estimatedLoad_ = smoothedLoad_ + extraLoad;
}
```

- `LOAD_SMOOTHING_BIAS = 0.05`(配置项 `loadSmoothingBias`)
- 含义:每秒只吸收 5% 的新值,95% 保留旧值
- 时间常数 τ ≈ 19 秒(即 1/0.05)
- 效果:负载的瞬时尖峰(如 GC、网络抖动)被滤掉,只有持续高负载才会触发迁移

**为什么不直接用瞬时值?** 因为迁移代价高昂(实体状态、Ghost 关系重建),如果用瞬时值会触发"过度迁移"——刚迁移完负载又下降,造成抖动。

#### 11.4.2 预估负载(estimatedLoad)

```cpp
estimatedLoad_ = smoothedLoad_ + extraLoad;
```

`extraLoad` 是 CellAppMgr 在为该 CellApp 新建 Cell 或迁移 Cell 时累加的"预估负载"。这样即使新 Cell 还没上报负载,CellAppMgr 也不会继续往这个 CellApp 上塞 Cell,避免"短时间内连续分配"。

**清零时机**:当 CellApp 实际上报负载时,`extraLoad` 会被减去相应的量(由 `CellApp::informOfLoad` 配合 `addCell`/`eraseCell` 维护)。

#### 11.4.3 侵略性自适应

侵略性参数在每个 EntityApp 内部维护,核心循环:

```
每个 balance tick:
  if (shouldOffload):
    aggression_ *= aggressionDecrease  // 0.5,减半
    performOffload(...)
  else:
    aggression_ *= aggressionIncrease   // ~1.007,缓慢恢复
  aggression_ = clamp(aggression_, minAggression, maxAggression)
```

**触发卸载的条件**:实体负载超过 `avgSmoothedLoad * (1 + tolerance * aggression_)` 时考虑卸载。侵略性越高,容忍度越低,越容易触发。

#### 11.4.4 容差(tolerance)与侵略性的耦合

`cellappmgr_config.hpp` 中 `tolerance = 0.05`,但在实际触发迁移时,真正的容差是 `tolerance * aggression_`:

- 侵略性 = 1.0 时:容差 = 5%,即负载超过平均的 1.05 倍时触发
- 侵略性 = 0.5 时:容差 = 2.5%,即负载超过平均的 1.025 倍时触发
- 侵略性 = 0.0625 时:容差 = 0.3%,即负载超过平均的 1.003 倍时触发

**反直觉**:侵略性低时容差反而小?是的,因为侵略性低意味着"刚发生过卸载,系统正在稳定",此时应该更敏感地响应真正的过载(容差小);而侵略性高意味着"系统已稳定一段时间",此时应该更保守(容差大)以避免过度反应。

#### 11.4.5 Cell 评分动态更新

`CellData::updateLoad`(详见第三章)在每个 tick 重新计算 Cell 的负载评分:

```
newSmoothedLoad = EWMA(rawLoad, oldSmoothedLoad, smoothingBias)
combinedLoad = weighted_sum(proxyLoad, smoothedLoad, entitiesLoad, ...)
```

这个 `combinedLoad` 直接影响 BSP 分裂/合并决策。负载评分的动态性保证了:
- 短期尖峰被平滑(避免抖动)
- 长期趋势被捕捉(及时分裂)
- 临时重负载(如大规模战斗)被识别(快速响应)

#### 11.4.6 CellAppGroup 重建

`CellAppGroups` 在每次 `metaLoadBalance` 时重建:

1. 清空所有 CellApp 的 `pGroup_` 指针
2. 遍历所有 CellApp,对未分组的 CellApp 调用 `markGroup` 进行洪水填充
3. 洪水填充依据是 Cell 之间的邻接关系(同 Space 且 Cell 共享边界)
4. 形成新的分组列表

**重建频率**:`metaLoadBalancePeriod = 3s`。每次重建确保分组反映最新的拓扑结构(Cell 创建/销毁后邻接关系会变化)。

## 十二、性能分析

本章对负载均衡各关键路径做时间复杂度、空间复杂度、网络开销与延迟的量化分析。

### 12.1 时间复杂度

#### 12.1.1 BSP 树操作

设 BSP 树当前有 N 个叶子节点(即 N 个 Cell),H 为树高(平衡时 H ≈ log₂N)。

| 操作 | 时间复杂度 | 说明 |
|------|----------|------|
| `findCell(position)` | O(H) | 从根到叶子遍历,每层做一次轴对齐比较 |
| `addCell(cellData)` | O(H) | 在叶子处分裂,可能向上回溯调整边界 |
| `eraseCell(cellData)` | O(H) | 删除叶子,可能触发兄弟合并向上传播 |
| `balance()` | O(N) | 遍历所有叶子做评分比较 |
| `notifyOfCellRemoval()` | O(N) | 遍历邻居列表清理引用 |

**关键**:BSP 树高在最坏情况下可能退化为 O(N)(链状),但 BigWorld 通过"二分轴交替"(x/y/z 轮换)和定期重平衡保证树高接近 O(log N)。在典型 MMO 场景下 N ≤ 100,所以 BSP 操作近乎常数时间。

#### 12.1.2 CellApp 选择算法

`CellApps::findLeastLoadedCellApp` 的复杂度:

```cpp
// cellapps.cpp:446-463
CellApp * CellApps::findLeastLoadedCellApp() const
{
    CellApp * pBest = NULL;
    Map::const_iterator iter = map_.begin();
    while (iter != map_.end()) {
        if (!pBest || iter->second->estimatedLoad() < pBest->estimatedLoad())
            pBest = iter->second;
        ++iter;
    }
    return pBest;
}
```

- 时间复杂度:O(M),M 为 CellApp 总数
- 空间复杂度:O(1)

`findBestCellApp` 复杂度更高,因为它要考虑 Space 的几何关系:

```cpp
// cellapps.cpp:480-540(简化)
CellApp * CellApps::findBestCellApp( const Space & space,
    bool isNewSpace, float additionalLoad ) const
{
    // 1. 若 isNewSpace,直接返回 findLeastLoadedCellApp
    // 2. 否则遍历已有 Cell 的 CellApp,选择与 space 几何最接近的
    //    若都不接近,返回 findLeastLoadedCellApp
}
```

- 最坏:O(M)
- 最好:O(1)(有缓存)

#### 12.1.3 markGroup 洪水填充

`CellApp::markGroup` 的复杂度:

```cpp
void CellApp::markGroup( CellAppGroup & group, CellAppGroups & groups )
{
    pGroup_ = &group;
    group.addCellApp( this );
    
    Cells::iterator iter = cells_.begin();
    while (iter != cells_.end()) {
        const CellAppSet & neighbors = (*iter)->cellAppNeighbors();
        // 遍历邻居
        CellAppSet::const_iterator nIter = neighbors.begin();
        while (nIter != neighbors.end()) {
            if ((*nIter)->pGroup() == NULL) {
                (*nIter)->markGroup( group, groups );  // 递归
            }
            ++nIter;
        }
        ++iter;
    }
}
```

- 设总 CellApp 数 M,Cell 平均邻居数 K
- 每个 CellApp 恰好被访问一次(`pGroup_` 检查)
- 每个 Cell 的邻居检查:O(K)
- 总复杂度:O(M × K × avgCellsPerApp)

在典型部署中 M ≤ 50、K ≤ 8、avgCellsPerApp ≤ 10,总开销 < 4000 次指针解引用,微秒级。

#### 12.1.4 Cell 评分比较

`CellAppComparer::operator()` 是字典序比较:

```cpp
// 伪代码
bool operator()(CellApp * a, CellApp * b) {
    if (a->retiring() != b->retiring()) return !a->retiring();
    if (a->numCells() != b->numCells()) return a->numCells() < b->numCells();
    if (a->avgSmoothedLoad() != b->avgSmoothedLoad())
        return a->avgSmoothedLoad() < b->avgSmoothedLoad();
    // ... 更多 tiebreakers
    return a->addr() < b->addr();
}
```

- 比较次数:常数(最多 6-7 个字段)
- 排序所有 CellApp:O(M log M)

### 12.2 空间复杂度

#### 12.2.1 CellAppMgr 内存占用

主要数据结构:

| 数据结构 | 元素数 | 单元素大小(估) | 总内存(估) |
|---------|-------|--------------|-----------|
| `cellApps_` map | M | ~200B | 200M 字节 |
| `spaces_` map | S | ~500B | 500S 字节 |
| 每个 Space 的 BSP 树 | N | ~150B | 150N 字节 |
| 每个 CellData | - | ~300B | - |
| `cellAppGroups_` 列表 | G(≤M) | ~100B | 100G 字节 |

**典型 MMO 部署**:M = 20、S = 5、N = 50、G = 3
- CellApp 数据:20 × 200 = 4KB
- Space 数据:5 × 500 = 2.5KB
- BSP 树:50 × 150 = 7.5KB(每 Space)
- CellAppGroup:3 × 100 = 300B
- 总计:< 50KB

CellAppMgr 是控制平面进程,内存占用极小。

#### 12.2.2 CellApp 内存占用

CellApp 是数据平面进程,持有大量实体:

| 数据结构 | 元素数 | 单元素大小 | 总内存 |
|---------|-------|----------|--------|
| 实体(Entity) | E(~10K-100K) | ~500B-2KB | 5MB-200MB |
| Ghost 实体 | G(~2E) | ~200B | 4MB-40MB |
| CellInfo | N | ~1KB | N KB |
| CellAppChannel | M(邻居) | ~500B | 500M B |
| AOI 网格 | 网格数 × 槽数 | - | 视场景而定 |

**典型 MMO 部署**:CellApp 内存 100MB-2GB,瓶颈是实体状态。

### 12.3 网络开销

#### 12.3.1 负载上报(informOfLoad)

每个 CellApp 每秒上报一次负载:

```cpp
// cellappmgr_interface.hpp
// informOfLoad 消息格式:
//   CellAppID id;
//   float currLoad;
//   float extraLoad;
//   int numEntities;
//   EntityBoundLevels boundLevels;
```

- 单消息大小:~32 字节(含 Mercury 头)
- 频率:1 Hz
- 总带宽:M × 32 字节/秒 = 20 × 32 = 640 字节/秒

**结论**:负载上报带宽可忽略不计。

#### 12.3.2 元负载均衡(identifyGroups + markGroup)

每 3 秒一次 `metaLoadBalance`:
- 重建分组(本地计算):无网络开销
- 可能触发 Cell 迁移:每次迁移涉及多个消息
  - `startRetiring`(CellAppMgr → CellApp):~50 字节
  - `createCell`(CellAppMgr → 新 CellApp):~100 字节
  - 实体迁移消息(CellApp → CellApp):每个实体 ~500 字节-2KB

**单次 Cell 迁移成本**:假设 Cell 有 1000 实体,迁移耗时 1-5 秒,带宽 500KB-2MB。

#### 12.3.3 BSP 分裂/合并

每秒一次 `loadBalance`:
- 计算 loadSafetyBound:本地
- 遍历 BSP 叶子:本地
- 决定分裂/合并:本地
- 触发实体状态转换:每个实体 ~200 字节(Ghost 创建/Real 迁移)

**单次分裂成本**:1000 实体 × 200 字节 = 200KB,耗时 < 100ms。

### 12.4 延迟分析

#### 12.4.1 端到端延迟链

从负载尖峰到完成迁移的完整延迟链:

```
负载尖峰发生
    ↓ (1 tick: 100ms)
CellApp 内部负载采样
    ↓ (1 tick: 100ms)
CellApp 上报 informOfLoad
    ↓ (网络: < 5ms)
CellAppMgr 收到,更新 smoothedLoad
    ↓ (EWMA 吸收 5%/秒,达到 95% 需 ~60 秒)
smoothedLoad 接近真实负载
    ↓ (loadBalanceTimer 1 秒触发一次)
Space::loadBalance 决策
    ↓ (本地计算: < 1ms)
发送 startRetiring / createCell
    ↓ (网络: < 5ms)
CellApp 执行实体迁移
    ↓ (实体数 × 处理时间: 1-5 秒)
完成迁移
```

**关键延迟源**:
1. EWMA 平滑:这是最大延迟源,约 60 秒才能"看清"一个新负载水平
2. Balance timer 周期:1 秒,影响响应粒度
3. 实体迁移本身:取决于实体数和复杂度

**总延迟**:从持续负载变化到完成迁移,典型 30-90 秒。

#### 12.4.2 优化权衡

BigWorld 选择"保守 + 平滑"策略,牺牲响应速度换取稳定性:

| 设计选择 | 优点 | 缺点 |
|---------|------|------|
| EWMA(5% 吸收) | 抑制抖动 | 60 秒延迟 |
| 侵略性衰减(0.5) | 防止过度迁移 | 恢复需 10 秒 |
| 容差 5% | 避免小差异触发 | 集群整体偏高时也会触发 |
| 两阶段 Cell 迁移 | 状态一致 | 完成时间长 |

**反例**:如果用瞬时值 + 0 容差 + 立即迁移,延迟可降到 < 1 秒,但会造成"乒乓"——刚迁移完负载下降又触发反向迁移,系统永远无法稳定。

### 12.5 性能基准(经验值)

基于 BigWorld 官方文档和社区经验:

| 场景 | 配置 | 指标 |
|------|------|------|
| 中型 MMO(1K 并发) | 4 CellApp,2 BaseApp | CPU < 30%,延迟 < 50ms |
| 大型 MMO(10K 并发) | 20 CellApp,5 BaseApp | CPU < 50%,延迟 < 100ms |
| 超大型(50K 并发) | 100+ CellApp,20+ BaseApp | CPU < 70%,延迟 < 200ms |
| 单 Space 极限 | 1 CellApp,10K 实体 | 单进程瓶颈,需分裂 |

**关键瓶颈**:
1. 单 CellApp 实体数上限:约 5K-10K(取决于实体复杂度)
2. 单 Space Cell 数上限:理论上无限制,实际 < 100(管理开销)
3. 跨 CellApp 通信延迟:同机房 < 1ms,跨机房 10-100ms

## 十三、边界情况

本章分析负载均衡在极端场景下的行为,以及 BigWorld 的应对策略。

### 13.1 单 CellApp 退化场景

#### 13.1.1 只有一个 CellApp

**场景**:整个集群只有一个 CellApp。

**行为分析**:
- `findLeastLoadedCellApp` 总是返回该 CellApp
- `findBestCellApp` 同样返回该 CellApp
- BSP 分裂仍会发生(在同一个 CellApp 内创建多个 Cell)
- `metaLoadBalance` 时:CellAppGroup 只有一个成员,无迁移可能
- `identifyGroups` 形成单成员组
- `checkForOverloaded` 检查时:avgLoad == maxLoad,无法选出"低于平均"的目标

**潜在问题**:虽然 Cell 仍可分裂,但所有 Cell 在同一进程,无法实现真正的水平扩展。Cell 之间的边界穿越变成进程内通信,失去分布式优势。

**源码验证**:`cellapps.cpp:findLeastLoadedCellApp` 在循环开始 `pBest = NULL`,遍历后 `pBest` 必非空(只要 map 非空)。

#### 13.1.2 所有 CellApp 都在退役

**场景**:管理员触发集群缩容,所有 CellApp 都标记为 `isRetiring`。

**行为分析**:
- `findLeastLoadedCellApp` 跳过所有 retiring 的 CellApp:`if (!pApp->isRetiring())` 失败,返回 `NULL`
- `findBestCellApp` 同样返回 `NULL`
- 新 Space 创建失败:`addCell` 时无可用 CellApp
- 已有 Cell 仍可工作,但不再有迁移目标

**应对策略**:
- 应该在缩容前先启动新的 CellApp
- 或者保留至少一个非 retiring 的 CellApp 作为兜底
- 源码中没有特殊兜底逻辑,这是管理员的责任

#### 13.1.3 CellApp 死亡时的迁移

**场景**:某 CellApp 突然死亡,其上的所有 Cell 都失效。

**行为分析**(详见 `cellapp.cpp:handleUnexpectedDeath`):
1. CellAppMgr 收到 machined 的死亡通知
2. 遍历该 CellApp 上的所有 CellData,触发 `CellData::clearCellApp`
3. 受影响的 Space 进入"恢复模式":
   - 对每个失效的 Cell,在该 Space 中找另一个 CellApp 重建
   - 新 Cell 的边界可能与原 Cell 不同(BSP 重新平衡)
4. Real 实体从 BaseApp 的备份恢复(详见下文)
5. Ghost 实体由 Real 实体的拥有者重建

**关键源码路径**:
```
handleCellAppDeath (machined 通知)
  → CellApp::handleUnexpectedDeath
    → 对每个 CellData:
      → Space::eraseCell(cellData)
      → Space::addCell(...) 在新 CellApp 重建
    → BaseAppMgr::handleCellAppDeath 通知 Base 层恢复 Real 实体
```

### 13.2 Cell 数量边界

#### 13.2.1 单 Space 极多 Cell

**场景**:一个 Space 有 1000+ Cell(理论上限是多少?)。

**理论限制**:
- BSP 树节点:无固定上限,受内存限制
- CellData:每个 ~300B,1000 个 = 300KB,可接受
- 但 `loadBalance` 每秒遍历所有叶子:O(N) = O(1000),仍可接受

**实际问题**:
- 实体跨 Cell 边界频繁:Ghost 创建/销毁开销大
- 跨 CellApp 通信:Cell 数多意味着 CellApp 邻居多,通道开销大
- CellAppGroup 洪水填充:可能形成巨大单组,失去分组隔离意义

**实际建议**:单 Space Cell 数 < 100,超过应考虑分多个 Space。

#### 13.2.2 单 Cell 极多实体

**场景**:一个 Cell 有 10000+ 实体(如大规模战场)。

**行为分析**:
- Cell 负载评分飙升,触发分裂
- 分裂时实体迁移量大:10000 实体 × 200B = 2MB 网络流量
- 分裂完成后,新 Cell 又快速填充,可能再次分裂
- "分裂-合并"震荡风险

**应对策略**:
- 调高 `minEntityLoad` 阈值(若可配置)
- 调低 `loadBalancePeriod`(更频繁检查)
- 调高 `tolerance`(更宽容,减少触发)
- 设计上避免"热点 Cell":游戏机制分散玩家

#### 13.2.3 空间退化为单 Cell

**场景**:Space 只有 1 个 Cell(初始化或合并到最后)。

**行为分析**:
- BSP 树只有根节点(也是叶子)
- `balance` 时无兄弟可合并
- `addCell` 时会分裂根,产生两个叶子
- 单 Cell 时所有实体在同一 CellApp,无 Ghost 开销

**源码验证**:`space.cpp:addCell` 检查 `pRoot_`,若为空则直接创建根;否则在合适位置插入。

### 13.3 负载评分边界

#### 13.3.1 负载为零

**场景**:CellApp 上没有实体(刚启动,或所有 Cell 都被迁走)。

**行为分析**:
- `currLoad = 0.0`
- `smoothedLoad = 0.0`(EWMA 吸收 0)
- `estimatedLoad = 0.0 + extraLoad`
- `findLeastLoadedCellApp` 优先选这个 CellApp

**潜在问题**:
- 所有新 Cell 都往这个 CellApp 塞,可能瞬间过载
- `extraLoad` 机制部分缓解:每分配一个 Cell,`extraLoad` 累加,使后续选择避开

#### 13.3.2 负载饱和(>1.0)

**场景**:CellApp CPU 使用率 100%,负载评分 > 1.0。

**行为分析**:
- `currLoad > 1.0`
- `loadSafetyBound = max(0.85, avgSmoothedLoad * 1.1)`
- 若该 CellApp 是最重的,会触发分裂/迁移
- 若整个集群都饱和:`avgSmoothedLoad * 1.1` 也很高,`loadSafetyBound` 水涨船高,可能不触发迁移

**关键问题**:集群整体饱和时,负载均衡无法解决,需要扩容。

#### 13.3.3 负载抖动(频繁变化)

**场景**:负载在 0.3-0.7 之间快速变化(GC、网络抖动)。

**行为分析**:
- EWMA 平滑:5% 吸收率,平滑后负载变化幅度减小
- 侵略性衰减:每次迁移后侵略性减半,减少后续触发
- 容差 5%:负载差异 < 5% 不触发迁移

**三重保险**共同作用,典型抖动场景下不会触发过度迁移。

### 13.4 时序边界

#### 13.4.1 启动时序竞态

**场景**:CellAppMgr 启动时,CellApp 还没注册;或 CellApp 启动时 CellAppMgr 还没就绪。

**BigWorld 的处理**:
- CellAppMgr 启动时向 machined 注册 birth/death listener
- CellApp 启动时调用 `CellAppMgrInterface::registerCellApp`
- CellAppMgr 收到后创建 `CellApp` 视图,返回 ack
- CellApp 收到 ack 后才算"注册完成"

**竞态保护**:
- 若 CellApp 找不到 CellAppMgr,会重试(`numStartupRetries`)
- 若 CellAppMgr 在 CellApp 注册前收到 Space 创建请求,会延迟处理(队列)
- 若 CellApp 注册时 CellAppMgr 还没就绪,CellApp 会等待

#### 13.4.2 关停时序

**场景**:管理员触发 CellAppMgr 关停。

**BigWorld 的两阶段关停**(详见 `shutdown_handler.cpp`):
1. **阶段 1**:CellAppMgr 发送 `retireAllCellApps`,所有 CellApp 进入 retiring 状态
2. **阶段 2**:等待所有 CellApp 的 Real 实体迁移到 BaseApp 备份
3. **阶段 3**:CellAppMgr 等所有 CellApp 退出后自身退出

**关键保护**:
- 关停期间不接受新登录
- 关停期间 Space 不再创建新 Cell
- 关停可被取消(`cancelShutdown`)

#### 13.4.3 时钟不同步

**场景**:不同机器的时钟偏差较大。

**影响**:
- TimeKeeper 维护"游戏时间",独立于墙钟
- CellApp 之间通过 game tick 同步(10Hz)
- 负载均衡不依赖绝对时钟,只依赖 tick 计数

**结论**:时钟不同步对负载均衡无直接影响,但可能影响游戏逻辑(如时间戳)。

#### 13.4.4 网络分区

**场景**:CellAppMgr 与部分 CellApp 网络中断。

**BigWorld 的处理**:
- Mercury 通道有超时检测:`channelTimeoutPeriod`(默认 30 秒)
- 超时后通道被视为"死亡",触发 `handleCellAppDeath`
- 死亡的 CellApp 上的 Real 实体从备份恢复

**潜在问题**:
- "假死亡":CellApp 实际还在运行,但被视为死亡,可能导致"双写"
- BigWorld 通过 `reviver` 机制确保"真死亡"才恢复(详见专题01)

#### 13.4.5 队列堆积

**场景**:某 CellApp 处理不过来,消息队列堆积。

**行为分析**:
- CellApp 上报的 `currLoad` 升高
- CellAppMgr 减少往该 CellApp 分配新 Cell
- 已有 Cell 可能触发分裂,迁移到其他 CellApp

**潜在问题**:
- 迁移本身也是消息,可能加重队列堆积
- 极端情况下 CellApp 完全卡死,无法响应迁移请求
- 应对:超时机制 + 强制死亡恢复

### 13.5 数据一致性边界

#### 13.5.1 实体迁移中的状态丢失

**场景**:实体从 CellApp A 迁移到 CellApp B,迁移过程中 A 收到对该实体的修改请求。

**BigWorld 的两阶段提交**:
1. A 发起迁移,通知 B "即将创建 Ghost"
2. B 创建 Ghost,回复 ack
3. A 收到 ack 后,将实体降级为 Ghost,通知 B "升级为 Real"
4. B 升级为 Real,通知 A 销毁
5. A 销毁本地副本

**保护**:迁移期间实体处于"过渡态",A 仍是 Real,B 是 Ghost。修改请求仍由 A 处理,迁移完成后由 A 转发到 B。

#### 13.5.2 Cell 边界附近的实体

**场景**:实体位于 Cell 边界附近,频繁穿越。

**行为分析**:
- 每次穿越触发 Ghost 创建/销毁
- 实体在边界来回走动会造成"乒乓"

**BigWorld 的缓解**:
- AOI 滞后:Ghost 销毁有延迟,边界附近保持 Ghost
- BSP 边界调整:可微调边界减少穿越
- `ghostDistance`:配置 Ghost 保持距离,避免边界震荡

#### 13.5.3 跨 Space 实体

**场景**:实体尝试从一个 Space 跳到另一个 Space(如传送门)。

**BigWorld 的处理**:
- 跨 Space 是显式操作,不是负载均衡范畴
- 通过 `Entity::teleport(space, position)` API
- 源 Space 销毁实体,目标 Space 创建实体
- 状态通过 BaseApp 中转(因 BaseApp 是 Real 权威)

## 十四、与其他引擎对比

本章将 BigWorld 的负载均衡方案与主流游戏服务器引擎对比,分析各自的设计取舍。

### 14.1 与 Unreal Engine 对比

#### 14.1.1 架构对比

| 维度 | BigWorld | Unreal Engine |
|------|----------|--------------|
| 分布式架构 | 多进程(CellApp + BaseApp + DBApp) | 单进程为主,UE5 有 World Partition |
| 空间分割 | BSP 树(2D/3D 矩形) | World Partition(2D 网格) |
| 实体迁移 | Real/Ghost 两阶段提交 | Streaming(流式加载/卸载) |
| 网络架构 | Mercury 自研 UDP | Replication(基于 UDP) |
| 持久化 | DBApp + 数据库 | SaveGame / Level Streaming |

#### 14.1.2 设计哲学

**BigWorld**:面向 MMO,核心是"水平扩展 + 在线持久化"
- 多进程隔离,一个进程崩溃不影响其他
- 实体可在运行时迁移,无需停服
- 数据库是 Real 权威,CellApp 只是缓存

**Unreal**:面向单机/小规模多人,核心是"画面表现 + 内容流式加载"
- 单进程为主,World Partition 是为了支持大世界
- Streaming 是空间分区加载,不是分布式
- UE5 的 MassEntity 是 ECS 优化,仍是单进程

#### 14.1.3 负载均衡对比

**BigWorld 的优势**:
- 真正的分布式,可水平扩展到 100+ 进程
- 在线迁移,无需停服
- 备份容错,单进程死亡可恢复

**Unreal 的优势**:
- 单进程延迟低,无跨进程通信
- 开发简单,无需考虑分布式
- 画面与逻辑统一,无 Ghost 同步问题

### 14.2 与 Photon Engine 对比

#### 14.2.1 架构对比

| 维度 | BigWorld | Photon |
|------|----------|--------|
| 节点角色 | CellAppMgr + CellApp(空间)+ BaseAppMgr + BaseApp(逻辑) | NameServer + GameServer + MasterServer |
| 空间管理 | BSP 树 + Cell 数据结构 | Room(房间)概念 |
| 实体位置 | 显式空间坐标(x, y, z) | 隐式(在某个 Room 中) |
| 负载均衡粒度 | Cell(空间分区) | Room(逻辑单元) |

#### 14.2.2 负载均衡策略

**Photon**:
- 以 Room 为最小迁移单元
- GameServer 间迁移整个 Room
- 不做空间分割,一个 Room = 一个 GameServer

**BigWorld**:
- 以 Cell 为最小迁移单元
- Cell 是空间分区,一个 CellApp 可有多个 Cell
- 玩家在 Cell 边界无缝穿越

#### 14.2.3 适用场景

**Photon 适合**:
- 房间制游戏(射击、MOBA、卡牌)
- 每局独立,玩家数固定(如 5v5)
- 单 Room 内通信密集,跨 Room 通信少

**BigWorld 适合**:
- 开放世界 MMO
- 玩家自由移动,无房间概念
- 跨区域通信频繁(如全服广播)

### 14.3 与 Kubenetes/微服务对比

#### 14.3.1 负载均衡粒度

**K8s**:
- 以 Pod 为最小单元
- 通过 Service + Endpoints 做请求级负载均衡
- 无状态(理想情况),水平扩展简单

**BigWorld**:
- 以 Cell 为最小单元(比 Pod 更细)
- 通过 CellAppMgr 做空间感知的负载均衡
- 有状态(实体状态),迁移复杂

#### 14.3.2 调度策略

**K8s Scheduler**:
- 主要考虑资源(CPU/内存/GPU)
- 不感知应用内逻辑
- 一次调度,后续不迁移(除非驱逐)

**BigWorld CellAppMgr**:
- 考虑负载评分(综合 CPU、实体数、Ghost 数)
- 感知空间拓扑(Cell 邻接)
- 持续调度(每秒检查,每 3 秒元均衡)

#### 14.3.3 适用边界

**K8s 适合**:
- 无状态服务(API、Web)
- 请求级负载均衡(HTTP、RPC)
- 容器化部署

**BigWorld 适合**:
- 有状态游戏服务
- 空间感知负载均衡
- 长连接、低延迟

### 14.4 与 Unity DOTS / Mirror 对比

#### 14.4.1 Unity DOTS

**Unity DOTS**(Data-Oriented Technology Stack):
- ECS 架构,单进程优化
- 多线程 Job System + Burst 编译
- 不解决分布式,只优化单机性能

**对比 BigWorld**:
- DOTS 是"垂直扩展"(单机压榨)
- BigWorld 是"水平扩展"(多机协同)
- 两者可结合:CellApp 内部用 ECS,外部用 BigWorld 分布式

#### 14.4.2 Mirror

**Mirror**(Unity 开源网络库):
- 基于 RPC 的同步
- Server Authority 模式
- 单 Room 一对多同步

**对比 BigWorld**:
- Mirror 是"客户端-服务器"二层架构
- BigWorld 是"客户端-BaseApp-CellApp-DBApp"多层架构
- Mirror 简单但无法支撑 MMO 规模

#### 14.4.3 综合对比表

| 引擎 | 架构 | 最大并发 | 空间分割 | 在线迁移 | 适用场景 |
|------|------|---------|---------|---------|---------|
| BigWorld | 多进程分布式 | 50K+ | BSP 树 | ✓ | MMO |
| Unreal | 单进程 + Streaming | 100-1K | World Partition | ✗ | 单机/小多人 |
| Photon | 多进程 Room 制 | 10K+ | Room | ✓(Room 级) | 房间制 |
| K8s | 容器编排 | 无上限 | 无 | ✗(只调度) | 无状态服务 |
| Unity DOTS | ECS 单进程 | 10K-100K(单机) | ECS Chunk | ✗ | 单机高性能 |
| Mirror | Client-Server | 100-1K | 无 | ✗ | 小型多人 |

### 14.5 BigWorld 独特设计总结

#### 14.5.1 创新点

1. **空间感知负载均衡**:不仅看 CPU,还看 Cell 邻接关系,避免跨 CellApp 通信过多
2. **三层负载均衡**:Cell 内(分裂/合并)+ CellApp 间(迁移)+ CellAppGroup 间(元均衡)
3. **Real/Ghost 双状态**:实现无缝迁移,实体无需停顿
4. **侵略性自适应**:根据历史行为调整激进程度,防止抖动
5. **EWMA 平滑**:负载采样平滑,避免尖峰触发

#### 14.5.2 局限性

1. **复杂度高**:实现复杂,调试困难
2. **延迟较大**:EWMA + 容差导致 30-90 秒响应延迟
3. **状态依赖强**:CellAppGroup 依赖邻接关系,拓扑变化敏感
4. **单点风险**:CellAppMgr 是单点,故障影响全局(有 Reviver 保护)
5. **配置敏感**:20+ 配置项,调优需要经验

#### 14.5.3 借鉴价值

BigWorld 的负载均衡设计对现代游戏引擎有重要借鉴价值:

1. **空间感知调度**:不仅仅是 CPU 负载,还要考虑通信拓扑
2. **平滑 + 自适应**:面对抖动的双重保险
3. **两阶段提交**:分布式状态迁移的标准模式
4. **控制平面/数据平面分离**:Manager + Worker 的清晰分工

## 十五、总结

### 15.1 核心机制回顾

本专题系统剖析了 BigWorld Engine 14.4.1 的负载均衡算法,核心机制可总结为"三层 + 三机制":

#### 15.1.1 三层负载均衡

| 层次 | 触发周期 | 决策者 | 操作对象 | 核心目标 |
|------|---------|--------|---------|---------|
| **Cell 内层** | 1 秒 | CellAppMgr(Space::loadBalance) | CellData(BSP 叶子) | 空间内负载重分(分裂/合并) |
| **CellApp 间层** | 1 秒/3 秒 | CellAppMgr(metaLoadBalance) | Cell(整 Cell 迁移) | 跨 CellApp 负载再分配 |
| **CellAppGroup 元层** | 3 秒 | CellAppMgr(identifyGroups) | CellAppGroup(整组) | 隔离负载域,避免跨组干扰 |

#### 15.1.2 三大核心机制

**机制一:BSP 空间分割树**
- 数据结构:BinaryNode/QuadNode 模板 + InternalNode/CellData 派生
- 算法:轴对齐二分,轴交替(x/y 或 x/y/z)
- 关键操作:`findCell`、`addCell`、`eraseCell`、`balance`
- 复杂度:O(H),H ≈ log₂N

**机制二:Cell 评分体系**
- 数据来源:proxyLoad(代理数)+ smoothedLoad(EWMA 平滑负载)+ entitiesLoad(实体数)+ ghostUpdateAvgLoad(Ghost 更新)+ avgEntityLoad(实体均载)
- 合并算法:EntityBoundLevels 按 5 个级别加权合并
- 决策依据:CellAppComparer 字典序比较(retiring → numCells → avgSmoothedLoad → ...)

**机制三:侵略性自适应**
- 衰减:卸载后 `aggression *= 0.5`
- 增长:每 tick `aggression *= ~1.007`
- 派生:`minAggression = maxAggression × 0.5^(40/10) = 0.0625`
- 效果:防止"乒乓"迁移,给系统稳定时间

### 15.4 设计哲学

BigWorld 负载均衡的设计哲学可概括为三点:

#### 15.4.1 保守优于激进

- EWMA 5% 吸收:60 秒才能看清新负载水平
- 容差 5%:小差异不触发迁移
- 侵略性衰减:卸载后立即减半,10 秒恢复

**代价**:响应延迟 30-90 秒
**收益**:稳定性,避免"乒乓"迁移

#### 15.4.2 空间感知优于纯负载

- CellAppGroup 按邻接关系分组
- findBestCellApp 考虑几何接近
- 跨 CellApp 通信成本被纳入决策

**代价**:调度复杂度增加
**收益**:跨进程通信最小化

#### 15.4.3 控制平面/数据平面分离

- CellAppMgr 不持有实体,只做调度
- CellApp 不做调度,只执行
- 通过 Mercury 消息解耦

**代价**:跨进程通信开销
**收益**:单一职责,故障隔离

### 15.5 实践建议

基于本专题分析,对 BigWorld 部署调优给出以下建议:

#### 15.5.1 容量规划

1. **CellApp 数量**:按"单 CellApp 5K-10K 实体"估算,留 30% 余量
2. **BaseApp 数量**:按"单 BaseApp 5K-10K 实体"估算
3. **Space 数量**:按业务逻辑划分,避免单 Space 过大
4. **网络**:同机房部署,避免跨机房通信

#### 15.5.2 参数调优

1. **稳定优先**:保持默认值,不要轻易调低 `tolerance` 或 `LOAD_SMOOTHING_BIAS`
2. **响应性**:若需要更快响应,可调高 `loadBalancePeriod` 频率(但 < 0.5 秒会过载)
3. **卸载量**:`maxCPUOffload = 0.02` 适合大多数场景,过大可能导致单次迁移太重
4. **监控**:配置 `warningLevel = 0.75` 及时发现过载

#### 15.5.3 运维要点

1. **缩容**:先启动新 CellApp 再退役旧的,避免"全部 retiring"
2. **扩容**:新 CellApp 启动后,等待 60 秒让 EWMA 稳定再判断效果
3. **故障恢复**:CellApp 死亡后,Real 实体从 BaseApp 备份恢复,需确保备份机制正常
4. **监控指标**:avgLoad、maxLoad、numCells、numEntities、retiring 状态

### 15.8 总结陈述

BigWorld Engine 14.4.1 的负载均衡是一个**精心设计的分布式系统**:
