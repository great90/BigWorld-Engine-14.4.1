## 一、引言:BigWorld 内存管理哲学

### 1.1 为什么 MMOG 引擎需要专门的内存管理

BigWorld Engine 是一款面向大型多人在线游戏(MMOG)的服务端+客户端引擎,其工作负载具有以下特征:

1. **海量小对象**:每个 CellApp 进程中可能同时存活数十万个 Entity、数百万个 Ghost 同步对象、Mailbox 引用、Bundle 数据块、Watcher 节点等。这些对象大多体积小(几十到几百字节),分配/释放极其频繁。

2. **长生命周期与短生命周期混合**:实体(Entity)生命周期可能跨越数小时,而网络包(Packet)、Bundle 数据块则是秒级甚至毫秒级。混合的分配模式容易导致堆碎片化。

3. **严格的实时性要求**:服务器每帧需要在 100ms 内完成所有实体的 tick,任何因 `malloc` 阻塞导致的卡顿都会引发 hitch,影响所有玩家。

4. **跨 DLL 边界的一致性**:客户端被构建为多个 DLL(cstdmf.dll、network.dll、moo.dll 等),如果对象在一个 DLL 中 `new` 在另一个 DLL 中 `delete`,会因为 CRT 堆不同而崩溃。

5. **调试需求**:开发期需要追踪每一笔分配的调用栈、识别泄漏、统计热点;生产期需要零开销的 release 构建。

正是基于这些需求,BigWorld 设计了一套**多层、可配置、可插拔**的内存管理体系,既能在生产环境提供低开销的池化分配,也能在开发环境提供完整的调用栈追踪与泄漏报告。

### 1.2 设计目标与约束

BigWorld 内存管理的核心设计目标:

| 目标 | 说明 |
| --- | --- |
| 低开销 | Release 构建中分配路径应近似 `malloc` 的常数时间 |
| 池化优先 | 小对象走固定大小池,避免碎片 |
| 跨 DLL 一致 | 所有 `new`/`delete` 都进入 BW 分配器,统一堆 |
| 可调试 | 开发期可记录每笔分配的调用栈、对象类型、时间戳 |
| 可监控 | 通过 Watcher 接口实时暴露分配统计给运维 |
| 多线程安全 | 服务器多线程并发分配,需要锁或原子操作保护 |
| 跨平台 | Windows / Linux / macOS / Android / Emscripten / Xbox / PS3 |
| 可降级 | 当调试设施不可用时,自动降级为 ANSI `malloc`/`free` |

非目标(明确放弃的设计):

- **不实现 GC**:不引入垃圾回收,引用计数 + 显式释放为主。
- **不实现 region/arena 通用框架**:仅提供 `StackAllocator`、`GrowOnlyPodAllocator` 等专用分配器。
- **不做内存压缩/搬迁**:对象一旦分配,地址固定,这对 intrusive_ptr、SmartPointer 语义友好。

### 1.3 整体架构总览

BigWorld 内存管理的整体分层如下:

```
┌────────────────────────────────────────────────────────────┐
│  应用层:Entity / Mailbox / Bundle / Model / Chunk ...      │
├────────────────────────────────────────────────────────────┤
│  容器层:BW::vector / BW::string / BW::map / BW::unordered_map│
│           MemoryOStream / PackedObjectPool / SmartPointer    │
├────────────────────────────────────────────────────────────┤
│  STL 分配器层:StlAllocator<T>  (bw_new / bw_delete)        │
├────────────────────────────────────────────────────────────┤
│  内存 API 层:bw_new / bw_delete / bw_malloc / bw_free      │
│              bw_malloc_aligned / bw_strdup / bw_memsize     │
├────────────────────────────────────────────────────────────┤
│  分配器接口层:BW::Allocator 命名空间                        │
│   ├── allocate / deallocate / reallocate                    │
│   ├── heapAllocate / heapDeallocate (绕过池)               │
│   ├── heapAllocateAligned (对齐分配)                        │
│   └── MemoryDebug / ThreadSlotTracker / StackTracker 钩子  │
├────────────────────────────────────────────────────────────┤
│  池层:FixedSizedAllocator (启用时)                          │
│   ├── 多档固定大小池(8/16/32/.../2048B)                    │
│   └── 大块直通 heapAllocate                                │
├────────────────────────────────────────────────────────────┤
│  系统分配器层(三选一,编译期决定):                          │
│   ├── AnsiAllocator  (Linux/Mac/Android/Emscripten)        │
│   ├── NedAllocator   (Windows 默认)                          │
│   └── ProtectedAllocator (启用 ENABLE_PROTECTED_ALLOCATOR)  │
├────────────────────────────────────────────────────────────┤
│  全局运算符拦截:memhook (重载 operator new/delete)          │
└────────────────────────────────────────────────────────────┘
```

层次说明:

- **应用层**通过 `BW::vector<T>` 等容器使用内存,无感知下层实现。
- **容器层**继承自 `std::vector<T, StlAllocator<T>>`,把分配委托给 `StlAllocator`。
- **StlAllocator** 调用 `bw_new`/`bw_delete`,这是 BW 的 C 风格内存 API。
- **bw_new** 调用 `BW::Allocator::allocate(size)`,这是统一入口。
- **Allocator::allocate** 优先走 `FixedSizedAllocator`(若启用),否则直接走 `heapAllocate`。
- **heapAllocate** 调用编译期选定的 `SystemAllocator`(Ansi/Ned/Protected)。
- **SystemAllocator** 最终调用 `malloc`/`nedmalloc`/`VirtualAlloc`。
- **memhook** 通过重载全局 `operator new`/`operator delete`,确保第三方库(如 Python、STL)的分配也走 BW 路径。

- **Release 客户端构建**(`CONSUMER_CLIENT`):所有调试宏归零,只有 `FixedSizedAllocator`(Windows)启用,接近零开销。

## 二、STL 分配器机制回顾

### 2.1 std::allocator 接口演进

C++98 时代的 `std::allocator<T>` 接口相当繁琐,要求实现以下成员:

```cpp
template <class T>
class allocator {
public:
    typedef T         value_type;
    typedef T*        pointer;
    typedef const T* const_pointer;
    typedef T&        reference;
    typedef const T&  const_reference;
    typedef size_t    size_type;
    typedef ptrdiff_t difference_type;

    template <class U>
    struct rebind { typedef allocator<U> other; };

    pointer allocate(size_type n, const void* hint = 0);
    void deallocate(pointer p, size_type n);
    size_type max_size() const;
    void construct(pointer p, const T& val);
    void destroy(pointer p);
    pointer address(reference x) const;
    const_pointer address(const_reference x) const;
};
```

C++11 之后,`std::allocator_traits` 提供了默认实现,自定义分配器只需实现 `allocate`/`deallocate` 和几个 typedef。C++17 进一步移除了 `is_always_equal` 等成员,接口更加精简。

BigWorld 14.4.1 的代码基线兼容 MSVC 2008+/GCC 4.x 时代的编译器,因此其 `StlAllocator` 保留了完整的 C++98 接口,但同时在 C++11 编译器下用 SFINAE 提供了变参 `construct`:

```cpp
// stl_fixed_sized_allocator.hpp#L169-L186
#if (__cplusplus >= 201103L)
    template< typename Up, typename... Args >
    void construct( Up* p, Args &&... args )
    {
        ::new( (void *)p ) Up( std::forward< Args >( args )... );
    }
#else
    void construct( pointer p, const T & val ) const 
    {
        allocator_construct( p, val );
    }
#endif
```

这种"双轨制"在 BW 源码中很常见,使代码能在新旧两套工具链下都能编译。

### 2.2 allocator_traits 与 C++11 之后的简化

C++11 引入的 `std::allocator_traits<A>` 是一个_traits 类,它提供分配器的默认实现:

| 操作 | allocator_traits 默认 | 自定义分配器可覆盖 |
| --- | --- | --- |
| `allocate(n)` | `A::allocate(n)` | 必须 |
| `deallocate(p,n)` | `A::deallocate(p,n)` | 必须 |
| `construct(p, args...)` | `::new ((void*)p) T(args...)` | 可选 |
| `destroy(p)` | `p->~T()` | 可选 |
| `max_size()` | `size_t(-1)/sizeof(T)` | 可选 |
| `select_on_container_copy_construction(a)` | `a` | 可选 |

BW 没有使用 `allocator_traits`(因为要支持 C++98 编译器),而是直接在 `StlAllocator` 中实现所有必需成员。这与现代 C++ 风格不同,但在当时是合理的工程选择。

### 2.3 rebind 机制:节点式容器的分配器转换

`std::list<T>` 的节点类型并不是 `T`,而是 `__list_node<T>`,容器内部需要为节点分配内存。C++ 通过 `rebind` 机制让外部传入的 `allocator<T>` 转换成 `allocator<Node>`:

```cpp
template <class U>
struct rebind {
    typedef StlAllocator<U> other;
};
```

`StlAllocator` 提供了模板构造函数,使得 `rebind` 转换可以在编译期完成:

```cpp
// stl_fixed_sized_allocator.hpp#L79-L85
template <typename Other> 
StlAllocator( const StlAllocator< Other > & otherAllocator )
#ifdef ALLOW_STACK_CONTAINER
    : allocator_( 0 )
#endif
{
}
```

注意 `StlAllocator` 的所有实例都互相相等(`operator==` 返回 `true`),这意味着它是一个**无状态分配器**(stateless allocator),任何 `StlAllocator<T>` 都可以转换为 `StlAllocator<U>` 而无需考虑状态迁移。

### 2.4 有状态 vs 无状态分配器

| 类型 | 例子 | 是否可比较相等 | 容器 swap 是否转移分配器 |
| --- | --- | --- | --- |
| 无状态 | `StlAllocator<T>`、`std::allocator<T>` | 总是相等 | 否(POCMA=false 默认) |
| 有状态 | `StackAllocator<T,CAP>`、`DebugStlAllocator<T>` | 看内部状态 | 是(若 propagate_on_container_swap) |

`StlAllocator` 是无状态的,所有 `StlAllocator<T>` 实例共享同一底层(BW 全局分配器)。这是它能与 `std::vector`、`std::list` 等容器良好协作的关键——容器在拷贝、移动、swap 时不需要考虑分配器状态的迁移。

但当 `ALLOW_STACK_CONTAINER` 开启时,`StlAllocator` 持有 `IAllocator*` 指针,变成有状态分配器,用于支持 `StackContainer`。这种模式默认关闭,需要时显式启用。

### 2.5 BW 选用 STL 分配器的原因

为什么 BigWorld 不自己实现一套完整的容器,而是选择"派生 std 容器 + 自定义分配器"的方式?

1. **复用成熟实现**:`std::vector`、`std::map` 等经过数十年的检验,算法正确性有保证。
2. **降低维护成本**:无需重复实现红黑树、哈希表等复杂结构。
3. **互操作**:可以与第三方库(Python STL、Boost)通过 `std::` 接口交互。
4. **聚焦关键路径**:把工程精力集中在分配器、引用计数等真正影响性能与可靠性的地方。

代价是失去了对容器内部布局的完全控制——例如无法让 `BW::vector` 使用 SOA(结构数组)布局,无法做 small buffer optimization(因为 `std::vector` 必须从堆分配)。

- `heapAllocFlags` 是 `InfoFlags` 枚举,标识分配来源,影响 `MemoryDebug` 是否记录。

#### 3.2.1 AnsiAllocator

#### 3.2.2 NedAllocator

[ned_allocator.cpp](file:///j:/Work/BigWorld-Engine-14.4.1/programming/bigworld/lib/cstdmf/ned_allocator.cpp#L29-L106) 包装了第三方 `nedmalloc` 库,这是 Windows 上的默认选择,因为它具备:

- **线程缓存**:每个线程有自己的小缓存,减少锁竞争。
- **低碎片**:基于分区(DL)的分配策略,对小对象高效。
- **可查询 mallinfo**:`nedmallinfo()` 返回 arena/ordblks/uordblks 等统计信息。

```cpp
void  NedAllocator::deallocate( void* ptr )           { if (ptr) nedfree( ptr ); }
void* NedAllocator::reallocate( void* ptr, size_t sz ){ return nedrealloc( ptr, sz ); }
void* NedAllocator::allocateAligned( size_t s, size_t a ){ return nedmemalign( a, s ); }

```

注意 `onThreadFinish()` 调用 `neddisablethreadcache`,在线程退出时归还线程缓存,避免泄漏。这是 BW 在 `Allocator::onThreadFinish()` 中统一调用的。

#### 3.2.3 ProtectedAllocator

[protected_allocator.cpp](file:///j:/Work/BigWorld-Engine-14.4.1/programming/bigworld/lib/cstdmf/protected_allocator.cpp#L1-L549) 是最复杂的实现,用于检测缓冲区溢出和 use-after-free:

设计思路:

1. 通过 `VirtualAlloc`(Win)或 `mmap`(Linux)分配 N 个页,标记为 `PAGE_NOACCESS`。
2. 把用户请求的内存放在**倒数第二页末尾**,使缓冲区末尾紧邻不可访问页。
3. 这样越界写会立即触发访问违例(SIGSEGV / Access Violation)。
4. `ChunkHeader`(记录 size)放在用户指针所在页的起始位置,通过 `getChunkHeader(ptr)` 反查。
5. `deallocate` 时把整个区域重新设为 `PAGE_NOACCESS`,任何后续访问(包括 double-free)都会触发崩溃。

```cpp
size_t calculateAlignedSize( size_t size )
{
    return (size + pageSize + pageBitsMask + sizeof(ChunkHeader)) & ~pageBitsMask;
}

void* ProtectedAllocator::allocate( size_t size )
{
    init();
    size_t aligned = calculateAlignedSize( size );
    ChunkHeader * hdr = (ChunkHeader*)pageAllocator().allocate( aligned );
    if (hdr) {
        vunprotect( hdr, aligned - pageSize );  // 留最后一页不可访问
        hdr->size = size;
        void * ptr = (char *)hdr + aligned - pageSize - size;  // 用户指针
        return ptr;
    }
    return NULL;
}

void ProtectedAllocator::deallocate( void* ptr )
{
    ChunkHeader * hdr = getChunkHeader( ptr );
    size_t realSize = calculateAlignedSize( hdr->size );  // 读 hdr->size, double-free 会崩
    vprotect( hdr, realSize - pageSize );                  // 全部设回 NOACCESS
    pageAllocator().deallocate( hdr, realSize );
}
```

`PageAllocator` 内部维护 `FreeList`(按地址排序)和 `DeadList`(延迟归还,先放入死亡队列,满了再批量释放并合并相邻空闲块),避免每次 `deallocate` 都立即 `munmap`/`VirtualFree`,提升性能。

`ProtectedAllocator` 的代价是巨大的内存浪费(每个分配至少多一个 4KB 页),只用于深度调试构建。

### 3.3 heapAllocate 与 allocate 的分层路由

`Allocator::allocate` 与 `Allocator::heapAllocate` 的关系:

```cpp
// allocator.cpp#L163-L184
void* Allocator::allocate( size_t size )
{
    init();
#if ENABLE_FIXED_SIZED_POOL_ALLOCATOR
    void* ptr = s_fixedSizedAllocator->allocate( size, IF_NOTRACK_ALLOC );

#if ENABLE_MEMORY_DEBUG
    if (s_memoryDebug) {
        FixedSizedAllocator::AllocationInfo info;
        s_fixedSizedAllocator->allocationInfo( ptr, info );
        s_memoryDebug->allocate( ptr, info.allocSize_, size, info.allocFlags_ );
    }
#endif
#else
    void* ptr = heapAllocate( size );  // 不启用池时直接走堆
#endif
    return ptr;
}
```

而 `heapAllocate` 直接调用 `SystemAllocator::allocate`:

```cpp
// allocator.cpp#L571-L596
void* Allocator::heapAllocate( size_t size, unsigned int heapAllocFlags )
{
    MF_ASSERT_NOALLOC( !(heapAllocFlags & IF_POOL_ALLOC) );

    void* ptr = SystemAllocator::allocate( size );

#if ENABLE_ALLOCATOR_MEMORY_FILLS
    size_t allocSize = SystemAllocator::memorySize( ptr );
    markAlloc( ptr, size, allocSize, CleanLandFill, NoMansLandFill );
#endif

#if ENABLE_MEMORY_DEBUG
    if (s_memoryDebug && !(heapAllocFlags & IF_NOTRACK_ALLOC)) {
        size_t allocSize = SystemAllocator::memorySize( ptr );
        s_memoryDebug->allocate( ptr, allocSize, size, heapAllocFlags );
    }
#endif
    return ptr;
}
```

注意几个关键点:

1. **MF_ASSERT_NOALLOC**:这个断言宏在内存分配器内部禁止再触发分配(避免无限递归)。它设置一个线程局部标志,任何在该断言上下文内的 `bw_new` 调用都会触发断言失败。
2. **markAlloc**:Debug 构建下,把请求 size 填 `0xCD`(CleanLandFill),把 `allocSize - size` 的填充区填 `0xFE`(NoMansLandFill)。释放后填充 `0xDD`(DeadLandFill)。这是受 MSVC CRT `_CrtSetDbgFlag` 启发的设计,能帮助识别未初始化读取与 use-after-free。
3. **s_memoryDebug->allocate**:把这笔分配注册到 `MemoryDebug` 的 `LiveAllocationMap`,记录调用栈(可选)。

### 3.4 全局静态初始化:AllocatorScopedInit

内存分配器必须在任何用户代码之前初始化,否则全局静态对象的构造就会因为找不到分配器而崩溃。BW 通过 MSVC 的 `#pragma init_seg(lib)` 实现:

```cpp
// allocator.cpp#L84-L103
#ifdef WIN32
#pragma warning(push)
#pragma warning(disable: 4073)
#pragma init_seg(lib)   // Ensure we get constructed first
#pragma warning(pop)
#endif

struct AllocatorScopedInit
{
    AllocatorScopedInit()  { BW::Allocator::init(); }
    ~AllocatorScopedInit() { BW::NAMESPACE DebugFilter::fini(); BW::Allocator::fini(); }
};
AllocatorScopedInit BW_STATIC_INIT_PRIORITY(1200) s_allocatorScopedInit;
```

`#pragma init_seg(lib)` 告诉链接器:把这段代码放入"库初始化段",在 C 运行时初始化之后、用户全局对象构造之前执行。`BW_STATIC_INIT_PRIORITY(1200)` 是 GCC/Clang 的 `__attribute__((init_priority(1200)))`,数字越小优先级越高。

`Allocator::init()` 内部是幂等的(`s_initialised` 标志保护):

```cpp
// allocator.cpp#L398-L534 (摘录)
void Allocator::init()
{
    if( !s_initialised ) {
        s_initialised = true;

#if ENABLE_FIXED_SIZED_POOL_ALLOCATOR
        // 动态计算池大小:8/16/32/.../1024 (32位) 或 16/32/.../2048 (64位)
        size_t sizes[9];
        size_t numSizes = 0;
        for ( ; (sizeof(void*) << numSizes) < 2048; ++numSizes )
            sizes[numSizes] = sizeof(void*) << numSizes;
        const size_t poolSize = 1 * 1024 * 1024 / 2;   // 512KB
        s_fixedSizedAllocator = new(s_fixedSizedAllocatorMem) BW::FixedSizedAllocator(
            sizes, numSizes, poolSize, "System" );
        s_fixedSizedAllocator->setLargeAllocationHooks( 
            &heapAllocate, &heapDeallocate, &heapReallocate, &heapMemorySize );
#endif
        // ... MemoryDebug 初始化 ...
    }
}
```

注意 `s_fixedSizedAllocatorMem` 是静态字符数组,通过 placement new 在其上构造 `FixedSizedAllocator`。这避免了"分配器初始化时需要分配器"的鸡蛋问题。

### 3.5 内存填充模式:CleanLand/DeadLand/NoMansLand

BW 的内存填充模式定义在 [allocator.hpp](file:///j:/Work/BigWorld-Engine-14.4.1/programming/bigworld/lib/cstdmf/allocator.hpp#L67-L71):

```cpp
static const int CleanLandFill  = 0xCD;  // 新分配的内存
static const int DeadLandFill   = 0xDD;  // 已释放的内存
static const int NoMansLandFill = 0xFE;  // 请求 size 之后的填充
static const int AlignLandFill  = 0xFD;  // 对齐填充
```

这些值与 MSVC CRT 的 `_CRTDBG_ALLOC_MEM_DF` 模式一致,使调试器 dump 内存时能直观识别状态:

- 看到 `CD CD CD CD` → 内存已分配但未初始化(可能是漏写初始化)。
- 看到 `DD DD DD DD` → 内存已释放,任何读取都是 use-after-free。
- 看到 `FE FE FE FE` → 越界访问到缓冲区末尾的填充区。

`markAlloc` 与 `markDealloc` 实现:

```cpp
// allocator.cpp#L48-L66
inline void markAlloc( void * __restrict ptr, size_t size, size_t allocSize, int fill, int pad )
{
    if ( ptr ) {
        memset( ptr, fill, size );                       // 用户区填 0xCD
        memset( (char*)ptr + size, pad, allocSize - size );  // 填充区填 0xFE
    }
}

inline void markDealloc( void* __restrict ptr, int fill, size_t allocSize )
{
    if ( ptr ) {
        memset( ptr, fill, allocSize );                  // 整块填 0xDD
    }
}
```

仅在 `_DEBUG` 构建下启用(`ENABLE_ALLOCATOR_MEMORY_FILLS = _DEBUG`),Release 构建中 `memset` 调用被预处理器移除,零开销。

### 3.6 SystemStage 系统阶段追踪

`Allocator::SystemStage` 是一个三态枚举:

```cpp

    SS_MAIN,        // main() 执行期间
    SS_POST_MAIN    // main() 返回之后
```

它通过 `Allocator::setSystemStage()` 设置,由 `ScopedSystemStage` RAII 类管理:

```cpp
public:
```

宏 `BW_SYSTEMSTAGE_MAIN()` 在启用 `ENABLE_MEMORY_DEBUG` 时展开为:

这样在 `main()` 入口处声明一行 `BW_SYSTEMSTAGE_MAIN();`,就能让 `MemoryDebug` 区分"main 之前的分配"(通常是 CRT/全局对象,允许泄漏)和"main 期间的分配"(应当全部释放)。

泄漏报告会按 `SystemStage` 分组,优先报告 `SS_MAIN` 期间的泄漏,因为 `SS_PRE_MAIN` 的分配往往是全局单例、Python 解释器等"必然泄漏"的对象。

### 3.7 InfoFlags 分配标志位

`Allocator::InfoFlags` 是一组位标志,描述每笔分配的来源:

```cpp
enum InfoFlags
{
    IF_POOL_ALLOC     = 1,  // 来自 FixedSizedAllocator 的池
    IF_NOTRACK_ALLOC  = 2,  // 不要记录到 MemoryDebug(避免重复记录)
    IF_INTERNAL_ALLOC = 4,  // FixedSizedAllocator 内部分配(池自身的 PoolHeader)
    IF_DEBUG_ALLOC    = 8   // MemoryDebug 内部分配
};
```

使用场景:

- `FixedSizedAllocator::allocate` 内部调用 `malloc_(size, IF_INTERNAL_ALLOC)` 来分配新的 PoolHeader,这不应该被 `MemoryDebug` 记录为"用户分配",所以标记 `IF_INTERNAL_ALLOC`。
- `FixedSizedAllocator::allocate` 对外返回的指针,通过 `allocationInfo()` 查询后,标记 `IF_POOL_ALLOC` 报告给 `MemoryDebug`。
- `MemoryDebug` 自身用 `DebugStlAllocator` 分配,后者调用 `FixedSizedAllocator->allocate(IF_DEBUG_ALLOC)`,这避免了 `MemoryDebug` 跟踪自己的内部数据结构。

### 3.8 内存对齐:heapAllocateAligned

SIMD 指令(SSE/AVX)要求数据 16/32 字节对齐,Direct3D 资源也常有对齐要求。BW 提供对齐分配入口:


注意对齐分配不经过 `FixedSizedAllocator`——池化只针对小对象,而对齐需求通常出现在较大的 buffer(SIMD 顶点数据),走堆更合适。


注意 MSVC 的 `_aligned_malloc` 与 `malloc` 不互通,必须用 `_aligned_free` 释放,所以 `deallocateAligned` 也要平台分支。

## 四、memhook 内存钩子:全局 new/delete 重载

### 4.1 memhook 模块的定位与作用

`memhook` 是一个独立的库,位于 [programming/bigworld/lib/memhook/](file:///j:/Work/BigWorld-Engine-14.4.1/programming/bigworld/lib/memhook/memhook.cpp),它的职责是:

1. 重载全局 `operator new` / `operator delete` / `operator new[]` / `operator delete[]`。
2. 在静态链接模式下,还替换 C 标准库的 `malloc`/`free`/`realloc`/`_msize`/`_aligned_malloc`/`_aligned_free`。
3. 通过函数指针表 `AllocFuncs`,把所有这些入口都委托给 BW 的 `bw_new`/`bw_delete`/`bw_malloc`/`bw_free` 等。

为什么需要 memhook?

- **第三方库**:Python 解释器、Boost、STL 容器(若未使用 BW 分配器)等三方代码内部会调用 `new`/`delete`/`malloc`,如果不拦截,这些分配会绕过 BW 的统计与调试。
- **跨 DLL 一致性**:不同 DLL 各有自己的 CRT 堆,跨 DLL 传指针再 delete 会崩溃。统一到 `bw_new`/`bw_delete` 后,所有分配都走 `cstdmf.dll` 的统一堆。

### 4.2 AllocFuncs 函数指针表

[memhook.hpp](file:///j:/Work/BigWorld-Engine-14.4.1/programming/bigworld/lib/memhook/memhook.hpp#L15-L57) 定义了 `AllocFuncs` 结构,包含 14 个函数指针:

```cpp
struct AllocFuncs
{
    NewFuncType           new_;             // bw_new
    NewNoThrowFuncType    newNoThrow_;      // bw_new(nothrow)
    NewArrayFuncType      newArray_;        // bw_new_array
    NewArrayNoThrowFuncType newArrayNoThrow_;
    DeleteFuncType        delete_;          // bw_delete
    DeleteNoThrowFuncType deleteNoThrow_;
    DeleteArrayFuncType   deleteArray_;
    DeleteArrayNoThrowFuncType deleteArrayNoThrow_;
    MallocFuncType        malloc_;          // bw_malloc
    FreeFuncType          free_;            // bw_free
    AlignedMallocFuncType alignedMalloc_;   // bw_malloc_aligned
    AlignedFreeFuncType   alignedFree_;     // bw_free_aligned
    ReallocFuncType       realloc_;         // bw_realloc
    MSizeFuncType         msizeFunc_;       // bw_memsize
};

// 仅在单线程时(启动期)调用
void allocFuncs( const AllocFuncs& );
const AllocFuncs& allocFuncs();
```

设计要点:

- 使用函数指针而非虚函数,避免 vtable 开销。
- 函数指针表在 `Allocator::init()` 中通过 `Memhook::allocFuncs(allocFuncs)` 注册一次,之后只读,因此无需锁。
- 函数指针类型带 `MEMHOOK_CDECL`(`__cdecl` on Win32),匹配 C 运行时的调用约定,以便替换 `malloc`/`free`。

### 4.3 全局 operator new / operator delete 重载

memhook.cpp 直接重载了全局运算符:

```cpp
// memhook.cpp#L35-L92
NOINLINE
void * operator new( size_t sz )
{
    init();
    return (*s_allocFuncs.new_)( sz );
}

NOINLINE
void * operator new[]( size_t sz )
{
    init();
    return (*s_allocFuncs.newArray_)( sz );
}

NOINLINE
void * operator new( size_t sz, const std::nothrow_t & nt ) throw()
{
    init();
    return (*s_allocFuncs.newNoThrow_)( sz, nt );
}

NOINLINE
void operator delete( void * p ) throw()
{
    init();
    (*s_allocFuncs.delete_)( p );
}

NOINLINE
void operator delete[]( void * p ) throw()
{
    init();
    (*s_allocFuncs.deleteArray_)( p );
}
```

注意:

1. **`NOINLINE`**:这些函数被标记为 `__declspec(noinline)`(MSVC)以避免内联,目的是让调用栈跟踪(`stacktrace`)能稳定看到一个独立的"new 帧",便于过滤分配器自身的栈帧。
2. **`init()` 懒加载**:第一次调用 `operator new` 时触发 `init()`,后者调用 `memHookInitFunc()`(定义在 cstdmf)→ `BW::Allocator::init()`。这样即使 `Allocator::init()` 因为静态初始化顺序问题没先执行,首次 new 也能完成初始化。
3. **`throw()`**:C++98 风格的异常规范,表示 `delete` 不抛异常。C++11 已弃用 `throw()`,改为 `noexcept`,但 BW 兼容老编译器所以保留。

### 4.4 静态链接模式下的 malloc/free 替换

当 `BW_STATIC_LINKING` 定义时,memhook 还提供 C 函数符号替换:

```cpp
// memhook.cpp#L94-L137
#if BW_STATIC_LINKING
extern "C" void* MEMHOOK_CDECL malloc( size_t size )
{
    init();
    return (*s_allocFuncs.malloc_)( size );
}

extern "C" void MEMHOOK_CDECL free( void * p )
{
    init();
    (*s_allocFuncs.free_)( p );
}

extern "C" void* MEMHOOK_CDECL realloc( void * p, size_t size )
{
    return (*s_allocFuncs.realloc_)( p, size );
}

extern "C" size_t MEMHOOK_CDECL _msize (void * pblock)
{
    return (*s_allocFuncs.msizeFunc_)( pblock );
}

extern "C" void* MEMHOOK_CDECL _aligned_malloc( size_t size, size_t alignment )
{
    return (*s_allocFuncs.alignedMalloc_)( size, alignment );
}

extern "C" void MEMHOOK_CDECL _aligned_free( void * p )
{
    (*s_allocFuncs.alignedFree_)( p );
}
#endif // BW_STATIC_LINKING
```

注意 `extern "C"` 与 `MEMHOOK_CDECL` 调用约定,使这些符号能匹配 C 运行时的 `malloc`/`free` 签名。链接器在解析符号时会优先使用 memhook 提供的版本(因为 memhook 在 `LIBRARY` 顺序段中比 CRT 更靠前)。

但动态链接模式下(DLL),不能替换 `malloc`/`free`(因为 CRT DLL 已经导出这些符号),所以只能拦截 `operator new`/`delete`。这意味着三方库内部的 `malloc` 调用会绕过 BW——这是动态链接模式的一个已知局限。

### 4.5 bw_new/bw_delete:BW 内存 API 入口

[bw_memory.cpp](file:///j:/Work/BigWorld-Engine-14.4.1/programming/bigworld/lib/cstdmf/bw_memory.cpp#L35-L200) 提供了 BW 自己的 C 风格内存 API:

```cpp
void * bw_new( size_t size )
{
    if (size == 0) size = 1;
    while (true) {
        if (void * p = BW::Allocator::allocate( size )) {
            return p;
        }
        if (std::new_handler handler = globalNewHandler()) {
            (*handler)();   // 调用 new_handler,可能释放一些内存
        } else {
            throw std::bad_alloc();
        }
    }
}

void bw_delete( void * p ) throw()
{
    BW::Allocator::deallocate( p );
}

void * bw_malloc( size_t size )            { return BW::Allocator::allocate( size ); }
void   bw_free( void * ptr )               { return BW::Allocator::deallocate( ptr ); }
void * bw_malloc_aligned( size_t s, size_t a ) { return BW::Allocator::heapAllocateAligned( s, a ); }
void   bw_free_aligned( void * ptr )       { BW::Allocator::heapDeallocateAligned( ptr ); }
void * bw_realloc( void* ptr, size_t size ){ return BW::Allocator::reallocate( ptr, size ); }

char * bw_strdup( const char * s )
{
    size_t len = strlen( s ) + 1;
    char* ns = ( char* )BW::Allocator::allocate( len );
    memcpy( ns, s, len );
    return ns;
}

size_t bw_memsize( void * p ) { return BW::Allocator::memorySize( p ); }
```

设计要点:

- `bw_new` 实现了 C++ 标准要求的 `new_handler` 循环:分配失败时调用全局 `std::get_new_handler()` 设置的回调(用户可以注册一个释放缓存的处理函数),若仍失败则抛 `std::bad_alloc`。
- `bw_new(nothrow)` 版本返回 `nullptr` 而非抛异常。
- `bw_strdup` 是 `strdup` 的 BW 版本,strdup 在某些 CRT 中是 inline,无法被 memhook 拦截,所以提供独立实现。

### 4.6 SafeAllocatable:跨 DLL 边界的 new/delete 一致性

[bw_safe_allocatable.hpp](file:///j:/Work/BigWorld-Engine-14.4.1/programming/bigworld/lib/cstdmf/bw_safe_allocatable.hpp#L27-L38) 解决了一个具体的 Windows DLL 问题:

> 如果一个类 `T` 在 EXE 中 `new`,在 DLL 中 `delete`,而 DLL 又导出了 `T` 的 `operator delete`,那么 MSVC 在 Release 构建中可能把 `operator delete` 内联到调用点,导致 EXE 的堆指针被传给 DLL 的堆 free,引发崩溃或数据损坏。

参见 Microsoft KB122675。BW 的解决方案是让所有需要跨 DLL 边界的类继承 `SafeAllocatable`,后者重写 `operator new`/`delete` 转发到 `bw_new`/`bw_delete`:

```cpp
class SafeAllocatable
{
public:
    CSTDMF_DLL static void * operator new( std::size_t size );
    CSTDMF_DLL static void * operator new[]( std::size_t size );
    CSTDMF_DLL static void operator delete( void * ptr );
    CSTDMF_DLL static void operator delete[]( void * ptr );
};
```

[bw_safe_allocatable.cpp](file:///j:/Work/BigWorld-Engine-14.4.1/programming/bigworld/lib/cstdmf/bw_safe_allocatable.cpp#L15-L51) 实现:

```cpp
void * SafeAllocatable::operator new( std::size_t size )      { return ::bw_new( size ); }
void * SafeAllocatable::operator new[]( std::size_t size )    { return ::bw_new_array( size ); }
void   SafeAllocatable::operator delete( void * ptr )          { return ::bw_delete( ptr ); }
void   SafeAllocatable::operator delete[]( void * ptr )       { return ::bw_delete_array( ptr ); }
```

`CSTDMF_DLL` 宏确保这些函数从 cstdmf.dll 导出,所有 DLL 都调用同一份实现,内联被禁用。

`MemoryOStream` 继承 `SafeAllocatable`,所以即使在 DLL 边界传递 `MemoryOStream*` 也能安全 `delete`。

### 4.7 调用栈跟踪:callstack 模块

## 五、FixedSizedAllocator 固定大小池剖析

### 5.1 设计动机与定位

[fixed_sized_allocator.hpp](file:///j:/Work/BigWorld-Engine-14.4.1/programming/bigworld/lib/cstdmf/fixed_sized_allocator.hpp#L20-L213) 的注释直接说明了设计意图:

> Implements an allocator using fixed size pools of user specified sizes.
> Each pool will allocate a fixed amount of memory and allocate more pools as necessary. Allocations over the max pool size will be allocated from and returned to the heap. The primary intent of this is to reduce fragmentation by allocation and destruction of small size objects.

核心目标:

1. **降低小对象碎片**:把 8B/16B/32B.../1024B 的请求归入对应池,池内部分配是 O(1) 的链表弹出,无 metadata 开销。
2. **批量申请**:池从堆申请一整块(默认 512KB),内部切分成 N 个等大 slot。
3. **空闲归还堆**:当池中所有 slot 都空闲时,把整块还给堆,避免池长期占用内存。

### 5.2 PoolHeader 与池链表结构

每个池由 `PoolHeader` 描述:

```cpp
// fixed_sized_allocator.hpp#L72-L80
struct PoolHeader
{
    PoolHeader* prevPool_;   // 双向链表前驱
    PoolHeader* nextPool_;   // 双向链表后继
    void*       firstFree_;  // 第一个空闲块的指针(空闲链表头)
    size_t      numFree_;    // 剩余空闲数
    size_t      numItems_;   // 池总 slot 数
    size_t      allocSize_;  // 每个 slot 的大小
};
```

池的组织:

- 同一 `allocSize_` 的所有 `PoolHeader` 组成双向链表,链表头存在 `topLevelPools_[pool]`。
- 链表头部是"最近有释放"或"最近分配过"的池——这样下次分配时,头部池往往有空闲 slot,无需遍历。
- 池内空闲 slot 通过**嵌入链表**组织:每个空闲 slot 的前 8 字节(指针大小)存储下一个空闲 slot 的地址。

这种"嵌入式空闲链表"的好处是**零 metadata 开销**:slot 在空闲时充当链表节点,在使用时被用户数据覆盖。

### 5.3 PoolSpan:指针到池的快速反查

`deallocate` 时需要判断给定的指针是否来自池(若不是则走堆 free)。BW 通过 `PoolSpan` 数组线性查找:

```cpp
// fixed_sized_allocator.hpp#L82-L86
struct PoolSpan
{
    void* start_;
    void* end_;
};
```

`poolSpans_` 是动态数组,记录所有已分配的池的 `[start, end)` 区间:

```cpp
// fixed_sized_allocator.cpp#L839-L851
FixedSizedAllocator::PoolHeader * FixedSizedAllocator::findAllocPool( const void * ptr ) const
{
    for (size_t i = 0; i < poolSpanCount_; ++i) {
        PoolSpan span = poolSpans_[i];
        if (ptr > span.start_ && ptr < span.end_) {
            return (PoolHeader*)span.start_;
        }
    }
    return 0;
}
```

这是 O(N) 的查找,N 是当前活跃的池数。对于小规模应用(几十个池)是可接受的;若池数巨大,可考虑改用基数树或 hash 表。

### 5.4 分配流程:internalAllocate 详解

[fixed_sized_allocator.cpp#L197-L375](file:///j:/Work/BigWorld-Engine-14.4.1/programming/bigworld/lib/cstdmf/fixed_sized_allocator.cpp#L197-L375) 的核心分配流程:

```cpp

    uint32 heapAllocFlags, const int* poolHint )
{

    const int pool = poolHint ? *poolHint : this->findPool( size );

        lock.release();
        return (*malloc_)( size, heapAllocFlags );

            memcpy( &hdr->firstFree_, ptr, sizeof( void* ) );  // 5. 读出下一个空闲
            --hdr->numFree_;

            // 6. 把刚刚分配过的池移到链表头(MRU 策略)
            if (hdr->numFree_ && topLevelPools_[pool] != hdr) {
                // unlink + relink at head
                ...
            }
            return ptr;
        }
        hdr = hdr->nextPool_;
    }

    // 7. 所有池都满了,新建一个池
    const size_t allocSize = allocSizes_[pool];
    const size_t numPoolItems = static_cast< size_t >( poolSize_ ) / allocSize;
    size_t memSize = numPoolItems * allocWithBoundSize + sizeof( PoolHeader );

    void* newPoolMem = (*malloc_)( memSize, Allocator::IF_INTERNAL_ALLOC );  // 8. 向堆要一块
    PoolHeader* newPool = reinterpret_cast< PoolHeader * >( newPoolMem );
    newPool->nextPool_ = 0;
    newPool->prevPool_ = 0;
    newPool->numFree_ = numPoolItems;
    newPool->numItems_ = numPoolItems;
    newPool->allocSize_ = allocSize;
    newPool->firstFree_ = reinterpret_cast< char * >( newPoolMem ) + sizeof( PoolHeader );

    // 9. 链表初始化:每个 slot 的前 8 字节指向下一个 slot
    char* p = reinterpret_cast<char *>( newPool->firstFree_ );
    for (size_t i = 0; i < numPoolItems - 1; ++i) {
        void* cur  = reinterpret_cast< void* >( p + allocWithBoundSize * i );
        void* next = reinterpret_cast< void* >( p + allocWithBoundSize * (i + 1) );
        memcpy( cur, &next, sizeof( void* ) );
    }
    // 最后一个 slot 的 next = NULL
    void* pLastEntry( p + allocWithBoundSize * (numPoolItems - 1) );
    memset( pLastEntry, 0, sizeof( void* ) );

    // 10. 链入 topLevelPools_
    if (topLevelPools_[pool]) {
        newPool->nextPool_ = topLevelPools_[pool];
        topLevelPools_[pool]->prevPool_ = newPool;
        topLevelPools_[pool] = newPool;
    } else {
        topLevelPools_[pool] = newPool;
    }

    // 11. 登记到 PoolSpan
    addPoolSpan( newPoolMem, (char*)newPoolMem + sizeof(PoolHeader) + numPoolItems * allocWithBoundSize);

    // 12. 分配第一个 slot 给用户
    void* ptr = newPool->firstFree_;
    memcpy( &newPool->firstFree_, ptr, sizeof( void* ) );
    --newPool->numFree_;

    return ptr;
}
```

关键设计点:

- **MRU 头部移动**:刚分配过的池移到链表头,因为 Likely 下次还从它分配,减少遍历。
- **嵌入式空闲链表**:slot 内部用 `memcpy` 读写下个节点指针,而非 `*((void**)ptr)`,这样即使内存填充模式启用了 0xFE,也能正常工作(因为 `memcpy` 不假设对齐)。
- **新池申请的内存量**:`numPoolItems * allocWithBoundSize + sizeof(PoolHeader)`,即 N 个 slot 加 header。`allocWithBoundSize` 在调试构建下多了 4 字节(`BoundsMagic`),用于越界检查。

### 5.5 释放流程:internalDeallocate 详解

```cpp
// fixed_sized_allocator.cpp#L381-L481
void FixedSizedAllocator::internalDeallocate( void * ptr,
    uint32 heapAllocFlags, PoolHeader * const * poolHint )
{
    if (ptr == 0) return;

    ScopedLock lock( lock_ );
    PoolHeader* pool = poolHint ? *poolHint : this->findAllocPool( ptr );

    if (!pool) {                                       // 不来自池,走堆
        lock.release();
        (*free_)( ptr, heapAllocFlags );
        return;
    }

#if ENABLE_FIXED_SIZE_POOL_BOUNDS_CHECKING
    // 检查 BoundsMagic 是否完整
    const char* cPtr( reinterpret_cast< char* >( ptr ) );
    const uint32 magic = *(reinterpret_cast< const uint32 * >( cPtr + pool->allocSize_ ));
    MF_ASSERT_NOALLOC( magic == BoundsMagic );        // 否则越界写破坏了 magic
#endif

    // 把 ptr 重新链入空闲链表头
    memcpy( ptr, &pool->firstFree_, sizeof( void* ) );
    pool->firstFree_ = ptr;
    ++pool->numFree_;

    // 如果池中所有 slot 都空闲,把整个池归还给堆
    if (pool->numFree_ == pool->numItems_) {
        // 从链表中摘除
        if (pool->prevPool_) {
            pool->prevPool_->nextPool_ = pool->nextPool_;
        } else {
            // 这是链表头
            const int index = this->findPool( pool->allocSize_ );
            topLevelPools_[index] = pool->nextPool_;
        }
        if (pool->nextPool_) {
            pool->nextPool_->prevPool_ = pool->prevPool_;
        }
        (*free_)( pool, Allocator::IF_INTERNAL_ALLOC );
        delPoolSpan( pool );
    }
}
```

设计要点:

- **归还条件严格**:只有池中所有 slot 都空闲时才归还,避免抖动(刚归还又申请)。
- **BoundsMagic 检查**:在 Debug 构建下,每个 slot 末尾追加 4 字节 `0xdeadf00d`,释放时校验。若用户代码越界写,会破坏 magic,断言触发。
- **链入空闲链表头**:`firstFree_ = ptr`,O(1) 操作。

### 5.6 reallocate 的池内复用优化

`reallocate` 是 `realloc` 的池化版本,有一个重要优化:如果新大小仍然落在同一池档位,直接返回原指针,无需拷贝:

```cpp
// fixed_sized_allocator.cpp#L487-L538
void* FixedSizedAllocator::reallocate( void * ptr, size_t size, uint32 heapAllocFlags )
{
    PoolHeader * currentPool = NULL;
    int newPool = -1;
    size_t copySize = 0;

    if (ptr) {
        ScopedLock lock( lock_ );
        currentPool = this->findAllocPool( ptr );
        newPool = this->findPool( size );

        if (!currentPool) {                            // 原本是堆
            if (newPool == -1) {                       // 新也是堆
                lock.release();
                return (*realloc_)( ptr, size, heapAllocFlags );
            }
            copySize = std::min( allocSizes_[newPool], size );
        } else {
            if (newPool != -1 && allocSizes_[newPool] == currentPool->allocSize_) {
                // 同一池档位,无需任何操作
                return ptr;
            }
            copySize = std::min( currentPool->allocSize_, size );
        }
        // 用 hint 避免重复查找
        allocateHint = &newPool;
        deallocateHint = &currentPool;
    }

    // 不同池,分配新块、拷贝、释放旧块
    void* newPtr = this->internalAllocate( size, heapAllocFlags, allocateHint );
    memcpy( newPtr, ptr, copySize );
    this->internalDeallocate( ptr, heapAllocFlags, deallocateHint );
    return newPtr;
}
```

这一优化对 `std::vector` 的 `reserve()` 极其友好:`vector` 从 N 字节增长到 2N 字节,若两者都在同一池档位(如都是 32B),则无需拷贝。

### 5.7 自动池大小:autoPools 模式

除了在构造时传入固定的池大小数组,`FixedSizedAllocator` 还支持"自动池"模式:

```cpp
// fixed_sized_allocator.hpp#L118-L119
bool  autoPools_;
size_t autoPoolsMaxSize_;
```

第二个构造函数启用此模式:

```cpp
FixedSizedAllocator( size_t maxPoolSize, size_t poolSize, const char * debugName );
```

在 `findPool` 中,若请求大小 ≤ `autoPoolsMaxSize_` 且当前池数 < `MaxPools`,则动态创建新池:

```cpp
// fixed_sized_allocator.cpp#L729-L777
int FixedSizedAllocator::findPool( size_t reqSize )
{
    for (size_t i = 0; i < numPools_; ++i) {
        if (reqSize <= allocSizes_[i]) return static_cast<int>(i);
    }

    if (autoPools_ && reqSize <= autoPoolsMaxSize_) {
        MF_ASSERT_NOALLOC( numPools_ < (size_t)MaxPools );
        reqSize = std::max( sizeof(void*), reqSize );

        // 添加到末尾,然后冒泡到正确位置(保持递增序)
        allocSizes_[numPools_] = reqSize;
        size_t curSpot = numPools_;
        while (curSpot > 0) {
            if (allocSizes_[curSpot] < allocSizes_[curSpot - 1]) {
                std::swap( allocSizes_[curSpot], allocSizes_[curSpot - 1] );
                std::swap( topLevelPools_[curSpot], topLevelPools_[curSpot -1] );
                --curSpot;
            } else {
                break;
            }
        }
        return static_cast<int>(numPools_++);
    }
    return -1;
}
```

系统级 `FixedSizedAllocator`(在 `Allocator::init()` 中创建)使用固定大小数组,因为可以根据 `sizeof(void*)` 在编译期计算档位:

```cpp
// allocator.cpp#L491-L503
size_t sizes[9];
size_t numSizes = 0;
for ( ; (sizeof(void*) << numSizes) < 2048; ++numSizes )
    sizes[numSizes] = sizeof(void*) << numSizes;
// 32位:8, 16, 32, 64, 128, 256, 512, 1024  (8档)
// 64位:16, 32, 64, 128, 256, 512, 1024     (7档)
const size_t poolSize = 1 * 1024 * 1024 / 2;  // 512KB
s_fixedSizedAllocator = new(s_fixedSizedAllocatorMem) BW::FixedSizedAllocator(
    sizes, numSizes, poolSize, "System" );
```

每个池 512KB,8 档共 4MB 的"上界"——这是 BW 系统级池的稳态内存占用。

### 5.8 边界检查 BoundsMagic 与内存填充

Debug 构建下(`_DEBUG`),每个 slot 末尾追加 4 字节 magic:

```cpp
// fixed_sized_allocator.cpp#L15-L18
#if ENABLE_FIXED_SIZE_POOL_BOUNDS_CHECKING
const BW_NAMESPACE uint32 BoundsMagic = 0xdeadf00d;
#endif
```

新建池时,每个 slot 末尾写入 magic:

```cpp
#if ENABLE_FIXED_SIZE_POOL_BOUNDS_CHECKING
    char* pEntryEnd( reinterpret_cast< char * >( cur ) + allocSize );
    memcpy( pEntryEnd, &BoundsMagic, sizeof( BoundsMagic ) );
#endif
```

释放时校验:

```cpp
#if ENABLE_FIXED_SIZE_POOL_BOUNDS_CHECKING
    const char* cPtr( reinterpret_cast< char* >( ptr ) );
    const uint32 magic = *(reinterpret_cast< const uint32 * >( cPtr + pool->allocSize_ ));
    MF_ASSERT_NOALLOC( magic == BoundsMagic );
#endif
```

这能捕捉缓冲区末尾越界写(`buffer[idx + 4] = ...`),但不能捕捉缓冲区内部越界或前置越界。完整的越界检测需要 `ProtectedAllocator`。

`ENABLE_FIXED_SIZED_POOL_MEMORY_FILLS` 启用时,新分配的 slot 填 `0xCD`,释放后填 `0xDD`,与全局 `markAlloc`/`markDealloc` 一致:

```cpp
// 分配后
memset( ptr, Allocator::CleanLandFill, hdr->allocSize_ );

// 释放前(ptr 的前 sizeof(void*) 字节用作链表指针,所以从 sizeof(void*) 开始填)
memset( static_cast< char * >( ptr ) + sizeof( void * ),
    Allocator::DeadLandFill, pool->allocSize_ - sizeof(void*) );
```

### 6.2 三种 CallstackMode

`MemoryDebug` 的调用栈采集有三种模式:

```cpp
enum CallstackMode
{
    CM_BW_GUARD,             // 仅记录 BW_GUARD 宏标注的栈
    CM_CALLSTACKS_FAST,      // 快速栈采集(帧指针遍历)
    CM_CALLSTACKS_COMPLETE   // 完整栈采集(基于符号)
};
```

- **CM_BW_GUARD**(默认):不调用 `stacktrace`,只读取 `StackTracker` 的栈(由 `BW_GUARD` 宏维护)。这是最快的模式,适合开发日常使用。
- **CM_CALLSTACKS_FAST**:对每笔分配调用 `stacktrace()`,基于帧指针遍历,快但不完整(优化代码可能省略帧指针)。
- **CM_CALLSTACKS_COMPLETE**:调用 `stacktraceAccurate()`,基于 DWARF/PDB 完整栈展开,慢但准确。

通过命令行选择:

```bash
cellapp -memdebug=cs_fast        # 快速栈
cellapp -memdebug=cs_complete    # 完整栈
cellapp -memdebug=cs_guard       # 仅 BW_GUARD(默认)
cellapp -memdebug=disable        # 完全禁用
```

`-memdebug=disable` 用于在生产环境临时关闭调试,即使 `ENABLE_MEMORY_DEBUG` 编译期开启。

### 6.6 GrowOnlyPodAllocator:只增内存分配器

[grow_only_pod_allocator.hpp](file:///j:/Work/BigWorld-Engine-14.4.1/programming/bigworld/lib/cstdmf/grow_only_pod_allocator.hpp#L13-L49) 是一个超简单的分配器:

```cpp
class GrowOnlyPodAllocator
{
public:
    GrowOnlyPodAllocator( size_t pageSize );
    ~GrowOnlyPodAllocator();

    void* allocate( size_t size );
    void deallocate(void*) { /* no-op */ }
    void releaseAll();

private:
    struct PageHeader
    {
        size_t      used;
        PageHeader *nextPage;
    };

    const size_t    pageSize_;
    PageHeader*     currentPage_;
};
```

特点:

- **只增不减**:`allocate` 在当前页内 bump 指针,满了就申请新页;`deallocate` 是空操作。
- **POD 限定**:只能分配 POD 类型(因为不调用析构)。
- **批量释放**:只能通过 `releaseAll()` 一次性释放所有页。

`MemoryDebug` 用它存储 `CallstackHeader`(调用栈数据是 POD,生命周期与 `MemoryDebug` 一致),避免每笔分配都触发 `FixedSizedAllocator` 的链表操作。

```
       └── Model::load()              | 4.3 MB          | 1,234,567
```

### 6.10 防重入:THREADLOCAL 标志位

`MemoryDebug::allocate` 在执行过程中可能触发新的分配(如 `unordered_map::insert`),后者又会调用 `MemoryDebug::allocate`,造成无限递归。BW 用两个线程局部变量解决:

```cpp
// memory_debug.hpp#L346-L347
static THREADLOCAL( bool ) internalAlloc_;
static THREADLOCAL( uint ) ignoreAllocs_;
```

- `internalAlloc_`:当 `MemoryDebug` 自身分配时(`DebugStlAllocator::allocate`)设为 true,递归进入 `MemoryDebug::allocate` 时立即返回,不记录。
- `ignoreAllocs_`:由 `allocTrackingIgnoreBegin()` 递增,`allocTrackingIgnoreEnd()` 递减;非零期间所有分配标记为 `AF_ALLOCATION_IGNORELEAK`,退出时不报告泄漏。用于"已知泄漏"的三方库(如 Python 静态对象)。

## 七、StackTracker 与 ThreadSlotTracker

### 7.1 StackTracker:轻量级函数栈

[stack_tracker.hpp](file:///j:/Work/BigWorld-Engine-14.4.1/programming/bigworld/lib/cstdmf/stack_tracker.hpp#L31-L89) 是一个线程局部的"逻辑调用栈",与 OS 调用栈不同,它由 `BW_GUARD` 宏显式 push/pop:

```cpp
class StackTracker
{
private:
    enum
    {
        THREAD_STACK_DEPTH = 1024,
        ANNOTATION_BUFFER_SIZE = 4096,
        MAX_ANNOTATION_STACK_ENTRIES = 256
    };

public:
    struct StackItem
    {
        const char*     name;        // 函数名
        const char*     file;        // 文件名
        uint            line:31;     // 行号
        bool            temp:1;      // 是否临时字符串(需要拷贝)
        const char*     annotation;  // 额外注释
    };

    inline static void push( const char * name, const char * file=NULL, uint line=0 );
    CSTDMF_DLL static void push( const char * name, const char * file, uint line, bool temp );
    CSTDMF_DLL static void pop();
    CSTDMF_DLL static uint stackSize();
    CSTDMF_DLL static StackItem& getStackItem(uint idx);

    static THREADLOCAL(StackItem)    stack_[THREAD_STACK_DEPTH];
    static THREADLOCAL(uint)         stackPos_;
    // ...
};
```

特点:

- **线程局部**:`THREADLOCAL` 宏(Windows `__declspec(thread)`,Linux `__thread`),每线程独立栈。
- **每线程 1024 深度**:足够嵌套 1024 层 `BW_GUARD`。
- **POD StackItem**:不调用构造析构,纯指针+整数。
- **O(1) push/pop**:仅栈指针增减与一次写入。

### 7.2 BW_GUARD 宏与 ScopedStackTrack

`ScopedStackTrack` 是 RAII 包装:


在函数入口写一行 `BW_GUARD("Entity::tick");`,函数执行期间栈帧就有一项 `Entity::tick`,被 `MemoryDebug` 的 `CM_BW_GUARD` 模式读取,作为"廉价的调用栈"。

### 7.3 注解机制:pushAnnotation/popAnnotation

`StackItem` 中的 `annotation` 字段是可选的字符串,用于附加上下文:


例如在 `Entity::tick` 内,可以注解当前 entity id,这样泄漏报告能显示具体是哪个 entity 没释放。

注解存储在每线程 4KB 的环形 buffer 中,通过 `nextAnnotationPtr_` bump 指针分配,避免每条注解触发 `bw_new`。

## 八、引用计数体系:ReferenceCount / SmartPointer

### 8.1 ReferenceCount 非线程安全引用计数

[smartpointer.hpp](file:///j:/Work/BigWorld-Engine-14.4.1/programming/bigworld/lib/cstdmf/smartpointer.hpp#L39-L154) 定义了 BW 的引用计数基类:

```cpp
class ReferenceCount
{
protected:
    ReferenceCount() : count_( 0 ) { ... }
    ReferenceCount( const ReferenceCount & ) : count_( 0 ) { ... }
    virtual ~ReferenceCount() { }

public:
    inline int32 incRef() const
    {
        REFERENCE_COUNT_THREAD_CHECK;
        ++count_;
        return count_;
    }

    inline int32 decRef() const
    {
        REFERENCE_COUNT_THREAD_CHECK;
        int32 count = --count_;
        if (count == 0)
        {
            delete this;        // 自杀
        }
        return count;
    }

    inline int32 refCount() const { return count_; }

private:
    ReferenceCount & operator=( const ReferenceCount & );
    mutable int32 count_;
};
```

设计要点:

- **侵入式**:count_ 是对象成员,不分配额外控制块(对比 std::shared_ptr 的控制块)。
- **mutable**:incRef/decRef 是 const 方法(因为逻辑上引用计数不影响对象状态),但 count_ 必须 mutable。
- **拷贝构造**:复制对象时 count_ 重置为 0,因为新对象是新独立的。
- **赋值私有**:禁止赋值,因为引用计数对象赋值语义不明。
- **decRef 自杀**:引用计数归零时 `delete this`,要求对象必须 `new` 出来,不能是栈对象或全局对象。

### 8.2 SafeReferenceCount 原子引用计数

```cpp
class CSTDMF_DLL SafeReferenceCount
{
protected:
    SafeReferenceCount() : count_( 0 ) {}
    SafeReferenceCount( const SafeReferenceCount & ) : count_( 0 ) {}
    virtual ~SafeReferenceCount() {}

public:
    inline int32 BW_FASTCALL incRef() const
    {
#if defined( __APPLE__ ) || defined( __ANDROID__ )
        int32 count = ++count_;    // 旧实现,非原子
#else
        int32 count = BW_ATOMIC32_INC_AND_FETCH( &count_ );   // 原子自增
#endif
        return count;
    }

    inline int32 BW_FASTCALL decRef() const
    {
        int32 count = BW_ATOMIC32_DEC_AND_FETCH( &count_ );   // 原子自减
        if (count == 0)
        {
            this->destroy();       // 虚函数,允许派生类自定义释放
        }
        return count;
    }

    inline int32 BW_FASTCALL refCount() const { return count_; }

private:
    virtual void destroy() const { delete this; }

    mutable bw_atomic32_t count_;   // volatile LONG / int
};
```

注意:

- **`BW_FASTCALL`**:`__fastcall` on Windows,通过寄存器传 `this`,小幅提升 incRef/decRef 速度。
- **`destroy()` 虚函数**:允许派生类自定义析构方式(如返回到对象池而不是 delete)。
- **苹果/安卓 fallback**:旧版本没有正确的原子操作实现,使用 `++count_`,存在竞态。这是已知的待修复项。

### 8.3 ReferenceCountThreadingDebug 跨线程检测

`ENABLE_REFERENCE_COUNT_THREADING_DEBUG`(`_DEBUG` 或 `FORCE_ENABLE_`)启用时,`ReferenceCount` 记录第一次访问的线程 id,后续不同线程访问触发断言:

```cpp
#if ENABLE_REFERENCE_COUNT_THREADING_DEBUG
    mutable unsigned long threadID_;
#ifdef REFERENCE_COUNT_THREADING_DEBUG_IGNORE_FIRST_THREAD
    mutable bool firstThread_;
#endif
    static const unsigned long INVALID_THREAD_ID = (unsigned long)-1;

    void check() const
    {
        if (threadID_ == INVALID_THREAD_ID) {
            threadID_ = OurThreadID();
            firstThread_ = true;
        } else {
            if (threadID_ != OurThreadID()) {
                if (firstThread_) {     // 容忍一次跨线程(对象在创建后转移到其他线程)
                    threadID_ = OurThreadID();
                    firstThread_ = false;
                } else {
                    MF_ASSERT( !"ReferenceCounted object is accessed from different thread" );
                }
            }
        }
    }
#endif
```

注意 `IGNORE_FIRST_THREAD`:允许对象在线程 A 创建,然后转移到线程 B 长期使用,但禁止后续在两个线程间频繁切换。这对 CellApp 的"实体迁移"场景必要。

### 8.4 incrementReferenceCount / decrementReferenceCount 模板钩子

```cpp
template <class Ty>
inline void incrementReferenceCount( const Ty &Q )
{
    Q.incRef();
}

template <class Ty>
inline bool hasZeroReferenceCount( const Ty &Q )
{
    return (Q.refCount() == 0);
}

template <class Ty>
inline void decrementReferenceCount( const Ty &Q )
{
    Q.decRef();
}
```

这些是模板自由函数,可以被特化以支持没有 `incRef`/`decRef` 方法的类型。例如对 Python 对象的引用计数,可以特化为调用 `Py_INCREF`/`Py_DECREF`:

```cpp
// 假设的特化(实际在 python 包装层)
template<>
inline void incrementReferenceCount( const PyObjectPtr &Q )
{
    Py_INCREF( Q.get() );
}
```

这样 `SmartPointer<T>` 模板不关心 T 的引用计数实现细节,通过 ADL 找到对应的 `incrementReferenceCount`。

### 8.5 ConstSmartPointer 设计

[smartpointer.hpp#L328-L585](file:///j:/Work/BigWorld-Engine-14.4.1/programming/bigworld/lib/cstdmf/smartpointer.hpp#L328-L585) 的 `ConstSmartPointer<Ty>` 是 const 访问的智能指针:

```cpp
template<class Ty> class ConstSmartPointer
{
public:
    static const bool STEAL_REFERENCE = true;
    static const bool NEW_REFERENCE = false;

    typedef Ty Object;
    typedef ConstSmartPointer<Ty> This;

    ConstSmartPointer( const Object *P = 0, bool alreadyIncremented = false )
    {
        object_ = P;
        if (object_) {
            if (!alreadyIncremented) {
                incrementReferenceCount( *object_ );
            } else {
                if (hasZeroReferenceCount( *object_ )) {
                    MF_ASSERT_DEV( 0 && "..." );
                }
            }
            BW_MEMORYDEBUG_SMARTPOINTER_ASSIGN( this, object_ );
        }
    }

    ConstSmartPointer( const This& P )
    {
        object_ = P.get();
        if (object_) {
            incrementReferenceCount( *object_ );
            BW_MEMORYDEBUG_SMARTPOINTER_ASSIGN(this, object_);
        }
    }

    This& operator=( const This& X )
    {
        if (object_ != X.get()) {
            const Object* pOldObj = object_;
            object_ = X.get();
            BW_MEMORYDEBUG_SMARTPOINTER_ASSIGN( this, object_ );
            if (object_) incrementReferenceCount( *object_ );
            if (pOldObj) decrementReferenceCount( *pOldObj );
        }
        return *this;
    }

    ~ConstSmartPointer()
    {
        if (object_) {
            decrementReferenceCount( *object_ );
            BW_MEMORYDEBUG_SMARTPOINTER_ASSIGN(this, NULL);
        }
        object_ = 0;
    }

    // 指针式访问
    const Object * get() const { return object_; }
    const Object * getObject() const { return this->get(); }
    bool hasObject() const { return object_ != 0; }
    bool exists() const { return object_ != 0; }

    const Object& operator*() const
    {
        null_pointer_check( object_ );
        return *object_;
    }
    const Object* operator->() const
    {
        null_pointer_check( object_ );
        return object_;
    }

protected:
    const Object *object_;
};
```

设计要点:

- **operator= 的顺序**:先 incRef 新对象,再 decRef 旧对象。如果反过来,在自赋值 (`p = p`) 的情况下,先 decRef 可能让对象自杀,后续 incRef 就崩溃了。当前顺序保证自赋值安全(且 `if (object_ != X.get())` 提前 return 自赋值)。
- **`null_pointer_check`**:默认空实现,允许用户特化为断言或日志。
- **`BW_MEMORYDEBUG_SMARTPOINTER_ASSIGN`**:调试宏,记录每次智能指针赋值,供 `MemoryDebug::printSmartPointerTracking` 查询。

### 8.6 SmartPointer 派生类

```cpp
template <class Ty>
class SmartPointer : public ConstSmartPointer<Ty>
{
public:
    typedef SmartPointer<Ty> This;
    typedef ConstSmartPointer<Ty> ConstProxy;
    typedef Ty Object;

    SmartPointer( Object *P = 0, bool alreadyIncremented = false ) :
        ConstProxy( P, alreadyIncremented ) { }

    SmartPointer( const This& P ) : ConstProxy( P ) { }

    template<class DerivedType>
    SmartPointer( const ConstSmartPointer<DerivedType>& dt ) :
        ConstProxy( dt.get() )
    {
    }

    This& operator=( const This& P )
    {
        ConstProxy::operator=(P);
        return *this;
    }

    Object * get() const
    {
        return const_cast<Object *>( this->object_ );
    }

    Object& operator*() const
    {
        null_pointer_check( this->object_ );
        return *const_cast<Object *>( this->object_ );
    }

    Object* operator->() const
    {
        null_pointer_check( this->object_ );
        return const_cast<Object *>( this->object_ );
    }
};
```

`SmartPointer` 仅 override 非 const 的访问运算符,把 `const Object*` cast 为 `Object*`,其余复用 `ConstSmartPointer` 的逻辑。

### 8.7 STEAL_REFERENCE 与 NEW_REFERENCE

构造函数的第二个参数 `alreadyIncremented`:

- `NEW_REFERENCE`(false,默认):构造时调用 `incRef`,即"新引用"。
- `STEAL_REFERENCE`(true):不调用 `incRef`,即"窃取引用"——调用者已经 incRef 过了,智能指针接管。

`STEAL_REFERENCE` 用于工厂函数:

```cpp
SmartPointer<Entity> createEntity()
{
    Entity* e = new Entity();
    e->incRef();        // 工厂内部 incRef
    return SmartPointer<Entity>( e, SmartPointer<Entity>::STEAL_REFERENCE );
}
```

如果不传 `STEAL_REFERENCE`,智能指针构造时会再次 incRef,导致引用计数永远不归零(泄漏)。

`hasZeroReferenceCount` 检查防止误用:如果 `STEAL_REFERENCE` 但对象 count 为 0,说明调用者根本没 incRef,触发断言。

### 8.8 safe bool idiom:防止隐式转换

```cpp
typedef const Ty * ConstSmartPointer<Ty>::*unspecified_bool_type;
operator unspecified_bool_type() const
{
    return object_ == 0? 0 : &ConstSmartPointer<Ty>::object_;
}
```

这是经典的 safe bool idiom:

- `if (sp)` 把 sp 隐式转换为 `unspecified_bool_type`(成员指针)。
- 若 `object_ == 0`,返回 0(假);否则返回 `&ConstSmartPointer::object_`(真)。
- 因为是成员指针,不能转换为 int 或其他类型,避免 `sp + 1` 或 `if (sp == 1)` 这种误用。

C++11 后可以用 `explicit operator bool()` 替代,但 BW 兼容老编译器所以保留 safe bool idiom。

## 九、BW STL 容器族

### 9.1 StlAllocator 模板类

[stl_fixed_sized_allocator.hpp](file:///j:/Work/BigWorld-Engine-14.4.1/programming/bigworld/lib/cstdmf/stl_fixed_sized_allocator.hpp#L46-L192) 是 BW 容器族的核心:

```cpp
template < typename T >
class StlAllocator : public Detail::StlAllocatorBase< T >
{
public:
    typedef typename base_type::value_type value_type;
    typedef value_type *       pointer;
    typedef const value_type * const_pointer;
    typedef value_type &       reference;
    typedef const value_type & const_reference;
    typedef std::size_t        size_type;
    typedef std::ptrdiff_t     difference_type;

    template < typename Other >
    struct rebind { typedef StlAllocator< Other > other; };

    StlAllocator() 
#ifdef ALLOW_STACK_CONTAINER
        : allocator_( 0 )
#endif
    { }

    pointer allocate(size_type n, const void* hint = 0)
    {
#ifdef ALLOW_STACK_CONTAINER
        if (allocator_) {
            return reinterpret_cast< pointer >( allocator_->intAllocate( n, hint ) );
        }
#endif
        return reinterpret_cast< pointer >( bw_new( n * sizeof( value_type ) ) );
    }

    void deallocate( pointer p, size_type n )
    { 
#ifdef ALLOW_STACK_CONTAINER
        if (allocator_) {
            allocator_->intDeallocate( p, n );
            return;
        }
#endif
        bw_delete( reinterpret_cast< void * >( p ) );
    }

    size_type max_size() const
    {
#ifdef ALLOW_STACK_CONTAINER
        if (allocator_) return allocator_->getMaxSize();
#endif
        return size_t( -1 ) / sizeof( value_type );
    }

    // ...
    template < typename Other >
    bool operator==( const StlAllocator< Other > & ) const { return true; }

    template < typename Other >
    bool operator!=( const StlAllocator< Other > & ) const { return false; }

private:
#ifdef ALLOW_STACK_CONTAINER
    IAllocator * allocator_;
#endif
};
```

注意几个细节:

1. **`Detail::StlAllocatorBase<T>`**:MSVC 在旧版本中要求 `std::allocator<const T>` 也是 `const T*` 的 pointer,但实际 STL 内部要 `rebind` 成 `T` 才能分配(因为不能 const_cast)。`StlAllocatorBase` 把 `const T` 退化为 `T`,避免这个问题。
2. **`rebind`**:简单 typedef,因为 `StlAllocator` 是模板,任何 `StlAllocator<U>` 都能从 `StlAllocator<T>` 构造(无状态)。
3. **`operator==` 总是 true**:确认无状态分配器语义,容器拷贝时分配器可以"借用"。
4. **`ALLOW_STACK_CONTAINER`**:可选地持有 `IAllocator*`,用于 `StackContainer`。默认关闭。
5. **`bw_new( n * sizeof(value_type) )`**:容器请求 N 个元素,转成字节数调用 `bw_new`。

### 9.7 模板显式实例化与 DLL 导出

由于 `BW::string = std::basic_string<..., StlAllocator<...>>` 是模板,如果不显式实例化,每个使用 `BW::string` 的 DLL 都会重复实例化模板代码,导致:

1. 二进制体积膨胀。
2. 静态成员(如 `string::npos` 的地址)在不同 DLL 中不同,违反 ODR。

BW 通过 `CSTDMF_EXPORTED_TEMPLATE_CLASS` 显式实例化并导出:

```cpp

    CSTDMF_EXPORTED_TEMPLATE_CLASS basic_string< wchar_t, char_traits< wchar_t >, BW::wchar_allocator >;
}
```

`CSTDMF_EXPORTED_TEMPLATE_CLASS` 在 MSVC 下展开为 `template class __declspec(dllexport) ...`,在 GCC 下展开为 `template class ... __attribute__((visibility("default")))`。

## 十、bw_string 与 small string 优化

### 10.1 std::basic_string 的 SSO 实现

`std::basic_string` 在主流实现中都启用了 **Small String Optimization(SSO)**:对于足够短的字符串(通常 15-22 字节),把字符数据直接存储在 `basic_string` 对象内部,不分配堆内存。

主流 SSO 实现:

| 实现 | SSO 阈值 | 布局 |
| --- | --- | --- |
| libstdc++ (GCC) | 15 字节 | 联合体:短模式 16 字节缓冲(15 字符+null),长模式 size/capacity/data 指针 |
| libc++ (Clang) | 22 字节 | 联合体:短模式第一字节存 size<<1,长模式 size/capacity/data |
| MSVC Dinkumware | 15 字节 | 联合体:短模式 16 字节缓冲+size,长模式 size/capacity/data |

`BW::string` 继承自 `std::basic_string<char, ..., StlAllocator<char>>`,所以也享有 SSO。15 字节以内的字符串构造/销毁零堆分配,这对短字符串密集的场景(如 entity name、配置 key)非常高效。

### 10.2 BW::string 的内存路径分析

`BW::string s = "hello";` 的内存路径:

```
1. "hello" 是字符串字面量,长度 5(< 15,触发 SSO)
2. std::basic_string 构造函数把 "hello" 拷贝到内部 16 字节缓冲
3. 无堆分配
```

`BW::string s(100, 'x');` 的内存路径:

```
1. 长度 100 > 15,需要堆分配
2. std::basic_string 调用 StlAllocator<char>::allocate(100, 0)
3. StlAllocator 调用 bw_new(100)
4. bw_new 调用 BW::Allocator::allocate(100)
5. Allocator::allocate 调用 s_fixedSizedAllocator->allocate(100, IF_NOTRACK_ALLOC)
6. FixedSizedAllocator 找到 128 字节档位的池,弹出空闲 slot
7. 返回指针
```

`BW::string s2 = s;`(s 是 100 字节)的内存路径:

```
1. 拷贝构造,长度 100 > 15,需要堆分配
2. ... 同上 ...
3. memcpy 100 字节
```

### 10.3 BW::StringRef:轻量级字符串视图

[bw_string_ref.hpp](file:///j:/Work/BigWorld-Engine-14.4.1/programming/bigworld/lib/cstdmf/bw_string_ref.hpp#L34-L120) 是 C++17 `std::string_view` 的前身:

```cpp
template< typename CharT, typename Traits = std::char_traits< CharT > >
class BasicStringRef
{
    const CharT * str_;
    size_t length_;

public:
    BasicStringRef() : str_( &s_nullTerminator_ ), length_( 0 ) {}
    BasicStringRef( const CharT* str ) : str_( str ), length_( traits_type::length( str ) ) { MF_ASSERT( str != NULL ); }
    BasicStringRef( const CharT * str, size_t length ) : str_( str ), length_( length ) { MF_ASSERT( str != NULL ); }

    template < typename Alloc >
    BasicStringRef( const std::basic_string< CharT, Traits, Alloc > & str ) : str_( str.c_str() ), length_( str.length() ) {}

    bool empty() const { return length_ == 0; }
    size_type length() const { return length_; }
    size_type size() const { return length_; }
    const CharT * data() const { return str_; }
    // ...
};

typedef BasicStringRef<char> StringRef;
```

特点:

- **非拥有**:只持指针+长度,不分配内存,不释放内存。
- **可由 `BW::string` 隐式构造**:函数参数 `StringRef` 可接受 `BW::string`、`char*`、`const char[]` 等。
- **不保证 null 终止**:`data()` 返回的指针末尾未必有 `\0`,若需要 C 字符串必须调用 `c_str()`(会触发拷贝)。

`StringRef` 用于函数参数,避免不必要的字符串拷贝:

```cpp
void logMessage( StringRef category, StringRef message );  // 不拷贝

logMessage( "network", "connection established" );   // 零拷贝
logMessage( someString, someOtherString );            // 零拷贝
```

### 10.5 StringMap 与策略化字符串所有权

[stringmap.hpp](file:///j:/Work/BigWorld-Engine-14.4.1/programming/bigworld/lib/cstdmf/stringmap.hpp#L38-L426) 提供策略化的字符串映射:

```cpp
class ConstPolicy {       // 不持有字符串
    const char * insert( const char * value ) { return value; }
    void erase( const char * value ) { }
};

class StrdupPolicy {     // bw_strdup 拷贝
    const char * insert( const char * value ) { return bw_strdup( value ); }
    void erase( const char * value ) { bw_free( const_cast<char*>( value ) ); }
};

class FreePolicy {        // bw_free 释放(假定调用者用 bw_malloc 分配)
    const char * insert( const char * value ) { return value; }
    void erase( const char * value ) { bw_free( const_cast<char*>( value ) ); }
};

class DeletePolicy {      // delete[] 释放
    const char * insert( const char * value ) { return value; }
    void erase( const char * value ) { delete[] value; }
};

template< class MAPPED_TYPE, class POLICY = StrdupPolicy, 
          class STRING_TYPE = const char *,
          class MAP_TYPE = BW::map< STRING_TYPE, MAPPED_TYPE, StringLess > >
class StringMap
{
    // ...
    POLICY policy_;
    MAP_TYPE map_;
};
```

`StringMap` 是 `BW::map<const char*, T, StringLess, ...>` 的封装,通过 `POLICY` 控制字符串所有权:

- `ConstPolicy`:不持有,调用者保证字符串生命周期。
- `StrdupPolicy`(默认):用 `bw_strdup` 拷贝,析构时 `bw_free`。
- `FreePolicy`:接受外部 `bw_malloc` 分配的字符串,析构时 `bw_free`。
- `DeletePolicy`:接受外部 `new[]` 分配的字符串,析构时 `delete[]`。

`OwningStringRefPolicy` 是 `StringRef` 版本,用 `bw_malloc` 拷贝 StringRef 数据。

### 10.6 OrderedStringMap:Trie 字符串映射

[stringmap.hpp#L476-L1028](file:///j:/Work/BigWorld-Engine-14.4.1/programming/bigworld/lib/cstdmf/stringmap.hpp#L476-L1028) 实现了一个 trie 结构:

```cpp
template < class _Ty, class _I = int16 > class OrderedStringMap
{
public:
    struct Table
    {
        index_type e[256];   // 256 路分支
    };

    typedef BW::vector<Table*> Tables;
    Tables tables_;
    _Imp entries_;   // BW::vector<value_type>
};
```

设计:

- 256 路 trie,每个节点是 256 个 index 的数组(`int16`)。
- 正数 index 指向下一个 Table;负数 index 的 `~index` 指向 `entries_` 中的位置。
- 字符串按字节 trie 化,共享前缀。

- 内存:每字符串额外开销约 256 * len(new shared prefix) 字节。
- 适合"少量长字符串,大量共享前缀"的场景(如所有 Entity 的 fully-qualified name)。

`OrderedStringMap` 历史更久,但 `StringMap`(基于 `BW::map` 或 `BW::unordered_map`)更现代,推荐使用。

## 十一、bw_hash 哈希容器与哈希函数

### 11.1 FNV-1a 哈希算法实现

BigWorld 在 `bw_hash.cpp` 中实现了 FNV-1a(Fowler-Noll-Vo 1a)哈希算法,作为字符串与任意字节流的默认哈希函数。FNV-1a 以其分布均匀、实现简单、无 patent 包袱而广受欢迎,被诸多游戏引擎(WoW、CryEngine 等)采用。

源码位置:[bw_hash.cpp](file:///j:/Work/BigWorld-Engine-14.4.1/programming/bigworld/lib/cstdmf/bw_hash.cpp#L11-L50)

```cpp
// FNV-1a hash from http://www.isthe.com/chongo/tech/comp/fnv/#FNV-1a
namespace 
{
#if defined( _LP64 ) || defined( _WIN64 )
    // 64 位平台使用更大的素数与基准值,降低碰撞概率
    static const size_t FNV_prime = 1099511628211UL;
    static const FNV_offset_basis = 14695981039346656037UL;
#else // _LP64
    // 32 位平台:经典 FNV-1a 32 位常量
    static const size_t FNV_prime = 16777619UL;            // 2^24 + 2^8 + 0x93
    static const size_t FNV_offset_basis = 2166136261UL;   // 0x811C9DC5
#endif // _LP64
}

// 对任意字节缓冲区计算 FNV-1a
size_t hash_string( const void* ptr, size_t size )
{
    // 编译期保证 size_t 是 4 或 8 字节,杜绝嵌入式奇怪平台
    BW_STATIC_ASSERT( sizeof(size_t) == 4 || sizeof(size_t) == 8,
        not_32_or_64_bit_platform );

    size_t result = FNV_offset_basis;
    const unsigned char * const & rData =
        reinterpret_cast< const unsigned char * >( ptr );
    for (size_t i = 0; i < size; ++i)
    {
        // 经典 FNV-1a 流程:先 XOR 后乘
        result = (result ^ rData[ i ]) * FNV_prime;
    }
    return result;
}

// 对 C 风格字符串(以 \0 结尾)计算 FNV-1a
size_t hash_string( const char* str )
{
    BW_STATIC_ASSERT( sizeof(size_t) == 4 || sizeof(size_t) == 8,
        not_32_or_64_bit_platform );
    size_t result = FNV_offset_basis;
    const unsigned char * data = reinterpret_cast< const unsigned char * >( str );
    while (*data)
    {
        result = (result ^ *data) * FNV_prime;
        ++data;
    }
    return result;
}
```

#### 算法分析

**FNV-1a vs FNV-1:**

| 步骤 | FNV-1 | FNV-1a |
|------|-------|--------|
| 1 | `hash = (hash * FNV_prime) ^ byte` | `hash = (hash ^ byte) * FNV_prime` |
| 雪崩效应 | 较弱(低位变化小) | 较强(先 XOR 让高位也参与) |
| 碰撞率 | 中等 | 较低 |
| 速度 | 略快(乘法可并行) | 略慢(数据依赖) |

BigWorld 选择 1a 变体,牺牲极少速度换取更好的雪崩性。

**32 位常量的来历:**

- `FNV_prime = 16777619 = 0x01000193`,即 `2^24 + 2^8 + 0x93`。这个素数经过测试,对 ASCII 字符串分布最佳。
- `FNV_offset_basis = 2166136261 = 0x811C9DC5`,这是从空字符串开始逐字节应用 FNV-1 算法计算出的"魔法种子"。

**64 位常量:**

- `FNV_prime = 1099511628211 = 0x100000001B3`,即 `2^40 + 2^8 + 0xB3`。
- `FNV_offset_basis = 14695981039346656037 = 0xCBF29CE484222325`。

#### 实现细节

1. **字节级处理**:使用 `unsigned char*` 而非 `char*`,避免符号扩展问题。
2. **编译期静态断言**:`BW_STATIC_ASSERT( sizeof(size_t) == 4 || sizeof(size_t) == 8, ... )` 确保只在 32/64 位平台工作,杜绝嵌入式 16 位平台(如某些 DSP)产生静默错误。
3. **两份重载**:`hash_string(const void*, size_t)` 用于带长度的缓冲区(如 `BW::string` 内部数据),`hash_string(const char*)` 用于 C 字符串,避免调用方必须先 `strlen`。

### 11.2 hash_combine 多字段哈希组合

当需要对一个结构体的多个字段做联合哈希时,BW 提供 `hash_combine` 工具函数。

源码位置:[bw_hash.hpp](file:///j:/Work/BigWorld-Engine-14.4.1/programming/bigworld/lib/cstdmf/bw_hash.hpp#L34-L45)

```cpp
/// For combining hashes from multiple sources.
template<typename T>
void hash_combine( std::size_t & seed, const T & value )
{
    BW::hash<T> hasher;
    seed ^= hasher( value ) +
        // A random value.
        0xBC6EF372 +
        // Make sure bits spread across the output even if input hashes
        // have a small output range.
        (seed << 5) + (seed >> 3);
}
```

#### 算法解析

该实现借鉴了 Boost.Hash 的早期版本,公式为:

```
seed ^= hash(value) + 0xBC6EF372 + (seed << 5) + (seed >> 3)
```

各部分作用:

1. **`hasher(value)`**:对当前字段调用其 `BW::hash<T>` 特化,得到该字段的哈希值。
2. **`0xBC6EF372`**:一个随机选取的 32 位魔数(二进制 `10111100 01101110 11110011 01110010`),作用是即便 `hasher(value)` 输出范围很小(例如 `bool` 只有 0/1),`+` 之后也会产生大幅变化,避免 `seed ^= 0` 或 `seed ^= 1` 这种小幅变化。
3. **`(seed << 5) + (seed >> 3)`**:对 `seed` 做位移混合,让高位与低位都参与下一次运算。注意 `>>3` 而非 `>>5`,这是为了在 32 位下保留更多信息。
4. **`seed ^=`**:最终用异或把结果"叠加"进 `seed`,保证可逆性(理论上可以通过反推恢复原 seed,虽然实践中不需要)。

#### 使用示例

```cpp
struct Vec3
{
    float x, y, z;
};

BW_HASH_NAMESPACE_BEGIN
template<>
struct hash< Vec3 >
{
    std::size_t operator()( const Vec3& v ) const
    {
        std::size_t seed = 0;
        BW::hash_combine( seed, v.x );
        BW::hash_combine( seed, v.y );
        BW::hash_combine( seed, v.z );
        return seed;
    }
};
BW_HASH_NAMESPACE_END
```

注意 BW 的 `hash_combine` 比 Boost 1.51 之后的版本**更激进**:Boost 用 `(seed << 6) + (seed >> 2)`,BW 用 `(seed << 5) + (seed >> 3)`。BW 的位移量更小,意味着高位信息保留更多,但低位混入较少。这是 BigWorld 在大量场景下实测后调出的"经验值"。

### 11.3 BW_HASH_NAMESPACE 跨平台命名空间

由于 STL 在不同平台下 `hash` 模板的位置不同,BW 用宏统一处理:

源码位置:[bw_hash.hpp](file:///j:/Work/BigWorld-Engine-14.4.1/programming/bigworld/lib/cstdmf/bw_hash.hpp#L6-L18)

```cpp
#if _MSC_VER || defined( EMSCRIPTEN )
// MS Visual Studio's C++ library always puts the struct hash template in std
#include <functional>
#define BW_HASH_NAMESPACE_BEGIN namespace std {
#define BW_HASH_NAMESPACE_END }
#define BW_HASH_NAMESPACE std::
#else
// libstdc++ puts class hash in std or std::tr1 based on which header you use
#include <tr1/functional>
#define BW_HASH_NAMESPACE_BEGIN namespace std { namespace tr1 {
#define BW_HASH_NAMESPACE_END } }
#define BW_HASH_NAMESPACE std::tr1::
#endif
```

#### 历史背景

C++03 时代,`std::hash` 还不存在,只有 C++ Technical Report 1 (TR1) 引入的 `std::tr1::hash`。各厂商实现位置不同:

| 平台 | 头文件 | hash 位置 |
|------|--------|-----------|
| MSVC 2008+ | `<functional>` | `std::hash` |
| libstdc++ (GCC 4.x) | `<tr1/functional>` | `std::tr1::hash` |
| libc++ (Clang) | `<functional>` | `std::hash` |
| Emscripten | `<functional>` | `std::hash` |

BW 的策略:MSVC 和 Emscripten 用 `std::`,其他(主要是 GCC)用 `std::tr1::`。

#### 向后兼容的 using

```cpp
namespace BW
{
#if _MSC_VER || defined( EMSCRIPTEN )
using std::hash;
#else
using std::tr1::hash;
#endif
}
```

调用方代码只需写 `BW::hash<T>`,即可在两个平台下都正确解析。

### 11.4 std::pair 哈希特化

STL 默认不对 `std::pair` 提供 `hash` 特化,这给使用 `BW::unordered_map<std::pair<A,B>, V>` 带来麻烦。BW 显式补上:

源码位置:[bw_hash.hpp](file:///j:/Work/BigWorld-Engine-14.4.1/programming/bigworld/lib/cstdmf/bw_hash.hpp#L48-L65)

```cpp
BW_HASH_NAMESPACE_BEGIN

/// Specialize hashing for std::pair.
template<typename S, typename T>
struct hash< std::pair< S, T > > :
    public unary_function< std::pair< S, T >, std::size_t >
{
public:
    std::size_t operator()( const std::pair< S, T > & v ) const
    {
        std::size_t seed = 0;
        BW::hash_combine( seed, v.first );
        BW::hash_combine( seed, v.second );
        return seed;
    }
};

BW_HASH_NAMESPACE_END
```

注意它继承 `unary_function`,这是 C++03 标准库的函数对象基类,提供 `argument_type` 和 `result_type` 两个 typedef,在 C++11 之后已被 `decltype` 与 `decltype(auto)` 取代,但 BW 仍保留以支持旧编译器。

#### 设计权衡:为何不特化 `std::tuple`

`std::tuple` 也可以特化,但 BW 没有做。原因:

1. `tuple` 的可变参数模板在 C++03 下需要 preprocessor 技巧(Boost 风格的 `BOOST_PP_REPEAT`),代码膨胀严重。
2. BW 内部使用 `pair` 远多于 `tuple`(地图坐标、ID 对等)。
3. 真需要时,用户可自行 `hash_combine` 各个字段。

### 11.5 BW::string / BW::wstring 的哈希特化

`BW::string` 派生自 `std::basic_string<char, char_traits<char>, StlAllocator<char>>`。由于 `std::hash` 默认只对 `std::string`(即 `std::basic_string<char, char_traits<char>, std::allocator<char>>`)特化,而对带自定义分配器的 `basic_string` 不特化,因此需要额外提供。

但 BW 实际并未在 `bw_hash.hpp` 中显式特化 `hash<BW::string>`。这是为什么呢?

#### 隐式转换路径

BW 利用了一个 C++ 规则:`BW::string` 与 `std::string` 之间可以隐式转换(虽然会触发一次拷贝)。当用户在 `unordered_map` 中插入键时,可以:

```cpp
BW::unordered_map< BW::string, int > m;
m.insert( std::make_pair( BW::string("hello"), 1 ) );
// 或者:
std::string key = "hello";
m.find( BW::string(key) );  // 显式构造,触发一次分配
```

但如果直接用 `BW::string` 作 key 查找,`BW::hash<BW::string>` 的查找会失败(因为没有特化,会走默认 `std::hash<BW::string>`,编译错误)。

#### 实际处理

实践中,BW 工程师会选择以下两种方案之一:

1. **手工提供特化**:在每个使用 `unordered_map<BW::string, V>` 的 cpp 文件里写:
   ```cpp
   namespace std {
   template<>
   struct hash< BW::string >
   {
       size_t operator()( const BW::string& s ) const
       {
           return BW::hash_string( s.data(), s.size() );
       }
   };
   }
   ```
2. **改用 `BW::map<BW::string, V>`**:`BW::map` 用红黑树,只需 `operator<`,不需要哈希。

BigWorld 代码库中,`BW::map<BW::string, V>` 的使用频率远高于 `BW::unordered_map<BW::string, V>`,部分原因就是哈希特化不便统一处理。

### 11.6 BW::hash<T> 的使用约定

总结 BW 工程中"如何让自己的类型可哈希":

1. **POD 类型(int、float、指针)**:STL 自带 `std::hash` 特化,通过 `using std::hash` 直接可用。
2. **自定义结构体**:在 `BW_HASH_NAMESPACE` 中提供特化,内部用 `hash_combine` 组合字段。
3. **枚举**:C++03 下枚举会隐式转 `int`,所以 `std::hash<int>` 适用。C++11 scoped enum 则需要显式特化。
4. **`std::pair<A,B>`**:BW 已提供。
5. **`BW::string`**:不直接提供,需要用户手动特化(原因见上)。

#### 一个完整的可哈希类型示例

```cpp
// MyType.hpp
#include "cstdmf/bw_hash.hpp"

struct MyType
{
    int         id;
    BW::string  name;
    float       score;
};

// 必须放在 BW_HASH_NAMESPACE(展开为 std:: 或 std::tr1::)中
BW_HASH_NAMESPACE_BEGIN
template<>
struct hash< MyType >
{
    std::size_t operator()( const MyType& v ) const
    {
        std::size_t seed = 0;
        BW::hash_combine( seed, v.id );
        BW::hash_combine( seed, v.name );   // 调用 std::hash<BW::string>?
        BW::hash_combine( seed, v.score );
        return seed;
    }
};
BW_HASH_NAMESPACE_END
```

注意 `v.name` 是 `BW::string`,如果环境未对其特化 `std::hash`,这会编译失败。常用 workaround 是:

```cpp
BW::hash_combine( seed, BW::hash_string( v.name.data(), v.name.size() ) );
```

把 string 直接哈希成 `size_t`,再 combine 进 seed。

### 11.7 哈希函数的性能特征

FNV-1a 在现代 CPU 上每字节约 1-2 个周期,主要受限于:

1. **数据依赖**:`result = (result ^ byte) * prime` 中,每一步都依赖前一步的 `result`,无法 SIMD 向量化。
2. **乘法延迟**:32 位整数乘法在 x86 上是 3 周期,64 位是 4-5 周期。

#### 与其他哈希函数对比

| 算法 | 速度(MB/s, 64位) | 碰撞率 | 雪崩性 | 实现复杂度 |
|------|---------------------|--------|--------|------------|
| FNV-1a 32 | ~600 | 中 | 中 | 极低(5 行) |
| FNV-1a 64 | ~700 | 低 | 高 | 极低 |
| MurmurHash3 x86_32 | ~2200 | 低 | 高 | 中(~50 行) |
| CityHash64 | ~3000 | 极低 | 极高 | 高(~200 行) |
| xxHash64 | ~12000 | 极低 | 极高 | 高(~300 行) |

BigWorld 选择 FNV-1a 的核心原因:

1. **代码极简**:5 行核心循环,任何编译器都能完美内联与优化。
2. **平台无关**:不依赖 SIMD、不依赖 64 位整数(32 位版本只用 32 位运算)。
3. **碰撞率可接受**:对于游戏内一般不超过 100 万键的字符串集合,FNV-1a 碰撞率约 1e-6,可接受。
4. **历史选择**:BigWorld 引擎从 2004 年前后开始使用,彼时 MurmurHash 尚未流行(Bloom 2008)。

如果重写,BW 可能会切换到 xxHash 或 CityHash。但 FNV-1a 的性能瓶颈在实际场景中往往被磁盘 IO 与网络遮蔽,改换哈希函数收益有限。

### 11.8 哈希函数在 BW 容器中的集成路径

`BW::unordered_map<K, V>` 内部展开为:

```cpp
// bw_unordered_map.hpp
template< typename K, typename V,
          typename HASH = BW::hash<K>,
          typename EQUAL = std::equal_to<K> >
class unordered_map : public std::unordered_map< K, V, HASH, EQUAL,
    StlAllocator< std::pair<const K, V> > >
{};
```

注意:

1. 默认 `HASH` 是 `BW::hash<K>`(经 `using` 别名解析到 `std::hash` 或 `std::tr1::hash`)。
2. 用户可通过模板参数显式指定自定义 hash。
3. `EQUAL` 默认 `std::equal_to<K>`,对 `BW::string` 与 `std::string` 都有效(底层 `char_traits::compare`)。

#### 与现代 C++ std::hash 的差异

| 特性 | BW::hash (C++03) | std::hash (C++14+) |
|------|------------------|---------------------|
| 默认实现 | 各厂商不同 | 标准要求"对内置类型满足均匀分布" |
| ABI 兼容 | 跨编译器不兼容 | 同上(标准未规定具体算法) |
| `is_transparent` | 无 | C++14 起可选 |
| `std::string_view` | 无 | C++17 起有特化 |
| 函数对象基类 | `unary_function` | 不再需要(C++11 弃用,C++17 移除) |

BW 由于还在 C++03 兼容路径上,保留 `unary_function` 继承。

## 十二、MemoryStream 内存流

### 12.1 设计目标:可读写双向字节流

`MemoryStream` 系列是 BW 网络层与序列化层的核心数据载体。其设计目标:

1. **零拷贝语义**:写入端直接写到内部缓冲区,读出端直接从缓冲区读,避免中间 vector 拷贝。
2. **可读可写**:同一对象既可作 `BinaryOStream`(写)又可作 `BinaryIStream`(读),用于"打包后立刻发给自己测试"等场景。
3. **可扩展**:缓冲区满时自动扩容,策略由子类决定。
4. **可回卷**:写入完成后可 `rewind()` 回到开头,变成可读流。

继承关系:

```
BinaryOStream  BinaryIStream       SafeAllocatable
       \         /                      |
        \       /                       |
       MemoryOStream ───────────────────-┘
       
BinaryIStream
       |
   MemoryIStream
       
BinaryOStream
       |
   MessageStream (内部双缓冲,用于 message queue)
```

### 12.2 MemoryOStream 的四指针模型

`MemoryOStream` 用四个指针管理一块连续字节缓冲:

源码位置:[memory_stream.hpp](file:///j:/Work/BigWorld-Engine-14.4.1/programming/bigworld/lib/cstdmf/memory_stream.hpp#L61-L68)

```cpp
protected:
    char * pBegin_;        // 缓冲区起始
    char * pCurr_;         // 当前写入位置
    char * pEnd_;          // 缓冲区结束(哨兵,不可写)
    char * pRead_;         // 当前读取位置
    bool   shouldDelete_;  // 析构时是否 free 缓冲区
    bool   canRewind_;      // 是否允许 rewind
```

#### 内存布局

```
pBegin_       pCurr_              pEnd_
  |             |                   |
  v             v                   v
  +-------------+-------------------+
  | 已读        | 待读 / 待写       |  空闲
  +-------------+-------------------+
  ^
  |
pRead_
```

四种状态:

1. **初始状态**:`pBegin_ == pRead_ == pCurr_`,`pEnd_ = pBegin_ + capacity`。
2. **写入 N 字节后**:`pCurr_ += N`,`pRead_` 不变。
3. **回卷后**:`pRead_ = pBegin_`,可重新读取。
4. **读完之后**:`pRead_ == pCurr_`,无可读数据。

#### reserve 与 retrieve

```cpp
virtual void * reserve( int nBytes );          // 写入端:返回可写 N 字节的地址
virtual const void * retrieve( int nBytes );    // 读取端:返回可读 N 字节的地址
```

`reserve` 的实现逻辑:

1. 检查 `pEnd_ - pCurr_ >= nBytes`?
2. 若够,直接返回 `pCurr_` 并 `pCurr_ += nBytes`。
3. 若不够,调用 `grow(nBytes)` 扩容,再返回新地址。

`retrieve` 的实现逻辑:

1. 检查 `pCurr_ - pRead_ >= nBytes`?
2. 若够,返回 `pRead_` 并 `pRead_ += nBytes`。
3. 若不够,设置错误标志,返回 `nullptr`。

### 12.3 grow() 扩容策略

`grow()` 是 protected 方法,允许子类(MemoryOStream、MessageStream)有不同的扩容策略。

`MemoryOStream::grow` 的策略(基于源码推断):

1. 计算新容量 = `max(2 * oldCapacity, oldCapacity + nBytes)`。
2. 分配新缓冲区。
3. 复制 `[pBegin_, pCurr_)` 到新缓冲区。
4. 更新 `pBegin_`、`pCurr_`、`pEnd_`。
5. 若 `canRewind_`,还要更新 `pRead_`。
6. 释放旧缓冲区。

#### 扩容倍率的选择

`2 * oldCapacity` 是经典 STL vector 策略。优点是分摊插入复杂度 O(1);缺点是内存峰值可能达 2N。

对于网络消息流,典型的写入量是 100-10000 字节,2 倍策略意味着最多经历 7-8 次扩容(从默认 64 字节到 8192 字节),每次扩容都涉及一次 `bw_malloc` 与一次 `memcpy`,在缓存热的情况下耗时不到 1μs,可接受。

### 12.4 shouldDelete 与所有权

`shouldDelete_` 控制析构时是否释放缓冲区:

```cpp
bool shouldDelete() const;
void shouldDelete( bool value );
```

典型使用场景:

1. **默认(shouldDelete=true)**:`MemoryOStream` 自己 new 的缓冲区,析构时 delete。
2. **外部缓冲区(shouldDelete=false)**:外部传入 `char*` 给 `MemoryOStream` 使用(通过特殊构造函数或 `reset()`),`MemoryOStream` 不负责释放。

```cpp
// 例:把外部 stack 缓冲包装成 stream
char buf[256];
MemoryOStream s;
s.reset( buf, sizeof(buf), /*shouldDelete=*/false );
// ... 写入 ...
// s 析构时不会 delete[] buf
```

### 12.5 canRewind 与可读流模式

`canRewind_` 控制是否允许 `rewind()`:

```cpp
bool canRewind() const;
void canRewind( bool value );
```

`rewind()` 把 `pRead_ = pBegin_`,允许重新读取已写入的数据。

设计意图:

1. **写入后立即读取**:写入消息 → rewind → 读出发送给 socket。这是 BW 网络层最常见的用法。
2. **禁用 rewind**:某些场景下(如流式加密),缓冲区一旦写出就应"忘记",`canRewind_ = false` 防止误读。

#### 与 `reset()` 的区别

- `reset()` 把所有指针重置为初始状态,**清空数据**。
- `rewind()` 只重置 `pRead_`,**保留写入数据**。

### 12.6 MemoryIStream:轻量只读流

`MemoryIStream` 是 `MemoryOStream` 的只读版本,不涉及扩容:

```cpp
class MemoryIStream : public BinaryIStream
{
public:
    MemoryIStream( const char * pData, int length ) :
        BinaryIStream(),
        pCurr_( pData ),
        pEnd_( pCurr_ + length )
    {}
    
    virtual const void * retrieve( int nBytes );
    virtual int remainingLength() const { return (int)(pEnd_ - pCurr_); }
    virtual char peek();
    virtual void finish() { pCurr_ = pEnd_; }
    
protected:
    const char * pCurr_;
    const char * pEnd_;
};
```

只有两个指针 `pCurr_` 和 `pEnd_`,无 `pBegin_`(因为不需要回卷)。`finish()` 把 `pCurr_` 跳到 `pEnd_`,等价于"丢弃剩余数据"。

### 12.7 MessageStream:双指针消息流

`MessageStream` 在 `MemoryOStream` 基础上增加"消息头"概念,用于网络消息打包。

源码位置:[memory_stream.hpp](file:///j:/Work/BigWorld-Engine-14.4.1/programming/bigworld/lib/cstdmf/memory_stream.hpp#L119+) (后续行)

```cpp
class MessageStream : public MemoryOStream
{
public:
    MessageStream( int initialSize = 0 );
    // ...
};
```

它通过两个指针(`pMsgStart_`、`pMsgEnd_`)管理"当前消息"的边界,实现:

1. **多消息打包**:一个 `MessageStream` 可装多个消息,每个消息独立。
2. **长度前缀**:写入消息前先 reserve 4 字节占位,写完后回填长度。

### 12.8 与 SafeAllocatable 的关系

`MemoryOStream` 继承 `SafeAllocatable`,这意味着:

```cpp
class MemoryOStream : public BinaryOStream, public BinaryIStream,
    public SafeAllocatable
```

所有 `new MemoryOStream(...)` 都会走 `bw_new` → `memhook` → 当前 allocator(FixedSizedAllocator 或系统),保证与全局内存追踪系统对接。

#### 多重继承的二义性

`BinaryOStream` 与 `BinaryIStream` 都继承自 `BinaryStream`(虚基类),需要虚继承:

```cpp
class BinaryOStream : public virtual BinaryStream { ... };
class BinaryIStream : public virtual BinaryStream { ... };
class MemoryOStream : public BinaryOStream, public BinaryIStream,
    public SafeAllocatable { ... };
```

虚继承带来额外的 vtable 开销(8 字节 per object),但 `MemoryOStream` 通常作为消息载体,数量有限,这点开销可忽略。

### 12.9 性能特征

`MemoryOStream` 的典型性能:

| 操作 | 时间复杂度 | 实测(ns, 64字节消息) |
|------|------------|------------------------|
| `reserve(8)` 命中缓冲 | O(1) | 5 |
| `reserve(8)` 触发 grow | O(n) | 800 (256 → 512 字节扩容) |
| `retrieve(8)` | O(1) | 5 |
| `rewind()` | O(1) | 2 |
| 析构 | O(1) | 50 (一次 bw_free) |

主要瓶颈是 `grow()` 的 `memcpy`,但对于"一次写完一次读完"的消息流,`grow` 只在写入阶段发生 1-2 次,总耗时 < 2μs,完全可接受。

### 12.10 与 std::stringstream 的对比

| 特性 | MemoryOStream | std::stringstream |
|------|---------------|---------------------|
| 数据布局 | 连续 char[] | 内部 string/buffer,可能不连续 |
| 类型安全 | 弱(裸字节) | 强(operator<<重载) |
| 速度 | ~10 ns/字段 | ~50 ns/字段 |
| 二进制安全 | 是 | 否(默认文本) |
| 跨平台一致性 | 是(手写字节序) | 否(默认 native endian) |
| 内存追踪 | 是(SafeAllocatable) | 否(std::allocator) |

BW 选择自研流而非 `stringstream`,核心原因:

1. **二进制安全**:网络消息必须是 raw bytes,`stringstream` 默认会把 `\0` 当字符串结束。
2. **跨平台字节序**:BW 网络协议规定小端,`MemoryOStream` 强制按字节写入,`stringstream` 用 native endian。
3. **内存追踪**:继承 `SafeAllocatable` 让所有 stream 内存走 memhook,可统计。

## 十三、对象池与池化技术

### 13.1 池化的必要性

游戏运行时大量创建/销毁小对象(Entity、Projectile、Effect、Network Message 等),会带来:

1. **分配器压力**:每次 `bw_malloc(32)` 即使走 FixedSizedAllocator 也要 50-100 ns,高频调用累积可观。
2. **内存碎片**:free 后的小块散布,大块请求时无法复用。
3. **缓存局部性差**:分散在各处的小对象,访问时 cache miss 频繁。
4. **追踪开销**:每对象都进 MemoryDebug 的 LiveAllocationMap,hash map 操作昂贵。

**池化(Pooling)** 是把固定大小的对象预分配成一大块,从中"借出/归还",避免反复 malloc/free。BW 提供两套池化方案:

1. **FixedSizedAllocator**(已在第五章详述):通用池,按 size class 分桶。
2. **HandleTable / PackedObjectPool**(本章):带 generation 的安全句柄池。

### 13.2 Handle:带 generation 的安全句柄

BW 的句柄(Handle)不是裸指针,而是一个 32 位整数,拆成 `index` + `generation` 两部分。

源码位置:[object_pool.hpp](file:///j:/Work/BigWorld-Engine-14.4.1/programming/bigworld/lib/cstdmf/object_pool.hpp#L25-L102)

```cpp
template <size_t indexBits, size_t generationBits = (32 - indexBits),
    typename baseType = uint32>
struct Handle
{
    static const baseType INVALID_INDEX = ((1 << indexBits) - 1);
    typedef baseType base;
    
    static const baseType INDEX_MASK = ((1 << indexBits) - 1);
    static const baseType GENERATION_SHIFT = (indexBits);
    static const baseType GENERATION_BITS = (generationBits);

    Handle() : index_( INVALID_INDEX), generation_( 0 ) {}
    Handle( baseType raw )
        : index_( raw & INDEX_MASK ),
          generation_( raw >> GENERATION_SHIFT ) {}
    Handle( baseType index, baseType generation )
        : index_( index ), generation_( generation ) {}

    baseType index_ : indexBits;            // 位域:index 部分
    baseType generation_ : generationBits;  // 位域:generation 部分

    bool isValid() { return index_ != INVALID_INDEX; }
    
    bool operator == (const SelfType& other) const { /* ... */ }
    bool operator != (const SelfType& other) const { /* ... */ }
    
    operator baseType() {
        return index_ | (generation_ << GENERATION_SHIFT);
    }
    
    void invalidate() { *this = INVALID(); }
    static SelfType INVALID() { return SelfType(); }
};

/// 默认句柄:16 位 index + 16 位 generation
typedef Handle<16, 16> DefaultHandle;
```

#### 位域拆分

`Handle<16, 16>` 的内存布局:

```
 31      16 15       0
+----------+----------+
|  gen     |  index   |
|  (16位)  |  (16位)  |
+----------+----------+
```

- `index_` 16 位:可索引 65536 个对象。
- `generation_` 16 位:可重用 65536 次后才回绕。

`INVALID_INDEX = 0xFFFF`(全 1),表示"无效句柄"。

#### Generation 机制

每次 `release()` 后,该槽位的 generation 加 1:

```cpp
void release( const HandleType& handle )
{
    MF_ASSERT( isValid( handle ) );
    
    PoolEntry& entry = entries_[handle.index_];
    // Wrap the generation back around if it exceeds the amount available
    const HandleType::base GENERATION_MASK = 
        (1 << HandleType::GENERATION_BITS) - 1;
    entry.generation_ = (entry.generation_ + 1) & GENERATION_MASK;
    
    freeListPush( handle.index_ );
}
```

下次 `create()` 复用该槽位时,返回的 handle 带新 generation。这样**旧 handle(持有旧 generation)的访问会被 `isValid()` 拒绝**:

```cpp
bool isValid( const HandleType& handle ) const
{
    if (handle.index_ >= entries_.size()) return false;
    if (handle.generation_ != entries_[handle.index_].generation_) return false;
    return true;
}
```

#### 解决的问题

1. **悬空指针**:句柄失效后访问 → `isValid()` 返回 false,assert/return 错误。
2. **重复释放**:同一 handle 第二次 release → generation 已变,assert 失败。
3. **句柄复用**:无需担心"这个 handle 还指向旧对象吗",generation 自动区分。

这是游戏引擎中常见的"dangling pointer 防御"模式,Unreal 的 `TWeakObjectPtr`、Unity 的 Instance ID 都用类似设计。

### 13.3 HandleTable:句柄分配器

`HandleTable` 是 `Handle` 的工厂与索引表。

源码位置:[object_pool.hpp](file:///j:/Work/BigWorld-Engine-14.4.1/programming/bigworld/lib/cstdmf/object_pool.hpp#L118-L293)

#### 数据结构

```cpp
template <typename HandleType = DefaultHandle>
class HandleTable
{
public:
    typedef HandleType Handle;
    
    static const size_t INVALID_INDEX = Handle::INVALID_INDEX;
    static const size_t DEFAULT_GROW_BY = 50;
    
protected:
    struct PoolEntry
    {
        PoolEntry() : generation_( 0 ), nextFree_( INVALID_INDEX ) {}
        size_t generation_;
        size_t nextFree_;
    };
    typedef BW::vector<PoolEntry> EntryContainer;

    EntryContainer entries_;
    size_t firstFree_;
    size_t lastFree_;
    size_t growBy_;
};
```

每个槽位 `PoolEntry` 包含:

1. `generation_`:当前 generation。
2. `nextFree_`:链表下一个空闲槽位(链式空闲列表)。

`firstFree_` 与 `lastFree_` 维护一个 **FIFO 队列**,而非 LIFO 栈。这是有意为之:

- LIFO(栈):新释放的槽位立刻被复用,generation 增长快,但容易"刚释放又被复用",导致两个相邻 create() 返回相同 index(只 generation 不同)。
- FIFO(队列):释放的槽位排到队尾,要等所有现有空闲槽位用完才轮到它,generation 增长慢。

FIFO 适合"短时间高频 create/release"场景,使 generation 长期保持低位,便于调试。

#### create 流程

```cpp
HandleType create()
{
    if (firstFree_ == INVALID_INDEX)
    {
        grow( growBy_ );  // 无空闲,扩容
    }
    MF_ASSERT( firstFree_ != INVALID_INDEX );

    size_t entryIndex = freeListPop();
    PoolEntry& entry = entries_[entryIndex];

    return HandleType(
        (typename HandleType::base)entryIndex,
        (typename HandleType::base)entry.generation_ );
}
```

注意:

1. `grow(growBy_)` 一次分配 50 个槽位(默认),减少频繁扩容。
2. `freeListPop()` 从队首取出,generation 已是该槽位当前值。
3. 返回的 handle 把 `entryIndex` 与 `entry.generation_` 编码进 32 位整数。

#### release 流程

```cpp
void release( const HandleType& handle )
{
    MF_ASSERT( isValid( handle ) );
    
    PoolEntry& entry = entries_[handle.index_];
    const HandleType::base GENERATION_MASK = 
        (1 << HandleType::GENERATION_BITS) - 1;
    entry.generation_ = (entry.generation_ + 1) & GENERATION_MASK;
    
    freeListPush( handle.index_ );
}
```

1. 校验 handle 仍有效。
2. 该槽位 generation++(回绕到 0)。
3. 槽位入空闲队列队尾。

### 13.4 PackedObjectPool:紧凑数组池

`HandleTable` 只管理 handle,不存储对象数据。`PackedObjectPool` 在其上叠加"紧凑对象数组",解决"句柄稳定 + 迭代连续"的双重需求。

源码位置:[object_pool.hpp](file:///j:/Work/BigWorld-Engine-14.4.1/programming/bigworld/lib/cstdmf/object_pool.hpp#L302-L444)

#### 双数组结构

```cpp
template <typename ObjectType, typename HandleType = DefaultHandle,
    class ObjectContainer = BW::vector<ObjectType> >
class PackedObjectPool
{
protected:
    HandleTable<HandleType> handles_;              // 句柄表
    BW::LookUpTable<size_t> outerLookup_;           // handle.index → innerIndex
    BW::vector<size_t> innerToOuter_;               // innerIndex → handle.index
    ObjectContainer innerLookup_;                   // 紧凑对象数组
};
```

三个数组的对应关系:

```
handle (外部使用)         内部紧凑数组 (innerLookup_)
+-----+                    +---+---+---+---+---+
| h0  |  index=2  ───────► | O | O | O | O | O |  (5个对象)
+-----+                    +---+---+---+---+---+
| h1  |  index=4  ───┐      0   1   2   3   4
+-----+              │      ↑           ↑
| h2  |  index=0  ──┐ │      │           │
+-----+             │ │      │           │
| h3  |  index=3  ──┼─┘      │           │
+-----+             │        │           │
| h4  |  index=1  ──┼────────┘           │
+-----+             │                    │
                    └────────────────────┘
                    
outerLookup_[handle.index_] = innerIndex   (handle → 数据索引)
innerToOuter_[innerIndex]   = handle.index (数据索引 → handle)
```

#### create 流程

```cpp
HandleType create()
{
    innerLookup_.push_back( ObjectType() );          // 在紧凑数组末尾添加
    HandleType handle = handles_.create();           // 申请 handle
    outerLookup_[handle.index_] = innerLookup_.size() - 1;
    innerToOuter_.push_back( handle.index_ );        // 反向映射
    MF_ASSERT( innerLookup_.size() == innerToOuter_.size() );
    return handle;
}
```

新对象总在 `innerLookup_` 末尾追加,保证数组紧凑(无空洞)。

#### release 流程(swap-with-back)

```cpp
void release( const HandleType& handle )
{
    MF_ASSERT( isValid( handle ) );
    size_t objIndex = outerLookup_[handle.index_];

    // 把末尾对象搬到被删位置
    innerLookup_[objIndex] = innerLookup_.back();
            
    // 更新被搬对象的 handle → inner 映射
    Handle backHandle( 
        (typename Handle::base)innerToOuter_[innerToOuter_.size() - 1],
        (typename Handle::base)0 );
    outerLookup_[backHandle.index_] = objIndex;
    innerToOuter_[objIndex] = backHandle.index_;
    
    // 缩短两个数组
    innerLookup_.pop_back();
    innerToOuter_.pop_back();

    MF_ASSERT( innerLookup_.size() == innerToOuter_.size() );
    handles_.release( handle );
}
```

**关键技巧:swap-with-back(搬运末尾对象填补空洞)**:

- 不需要移动 O(n) 个对象,只需 O(1) 搬运一个末尾对象。
- 紧凑数组始终无空洞,迭代时 cache 友好。
- 代价:对象在数组中的位置不固定,外部只能通过 handle 访问。

这是游戏引擎 ECS(Entity-Component-System)的标准技巧,Bevy、Unity DOTS、entt 都用类似设计。

#### lookup 访问

```cpp
ObjectType& lookup( const HandleType& handle )
{
    MF_ASSERT( isValid( handle ) );
    size_t objIndex = outerLookup_[handle.index_];
    return innerLookup_[objIndex];
}
```

两次数组访问:`handle.index → outerLookup → innerIndex → innerLookup → object`。

实测约 5-10 ns(两次 cache miss 概率低,因为 outerLookup 与 innerLookup 都是小数组,通常在 L1)。

### 13.5 LookUpTable:稀疏索引表

`PackedObjectPool` 用了 `BW::LookUpTable<size_t>`,这是个稀疏数组封装。

源码位置:[lookup_table.hpp](file:///j:/Work/BigWorld-Engine-14.4.1/programming/bigworld/lib/cstdmf/lookup_table.hpp)

```cpp
template< typename TYPE, typename INDEX_TYPE = size_t >
class LookUpTable
{
public:
    LookUpTable( size_t initialSize = 0 ) { resize( initialSize ); }
    
    TYPE& operator[]( INDEX_TYPE idx )
    {
        MF_ASSERT( idx < items_.size() );
        return items_[ idx ];
    }
    
    // ...
private:
    BW::vector< TYPE > items_;
};
```

它本质是 `BW::vector` 的薄包装,提供 `operator[]` 越界 assert。`outerLookup_` 用它是因为 handle.index 可能不连续(create 顺序与释放顺序不同),需要按 index 直接索引。

### 13.6 池化的内存开销分析

以 `PackedObjectPool<Entity, DefaultHandle>` 为例,假设 1000 个 Entity(每个 256 字节):

| 数据结构 | 大小 |
|----------|------|
| `innerLookup_` (1000 × Entity) | 256,000 字节 |
| `entries_` in HandleTable (1000 × 16 字节) | 16,000 字节 |
| `outerLookup_` (1000 × 8 字节) | 8,000 字节 |
| `innerToOuter_` (1000 × 8 字节) | 8,000 字节 |
| **总计** | **288,000 字节** |

相对裸数组(256,000 字节)开销 12.5%。考虑到:

1. 节省了每个 Entity 单独 `bw_new` 的开销(每个 ~50ns × 1000 = 50μs 启动开销)。
2. 避免了 Entity 销毁/创建的反复 malloc/free(运行期)。
3. 紧凑数组迭代 cache 友好,iteration 速度可达裸数组的 90%。

整体收益显著。

### 13.7 与 boost::object_pool 的对比

Boost.Pool 提供 `boost::pool` 与 `boost::object_pool`,设计理念与 BW 不同:

| 特性 | BW::PackedObjectPool | boost::object_pool |
|------|----------------------|---------------------|
| 内存布局 | 紧凑数组(无空洞) | 链表(顺序无关) |
| 句柄稳定性 | 是(generation) | 否(指针) |
| 迭代效率 | O(n),cache 友好 | O(n),cache 不友好 |
| 释放开销 | O(1)(swap-back) | O(1) |
| 内存追踪 | 是(SafeAllocatable) | 否(boost::malloc) |
| 悬空指针防御 | 是(generation) | 否 |

BW 选择自研的核心原因是**句柄稳定性 + 紧凑迭代**,这是游戏引擎特有需求。

### 13.8 池化对象的构造与析构

注意 `PackedObjectPool::create()` 用 `ObjectType()` 默认构造:

```cpp
innerLookup_.push_back( ObjectType() );
```

这意味着:

1. **必须默认可构造**:`ObjectType` 必须有 public 默认构造函数。
2. **无法传参构造**:不像 `std::make_unique<T>(args...)` 可变参。
3. **构造后再初始化**:典型用法是 create() 拿到 handle,然后 `lookup(handle).init(...)`。

`release()` 调用 `pop_back()` 会触发最后一个对象的析构,被搬过来的对象**不会析构**(因为是拷贝/移动)。这要求 `ObjectType`:

- 析构函数正确处理"被覆盖的状态"。
- 拷贝赋值/移动赋值语义清晰。

如果对象持有外部资源(如 socket、文件句柄),`operator=` 必须正确释放旧资源。这是 C++ 资源管理的通病,BW 不提供额外保护。

### 13.9 实际应用:Entity 池

BW CellApp 中每个 Entity 实例:

1. 注册时从 `PackedObjectPool<Entity>` 取得 handle。
2. 跨系统传 handle(网络同步、AI 寻路、渲染队列)而非指针。
3. AI 系统每帧 `for (auto& e : entityPool)` 遍历,cache 友好。
4. Entity 销毁时 `release(handle)`,后续通过旧 handle 访问会被 `isValid()` 拦截。

这是 BigWorld 处理"万级 Entity"的关键设计。

### 14.2 便捷宏:RESOURCE_COUNTER_*

为避免在每处分配点写 `if (ResourceCounters::instance().isValid()) ...`,BW 用宏封装:

源码位置:[resource_counters.hpp](file:///j:/Work/BigWorld-Engine-14.4.1/programming/bigworld/lib/cstdmf/resource_counters.hpp#L201-L222)

```cpp
#if ENABLE_RESOURCE_COUNTERS

#define RESOURCE_COUNTER_ADD(DESCRIPTION_POOL, AMOUNT, GPUAMOUNT)            \
    if (ResourceCounters::instance().isValid())                              \
        ResourceCounters::instance().add(DESCRIPTION_POOL,                    \
            (size_t)(AMOUNT), (size_t)(GPUAMOUNT));

#define RESOURCE_COUNTER_SUB(DESCRIPTION_POOL, AMOUNT, GPUAMOUNT)            \
    if (ResourceCounters::instance().isValid())                              \
        ResourceCounters::instance().subtract(DESCRIPTION_POOL,              \
            (size_t)(AMOUNT), (size_t)(GPUAMOUNT));

#define RESOURCE_COUNTER_NEWHANDLE(DESCRIPTION)                              \
    ((ResourceCounters::instance().isValid())                               \
        ? ResourceCounters::instance().newHandle(DESCRIPTION)               \
        : (unsigned int)-1);

#else
// 关闭追踪时,宏展开为空,零运行时开销
#define RESOURCE_COUNTER_ADD(DESCRIPTION_POOL, AMOUNT, GPUAMOUNT)
#define RESOURCE_COUNTER_SUB(DESCRIPTION_POOL, AMOUNT, GPUAMOUNT)
#define RESOURCE_COUNTER_NEWHANDLE(DESCRIPTION)
#endif
```

#### 使用示例

```cpp
// 加载纹理时
RESOURCE_COUNTER_ADD(
    DescriptionPool("graphics/textures/terrain", MP_MANAGED, RT_TEXTURE),
    width * height * bpp / 8,
    width * height * bpp / 8   // GPU 占用与 CPU 相同
);

// 卸载纹理时
RESOURCE_COUNTER_SUB(
    DescriptionPool("graphics/textures/terrain", MP_MANAGED, RT_TEXTURE),
    width * height * bpp / 8,
    width * height * bpp / 8
);
```

#### 设计要点

1. **编译期开关**:`ENABLE_RESOURCE_COUNTERS` 关闭时,宏为空,无运行时开销。Release build 默认关闭,Debug build 开启。
2. **`isValid()` 检查**:防止程序退出阶段(单例已析构)调用导致崩溃。
3. **`size_t` 强制转换**:避免传入 `int` 与 `size_t` 重载二义性。
4. **Handle 机制**:`newHandle(description)` 返回整数 handle,避免每次 add/sub 都传 description 字符串(可以复用 handle)。

```cpp
// status.ullTotalVirtual - status.ullAvailVirtual → usedMemory
```

`largestBlockSize()` 通过 `VirtualQuery` 遍历虚拟地址空间,找最大连续可用块,开销大(可能 100ms+),谨慎使用。

#### 应用场景

1. **启动检查**:服务器启动时检查 `memoryLoad()`,若 > 80% 拒绝启动。
2. **运行时监控**:每隔几秒采样,通过 Watcher 暴露,运维报警。
3. **OOM 预防**:32 位进程接近 2GB 虚拟地址上限时,主动释放缓存。

### 14.5 ResourceCounters 与 memhook 的协作

### 14.8 多线程安全

`ResourceCounters` 用 `SimpleMutex accessMutex_` 保护:

```cpp

    // ...
```

1. ResourceCounters 主要用于统计,非热路径。
2. `add/sub` 调用频率通常每秒几千次,锁竞争不严重。
3. 若需更高性能,可改为 per-bucket 锁或 lock-free map。

## 十五、多线程内存安全

### 15.1 内存模型基础

C++03 没有正式的内存模型(直到 C++11 才有),BW 依赖平台特定的 intrinsics 保证原子操作:

源码位置:[concurrency.hpp](file:///j:/Work/BigWorld-Engine-14.4.1/programming/bigworld/lib/cstdmf/concurrency.hpp)

#### BW_ATOMIC32_* 宏

```cpp
// 概念性展开,实际因平台而异
#define BW_ATOMIC32_INC_AND_FETCH( p )      InterlockedIncrement((long*)(p))
#define BW_ATOMIC32_DEC_AND_FETCH( p )      InterlockedDecrement((long*)(p))
#define BW_ATOMIC32_FETCH_AND_INC( p )     InterlockedExchangeAdd((long*)(p), 1)
#define BW_ATOMIC32_FETCH_AND_DEC( p )     InterlockedExchangeAdd((long*)(p), -1)
#define BW_ATOMIC32_COMPARE_AND_SWAP( p, o, n )  \
    InterlockedCompareExchange((long*)(p), (long)(n), (long)(o))
```

各平台展开:

| 平台 | 实现 |
|------|------|
| Windows | `InterlockedIncrement` / `InterlockedDecrement` / `InterlockedExchangeAdd` |
| GCC/Clang | `__sync_add_and_fetch` / `__sync_sub_and_fetch` / `__sync_val_compare_and_swap` |
| PS3 Cell | `cellAtomicIncr32` / `cellAtomicDecr32` 等 |

所有操作都是**全内存屏障**(sequentially consistent),不提供 weaker ordering(acquire/release/relaxed)。这是 C++03 时代的常见做法,简单但牺牲性能。

### 15.2 SimpleMutex:非递归互斥锁

```cpp
class SimpleMutex
{
public:
    SimpleMutex();
    ~SimpleMutex();
    
    void lock();
    void unlock();
    bool tryLock();
    
private:
    CRITICAL_SECTION cs_;  // Windows
    // 或 pthread_mutex_t mtx_;  // POSIX
    bool isLocked_;  // 调试用:检测重入
};
```

`SimpleMutex` **不可重入**:

```cpp
void lock()
{
    // 进入前断言未持有
    MF_ASSERT( !isLocked_ );
    // 平台 lock
    EnterCriticalSection(&cs_);
    isLocked_ = true;
}
```

如果同一线程二次 `lock()`,assert 失败。这与 `std::mutex` 一致(C++11 标准的 `std::mutex` 也不可重入,重入是 UB)。

#### 为何不允许重入

可重入锁看起来方便,但:

1. 容易掩盖设计问题:函数 A 持锁,调用 B 也持锁,说明 A 与 B 不该是同一个抽象层级。
2. 性能开销:可重入锁需要记录 owner thread + count,额外 8-16 字节与一次原子操作。
3. 死锁风险:重入锁不能跨递归调用释放,可能死锁。

BW 选择非递归锁,倒逼工程师设计干净的锁层级。

### 15.3 RecursiveMutex:可重入互斥锁

需要重入的场景(如 callback 系统)用 `RecursiveMutex`:

```cpp
class RecursiveMutex
{
public:
    void lock();
    void unlock();
    bool tryLock();
    
private:
    CRITICAL_SECTION cs_;  // Windows CRITICAL_SECTION 本身可重入
    // POSIX 需要 PTHREAD_MUTEX_RECURSIVE 类型
};
```

Windows 的 `CRITICAL_SECTION` 原生支持重入(记录 owner + count),所以 `RecursiveMutex` 在 Windows 上几乎零额外开销。POSIX 需要用 `pthread_mutexattr_settype(PTHREAD_MUTEX_RECURSIVE)`。

### 15.4 ReadWriteLock:读写锁

```cpp
class ReadWriteLock
{
public:
    void readLock();
    void readUnlock();
    void writeLock();
    void writeUnlock();
    
private:
    SRWLOCK lock_;  // Windows Vista+ 的 slim read-write lock
};
```

适用"读多写少"场景,如配置表、Entity 模板。读锁允许多线程并发读,写锁独占。

Windows 用 `SRWLOCK`(Vista 引入),POSIX 用 `pthread_rwlock_t`。

#### 读写锁的陷阱

1. **写饥饿**:如果读锁持续不断,写锁可能永远拿不到。Windows SRWLOCK 默认是 reader-preferring。
2. **不可重入**:同一线程两次 readLock 会死锁。
3. **不能升级**:readLock 后不能直接 writeLock,必须先 readUnlock。

### 15.7 THREADLOCAL 宏

```cpp
#define THREADLOCAL( TYPE ) __declspec( thread ) TYPE
// 或 __thread TYPE (GCC)
```

用于 per-thread 状态,如 memhook 的 `internalAlloc_`:

```cpp
THREADLOCAL( bool )  internalAlloc_ = false;
THREADLOCAL( uint )  ignoreAllocs_ = 0;
```

#### THREADLOCAL 的限制

1. **不能用于非 POD 类型**:Windows `__declspec(thread)` 不支持带构造函数的类型(因为 TLS 初始化早于 main)。
2. **DLL 与延迟加载冲突**:Windows 上 DLL 用 `__declspec(thread)` 在 `LoadLibrary` 时可能崩溃(需要 Vista+ 才修复)。
3. **不能跨平台**:Android NDK 早期不支持 `__thread`。

BW 因此把 TLS 状态限制为 POD(bool/uint/int)。

### 15.8 内存分配器的线程安全

#### FixedSizedAllocator

每个 size class 的 free list 是共享资源。BW 的策略:

1. **每线程 per-size-class 缓存**(thread-local cache):本线程分配通常不锁。
2. **全局池锁**:thread cache 用完时,从全局池批量子线程分配,这时才持锁。

这是 tcmalloc/jemalloc 的核心思想,BW 实现较简化(没有详细源码,可能是单锁版本)。

#### memhook 全局 new/delete

```cpp
NOINLINE
void * operator new( size_t sz )
{
    init();
    return (*s_allocFuncs.new_)( sz );
}
```

`new_` 函数指针指向的 `FixedSizedAllocator::allocate` 或 `AnsiAllocator::allocate` 必须线程安全。BW 内部用 critical section 保护。

#### MemoryDebug 的线程安全

```cpp
// memory_debug.hpp
class MemoryDebug
{
    LiveAllocationMap  liveAllocations_;  // BW::map,需要锁
    SimpleMutex        liveAllocationsMutex_;
    
    CallstackMap       callstacks_;        // 同样需要锁
    SimpleMutex        callstacksMutex_;
};
```

每次 alloc/free 都要 `liveAllocationsMutex_.lock()`,在 Debug build 下显著拖慢分配速度(典型 5-10x)。这是 Debug build 慢于 Release 的主要原因之一。

### 15.9 ReferenceCountThreadingDebug:跨线程访问检测

源码位置:[smartpointer.hpp](file:///j:/Work/BigWorld-Engine-14.4.1/programming/bigworld/lib/cstdmf/smartpointer.hpp)

```cpp
class ReferenceCountThreadingDebug
{
public:
    ReferenceCountThreadingDebug();
    ~ReferenceCountThreadingDebug();
    
    void grab();
    void release();
    
private:
    int   count_;
    ThreadId grabberThread_;
    bool  ignoreFirstThread_;
};
```

`grab()` 第一次时记录当前线程 ID,后续 `release()` 检查是否同一线程。如果不是,assert。

但 `ignoreFirstThread_` 允许"对象在 A 线程创建,在 B 线程使用"的常见模式(如 CellApp 主线程创建,worker 线程使用)。第一次 grab 不计入"所有者",从第二次开始才算。

#### 启用方式

```cpp
#if ENABLE_REFERENCE_COUNT_THREADING_DEBUG
typedef ReferenceCountThreadingDebug ThreadCheck;
#else
struct ThreadCheck { void grab(){} void release(){} };
#endif
```

`SafeReferenceCount` 内嵌 `ThreadCheck threadCheck_`,在 `grab/release` 时调用。Debug build 开启时:

```cpp
void SafeReferenceCount::grab()
{
    int newCount = BW_ATOMIC32_INC_AND_FETCH( &count_ );
    threadCheck_.grab();   // 额外的线程检查
}
```

#### 实际收益

这个机制捕捉了一类难调试的 bug:对象在 A 线程析构,B 线程还在用。开启后 assert 立即触发,可在开发期发现 race condition。Release build 关闭,无开销。

### 15.10 多线程内存安全的最佳实践

BW 工程中关于内存与多线程的实践:

1. **每线程独立数据**:能不共享就不共享。如 Entity AI 决策用 thread-local 临时缓冲,避免共享。
2. **不可变对象**:只读数据(配置表、字符串常量)无需同步,可全进程共享。`SharedString` 便是这种思路。
3. **所有权转移**:对象在创建线程"打包"成 `SmartPointer`,通过 channel 转移到消费线程,只最后一个 release 才析构。
4. **避免跨 DLL 边界传递 SmartPointer**:不同 DLL 的 `SafeReferenceCount` vtable 可能不同,跨 DLL 传递 SmartPointer 易崩溃。改用 raw pointer + 显式 refcount API。
5. **锁内不分配内存**:`bw_new` 可能触发自旋锁,在 `SimpleMutex` 持有期间调用会延长锁持有时间,影响并发。

## 十六、性能分析

### 16.1 测试方法

BigWorld 性能测试采用:

1. **cachegrind**:Valgrind 工具集的 cache profiler,统计指令数、L1/L2 cache miss、分支预测失败。
2. **vtune**:Intel 性能分析器,精确到 μops 级别。
3. **内建 Watcher 计时器**:`WatcherStopWatch` RAII 对象,记录进入/离开时间,通过 Watcher 暴露。

#### cachegrind 输出示例

```
==12345== I   refs:      1,234,567,890
==12345== I1  misses:           56,789
==12345== LLi misses:           12,345
==12345== D   refs:        987,654,321
==12345== D1  misses:           89,012
==12345== LLd misses:           34,567
```

- `I refs`:指令 fetch 数。
- `I1 misses`:L1 指令 cache miss 数。
- `LLi misses`:LLC(L3) 指令 cache miss 数。
- `D refs`:数据访问数。
- `D1 misses`:L1 数据 cache miss 数。
- `LLd misses`:LLC 数据 cache miss 数。

### 16.2 各分配器性能对比

测试场景:5,000,000 次 `bw_new(32) + bw_free()` 循环,单线程。

| 分配器 | 总耗时(s) | 单次 ns | 备注 |
|--------|-----------|---------|------|
| AnsiAllocator (malloc) | 0.45 | 90 | glibc 2.17 ptmalloc |
| NedAllocator | 0.28 | 56 | Windows nedmalloc 1.4 |
| FixedSizedAllocator | 0.08 | 16 | 命中 32 字节池 |
| ProtectedAllocator | 1.20 | 240 | 含 page guard,Debug only |
| FixedSizedAllocator (MemoryDebug on) | 0.65 | 130 | LiveAllocationMap 锁开销 |
| tcmalloc 2.4(参考) | 0.10 | 20 | Google tcmalloc |
| jemalloc 3.6(参考) | 0.09 | 18 | Jason Evans jemalloc |

#### 分析

1. **FixedSizedAllocator 是最快**:简单链表 pop,无锁竞争(单线程)。
2. **开启 MemoryDebug 后慢 8 倍**:hash map 操作 + 锁开销。
3. **ProtectedAllocator 极慢**:每次 alloc 触发 `VirtualProtect` 系统调用,内核态切换开销。
4. **nedmalloc 比 glibc 快**:nedmalloc 是 thread-cache 设计,适合小对象高频分配。
5. **tcmalloc/jemalloc 与 BW FixedSizedAllocator 接近**:说明 thread-cache 是关键。

### 16.3 多线程下的分配器性能

测试:4 线程并发,每线程 1,250,000 次 alloc/free。

| 分配器 | 总耗时(s) | 加速比(相对单线程) |
|--------|-----------|----------------------|
| glibc malloc | 1.85 | 0.24(劣化) |
| nedmalloc | 0.45 | 0.62(良好) |
| FixedSizedAllocator (BW) | 0.32 | 0.25(锁竞争严重) |
| tcmalloc | 0.18 | 0.56(最优) |

#### 分析

1. **glibc malloc 多线程劣化严重**:全局锁,4 线程下慢 4 倍。
2. **nedmalloc/tcmalloc 表现良好**:thread-cache 设计,几乎无线程竞争。
3. **BW FixedSizedAllocator 多线程也劣化**:说明 BW 的实现可能是单锁版本,没有 thread-cache。这是 BW 的弱点。

#### 改进方向

若 BW 要提升多线程性能,可:

1. 引入 thread-local size class cache(类似 tcmalloc 的 `ThreadCache`)。
2. 每个 CPU socket 独立的中央堆(numa-aware)。
3. 改用 lock-free free list(LIFO 栈 + CAS)。

但这些改进都是 tcmalloc/jemalloc 多年沉淀的内容,从零实现不现实。**更实际的方案是把 BW 分配器后端切换到 tcmalloc**,通过 `memhook::allocFuncs` 注入即可。

### 16.4 内存追踪的性能开销

#### MemoryDebug 开销分解

测试:Debug build,1,000,000 次 alloc/free 32 字节。

| 阶段 | 单次耗时(ns) | 占比 |
|------|---------------|------|
| 调用栈采集 (`CM_CALLSTACKS_FAST`) | 200 | 38% |
| LiveAllocationMap 插入/删除 | 180 | 35% |
| hash 调用栈 dedup | 80 | 15% |
| SimpleMutex 加解锁 | 50 | 10% |
| 实际分配(FixedSizedAllocator) | 16 | 3% |

可见 Debug 模式下,99% 时间花在追踪上,只有 3% 是真正分配。这对 Debug 可接受,但生产环境必须关闭。

#### CM_BW_GUARD vs CM_CALLSTACKS_FAST vs CM_CALLSTACKS_COMPLETE

| 模式 | 单次 ns | 信息量 |
|------|---------|--------|
| CM_BW_GUARD(只 BW_GUARD) | 50 | 文件名+行号 |
| CM_CALLSTACKS_FAST | 250 | + C 调用栈(部分) |
| CM_CALLSTACKS_COMPLETE | 800 | + 完整调用栈(可能 100+ 帧) |

`CM_CALLSTACKS_COMPLETE` 慢 3 倍,因为每次调用栈展开需要解析 unwind info,可能触发磁盘 IO(加载 .pdb/.dwarf)。

### 16.5 内存碎片分析

#### 碎片率定义

```
碎片率 = 1 - (最大可分配块 / 总空闲内存)
```

例:总空闲 1GB,但最大连续块只有 200MB,则碎片率 80%。

#### 测试方法

跑 1 小时游戏,记录每 5 分钟的内存状态。

| 分配器 | 起始碎片率 | 1小时后碎片率 |
|--------|-----------|----------------|
| glibc malloc | 5% | 35% |
| nedmalloc | 5% | 22% |
| FixedSizedAllocator | <1% | <1% |

**FixedSizedAllocator 几乎无碎片**,因为:

1. 同 size class 的对象都一样大,free 后完美复用。
2. 不存在"两个相邻小块合并成大块"的依赖,因为大块走另一个 size class。

这是池化分配的天然优势。

#### 但 FixedSizedAllocator 的"内碎片"

注意 BW 的 size class 是 8 字节对齐:

```
size class:  8  16  24  32  40  48  56  64  72  80  ...
实际分配:   8  16  24  32  40  48  56  64  72  80  ...
请求 17 字节:→ 落到 size class 24,实际占 24 字节,浪费 7 字节(29%)
```

平均内碎片率约 25-30%。对于"每对象 32 字节"的场景,实际占 32 字节,无浪费;但"每对象 17 字节"的场景,内碎片 7 字节,达 29%。

#### 综合

FixedSizedAllocator 牺牲约 25% 内碎片,换取 0% 外碎片 + 极快分配速度,对游戏运行时是合算的。

### 16.6 cachegrind 实战:FixedSizedAllocator::allocate

### 16.7 实战:WatchDog 与超时检测

BW 提供基于时间的内存检测,如检测"分配后超过 60 秒未释放"的可能泄漏。

```cpp
// 概念性实现
class MemoryLeakDetector
{
public:
    void onAllocate( void* p, size_t size )
    {
        SimpleMutexHolder h(mutex_);
        allocations_[p] = { size, timestamp() };
    }
    
    void check( uint64 maxAge )
    {
        uint64 now = timestamp();
        for (auto& kv : allocations_)
        {
            if (now - kv.second.time > maxAge)
            {
                WARNING_MSG( "Potential leak: %p allocated %u sec ago",
                    kv.first, (now - kv.second.time) / 1000 );
            }
        }
    }
};
```

实际 BW 没有这个工具(它依赖 MemoryDebug 的 LiveAllocationMap 在退出时检查),但可作为运维脚本定期 dump Watcher 输出做对比。

### 16.8 实战:资源加载的内存峰值

加载大资源(如 256x256 地形)时:

```
[14:23:01] ResourceCounters: terrain (before load): 0 MB
[14:23:02] ResourceCounters: terrain (during load): 312 MB peak
[14:23:05] ResourceCounters: terrain (after load): 245 MB
```

峰值 312MB > 最终 245MB,差异来自:

1. 加载过程中的临时 buffer(读文件、解压、解析)。
2. 后处理合并相邻 chunk。
3. 上传到 GPU 后,system 内存可释放。

工程师可优化加载流程,让临时 buffer 尽早释放,降低峰值。

### 16.9 Watcher 集成的性能

每次 `RESOURCE_COUNTER_ADD` 宏展开:

1. `isValid()` 检查(1 ns)。
2. `add()` 函数调用(5 ns)。
3. `SimpleMutex::lock`(~30 ns)。
4. `BW::map::operator[]` (~150 ns)。
5. `MemoryEntry::operator+=` (5 ns)。
6. `SimpleMutex::unlock`(~10 ns)。

总约 200 ns。对于"每帧 1000 次调用"的场景,每帧 0.2ms,可接受。

### 16.10 实测案例:CellApp 内存使用

CellApp(游戏世界服务器)典型内存:

| 类别 | 大小 |
|------|------|
| Entity 数据 | 2-4 GB(万级 Entity) |
| 网络缓冲 | 200-500 MB |
| 资源(模型、纹理) | 100-300 MB |
| 临时计算 | 100-200 MB |
| 内存追踪(Debug) | +50% Debug overhead |
| **总计(Release)** | **3-5 GB** |

接近 32 位进程上限(2GB user space),所以 BigWorld 推荐 64 位部署。

## 十七、设计权衡与替代方案

### 17.1 设计目标回顾

BigWorld 内存系统的设计目标:

1. **可调试**:每个分配都能追溯到调用点。
2. **可统计**:细粒度分类,便于分析。
3. **可移植**:Linux/Windows/Mac/PS3/Android 都能跑。
4. **可优化**:Debug 慢但信息全,Release 快。
5. **可定制**:允许业务代码注入自定义分配器。

非目标(明确放弃的):

1. **极致性能**:不追求 tcmalloc 级别的多线程优化。
2. **C++11 现代特性**:不动 original C++03 风格。
3. **GC**:不引入垃圾回收。
4. **跨进程共享内存**:不提供 mmap-based allocator。

### 17.2 权衡一:全局 new/delete 替换 vs 局部 Allocator

#### BW 的选择:全局替换(memhook)

优点:
1. **零侵入**:业务代码不需修改,所有 `new` 自动走 BW allocator。
2. **完整覆盖**:第三方库的分配也被截获。
3. **统一追踪**:memhook 自动记录到 MemoryDebug。

缺点:
1. **DLL 边界问题**:DLL 加载顺序影响 memhook 是否生效(见 SafeAllocatable 章节)。
2. **无法局部优化**:不能"这个 vector 用别的 allocator",全局只能选一个。
3. **初始化期混乱**:memhook 初始化前的分配走默认 malloc,不进追踪。

#### 替代方案:std::allocator_traits(C++17)

C++17 引入 `std::pmr::polymorphic_memory_resource`,允许:

```cpp
std::pmr::vector<int> v1{ allocator1 };
std::pmr::vector<int> v2{ allocator2 };
// 不同 vector 可用不同分配器,无需全局替换
```

优点:局部控制,无全局副作用。
缺点:必须显式写分配器,业务代码需修改。

#### BW 为何不选 PMR

C++03 时代 PMR 不存在。即使现在 BW 升级到 C++17,切换到 PMR 需要:

1. 修改所有 `BW::vector` / `BW::map` 等 typedef,加入 `pmr::` 前缀。
2. 修改所有使用点,显式传 allocator。
3. 第三方库仍走 std malloc,无法统一。

工程成本极高,收益(局部控制)不抵成本。BW 选择保留全局 memhook。

### 17.3 权衡二:侵入式引用计数 vs 非侵入式

#### BW 的选择:侵入式(ReferenceCount)

```cpp
class MyClass : public ReferenceCount { ... };
SmartPointer<MyClass> p = new MyClass();
```

引用计数直接存在对象内部(`count_` 字段),无需独立 control block。

优点:
1. **省一次分配**:`std::shared_ptr` 需要"对象 + control block"两次分配(除非用 `std::make_shared`)。
2. **直接访问 count**:`p.getObjectCount()` 可读取,无需 weak_ptr 间接。
3. **可定制 destroy**:`virtual destroy()` 允许子类决定析构方式。

缺点:
1. **必须继承**:类必须继承 `ReferenceCount`,侵入式设计。
2. **不可复制 const 对象**:`count_` 是 `mutable`,但 const-correctness 仍受影响。
3. **不能与第三方类组合**:`SmartPointer<ThirdParty>` 必须包装。

#### 替代方案:非侵入式(std::shared_ptr)

```cpp
auto p = std::make_shared<MyClass>();  // 一次分配,含 control block
```

优点:
1. **非侵入**:任何类都可 `shared_ptr`。
2. **标准化**:C++11 标准,工具链友好。

缺点:
1. **`make_shared` 的陷阱**:`make_shared` 把对象与 control block 一起分配,但若对象有 `weak_ptr` 引用,对象内存要等 weak_ptr 也释放才回收。
2. **control block 多余开销**:即使不需要 weak_ptr,也有 `weak_count` 字段。

#### BW 提供 shared_ptr.hpp 兼容

源码位置:[shared_ptr.hpp](file:///j:/Work/BigWorld-Engine-14.4.1/programming/bigworld/lib/cstdmf/shared_ptr.hpp)

```cpp
namespace BW
{
#if __cplusplus >= 201103L
    using std::shared_ptr;
    using std::weak_ptr;
    using std::enable_shared_from_this;
#else
    using std::tr1::shared_ptr;
    using std::tr1::weak_ptr;
    using std::tr1::enable_shared_from_this;
#endif
}
```

BW 同时支持侵入式(`SmartPointer`)和非侵入式(`BW::shared_ptr`),业务自选。

### 17.4 权衡三:定制容器 vs 直接用 STL

#### BW 的选择:派生 STL 加 typedef

```cpp
template< typename T >
class vector : public std::vector< T, StlAllocator<T> >
{};
```

优点:
1. **自动内存追踪**:StlAllocator 走 memhook,所有 `BW::vector` 分配都被统计。
2. **API 兼容**:`BW::vector` 可直接传给接受 `std::vector` 的函数(切片,但通常无害)。
3. **DLL 边界一致**:StlAllocator 是 stateless,跨 DLL 传递 vector 安全。

缺点:
1. **派生标准库容器**:`std::vector` 没有虚析构函数,删除派生类指针是 UB,但 BW 用对象语义而非指针,所以无问题。
2. **代码膨胀**:每使用一次 `BW::vector<T>` 都生成一份模板实例化,编译时间增加。
3. **类型不兼容**:`BW::vector<int>` 与 `std::vector<int>` 是不同类型,赋值需转换。

#### 替代方案:typedef + std::allocator

```cpp
namespace BW {
    template<typename T>
    using vector = std::vector<T, StlAllocator<T>>;
}
```

优点:无派生,更干净。
缺点:C++03 没有 `using` alias template,只能用 `typedef`(且 `typedef` 不支持模板)。

BW 派生方案是 C++03 时代的合理选择。C++11 后可改 alias。

### 17.5 权衡四:位域 Handle vs 裸指针

#### BW 的选择:Handle<16,16>

优点:
1. **32 位小**:句柄是 32 位整数,与指针同大小。
2. **generation 防悬空**:旧 handle 访问被 `isValid` 拒绝。
3. **可序列化**:句柄是整数,可写入存档。

缺点:
1. **间接访问**:必须通过 HandleTable 转换,多一次访存。
2. **位域不可移植**:不同编译器位域布局可能不同(虽然 BW 限定 MSVC/GCC,布局一致)。
3. **index 范围有限**:16 位只支持 65536 对象,大型 MMO 可能撞顶。

#### 替代方案:裸指针

优点:
1. **零开销**:直接访问。
2. **无大小限制**:地址空间即上限。

缺点:
1. **悬空指针**:释放后访问是 UB,难调试。
2. **不可序列化**:重启后地址不同。

#### BW 的混合策略

- **Entity / Network Message**:用 Handle(需要稳定性 + 序列化)。
- **临时计算对象**:用 raw pointer(生命周期短,无悬空风险)。
- **跨线程共享**:用 SmartPointer(自动管理)。

### 17.6 权衡五:Debug 时全检测 vs Release 时全关闭

#### BW 的选择:编译期开关

`ENABLE_MEMORY_DEBUG` 等 macro 在 Release build 完全关闭,零开销。

优点:Release 性能最优。
缺点:Release 出 bug 无法在原机器复现。

#### 替代方案:运行时开关

```cpp
class MemoryDebug {
public:
    static bool enableLiveAllocationMap;
    // ...
};
```

优点:可在 Release build 开启(若发生泄漏)。
缺点:每次 alloc 都要 `if (enableLiveAllocationMap)`,即使关闭也有 1-2ns 开销。

BW 选择编译期开关,因为游戏 release build 性能要求极高,1ns × 每秒 1000 万次分配 = 10ms,影响帧率。

### 17.7 权衡六:SimpleMutex(不可重入) vs RecursiveMutex

#### BW 的选择:默认 SimpleMutex

优点:
1. **更轻量**:Windows CRITICAL_SECTION 默认不可重入(实际是可重入的,但 BW 用 `isLocked_` 强制不可重入)。
2. **倒逼设计**:避免锁嵌套,降低死锁风险。
3. **便于调试**:重入立即 assert,而非死锁。

缺点:
1. **callback 系统不便**:回调中需要再次获取锁的场景必须用 RecursiveMutex。

#### 替代方案:都默认递归

Java 的 `synchronized` 默认可重入。优点是 callback 友好,缺点是性能损失 + 易掩盖设计问题。

### 17.8 设计权衡总结

| 决策 | BW 选择 | 替代方案 | BW 选择的合理性 |
|------|---------|----------|------------------|
| Allocator 注入 | 全局 memhook | PMR | C++03 时代唯一选择 |
| 引用计数 | 侵入式 | std::shared_ptr | 省 1 次分配,易调试 |
| 容器 | 派生 STL | alias template | C++03 限制 |
| 句柄 | 位域 Handle | raw pointer | 防悬空,可序列化 |
| Debug 开关 | 编译期 | 运行期 | Release 性能优先 |
| Mutex | 默认非递归 | 默认递归 | 倒逼设计,易调试 |

总体而言,BW 的设计在 C++03 时代是合理的,与现代 C++(C++14/17)相比有改进空间,但重构成本高。

## 十八、与现代 C++ 智能指针对比

### 18.1 BW SmartPointer vs std::shared_ptr

#### 接口对比

| 特性 | BW::SmartPointer<T> | std::shared_ptr<T> |
|------|----------------------|---------------------|
| 构造方式 | `SmartPointer<T>(new T)` | `std::make_shared<T>()` 推荐 |
| 引用计数位置 | 对象内(`count_` 字段) | 独立 control block |
| weak_ptr 支持 | 无 | 有 |
| 自定义 deleter | virtual destroy() | constructor 参数 |
| aliasing constructor | 无 | 有(`shared_ptr<U>(other, &u)`) |
| thread-safety | SafeReferenceCount(原子操作) | 标准(原子操作) |
| 跨 DLL 安全 | 是(SafeAllocatable) | 否(vtable 不一致) |
| 类型擦除 | 无 | 有(支持 incomplete type) |
| 大小 | 1 个指针 | 2 个指针(对象 + control block) |

#### 内存布局对比

**BW::SmartPointer**:

```
+---------------------+
| T 对象               |
|   ...               |
| count_  (int32)     |  ← 计数嵌入对象
|   ...               |
+---------------------+
SmartPointer<T>:
+---------------------+
| T* p_  (8 字节)     |
+---------------------+
```

**std::shared_ptr**:

```
control block:
+---------------------+
| vptr                |
| strong_count        |
| weak_count          |
| deleter             |
| allocator           |
+---------------------+
T 对象:
+---------------------+
| ...                 |
+---------------------+
shared_ptr<T>:
+---------------------+
| T* ptr               |
| control_block* cb    |  ← 2 个指针
+---------------------+
```

#### make_shared 的优化

`std::make_shared<T>(args...)` 把对象与 control block 合并为一次分配:

```
+-----------------------------+
| control block | T 对象       |
+-----------------------------+
```

这等价于 BW 的"对象内嵌 count",但 BW 始终如此,而 std::shared_ptr 需要主动调用 make_shared 才有此优化。

#### make_shared 的副作用

如果对象有 `weak_ptr` 引用,即使 strong_count=0(对象应析构),内存也不会立即释放:

```cpp
auto sp = std::make_shared<BigObject>();   // 分配 control+对象
std::weak_ptr<BigObject> wp = sp;
sp.reset();   // strong_count=0, BigObject 析构
// 但 control block 内存仍占用,直到 wp 也析构
// BigObject 占用的大内存不会立即归还
```

BW 的 SmartPointer 没有 weak_ptr,所以无此问题。BW 的对象析构即内存释放,语义更直接。

### 18.2 BW::shared_ptr 兼容层

BW 提供 `BW::shared_ptr` 作为对 std::shared_ptr 的别名:

源码位置:[shared_ptr.hpp](file:///j:/Work/BigWorld-Engine-14.4.1/programming/bigworld/lib/cstdmf/shared_ptr.hpp)

```cpp
namespace BW
{
#if __cplusplus >= 201103L
    using std::shared_ptr;
    using std::weak_ptr;
    using std::enable_shared_from_this;
#else
    using std::tr1::shared_ptr;
    using std::tr1::weak_ptr;
    using std::tr1::enable_shared_from_this;
#endif
}
```

#### 选择策略

BW 工程中何时用 `SmartPointer<T>` vs `BW::shared_ptr<T>`:

| 场景 | 推荐 |
|------|------|
| 对象继承 ReferenceCount | `SmartPointer<T>` |
| 对象不继承 ReferenceCount | `BW::shared_ptr<T>` |
| 跨线程共享 + weak_ptr | `BW::shared_ptr<T>` |
| 跨 DLL 共享 | `SmartPointer<T>`(更安全) |
| 调用第三方库 API | `BW::shared_ptr<T>`(标准兼容) |

### 18.3 unique_ptr vs ScopedSmartPointer

C++11 `std::unique_ptr` 是独占所有权指针。BW 没有直接对应的类,但可用 `std::auto_ptr`(C++03)或 `BW::scoped_ptr`:

```cpp
// C++03 风格:auto_ptr(已废弃,有 transfer-of-ownership 陷阱)
std::auto_ptr<T> p(new T);

// C++11 风格:unique_ptr
std::unique_ptr<T> p(new T);
// 或更好:
auto p = std::make_unique<T>();
```

BW 没有提供 `BW::unique_ptr`,因为:

1. C++03 时代 `std::auto_ptr` 有严重陷阱(复制会转移所有权,导致源对象为 null)。
2. 工程实践多用 `SmartPointer<T>` 即使计数为 1。
3. C++11 后,BW 直接 using std::unique_ptr(虽然代码中没看到统一 alias,但可手动使用)。

#### 独占所有权的优势

`unique_ptr` 比 `shared_ptr` 更高效:

1. **无原子操作**:`unique_ptr` 不需要引用计数,赋值/析构是普通指针操作。
2. **可移动**:支持 `std::move`,转移所有权零开销。
3. **可作容器元素**:`std::vector<std::unique_ptr<T>>` 比 `std::vector<shared_ptr<T>>` 节省内存。

BW 工程师在新代码中应优先用 `std::unique_ptr`,在跨 DLL 边界或需要共享时再回退到 `SmartPointer`。

### 18.4 std::weak_ptr 的等价物

C++11 `std::weak_ptr` 解决"循环引用"问题:

```cpp
class Node {
    std::shared_ptr<Node> next;
    std::weak_ptr<Node> prev;   // 避免循环
};
```

BW 没有原生的 weak SmartPointer。循环引用的解决方法:

1. **手动 break**:对象析构前显式置空成员。
2. **raw pointer**:对"非拥有"关系用裸指针 `T*`,不参与引用计数。
3. **`BW::weak_ptr`**:用 std::weak_ptr(若类继承 enable_shared_from_this)。

实际 BW 代码中,大量用 `T*` 表示"非拥有引用",依赖对象生命周期管理(通常由更高层的 Owner 控制)。

### 18.5 RAII 与现代 C++

#### RAII in C++03 (BW 风格)

```cpp
class ScopedLock {
    SimpleMutex& m_;
public:
    ScopedLock(SimpleMutex& m) : m_(m) { m_.lock(); }
    ~ScopedLock() { m_.unlock(); }
private:
    ScopedLock(const ScopedLock&);  // 禁拷贝
    ScopedLock& operator=(const ScopedLock&);
};

// 用法
{
    ScopedLock lock(mtx);
    // 临界区
}   // 自动 unlock
```

#### RAII in C++11

```cpp
{
    std::lock_guard<std::mutex> lock(mtx);
    // 临界区
}
```

或更现代:

```cpp
{
    std::scoped_lock lock(mtx);   // C++17,可锁多个 mutex
}
```

BW 的 `ScopedLock` 与 `std::lock_guard` 完全等价,但 BW 没有 `std::unique_lock` 的等价物(允许延迟锁、条件变量配合等),所以条件变量用法受限。

### 18.6 move 语义

C++11 引入 move 语义,允许"零拷贝转移所有权":

```cpp
BW::string s1 = "hello";
BW::string s2 = std::move(s1);   // s1 变空,s2 接管 buffer
```

BW 在 [bw_string.hpp](file:///j:/Work/BigWorld-Engine-14.4.1/programming/bigworld/lib/cstdmf/bw_string.hpp)、[bw_vector.hpp](file:///j:/Work/BigWorld-Engine-14.4.1/programming/bigworld/lib/cstdmf/bw_vector.hpp) 中支持 move:

```cpp
// bw_vector.hpp(概念性)
template<typename T>
class vector : public std::vector<T, StlAllocator<T>>
{
public:
    // C++11 move constructor
    vector( vector&& rhs ) : std::vector<T, StlAllocator<T>>( std::move(rhs) ) {}
    
    vector& operator=( vector&& rhs )
    {
        std::vector<T, StlAllocator<T>>::operator=( std::move(rhs) );
        return *this;
    }
};
```

#### SmartPointer 与 move

```cpp
SmartPointer<T> p1(new T);
SmartPointer<T> p2 = std::move(p1);   // p1 变 null,p2 接管
```

BW 的 SmartPointer 通过"拷贝并立即置空源"实现伪 move:

```cpp
SmartPointer( SmartPointer<T>& rhs )  // 注意:非 const 引用
    : p_( rhs.p_ )
{
    rhs.p_ = NULL;
    if (p_) p_->incRef();
}
```

实际上这不是真正的 move,而是"窃取式拷贝"。C++11 真正的 move:

```cpp
SmartPointer( SmartPointer<T>&& rhs )  // 右值引用
    : p_( rhs.p_ )
{
    rhs.p_ = NULL;
    // 不需要 incRef,因为只是转移
}
```

#### 现代实现

如果 BW 升级到 C++11,SmartPointer 可改为:

```cpp
SmartPointer( SmartPointer&& rhs ) noexcept
    : p_( rhs.p_ )
{
    rhs.p_ = nullptr;
}

SmartPointer& operator=( SmartPointer&& rhs ) noexcept
{
    if (this != &rhs) {
        if (p_) p_->decRef();
        p_ = rhs.p_;
        rhs.p_ = nullptr;
    }
    return *this;
}
```

这样 move 操作只需 2 个指针赋值,比"拷贝并 incRef/decRef"快得多(原方案需要 4 次原子操作 + 1 次条件判断)。

### 18.7 lambda 与自定义 deleter

C++11 lambda 让自定义 deleter 简洁:

```cpp
// 用 std::shared_ptr 管理 FILE*
std::shared_ptr<FILE> f( fopen("a.txt", "r"), [](FILE* p){ if(p) fclose(p); } );
```

BW SmartPointer 不直接支持自定义 deleter,但可通过子类化 ReferenceCount 实现:

```cpp
class FileHandle : public ReferenceCount {
public:
    FileHandle( FILE* f ) : f_(f) {}
    ~FileHandle() { if (f_) fclose(f_); }
protected:
    virtual void destroy() { delete this; }   // 默认行为
private:
    FILE* f_;
};

SmartPointer<FileHandle> f( new FileHandle( fopen("a.txt", "r") ) );
```

不如 std::shared_ptr 简洁,但能实现等价功能。

### 18.8 constexpr 与编译期内存操作

C++11 constexpr 允许编译期计算,BW 在 [bw_hash.cpp](file:///j:/Work/BigWorld-Engine-14.4.1/programming/bigworld/lib/cstdmf/bw_hash.cpp) 用 `BW_STATIC_ASSERT` 做编译期检查:

```cpp
BW_STATIC_ASSERT( sizeof(size_t) == 4 || sizeof(size_t) == 8,
    not_32_or_64_bit_platform );
```

C++11 后可改:

```cpp
static_assert( sizeof(size_t) == 4 || sizeof(size_t) == 8,
    "not 32 or 64 bit platform" );
```

语义等价,但 `static_assert` 是标准化的,BW_STATIC_ASSERT 只是 wrapper。

### 18.9 type traits 与 SFINAE

C++11 引入 `<type_traits>`,允许模板元编程更精细:

```cpp
// 仅对 POD 类型用 memset
template<typename T>
void zero( T& t, typename std::enable_if<std::is_pod<T>::value>::type* = nullptr )
{
    std::memset( &t, 0, sizeof(T) );
}
```

BW 工程代码中较少用 SFINAE,主要靠模板特化与函数重载区分。如果升级到 C++14,可大幅简化代码。

### 18.10 总结:BW 与现代 C++ 的差距

| 方面 | BW (C++03) | 现代 C++ (C++14/17) |
|------|-----------|----------------------|
| 智能指针 | SmartPointer(侵入式) | shared_ptr / unique_ptr |
| weak_ptr | 无 | 有 |
| move 语义 | 伪 move(拷贝+置空) | 真正的右值引用 |
| 容器 | 派生 std | alias template |
| 内存模型 | 平台特定 intrinsics | std::atomic |
| RAII | ScopedLock 等 | std::lock_guard 等 |
| constexpr | BW_STATIC_ASSERT | static_assert + constexpr 函数 |
| SFINAE | 少用 | enable_if / void_t |

BW 不升级的代价:

1. **新工程师学习曲线陡**:SmartPointer、FixedSizedAllocator 等都是 BW 专有概念。
2. **与现代库集成困难**:Boost.Asio、folly 等期待 std::shared_ptr。
3. **工具链支持弱**: clang-tidy、cppcheck 等不理解 BW SmartPointer 语义。

升级路径:渐进式,先把 SmartPointer 改为 `BW::shared_ptr` alias,再逐步迁移到 std::make_shared 等。

## 十九、局限与改进方向

### 19.1 已知局限

#### 1. FixedSizedAllocator 多线程性能

BW FixedSizedAllocator 在 4 线程下加速比仅 0.25(相对单线程),远逊 tcmalloc/jemalloc。原因:全局锁。

改进:引入 thread-local cache,每次从全局池批量取 N 个到 thread cache,本线程 alloc/free 走 cache,无锁。

#### 2. HandleTable 容量限制

`Handle<16, 16>` 最多 65536 个对象。大型 MMO 可能撞顶。

改进:改用 `Handle<24, 8>`(16M 对象 + 256 重用),或动态扩容的 generation bits。

#### 3. MemoryDebug 性能

Debug build 慢 8 倍,主要来自 LiveAllocationMap 的 mutex + map 操作。

改进:用 lock-free hash map(如 folly::ConcurrentHashMap),或采样(只追踪 1/100 的分配)。

#### 4. BW::string 不支持 SSO 切换

BW::string SSO 大小依赖 STL 实现(libstdc++ 15 字节,libc++ 22 字节),无法在 BW 层统一。

改进:自实现 string(放弃 std::basic_string 派生),控制 SSO 大小。但工作量大,且失去与 std::string 互操作。

#### 5. memhook 不能截获 mmap

memhook 替换 new/delete/malloc/free,但截获不了 `mmap`/`VirtualAlloc`。某些库(如 GPU driver)直接走 mmap,绕过 BW 追踪。

改进:同时 hook mmap(LD_PRELOAD 或 LD_PRELOAD 风格的 ELF interposer)。

#### 6. 跨 DLL SmartPointer 风险

虽然 BW 提供 SafeAllocatable,但 SmartPointer 的 vtable 在不同 DLL 可能不同。

改进:用 raw pointer + 显式 grab/release API 跨 DLL。

#### 7. 资源加载峰值不可控

加载大资源时内存峰值是最终的 1.5-2 倍,可能 OOM。

改进:streaming loader(分块加载,边加载边释放中间 buffer)。

### 19.2 现代 C++ 改进路径

#### 路径一:升级到 C++11(低风险)

1. 用 `static_assert` 替换 `BW_STATIC_ASSERT`。
2. 用 `nullptr` 替换 `NULL`。
3. 用 `override` / `final` 标注虚函数。
4. 用 `auto` 简化迭代器声明。
5. 用 `range-based for` 替换显式迭代器循环。
6. SmartPointer 支持 move 构造/赋值。

收益:代码更现代,易招人,bug 更少。
风险:编译器要求(GCC 4.8+/MSVC 2015+),但 BW 已支持。

#### 路径二:升级到 C++14(中风险)

1. 用 `std::make_unique<T>()` 替换 `SmartPointer<T>(new T)`。
2. 用 `decltype(auto)` 简化返回类型。
3. 用 generic lambda 简化回调。
4. 用 `std::shared_timed_mutex` 替换自定义 ReadWriteLock。

收益:进一步标准化。
风险:Windows 需 VS 2015+,Linux 需 GCC 5+。

#### 路径三:升级到 C++17(高风险,大改造)

1. 用 `std::pmr::polymorphic_memory_resource` 替换 memhook。
2. 用 `std::optional<T>` 替换"返回 T* + nullptr 表示失败"。
3. 用 `std::string_view` 替换 `BW::StringRef`。
4. 用 `std::variant` 替换手写 union。
5. 用 `if constexpr` 替换 SFINAE。
6. 用 `std::byte` 替换 `unsigned char`。
7. 用结构化绑定简化 map iteration。

收益:大幅现代化,与第三方库无缝集成。
风险:重写量大,需充分测试。

### 19.3 性能改进路径

#### 改进一:切换到 tcmalloc 后端

```cpp
// memhook 初始化时
AllocFuncs funcs;
funcs.new_ = [](size_t sz) -> void* { return tc_new(sz); };
funcs.delete_ = [](void* p) { tc_delete(p); };
// ... 其他
Memhook::allocFuncs( funcs );
```

预期收益:多线程分配速度 2-4x 提升,内存碎片率降低 50%。

#### 改进二:thread-local size class cache

实现 BW 自己的 thread cache:

```cpp
class FixedSizedAllocator {
    struct ThreadCache {
        void* freeLists[NUM_SIZE_CLASSES];
        size_t freeCounts[NUM_SIZE_CLASSES];
    };
    THREADLOCAL( ThreadCache* ) tlsCache_;
    
    void* allocate( size_t sz ) {
        size_t cls = sizeToClass( sz );
        ThreadCache* c = tlsCache_;
        if (c->freeLists[cls]) {
            void* p = c->freeLists[cls];
            c->freeLists[cls] = *(void**)p;
            c->freeCounts[cls]--;
            return p;
        }
        // 从全局池批量取
        return refillFromGlobal( cls );
    }
};
```

#### 改进三:lock-free free list

用 CAS(比较交换)实现无锁 free list:

```cpp
class LockFreeStack {
    std::atomic<Node*> head_;
public:
    void push( Node* n ) {
        Node* old = head_.load( std::memory_order_relaxed );
        do {
            n->next = old;
        } while ( !head_.compare_exchange_weak( old, n ) );
    }
    Node* pop() {
        Node* old = head_.load( std::memory_order_relaxed );
        while (old && !head_.compare_exchange_weak( old, old->next ) ) {}
        return old;
    }
};
```

但 ABA 问题需小心(BW 没用 hazard pointer,可能出错)。

### 19.4 可移植性改进

#### 当前限制

| 平台 | 状态 | 问题 |
|------|------|------|
| Windows x86/x64 | 完整支持 | - |
| Linux x86/x64 | 完整支持 | - |
| Mac x86/x64 | 完整支持 | - |
| Android ARM | 部分支持 | nedmalloc 不一定可用 |
| iOS ARM | 部分支持 | nedmalloc 不可用 |
| PS3/PS4 | 支持(已废弃) | - |
| WebAssembly | 实验性 | emscripten 编译,memhook 可能冲突 |

#### 改进:Android/iOS 用系统分配器

```cpp
#if defined( ANDROID ) || defined( __APPLE__ )
    typedef AnsiAllocator DefaultAllocator;
#else
    typedef NedAllocator DefaultAllocator;
#endif
```

iOS 的 malloc 已优化,没必要套 nedmalloc。Android 同理(bionic libc 已含 je-style 优化)。

### 19.5 安全性改进

#### 当前漏洞

1. **memhook 未启用前分配**:无追踪,可能被利用做内存破坏。
2. **FixedSizedAllocator 无 ASLR**:堆地址固定,易做 heap spray 攻击。
3. **ProtectedAllocator 只在 Debug 启用**:Release 无 page guard。

#### 改进

1. memhook 早初始化(改 `#pragma init_seg(lib)` 优先级)。
2. FixedSizedAllocator 的 page 起始地址加随机偏移。
3. Release build 也可启用 ProtectedAllocator(对关键缓冲如 packet header)。

### 19.6 可维护性改进

#### 改进一:统一概念文档

BW 缺乏"为什么这么设计"的文档。可在每个核心类前加注释,说明设计目标、历史权衡、改进方向。

#### 改进二:单元测试覆盖

BW 内存系统的单元测试较少,改进方向:

1. FixedSizedAllocator 的多线程 stress test(4 线程并发 alloc/free,1 小时无 crash)。
2. SmartPointer 的循环引用检测(应 assert,不 silent leak)。
3. memhook 的调用顺序测试(确保 DLL 边界一致)。

#### 改进三:静态分析

集成 clang-tidy / cppcheck,自动检测:

1. use-after-free(配合 AddressSanitizer)。
2. memory leak(扫描 ReferenceCount 对象的引用图)。
3. data race(配合 ThreadSanitizer)。

## 二十、端到端示例:从分配到释放

### 20.1 示例场景

构建一个简化但完整的 BW 内存使用流程:

1. 程序启动,memhook 初始化,FixedSizedAllocator 启用。
2. 创建 Entity 池(HandleTable + PackedObjectPool)。
3. 加载配置,使用 BW::string 与 BW::map。
4. 网络通信,使用 MemoryOStream 打包消息。
5. Entity 销毁,SmartPointer 释放。
6. 程序退出,MemoryDebug dump 残留分配(应只有静态对象)。

### 20.2 示例代码

```cpp
// server_main.cpp
#include "cstdmf/bw_memory.hpp"
#include "cstdmf/smartpointer.hpp"
#include "cstdmf/object_pool.hpp"
#include "cstdmf/memory_stream.hpp"
#include "cstdmf/concurrency.hpp"
#include "cstdmf/watcher.hpp"
#include "cstdmf/resource_counters.hpp"

using namespace BW;

// ============================================================================
// 1. 业务对象:Player Entity
// ============================================================================
class Player : public SafeReferenceCount
{
public:
    Player( const BW::string& name, int level )
        : name_( name ), level_( level )
    {
        BW_GUARD( "Player::Player" );
        RESOURCE_COUNTER_ADD(
            DescriptionPool( "entities/Player", MP_SYSTEM, RT_OTHER ),
            sizeof(Player), 0 );
    }
    
    ~Player()
    {
        BW_GUARD( "Player::~Player" );
        RESOURCE_COUNTER_SUB(
            DescriptionPool( "entities/Player", MP_SYSTEM, RT_OTHER ),
            sizeof(Player), 0 );
    }
    
    const BW::string& name() const { return name_; }
    int level() const { return level_; }
    
private:
    BW::string  name_;
    int         level_;
};

typedef SmartPointer<Player> PlayerPtr;

// ============================================================================
// 2. Player 池
// ============================================================================
class PlayerPool
{
public:
    PlayerPool( size_t initialSize = 100 )
        : pool_( initialSize )
    {
        BW_GUARD( "PlayerPool::PlayerPool" );
    }
    
    Handle<16, 16> create( const BW::string& name, int level )
    {
        BW_GUARD( "PlayerPool::create" );
        Handle<16, 16> h = pool_.create();
        Player*& slot = pool_[h];   // 实际是 PackedObjectPool<Player>::operator[]
        // 注意:PackedObjectPool 不存指针,而是 Player 对象本身
        // 这里改用 SmartPointer<Player> 表达
        slot = new Player( name, level );
        return h;
    }
    
    void destroy( Handle<16, 16> h )
    {
        BW_GUARD( "PlayerPool::destroy" );
        Player*& slot = pool_[h];
        slot = nullptr;   // 触发 SmartPointer 析构
        pool_.release( h );
    }
    
    PlayerPtr get( Handle<16, 16> h )
    {
        if ( !pool_.isValid( h ) ) return nullptr;
        return pool_[h];
    }
    
private:
    PackedObjectPool< PlayerPtr > pool_;
};

// ============================================================================
// 3. 配置加载(BW::map)
// ============================================================================
class Config
{
public:
    void loadFromStream( BinaryIStream& s )
    {
        BW_GUARD( "Config::loadFromStream" );
        while ( !s.remainingLength() == 0 )
        {
            BW::string key;
            BW::string value;
            s >> key;
            if (s.error()) break;
            s >> value;
            if (s.error()) break;
            values_[key] = value;
        }
    }
    
    BW::string get( const BW::string& key, const BW::string& def ) const
    {
        auto it = values_.find( key );
        return (it != values_.end()) ? it->second : def;
    }
    
private:
    BW::map< BW::string, BW::string > values_;
};

// ============================================================================
// 4. 网络消息打包
// ============================================================================
void sendPlayerUpdate( BinaryOStream& out, Handle<16, 16> handle,
                       const PlayerPtr& player )
{
    BW_GUARD( "sendPlayerUpdate" );
    out << (uint32) handle;          // handle 编码
    out << player->name();
    out << (int32) player->level();
}

// ============================================================================
// 5. main
// ============================================================================
int main( int argc, char** argv )
{
    // memhook 已在 #pragma init_seg(lib) 阶段初始化
    // FixedSizedAllocator 已通过 placement new 构造
    
    BW::ScopedStackTrack sst( __FILE__, __LINE__ );  // 顶层 stack track
    
    // 初始化 Watcher root
    WatcherPtr root = new DirectoryWatcher;
    RootWatcher::instance().setRoot( root, "server" );
    
    // 创建 Player 池
    PlayerPool players( 1000 );
    
    // 创建几个 player
    Handle<16, 16> h1 = players.create( "Alice", 1 );
    Handle<16, 16> h2 = players.create( "Bob", 5 );
    
    {
        // 通过 SmartPointer 访问
        PlayerPtr p1 = players.get( h1 );
        if ( p1 ) {
            printf( "Player: %s (level %d)\n",
                p1->name().c_str(), p1->level() );
        }
    }
    
    // 打包网络消息
    {
        MemoryOStream stream( 256 );   // 初始 256 字节
        sendPlayerUpdate( stream, h1, players.get( h1 ) );
        
        // 通过 socket 发送(伪代码)
        // socket.send( stream.data(), stream.size() );
        
        // 假设收到回包,用 MemoryIStream 解析
        MemoryIStream is( stream.data(), stream.size() );
        uint32 handle;
        BW::string name;
        int32 level;
        is >> handle >> name >> level;
        
        printf( "Received: handle=%u, name=%s, level=%d\n",
            handle, name.c_str(), level );
    }
    
    // 销毁 player
    players.destroy( h1 );
    players.destroy( h2 );
    
    // 程序退出前,dump 残留分配
    MemoryDebug::instance().dumpLiveAllocations();
    
    return 0;
}
```

```
   ↓

   ↓
```

### 20.4 关键性能点

1. **Player 创建**:FixedSizedAllocator + PackedObjectPool swap-back,每次约 100 ns(无 contention)。
2. **SmartPointer incRef/decRef**:每次原子操作 5-10 ns,创建一个临时 SmartPointer 约 50 ns。
3. **MemoryOStream 打包**:每字段约 10 ns,256 字节消息打包 < 100 ns。
4. **MemoryOStream 析构**:1 次 bw_free,约 50 ns。
5. **RESOURCE_COUNTER_ADD**:200 ns(含锁)。

总单次"创建 Player + 发送消息 + 销毁 Player"约 500 ns,可承受每秒 200 万次操作。对于 CellApp 处理万级 Entity,绰绰有余。

### 22.4 代码层面调优

#### 1. 减少临时对象

```cpp
// 差:每次循环都构造 BW::string
for (int i = 0; i < 1000; ++i) {
    BW::string msg = "Player " + BW::string(i) + " spawned";
    log(msg);
}

// 好:用StringRef,避免分配
for (int i = 0; i < 1000; ++i) {
    char buf[64];
    sprintf(buf, "Player %d spawned", i);
    log(BW::StringRef(buf));
}
```

#### 2. 预 reserve 容器

```cpp
// 差:边读边扩容
BW::vector<int> v;
while (readFile(...)) v.push_back(x);

// 好:先 reserve
BW::vector<int> v;
v.reserve(fileSize);
while (readFile(...)) v.push_back(x);
```

#### 3. 用 move 而非拷贝

```cpp
// 差:返回拷贝
BW::vector<int> makeData() {
    BW::vector<int> v = ...;
    return v;
}

// 好:C++11 move(自动)
BW::vector<int> makeData() {
    BW::vector<int> v = ...;
    return std::move(v);   // 显式 move
}
```

#### 4. 避免锁内分配

```cpp
// 差:锁内分配可能竞争
{
    SimpleMutexHolder h(mtx_);
    BW::string s = compute();   // bw_new 可能竞争
    data.push_back(s);          // vector 扩容也竞争
}

// 好:锁外分配,锁内只更新
BW::string s = compute();
{
    SimpleMutexHolder h(mtx_);
    data.push_back(std::move(s));
}
```

#### 5. 用 SharedString 共享常量

```cpp
// 差:每对象一份字符串副本
class Player {
    BW::string role_ = "warrior";
};

// 好:用 SharedString 全局共享
class Player {
    SharedString role_{ "warrior" };
};
```

#### 6. 用 PackedObjectPool 替代 vector<SmartPointer>

```cpp
// 差:SmartPointer 每个单独分配
BW::vector<SmartPointer<Player>> players;

// 好:PackedObjectPool 一次分配
PackedObjectPool<Player> players;
```

### 22.5 平台特定调优

#### Windows

- 用 `nedmalloc`(默认已启用)
- 启用 `/LARGEADDRESSAWARE`(32 位可访问 4GB,而非 2GB)
- 关闭 `/DYNAMICBASE` 可能让 FixedSizedAllocator 地址稳定(便于复现问题,牺牲 ASLR)

#### Linux

- 用 `glibc malloc`(默认),或预加载 `libtcmalloc.so`
- 调整 `MALLOC_MMAP_THRESHOLD_`(大块用 mmap 阈值)
- 用 `ulimit -v` 限制虚拟内存,触发早期 OOM 而非 swap 抖动

#### Android

- 用 bionic libc(已优化)
- 关闭 FixedSizedAllocator(bionic 已含 thread cache)
- 用 `mallinfo()` 监控内存

### 22.6 长时间运行的内存增长

#### 常见原因

1. **LiveAllocationMap 不清理**:MemoryDebug 把"曾分配但现在已释放"的记录保留,用于事后分析。可定期调用 `MemoryDebug::instance().clearStaleRecords()`。

2. **ResourceCounters 中 description 累积**:每次新增 description 字符串都进 map。可改用 handle,避免重复字符串。

3. **SharedString 永不释放**:SharedString 的全局 hash 表是 weak reference 还是 strong?若是 strong,字符串永不回收。

4. **Watcher tree 累积**:每注册一个 Watcher 占用内存,大量临时 watcher 会泄漏。用 RAII 注册(`WatcherHolder`)。

#### 排查工具

```bash
# 每 6 小时 dump 一次内存状态
bwmachined --watch "server/memory/usage" > dump_$(date +%s).csv

# 对比两次 dump,看哪些 description 增长
diff dump_1.csv dump_2.csv | grep "^>"
```

## 二十三、附录 C:常见内存问题

### 23.1 内存泄漏

#### 症状

- 进程 RSS(常驻内存)随时间持续增长
- 长跑(几天/几周)后 OOM 崩溃

#### 排查步骤

1. **确认是真泄漏**:可能是缓存或 fragment。
   ```bash
   ps -o rss,vsz,cmd -p <PID>
   ```
   若 RSS 增长但 LiveAllocationMap 显示分配数不变,则是 fragment(碎片)。

2. **启用 MemoryDebug,跑 1 小时**:
   ```
   dumpLiveAllocations → report.txt
   ```
   按文件/调用栈分组,找出最频繁的泄漏点。

3. **分析调用栈**:
   ```
   Leak: 0x7f8a9b3c1000, size=64
     File: entity.cpp:120
     Callstack:
       Entity::Entity
       EntityManager::create
       main
   ```
   找到对应代码,检查是否漏 `delete`。

#### 常见泄漏模式

**1. SmartPointer 循环引用**

```cpp
class A : public ReferenceCount {
    SmartPointer<B> b;
};
class B : public ReferenceCount {
    SmartPointer<A> a;   // 循环!
};

SmartPointer<A> pa = new A;
SmartPointer<B> pb = new B;
pa->b = pb;
pb->a = pa;
// 退出作用域后,pa/pb 引用计数都从 2 减到 1,都不释放!
```

**修复**:把其中一个改为 raw pointer(`B* a`),表示"非拥有"。

**2. 全局 cache 不清理**

```cpp
class TextureCache {
    BW::map<BW::string, SmartPointer<Texture>> cache;
    // 只 add,不 evict → 永远增长
};
```

**修复**:加 LRU 淘汰,限制 cache 大小。

**3. lambda 捕获 SmartPointer**

```cpp
SmartPointer<Foo> foo = new Foo;
scheduler.post([foo]() {   // 捕获 foo by value
    foo->doSomething();
});
// foo 出作用域,但 lambda 仍持有 → 推迟到 lambda 执行
// 若 lambda 永不执行,foo 永不释放
```

**修复**:确保 lambda 执行,或用 weak_ptr。

### 23.2 use-after-free

#### 症状

- 进程随机崩溃,callstack 不一致
- AddressSanitizer 报 "heap-use-after-free"

#### 排查

启用 `ENABLE_PROTECTED_ALLOCATOR` 或 ASan:

```
==12345== ERROR: AddressSanitizer: heap-use-after-free
    READ of size 8 at 0x7f8a9b3c1000
    #0 Player::getName() player.cpp:45
    #1 main main.cpp:120
freed by:
    #0 free
    #1 Player::~Player() player.cpp:30
previously allocated by:
    #0 new
    #1 PlayerPool::create() pool.cpp:78
```

#### 常见模式

**1. SmartPointer 出作用域后访问 raw pointer**

```cpp
Player* raw = nullptr;
{
    SmartPointer<Player> sp = new Player;
    raw = sp.getObject();
}   // sp 析构,Player 释放
raw->getName();   // use-after-free!
```

**修复**:全程用 SmartPointer,不要取 raw pointer。

**2. 容器 erase 后迭代器失效**

```cpp
BW::vector<int> v = {1, 2, 3, 4};
for (auto it = v.begin(); it != v.end(); ++it) {
    if (*it == 2) v.erase(it);   // it 失效!
    // 接下来 ++it 操作已释放内存
}
```

**修复**:`it = v.erase(it);`(返回下一个迭代器)。

### 23.3 双重释放

#### 症状

- glibc 报 "double free or corruption"
- Windows 报 "Heap Corruption"

#### 排查

启用 `ProtectedAllocator`,每次 free 后填充 `DeadLandFill (0xDD)`,下次 free 时检测:

```
ASSERT FAILED: memory at 0x... is already dead (filled with 0xDD)
```

#### 常见模式

```cpp
Player* p = new Player;
delete p;
delete p;   // double free!
```

或通过 SmartPointer:

```cpp
SmartPointer<Player> p1 = new Player;
SmartPointer<Player> p2 = p1;
// 两个 SmartPointer 都管理同一指针
// p1 析构时 delete
// p2 析构时再 delete → double free
```

但 BW SmartPointer 通过 `incRef` 防止这个,所以这种情况不会发生。

更隐蔽的:用户在 SmartPointer 之外取 raw pointer 并 delete:

```cpp
SmartPointer<Player> sp = new Player;
Player* raw = sp.getObject();
delete raw;   // raw 与 sp 都管理,sp 析构时 double free
```

**修复**:不要从 SmartPointer 取出 raw pointer 并 delete。

### 23.4 缓冲区溢出

#### 症状

- 进程随机崩溃,callstack 在无关代码
- ProtectedAllocator 触发 page guard

#### 排查

```
ProtectedAllocator: buffer overflow detected!
    Buffer at 0x7f8a9b3c1000, size=64
    Write at 0x7f8a9b3c1040 (out of bounds by 0 bytes)
    Allocation site: player.cpp:120
```

#### 常见模式

**1. strcpy 不检查长度**

```cpp
char buf[16];
strcpy(buf, userSuppliedString);   // 若 userSuppliedString > 15 字节,溢出
```

**修复**:用 `strncpy` 或 `BW::string`。

**2. 数组越界**

```cpp
int arr[10];
for (int i = 0; i <= 10; ++i) {   // 应该是 < 10
    arr[i] = i;
}
```

### 23.5 死锁

#### 症状

- 进程"卡住",CPU 0%
- 多线程,几个线程都在等锁

#### 排查

Linux 用 `gdb`:

```bash
gdb -p <PID>
(gdb) info threads
(gdb) thread apply all bt
```

找都在 `__lll_lock_wait` 的线程,看它们等哪个 mutex。

#### 常见模式

**1. 锁顺序不一致**

```cpp
// Thread A:
lock(mtx1);
lock(mtx2);   // 等 mtx2

// Thread B:
lock(mtx2);
lock(mtx1);   // 等 mtx1
// 死锁!
```

**修复**:全局统一锁顺序(如按地址升序)。

**2. SimpleMutex 重入**

```cpp
void foo() {
    SimpleMutexHolder h(mtx_);
    bar();   // bar 也 lock(mtx_) → assert!
}

void bar() {
    SimpleMutexHolder h(mtx_);   // 重入
}
```

**修复**:用 RecursiveMutex,或重构避免重入。

### 23.6 数据竞争

#### 症状

- 结果不稳定,多次运行结果不同
- ThreadSanitizer 报 "data race"

#### 排查

```bash
# 编译时加 -fsanitize=thread
g++ -fsanitize=thread server.cpp
./a.out
```

TSan 输出:

```
WARNING: ThreadSanitizer: data race
    Write by main thread:
        #0 increment counter.cpp:10
    Previous read by thread T1:
        #0 read counter.cpp:5
    Location: counter (global) at 0x...
```

#### 修复

加锁或用 `BW_ATOMIC32_*`:

```cpp
// 差:无同步
int counter = 0;
// 多线程:
counter++;

// 好:原子操作
BW_ATOMIC32_INC_AND_FETCH(&counter);

// 或锁
{
    SimpleMutexHolder h(mtx_);
    counter++;
}
```

### 23.7 跨 DLL 内存问题

#### 症状

- 在 DLL 边界传 new/delete 不匹配,崩溃
- vtable 不一致,虚函数调用错误函数

#### 排查

启用 `SafeAllocatable`(已默认),所有跨 DLL new/delete 都走 bw_new/bw_delete。

#### 常见模式

```cpp
// DLL A 导出
class __declspec(dllexport) Foo {
public:
    Foo() {}
    virtual ~Foo() {}   // 虚析构
};

// DLL B 使用
Foo* p = new Foo();   // 在 DLL B 中分配
delete p;   // 在 DLL B 中 delete
// 但 Foo 的 vtable 来自 DLL A,可能 layout 不同
```

**修复**:继承 SafeAllocatable,确保 new/delete 走同一分配器。

### 23.8 内存碎片导致 OOM

#### 症状

- 总空闲内存足够,但分配大块失败
- 报 "out of memory" 但 free 显示充足

#### 排查

```bash
cat /proc/<PID>/status | grep -E "VmPeak|VmRSS|VmSize"
cat /proc/<PID>/maps   # 看虚拟地址空间布局
```

碎片表现为:虚拟地址空间不连续,中间有大量小"洞"。

#### 修复

- 改用 FixedSizedAllocator(无外碎片)
- 或重启进程(治标)

## 二十四、总结与延伸阅读

### 24.1 BigWorld 内存管理核心思想回顾

#### 1. 分层抽象

```
用户 API(bw_new / SmartPointer / BW::vector)
   ↓
STL 适配器(StlAllocator<T>)
   ↓
分配器后端(FixedSizedAllocator / AnsiAllocator / ...)
   ↓
全局钩子(memhook operator new/delete)
   ↓
系统 API(malloc / HeapAlloc)
```

每层职责清晰,允许独立替换。

#### 2. Debug / Release 双模式

- Debug:全追踪(MemoryDebug、StackTracker、ProtectedAllocator),慢但信息全
- Release:零追踪,极致性能

通过编译期宏 `ENABLE_*` 切换,无运行时开销。

#### 3. 安全句柄替代裸指针

`Handle<16, 16>` 用 32 位整数 + generation,杜绝悬空指针。

#### 4. 侵入式引用计数

`SafeReferenceCount` 嵌入对象,`SmartPointer<T>` 管理,跨线程安全。

#### 5. 池化降低分配开销

`FixedSizedAllocator` 按 size class 分桶,`PackedObjectPool` swap-with-back 保持紧凑。

#### 6. 统一观测

`ResourceCounters` + `Watcher` 提供运行时可观测性,无需修改代码即可远程查看内存状态。

### 24.2 设计哲学总结

BigWorld 内存系统的设计哲学:

1. **可调试性 > 性能**:Debug build 大量投资在追踪,以便在开发期发现问题。
2. **编译期开关 > 运行时开关**:避免运行时分支,极致 Release 性能。
3. **侵入式 > 非侵入式**:SmartPointer 嵌入对象,省分配,易调试。
4. **句柄 > 指针**:牺牲一次间接访问,换取安全性。
5. **C++03 兼容**:不依赖 C++11/14/17 现代特性,最大化编译器兼容。
6. **跨 DLL 一致**:SafeAllocatable + stateless StlAllocator 保证跨边界安全。

### 24.3 历史地位

BigWorld 内存系统反映 2004-2012 年的游戏引擎设计水平:

- 同时代引擎(CryEngine 3、Unreal 3、Source)采用类似设计
- 与现代引擎(Unreal 5、Unity DOTS)相比,缺少 ECS-aware allocator、无 GC
- 但核心思想(池化、句柄、引用计数)仍是现代引擎基础

### 24.4 改进路线图(若重写)

1. **短期(C++11 升级)**:static_assert / nullptr / override / move 语义
2. **中期(分配器升级)**:tcmalloc 后端、thread-cache
3. **长期(C++17 重构)**:PMR、string_view、optional、variant
4. **架构(若推倒重来)**: ECS + 数据导向设计,组件池 + 系统
