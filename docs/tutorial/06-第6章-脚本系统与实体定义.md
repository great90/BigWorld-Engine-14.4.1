## 6.1 pyscript 库概述

### 6.1.1 位置与职责

`pyscript` 库位于 `programming/bigworld/lib/pyscript/`,它是 BigWorld 中所有 C++ 代码访问 Python 的统一入口。无论是服务器进程(CellApp / BaseApp / DBApp / LoginApp)调用 Python 实体脚本,还是工具链(`process_defs`、`WorldEditor`)读写 Python 描述对象,最终都要经过这一层。

它的职责可以概括为四点:

1. **解释器生命周期管理**:`Script::init` / `Script::fini` / 多线程锁(`PyThreadState`)。
2. **类型转换**:C++ 内建类型(`int`/`float`/`string`/`Vector3`/`Matrix`/`BW::map`/`BW::vector` …)与 Python 对象之间的双向转换。
3. **PyObject\* 封装**:用 `SmartPointer<PyObject>`(`PyObjectPtr`)与更高层的 `ScriptObject` 模板类把裸指针包成 RAII 对象,自动管理引用计数。
4. **类与方法导出**:`PyObjectPlus` 基类 + 一组 `PY_*` 宏,让 C++ 类(如 `PyEntityMailBox`、`PyDeferredResponse`)像 Python 类一样有属性、方法、`__repr__` 等。

### 6.1.2 设计理念

`pyscript` 在设计上贯彻三条原则:

| 原则 | 体现 |
|---|---|
| **零成本抽象** | 模板 + 内联函数实现类型转换,运行时无虚函数开销;只有"导出类"才走 PyObjectPlus。 |
| **错误策略可选** | 用模板参数 `ERROR_HANDLER`(如 `ScriptErrorPrint` / `ScriptErrorClear` / `ScriptErrorRetain`)让调用方决定如何处理 Python 异常。 |
| **引用计数自动** | `PyObjectPtr` 是 `SmartPointer<PyObject>`,自动 `Py_INCREF` / `Py_DECREF`,杜绝内存泄漏。 |

`lib/pyscript/` 下大约 30 个文件,可以按职责分组:

## 6.2 Python 集成基础

### 6.2.1 Script::init / fini

`Script` 命名空间(`script.hpp:46-481`)是 pyscript 的"门面"。引擎启动时,每个需要使用 Python 的进程都会调用:

```cpp
bool Script::init( const PyImportPaths & pythonPaths,
                   const char * componentName = "Unknown" );
```

`init` 的关键工作(`script.cpp` 第 55 行附近开始的 `init`)包括:

1. 设置 Python 路径(`PyImportPaths` 把多个目录组合成 `sys.path`)。
2. 调用 `Py_InitializeEx(0)` 初始化解释器。
3. 注册 BigWorld 自己的内置模块(`BigWorld`、`BWLog`、`Watcher`、`BigWorldFileHelper` 等)。
4. 安装钩子(Profiler / StackTracker / Hitch 检测)。
5. 在退出时通过 `Script::FiniTimeJob` 链按依赖顺序释放模块,避免悬空指针。

`Script::fini(shouldFinalise)` 负责反向清理:它会先调用注册的 `FiniTimeJob`(`init_time_job.hpp`),由它们负责解除对 Python 对象的引用,最后才调用 `Py_Finalize`。这一设计解决了"模块之间相互引用导致无法干净退出"的难题——`Personality`、`DataType`、`EntityDef` 等组件都可以注册自己的清理任务。

### 6.2.2 多解释器与线程锁

BigWorld 服务器是多线程的(BaseApp 有主线程 + 数据库线程,CellApp 有主线程 + 网络线程),但 Python 解释器不是完全线程安全的。`Script` 提供了三组接口来支持多解释器:

```cpp
PyThreadState* createInterpreter();
void destroyInterpreter( PyThreadState* pInterpreter );
PyThreadState* swapInterpreter( PyThreadState* pInterpreter );

class AutoInterpreterSwapper
{
    PyThreadState* pSwappedOutInterpreter_;
public:
    explicit AutoInterpreterSwapper( PyThreadState* pNewInterpreter ) :
        pSwappedOutInterpreter_( swapInterpreter( pNewInterpreter ) )
    {}
    ~AutoInterpreterSwapper()
    {
        swapInterpreter( pSwappedOutInterpreter_ );
    }
};
```

`AutoInterpreterSwapper` 是经典的 RAII:构造时切到子解释器,析构时切回原解释器。这样在数据库线程中执行 Python 时,只需写:

```cpp
{
    AutoInterpreterSwapper swapper( pDbInterpreter );
    // 在此作用域内,Python 调用都使用 pDbInterpreter
    entity.callMethod( "onLoadFromDB", ScriptErrorPrint() );
}
```

### 6.2.3 类型转换 setData / getData

`Script` 命名空间中最常用的两个函数家族是 `setData` 和 `getData`,它们构成了 C++ 与 Python 之间的双向桥梁。`setData(PyObject*, T&, varName)` 把 Python 对象转成 C++ 类型;`getData(const T&)` 把 C++ 类型转成 Python 对象。

`script.hpp:110-177` 列出了所有内建重载:

```cpp
int setData( PyObject * pObj, bool   & rVal, const char * varName = "" );
int setData( PyObject * pObj, int    & rVal, const char * varName = "" );
int setData( PyObject * pObj, float  & rVal, const char * varName = "" );
int setData( PyObject * pObj, double & rVal, const char * varName = "" );
int setData( PyObject * pObj, int64 & rVal, const char * varName = "" );
int setData( PyObject * pObj, Vector2 & rVal, const char * varName = "" );
int setData( PyObject * pObj, Vector3 & rVal, const char * varName = "" );
int setData( PyObject * pObj, Vector4 & rVal, const char * varName = "" );
int setData( PyObject * pObj, Matrix  & rVal, const char * varName = "" );
int setData( PyObject * pObj, BW::string  & rString, const char * varName = "" );
int setData( PyObject * pObj, BW::wstring & rString, const char * varName = "" );
int setData( PyObject * pObj, Mercury::Address & rAddr, ... );
...

PyObject * getData( const int data );
PyObject * getData( const float data );
PyObject * getData( const Vector3 & data );
PyObject * getData( const BW::string & data );
PyObject * getData( const Matrix & data );
...
```

返回值约定遵循 Python C-API 的惯例:`setData` 返回 `0` 表示成功,返回 `-1` 表示失败(同时 Python 异常状态已设置);`getData` 返回新的 `PyObject*` 引用(可能为 `NULL`)。`varName` 仅用于错误信息(如 `"player.pos.x"`),便于在异常时给出有意义的提示。

### 6.2.4 容器类型的模板化转换

`script.hpp:254-335` 提供了 STL 容器的自动转换:

```cpp
// setData for vectors
template <class T, class A> int setData( PyObject * pObj,
    BW::vector<T,A> & res, const char * varName = "" )
{
    return setDataSequence<T>( pObj, res, varName );
}

// setData for maps
template <class K, class T, class C, class A> int setData( PyObject * pObj,
    BW::map<K,T,C,A> & res, const char * varName = "" )
{
    return setDataMapping<K,T>( pObj, res, varName );
}
```

`setDataSequence` 内部用 `PySequence_Check` + `PySequence_GetItem` 把 Python `list`/`tuple` 转 `BW::vector`;`setDataMapping` 用 `PyDict_Next` 遍历 `dict` 转 `BW::map`。这种基于模板的转换对用户极其友好——你在 C++ 写一个 `BW::vector<BW::string>`,就能直接接收 Python 中传入的 `["a", "b", "c"]`。

### 6.2.5 整数范围检查

整数类型转换要小心平台差异。`script.hpp:181-198` 定义了 `INT_ACCESSOR` 宏,在 `int8`/`int16`/`uint8`/`uint16` 转换时先转成更大类型,再检查是否越界:

```cpp
#define INT_ACCESSOR( INPUT_TYPE, COMMON_TYPE )                 \
    inline PyObject * getData( const INPUT_TYPE data )           \
        { return getData( COMMON_TYPE( data ) ); }              \
    inline int setData( PyObject * pObject, INPUT_TYPE & rInt,   \
                        const char * varName = "" )             \
        {                                                       \
            COMMON_TYPE value;                                  \
            int result = setData( pObject, value, varName );    \
            rInt = INPUT_TYPE( value );                         \
            if (rInt != value )                                 \
            {                                                   \
                PyErr_SetString( PyExc_TypeError,               \
                    "Integer is out of range" );                \
                return -1;                                      \
            }                                                   \
            return result;                                      \
        }
```

这种"先转大类型再回塞小类型"的写法能优雅捕获 `int8 x = 200` 这类错误。

### 6.2.6 PY_SCRIPT_CONVERTERS 宏

为了让自定义的 `PyObjectPlus` 派生类也能享受 `setData/getData` 自动转换,`script.hpp:490-573` 提供了两个宏:

- `PY_SCRIPT_CONVERTERS_DECLARE(CLASS)`:声明特化版本。
- `PY_SCRIPT_CONVERTERS(CLASS)`:定义特化版本,内部调用 `CLASS::Check` / `CLASS::coerce` 完成类型检查。

声明之后,你就可以写:

```cpp
SmartPointer<Avatar> pAv;
Script::setData( pyObj, pAv, "avatar" );   // 自动类型检查
```

## 6.3 脚本对象模型

直接使用 `PyObject*` 与 `Script::setData/getData` 仍然不够安全:每次返回的新引用都要手动 `Py_DECREF`,容易出错。BigWorld 提供了更高层的封装,位于 `lib/script/`(注意不是 `lib/pyscript/`)。

### 6.3.1 PyObjectPtr - 智能指针特化

`pyobject_pointer.hpp:9-44` 是基础:

```cpp
typedef SmartPointer<PyObject> PyObjectPtr;

template <>
inline void incrementReferenceCount( const PyObject & Q )
{
    Py_INCREF( const_cast<PyObject*>( &Q ) );
}

template <>
inline void decrementReferenceCount( const PyObject & Q )
{
    Py_DECREF( const_cast<PyObject*>( &Q ) );
}
```

它利用 `cstdmf` 中通用的 `SmartPointer<T>` 模板,通过特化 `incrementReferenceCount` / `decrementReferenceCount` 把 Python 的引用计数"嫁接"到 C++ 的 RAII 上。`PyObjectPtr` 一旦析构,内部的 `Py_DECREF` 自动触发。

### 6.3.2 ScriptObject - 高层包装

`lib/script/py_script_object.hpp:211` 起定义的 `ScriptObject` 是 Python 对象的最常用包装:

```cpp
class BWENTITY_API ScriptObject : public PyObjectPtr
{
public:
    static const bool FROM_NEW_REFERENCE = true;
    static const bool FROM_BORROWED_REFERENCE = false;

    ScriptObject( PyObject * pObject, bool alreadyIncremented ) :
        PyObjectPtr( pObject, alreadyIncremented )
    {
    }
    ...
    template <class ERROR_HANDLER>
    ScriptObject getAttribute( const char * key,
        const ERROR_HANDLER & errorHandler ) const
    {
        PyObject * result = PyObject_GetAttrString( this->get(),
            const_cast< char * >( key ) );
        errorHandler.checkPtrError( result );
        return ScriptObject( result, ScriptObject::FROM_NEW_REFERENCE );
    }

    template <class ERROR_HANDLER>
    bool setAttribute( const char * key, const ScriptObject & value,
            const ERROR_HANDLER & errorHandler ) const
    {
        int result = PyObject_SetAttrString( this->get(), key, value.get() );
        errorHandler.checkMinusOne( result );
        return result != -1;
    }

    template <class ERROR_HANDLER>
    ScriptObject callMethod( const char * methodName,
            const ERROR_HANDLER & errorHandler,
            bool allowNullMethod = false ) const;
    ...
};
```

注意两个细节:

1. **构造函数显式要求"引用已增加否"**:用 `FROM_NEW_REFERENCE` 或 `FROM_BORROWED_REFERENCE` 显式表达。这是 BigWorld 团队在大量踩坑后总结出的设计——它强迫写代码的人每次都停下来想一下"这个 `PyObject*` 是 new ref 还是 borrowed ref"。
2. **错误处理通过模板参数注入**:`getAttribute` 等方法都接受一个 `ERROR_HANDLER`,可以是:
   - `ScriptErrorPrint`:打印并清除异常(用于一次性的"尽力而为"调用)。
   - `ScriptErrorClear`:静默清除(用于"探测"调用)。
   - `ScriptErrorRetain`:保留异常状态(用于调用方稍后用 `PyErr_Print` 详细处理)。

### 6.3.3 派生类:ScriptTuple / ScriptList / ScriptDict / ScriptModule

`ScriptObject` 之上还派生了多个特化类型,分别对应 Python 的 `tuple`、`list`、`dict`、`module`:

| 类 | 文件 | 用途 |

### 6.3.4 PyObjectPlus - 导出 C++ 类的基类

C++ 类要被 Python 看到,必须继承 `PyObjectPlus`(`pyobject_plus.hpp`)。`Py_Header` 宏(`pyobject_plus.hpp:60-97`)在每个派生类的开头声明一组静态函数,把 Python C-API 的 `tp_*` 回调转发到 C++ 实例方法:

```cpp
class PyEntityMailBox : public PyObjectPlus
{
    Py_Header( PyEntityMailBox, PyObjectPlus )    // 必须放在第一行
public:
    ...
    PyObject * pyGetAttribute( const ScriptString & attrObj );
    int pySetAttribute( const ScriptString & attrObj,
                        const ScriptObject & value );
};
```

`Py_Header` 展开后会生成:

```cpp
static void _tp_dealloc( PyObject * pObj ) {
    static_cast< PyEntityMailBox * >( pObj )->pyDel();
    delete static_cast< PyEntityMailBox * >( pObj );
}
static PyObject * _tp_getattro( PyObject * pObj, PyObject * name ) {
    return static_cast<PyEntityMailBox*>(pObj)->pyGetAttribute(...).newRef();
}
static int _tp_setattro( PyObject * pObj, PyObject * name, PyObject * value ) {
    return (value != NULL)
        ? (static_cast<PyEntityMailBox*>(pObj)->pySetAttribute(...) ? 0 : -1)
        : (static_cast<PyEntityMailBox*>(pObj)->pyDelAttribute(...) ? 0 : -1);
}
```

派生类还可以用一组 `PY_*` 宏声明方法与属性:

- `PY_BEGIN_METHODS` / `PY_METHOD(name)` / `PY_END_METHODS`:声明导出的 Python 方法。
- `PY_BEGIN_ATTRIBUTES` / `PY_RO_ATTRIBUTE_DECLARE` / `PY_RW_ATTRIBUTE_DECLARE`:声明属性。
- `PY_AUTO_METHOD_DECLARE(RET, NAME, ARGS)`:声明一个能自动解析参数的方法。
- `PY_FACTORY_DECLARE` / `PY_AUTO_FACTORY_DECLARE`:声明工厂方法(供 Python 创建 C++ 对象)。

例如 `mailbox_base.hpp:55-100` 的 `PyEntityMailBox`:

```cpp
class PyEntityMailBox: public PyObjectPlus
{
    Py_Header( PyEntityMailBox, PyObjectPlus )
public:
    ...
    PY_RO_ATTRIBUTE_DECLARE( this->id(), id );
    PyObject * pyGet_address();
    PY_RO_ATTRIBUTE_SET( address );
};
```

`PY_RO_ATTRIBUTE_DECLARE` 会把 `this->id()` 的返回值暴露成 Python 上的只读属性 `id`,Python 端写 `mailbox.id` 就能取到。

## 6.4 pickler 序列化

### 6.4.1 设计意图

实体持久化、Mailbox 引用、跨进程的对象传递,都需要把 Python 对象"扁平化"成字节流。BigWorld 没有自己实现一套序列化格式,而是直接复用 Python 标准库的 `pickle` 模块,通过 `Pickler` 类(`lib/script/pickler.hpp`、`lib/pyscript/pickler.cpp`)做了薄薄一层封装:

```cpp
class Pickler
{
public:
    static BW::string     pickle( ScriptObject pObj );
    static ScriptObject   unpickle( const BW::string & str );
    static bool           init();
    static void           finalise();
};
```

API 极简:`pickle` 把对象序列化成 `BW::string`,`unpickle` 反之。`init`/`finalise` 在引擎启动/退出时调用一次,缓存 `cPickle.dumps` / `cPickle.loads` 两个方法对象(`pickler.cpp:65-90`)以避免每次都 `PyObject_GetAttrString`。

### 6.4.2 实现:薄包装 + 容错

`Pickler::pickle`(`pickler.cpp:116`)的实现:

```cpp
BW::string Pickler::pickle( ScriptObject object )
{
    PyObject * pObj = object.get();
    if (!pObj)
    {
        ERROR_MSG( "Pickler::pickle: attempting to pickle NULL\n" );
    }
    else if (pObj->ob_type == &FailedUnpickle::s_type_)
    {
        // 已经是失败占位对象,直接返回其内部保存的原始字节
        return static_cast< FailedUnpickle * >( pObj )->pickleData();
    }
    else if (s_pPickleMethod != NULL)
    {
        PyObject * pResult = PyObject_CallFunction( s_pPickleMethod,
                                                    "(Oi)", pObj, 2 );
        if (pResult == NULL)
        {
            ERROR_MSG( "Pickler::pickle: failed to pickle object\n" );
            PyErr_Print();
        }
        else
        {
            BW::string str;
            str.assign( PyString_AsString( pResult ), PyString_Size( pResult ));
            Py_DECREF( pResult );
            return str;
        }
    }
    return "";
}
```

注意参数 `(Oi, pObj, 2)` 中的 `2` 是 `pickle.HIGHEST_PROTOCOL`,即使用最高协议版本以获得最高效率。

### 6.4.3 FailedUnpickle - 反序列化失败的优雅降级

`unpickle`(`pickler.cpp:160`)有一个巧妙的容错设计:如果反序列化失败(例如字节流损坏、或引用的类已不存在),它不会抛异常,而是创建一个 `FailedUnpickle` 占位对象:

```cpp
ScriptObject Pickler::unpickle( const BW::string & str )
{
    PyObject* pResult = NULL;
    if (s_pUnpickleMethod != NULL)
    {
        pResult = PyObject_CallFunction( s_pUnpickleMethod, "(s#)",
                str.data(), str.length() );
        if (pResult == NULL)
        {
            NOTICE_MSG( "Pickler::unpickle: "
                    "Failed to unpickle. Using stand-in object.\n" );
            PyErr_Print();
        }
    }
    if (pResult == NULL)
    {
        pResult = new FailedUnpickle( str );  // 占位对象,保留原始字节
    }
    return ScriptObject( pResult, ScriptObject::STEAL_REFERENCE );
}
```

`FailedUnpickle`(`pickler.cpp:21-37`)继承自 `PyObjectPlus`,内部持有原始字节。再次 `pickle` 它时,会直接返回保存的字节流(`pickler.cpp:124-127`)。这意味着:

- 加载存档时即使某个类的代码改了,不会让整个加载过程崩溃;
- 该对象被再次写回数据库时,仍能保留原始数据不丢失。

这种"宁可不解析,也不要丢失数据"的设计哲学在 MMOG 数据迁移场景下极其重要。

### 6.4.4 pickle 的使用场景

`Pickler` 的两个主要使用者:

1. **DBApp**:把实体的"Python 类型字段"(在 `.def` 中声明为 `PYTHON` 或 `ARRAY<...>`、`FIXED_DICT` 等包含任意 Python 对象的类型)序列化后存入数据库的 `blob` 列。
2. **Mailbox 引用序列化**:`EntityMailBoxRef` 会被序列化为字节流,在跨进程消息中传递。当对方进程的 Python 代码再次访问该 Mailbox 时,通过 `unpickle` 还原。

## 6.5 entitydef 库概述

### 6.5.1 位置与职责

`entitydef` 库位于 `programming/bigworld/lib/entitydef/`,它是 BigWorld "数据驱动"理念的核心。它的任务是:在引擎启动时把所有 `.def` 文件解析成内存中的 `EntityDescription` 对象,让 C++ 引擎与 Python 脚本都通过同一份元数据来理解实体。

它的职责可以概括为四点:

1. **类型定义解析**:把 XML 格式的 `.def` 文件解析成结构化的 `EntityDescription` / `DataDescription` / `MethodDescription`。
2. **运行时元数据**:在运行时为每个实体类型提供"属性列表、方法签名、暴露给客户端的消息 ID"等元数据,供网络层、数据库层、客户端层共享。
3. **自动序列化**:根据 `.def` 中声明的类型,自动把实体属性序列化到字节流(`BinaryOStream`)或 `DataSection`,反之亦然。
4. **属性变更传播**:通过 `PropertyChange` 描述属性变更,自动同步到客户端、Ghost、数据库。

## 6.6 .def 文件格式

### 6.6.1 一个完整的 .def 示例

我们直接看一个真实示例。`examples/client_integration/python/simple/res/scripts/entity_defs/ClientAvatar.def`:

```xml
<root>
    <Volatile>

        <yaw/>
        <pitch> 20 </pitch>
    </Volatile>

    <Properties>
        <playerName>
            <Type>           STRING              </Type>

        <prop1>
            <Type>           INT32               </Type>
            <Flags>          BASE_AND_CLIENT     </Flags>
            <Default>        1                   </Default>
        </prop1>

        <prop2>
            <Type>           INT16               </Type>
```

这份 `.def` 描述了一个名为 `ClientAvatar` 的实体类型,它的全部"接口契约"都体现在这里:有哪些属性、属性属于哪个进程、是否持久化、客户端能调用什么方法……

### 6.6.2 顶层结构

`.def` 文件是 XML,根节点 `<root>` 下有五大子节点:

| 节点 | 用途 | 是否必填 |
|---|---|---|
| `<Parent>` | 父实体名,用于继承 | 可选 |
| `<ClientName>` | 客户端类名(默认与文件名相同) | 可选 |
| `<Volatile>` | Volatile 信息(位置、朝向)的发送优先级 | 可选 |
| `<Properties>` | 属性列表 | 必填(可空) |
| `<ClientMethods>` | 客户端方法(从服务端调用) | 必填(可空) |
| `<CellMethods>` | Cell 方法 | 必填(可空) |
| `<BaseMethods>` | Base 方法 | 必填(可空) |
| `<LoDLevels>` | LoD 层级 | 可选 |
| `<Components>` | 组合的组件类型 | 可选 |
| `<Distribution>` | 显式声明脚本分布 | 可选 |
| `<NetworkCompression>` | 网络压缩配置 | 可选 |
| `<AppealRadius>` | AOI 半径补偿 | 可选 |
| `<IsManualAoI>` | 手动 AOI | 可选 |

### 6.6.3 字段类型

`<Type>` 标签声明属性的数据类型,可以是简单类型或复合类型:

| 类型 | 关键字 | 备注 |
|---|---|---|
| 整数 | `INT8` / `INT16` / `INT32` / `INT64` / `UINT8` / `UINT16` / `UINT32` / `UINT64` | 各种位宽 |
| 浮点 | `FLOAT32` / `FLOAT64` | |
| 字符串 | `STRING` / `UNICODE_STRING` | |
| 向量 | `VECTOR2` / `VECTOR3` / `VECTOR4` | 内建 |
| 矩阵 | `MATRIX34` | |
| 数组 | `ARRAY< T >` | 同质序列 |
| 元组 | `TUPLE< T >` | 同质不可变序列 |
| 字典 | `DICT` / `FIXED_DICT` | FIXED_DICT 需在 `alias.xml` 声明 |
| 类 | `CLASS` | 类似结构体,有命名子字段 |
| 邮箱 | `MAILBOX` | 跨进程实体引用 |
| 任意 Python | `PYTHON` | pickle 序列化,弱类型 |
| 用户类型 | `USER_TYPE <implementedBy>...` | 用户自定义,需提供 Python 实例 |
| Blob | `BLOB` | 二进制数据块 |

简单类型在 `lib/entitydef/data_types/integer_data_type.hpp`、`float_data_types.hpp`、`string_data_type.hpp` 等文件中实现。复合类型在 `array_data_type.hpp`、`fixed_dict_data_type.hpp` 等中实现。每个类型都是 `DataType`(`data_type.hpp:39`)的派生类,负责:

- `setDefaultValue` / `getDefaultValue`:默认值生成。
- `isSameType`:类型检查。
- `addToStream` / `createFromStream`:二进制序列化。
- `addToSection` / `createFromSection`:XML 序列化。
- `getDefaultValue(DataSink&)`:写入 Python 对象。

### 6.6.4 字段属性 Flags

`<Flags>` 决定属性属于哪个进程、是否同步。`data_description.cpp:72-83` 给出了所有取值:

```cpp
EntityDataFlagMapping s_entityDataFlagMappings[] =
{
    { "CELL_PRIVATE",        0 },                              // Cell 私有,不同步
    { "CELL_PUBLIC",         DATA_GHOSTED },                    // 同步到 ghost
    { "OTHER_CLIENTS",       DATA_GHOSTED|DATA_OTHER_CLIENT },  // 同步到其他客户端
    { "OWN_CLIENT",          DATA_OWN_CLIENT },                 // 同步到自己的客户端
    { "BASE",                DATA_BASE },                       // 只在 Base
    { "BASE_AND_CLIENT",    DATA_OWN_CLIENT|DATA_BASE },        // Base + 自己客户端
    { "CELL_PUBLIC_AND_OWN", DATA_GHOSTED|DATA_OWN_CLIENT },    // ghost + 自己客户端
    { "ALL_CLIENTS",         DATA_GHOSTED|DATA_OTHER_CLIENT|DATA_OWN_CLIENT },
    { "EDITOR_ONLY",         DATA_EDITOR_ONLY },                // 仅编辑器
};
```

`EntityDataFlags`(`data_description.hpp:30-41`)定义了所有标志位:

```cpp
enum EntityDataFlags
{
    DATA_GHOSTED        = 0x01,  // 同步到 ghost 实体
    DATA_OTHER_CLIENT   = 0x02, // 发给其他客户端
    DATA_OWN_CLIENT     = 0x04, // 发给自己的客户端
    DATA_BASE           = 0x08, // 存在于 Base 进程
    DATA_CLIENT_ONLY    = 0x10, // 仅客户端可见的静态数据
    DATA_PERSISTENT     = 0x20, // 持久化到数据库
    DATA_EDITOR_ONLY    = 0x40, // 仅编辑器读写
    DATA_ID             = 0X80, // 数据库索引列
    DATA_REPLAY         = 0x100 // 暴露给回放系统
};
```

这种位标志的组合很灵活——`ALL_CLIENTS` 同时具有 `DATA_GHOSTED | DATA_OTHER_CLIENT | DATA_OWN_CLIENT`,意味着这个属性既会被同步到 ghost,又会发给所有客户端。这就是 BigWorld 的"声明式同步":你只要在 `.def` 里写一行 `<Flags>ALL_CLIENTS</Flags>`,引擎就会自动处理"何时同步、同步给谁"。

### 6.6.5 Persistent / Identifier / Indexed

除了 `<Flags>` 之外,属性还可以有三个独立开关:

- `<Persistent>true</Persistent>`:加 `DATA_PERSISTENT` 标志,存进数据库。
- `<Identifier>true</Identifier>`:作为该实体类型的"业务主键",数据库会建唯一索引(如 `playerName`)。
- `<Indexed><Unique>true</Unique></Indexed>`:建立普通或唯一索引,加速查询。

这三个标签的解析位于 `data_description.cpp:220-252`。注意 `Identifier` 隐含 `Indexed/Unique=true`。

### 6.6.6 方法定义

方法按"调用方向"分四组,放在四个顶层节点:

| 节点 | 调用方 | 被调用方 |
|---|---|---|
| `<ClientMethods>` | 服务端 | 客户端 |
| `<CellMethods>` | Base / Client | Cell |
| `<BaseMethods>` | Cell / Client | Base |
| `<ServiceMethods>` | (服务间) | Service |

每个方法是一个子节点,名字是方法名:

```xml
<ClientMethods>
    <fromCell>
        <Arg> STRING </Arg>
    </fromCell>
</ClientMethods>
```

`<Arg>` 声明参数类型,可以有多个。可选的 `<Exposed/>` 标签(见 `ClientAvatar.def` 中的 `logOff`)表示该方法"暴露给客户端调用",客户端可以远程调用这个 Base 方法。

`<Exposed>` 的具体语义见 `method_description.hpp:177-200`——它把方法分为 `IS_EXPOSED_TO_ALL_CLIENTS` / `IS_EXPOSED_TO_OWN_CLIENT` 两类,决定哪些客户端有权限调用。

### 6.6.7 Volatile 信息

`<Volatile>` 节点声明实体的位置/朝向信息多久同步一次:

```xml
<Volatile>
    <position/>
    <yaw/>
    <pitch> 20 </pitch>
</Volatile>
```

`<position/>` 不带值表示"始终发送",数字 `<pitch> 20 </pitch>` 表示"每 20 个单位时间发送一次"。`VolatileInfo`(`volatile_info.hpp`)是 `EntityDescription` 的成员,内部用 `priority`(`-1.f` 表示不发送)存储四种数据(位置、yaw、pitch、roll)的发送优先级。这是 BigWorld 的"VIP(Volatile Interest Properties)"机制——见 6.11 节深入剖析。

### 6.6.8 entities.xml - 实体清单

引擎启动时,首先读 `scripts/entities.xml`(`constants.hpp:44`),它列出了所有可用的实体类型:

```xml
<root>
    <ClientServerEntities>
        <Guard/>
        <ClientAvatar/>
        <Account/>
        <Space/>
        <ClientOnly/>
    </ClientServerEntities>
    <ServerOnlyEntities/>
</root>
```

`<ClientServerEntities>` 下的实体会被注册到客户端与服务端;`<ServerOnlyEntities>` 下的实体仅服务端可见(如 NPC、Boss)。`EntityDescriptionMap::parse`(`entity_description_map.cpp:140-193`)就从这个文件开始,逐个加载 `<Name>.def`。

### 6.6.9 继承与组件

`.def` 支持 `<Parent>` 实现单继承——子实体会继承父实体的所有属性和方法。`EntityDescription::parse`(`entity_description.cpp:194-205`)在解析时会递归调用自身解析父类型。

更复杂的是 `<Components>` 节点,它允许把多个"组件类型"组合到一个实体中,实现 mixin 风格的代码复用:

```xml
<Components>
    <Combat/>
    <Inventory/>
</Components>
```

每个组件有自己的 `.def` 文件(位于 `scripts/component_defs/`),`EntityDescription::parseComponents`(`entity_description.cpp:452`)会把它们的属性/方法合并到当前实体里,并标记 `componentName_`,以便运行时分发到正确的 Python 方法。

### 6.7.3 数据域(DataDomain)概念

`EntityDescription::DataDomain`(`entity_description.hpp:141-152`)是一个枚举,把属性按"所属进程"分组:

```cpp
enum DataDomain
{
    BASE_DATA   = 0x1,
    CLIENT_DATA = 0x2,
    CELL_DATA   = 0x4,
    EXACT_MATCH = 0x8,
    ONLY_OTHER_CLIENT_DATA = 0x10,
    ONLY_PERSISTENT_DATA = 0x20,

    FROM_CELL_TO_CLIENT_DATA = (CELL_DATA | CLIENT_DATA | EXACT_MATCH),
    FROM_BASE_TO_CLIENT_DATA = (BASE_DATA | CLIENT_DATA | EXACT_MATCH)
};
```

这组常量是"属性过滤的掩码"。例如 `addAttributesToStream(..., FROM_CELL_TO_CLIENT_DATA)` 表示"把 Cell 与 Client 共享的属性写入流"。引擎在很多场景下需要按域过滤属性:

- **创建实体时**:把 Cell 创建时的初始属性发给 Cell 进程(`CELL_CREATION`)。
- **Ghost 创建时**:把 Cell 公共属性发给 Ghost 进程(`CELL_GHOST_CREATION`)。
- **客户端玩家创建时**:把 Client 属性发给客户端(`CLIENT_PLAYER_CREATION`)。
- **数据库存储**:把持久化属性写入数据库(`DATABASE_ENTITY`)。

`StreamContentType`(`entity_description.hpp:19-32`)枚举了所有这些场景:

```cpp
enum StreamContentType
{
    BASE_ENTITY_BACKUP,
    BASE_ENTITY_OFFLOAD,
    CELL_CREATION,
    CELL_GHOST_CREATION,
    CELL_ENTITY_BACKUP,
    CELL_ENTITY_OFFLOAD,
    CLIENT_ENTITY_CELL_CREATION,
    CLIENT_PLAYER_CREATION,
    CLIENT_PLAYER_CELL_CREATION,
    CLIENT_ENTITY_LOD_DATA,
    DATABASE_ENTITY
};
```

`getDataDomains(StreamContentType)`(`entity_description.cpp` 中实现)把场景映射到 `DataDomain` 掩码,然后 `addAttributesToStream` 按掩码过滤属性写入流。这是 BigWorld 序列化的精髓——**一份属性描述,多个序列化场景,通过掩码自动选择**。

### 6.7.4 parse 流程

`EntityDescription::parse`(`entity_description.cpp:180-361`)的流程:

1. **打开 `.def` 文件**:`BWResource::openSection(getDefsDir() + "/" + name + ".def")`。
2. **递归解析父类型**:如果 `<Parent>` 非空,先 parse 父类。
3. **解析 ClientName**:可选,默认等于 name。
4. **解析 Distribution**:用 `IEntityDistributionDecider` 决定 `canBeOnCell_` 等。
5. **调用 `parseInterface`**:解析 `<Properties>`、`<ClientMethods>` 等子节点。
6. **调整 LoD 索引**:把 LoD 层级从"声明顺序"转为"实际层级"。
7. **检查脚本与字段匹配**:如"声明了 Cell 属性但没 Cell 脚本"会发出警告。
8. **初始化压缩类型**、`appealRadius_`、`isManualAoI_` 等。

`parseInterface`(`entity_description.cpp:381-445`)是真正干活的地方,它依次调用:

- `BaseUserDataObjectDescription::parseInterface`:解析 `<Properties>` 与组件。
- `volatileInfo_.parse`:解析 `<Volatile>`。
- `parseMethods`:解析 `<ClientMethods>` / `<CellMethods>` / `<BaseMethods>`。
- `parseTempProperties`:解析 `<TempProperties>`。
- `parseComponents`:解析 `<Components>`。

### 6.7.5 方法分发器 EntityMethodDescriptions

`EntityMethodDescriptions`(`entity_method_descriptions.hpp:23`)是"单个上下文(Cell/Base/Client)的方法集合":

```cpp
class EntityMethodDescriptions
{
    Map  map_;             // 名字 → 内部下标
    List internalMethods_; // 方法描述列表
    BW::vector<unsigned int> exposedMethods_; // 暴露方法下标
    int maxExposedMethodCount_;
};
```

它提供两种查找:

- `internalMethod(index)`:按下标取,用于按 ID 调用。
- `find(name)`:按名字取,用于 Python 端 `mailbox.foo(args)` 风格调用。
- `exposedMethod(msgID, data, range)`:按网络消息 ID 取,用于客户端→服务端调用。

`EntityDescription` 持有三个 `EntityMethodDescriptions` 实例(`cell_`、`base_`、`client_`),分别对应三个上下文:

```cpp
BWENTITY_API const EntityMethodDescriptions & cell() const { return cell_; }
BWENTITY_API const EntityMethodDescriptions & base() const { return base_; }
BWENTITY_API const EntityMethodDescriptions & client() const { return client_; }
```

这种"按上下文分组"的设计,使得网络层在收到一个客户端消息时,可以直接通过 `client().exposedMethod(msgID)` 找到对应的方法,无需任何运行时反射。

### 6.7.6 MethodDescription - 方法描述

`MethodDescription`(`method_description.hpp:51`)的关键成员:

| 字段 | 类型 | 含义 |
|---|---|---|
| `flags_` | `uint8` | 最低 2 位是 `Component`(CLIENT/CELL/BASE),其余位是 `IS_EXPOSED_*` 标志 |
| `args_` | `MethodArgs` | 参数类型列表 |
| `returnValues_` | `MethodArgs` | 返回值类型列表 |
| `hasReturnValues_` | `bool` | 是否有返回值(双向方法) |
| `internalIndex_` | `int` | 同上下文内唯一索引 |
| `exposedIndex_` | `int` | 暴露给客户端的索引 |
| `exposedMsgID_` | `int16` | 网络消息 ID |
| `exposedSubMsgID_` | `int16` | 子消息 ID(扩展地址空间) |
| `priority_` | `float` | 方法优先级 |
| `replayExposureLevel_` | `ReplayExposureLevel` | 回放可见性 |
| `components_` | `set<string>` | 实现了该方法的组件列表 |

最常用的方法是 `callMethod`(`method_description.cpp:814`),它的核心流程:

```cpp
bool MethodDescription::callMethod( ScriptObject self,
    BinaryIStream & data, EntityID sourceID, int replyID, ... ) const
{
    ScriptObject spTuple( this->getArgsAsTuple( data, sourceID ) );
    if (spTuple.get() == NULL) return false;

    ScriptObject pFunction = this->getMethodFrom( self );
    if (!pFunction) { /* 处理未实现 */ return false; }

    ScriptObject returnValues(
        PyObject_CallObject( pFunction.get(), spTuple.get() ),
        PyObjectPtr::STEAL_REFERENCE );

    if (!returnValues) {
        this->handleException( replyID, *pReplyAddr, *pInterface, true );
        return false;
    }

    if (this->hasReturnValues()) {
        // 双向方法:把返回值通过 replyID 发回去
        // 如果返回值是 Twisted Deferred,挂上 callback/errback
        ...
    }
    return true;
}
```

这段代码展现了 BigWorld 调用 Python 方法的完整流程:**网络字节流 → 参数元组 → Python 方法 → 返回值/异常 → 网络字节流**。注意它对 Twisted Deferred(`PyDeferredResponse`)的支持——如果 Python 方法返回一个 Deferred,引擎会自动挂上 `callback`/`errback`,在异步完成时把结果发回去。这是 BigWorld 与 Twisted 框架集成的关键。

## 6.8 EntityDescriptionMap 注册表

### 6.8.1 数据结构

`EntityDescriptionMap`(`entity_description_map.hpp:26`)是所有实体类型的注册表,内部用一个 vector + 一个 map 双向索引:

```cpp
class EntityDescriptionMap
{
    DescriptionVector  vector_;   // vector<EntityDescription>
    DescriptionMap    map_;      // map<string, EntityTypeID>
    unsigned int maxClientServerPropertyCount_;
    unsigned int maxExposedClientMethodCount_;
    unsigned int maxExposedBaseMethodCount_;
    unsigned int maxExposedCellMethodCount_;
    MD5::Digest digest_;
};
```

vector 按下标存,用于按 ID 快速查找;map 按名字存,用于按名查找。两者在 `parse` 完成后保持一致。

### 6.8.2 parse 流程

`EntityDescriptionMap::parse`(`entity_description_map.cpp:140-292`)的完整流程:

1. **打开 `entities.xml`**,取出 `<ClientServerEntities>` 与 `<ServerOnlyEntities>` 两个子节点。
2. **`parseInternal`**(`entity_description_map.cpp:347-387`):遍历每个 `<Name/>` 子节点,创建 `EntityDescription`,调用其 `parse` 方法。如果该实体没有 Client 脚本(老式 entities.xml),放到 `pServerOnlyDescriptions`,延后插入到 vector 末尾。
3. **Services**:如果有 `services.xml`(`scripts/services.xml`),用 `parseServices` 解析服务实体。
4. **建立索引**:遍历 vector,给每个 `EntityDescription` 设置 `index_`,在 map 中登记 `name → index`。
5. **分配消息 ID**:`setExposedMessageIDs` 给所有暴露的方法分配唯一的网络消息 ID。
6. **生成 MD5 摘要**:`addToMD5(md5)` 把所有实体描述的内容哈希进 MD5,存到 `digest_`。这个摘要在客户端连接时用于校验"客户端与服务端的 .def 是否一致"——不一致会拒绝登录。

### 6.8.3 两种查找方式

```cpp
bool nameToIndex( const BW::string& name, EntityTypeID & index ) const;
const EntityDescription& entityDescription( EntityTypeID index ) const;
bool isEntity( const BW::string& name ) const;
void getNames( BW::vector< BW::string > & names ) const;
```

- `nameToIndex`:O(log n),从名字查 ID。
- `entityDescription`:O(1),从 ID 查描述。
- `isEntity`:判断名字是否是已知实体类型。

### 6.8.4 ExposedMessageRange - 消息 ID 分配

每个暴露给客户端的方法需要一个唯一的网络消息 ID。`ExposedMethodMessageRange`(`network/exposed_message_range.hpp`)负责分配:

- 客户端可见属性范围:`ClientInterface::Range::entityPropertyRange`
- 客户端方法范围:`ClientInterface::Range::entityMethodRange`
- Base 方法范围:`BaseAppExtInterface::Range::baseEntityMethodRange`
- Cell 方法范围:`BaseAppExtInterface::Range::cellEntityMethodRange`

`EntityDescriptionMap::setExposedMessageIDs`(`entity_description_map.cpp:299-334`)先统计每个实体的最大暴露方法数,然后调用 `EntityDescription::setExposedMsgIDs` 给每个方法分配 ID。当一个实体的暴露方法数超过单个 ID 空间时,会启用 `exposedSubMsgID_`(`method_description.hpp:300`)扩展地址空间,从而支持超过 256 个暴露方法。

### 6.8.5 MD5 摘要的用途

```cpp
void addToMD5( MD5 & md5 ) const;
void addPersistentPropertiesToMD5( MD5 & md5 ) const;
const MD5::Digest digest() const { return digest_; }
```

`digest_` 是所有实体描述的 MD5 摘要。它的用途:

1. **客户端登录校验**:客户端登录时,服务端把自己的 `digest` 发给客户端;客户端用自己的 `EntityDescriptionMap.digest` 比对,不一致就拒绝连接(避免运行时崩溃)。
2. **数据库版本**:`addPersistentPropertiesToMD5` 只把持久化属性纳入哈希,用于判断"数据库结构是否需要迁移"。
3. **资源缓存**:作为 `EntityDef.py` 等生成文件的版本号,旧版本会被自动重新生成。

## 6.9 Python 实体类

### 6.9.1 类层次

每种 `.def` 对应至少一个 Python 类,继承自 `BigWorld.Entity` 或 `BigWorld.Proxy`:

```python
import BigWorld

class Guard( BigWorld.Entity ):
    def __init__( self ):
        BigWorld.Entity.__init__( self )

class Account( BigWorld.Proxy ):
    def __init__( self ):
        BigWorld.Proxy.__init__( self )
```

`BigWorld.Entity` 是 C++ 侧导出的 PyObjectPlus 派生类,它定义了所有实体共有的属性与方法:

- **属性**:`id`(实体 ID)、`position`、`direction`、`velocity`、`spaceID`、`cell`(Cell Mailbox)、`base`(Base Mailbox)、`client`(Client Mailbox)、`aoiRadius` 等。
- **方法**:`addTimer` / `delTimer`(定时器)、`giveClientTo`(转交客户端)、`destroy`(销毁)、`onLoad` / `onSave` / `onRestore`(持久化钩子)等。

`BigWorld.Proxy` 是 Base 实体的特殊基类,表示"客户端代理"——它是真正与客户端连接的实体,可以转交(`giveClientTo`)给其他实体。

### 6.9.2 三份脚本的设计

一个完整实体类型最多有三份 Python 脚本(放在 `scripts/cell/`、`scripts/base/`、`scripts/client/` 三个目录),分别对应进程:

| 进程 | 路径 | 示例 |
|---|---|---|
| CellApp | `scripts/cell/<Name>.py` | `scripts/cell/Guard.py`(空实现) |
| BaseApp | `scripts/base/<Name>.py` | `scripts/base/Account.py`(登录、定时器、创建 Avatar) |
| Client | `scripts/client/<Name>.py` | `scripts/client/Account.py`(显示聊天消息) |

例如 `examples/client_integration/python/simple/res/scripts/base/Account.py`:

```python
class Account( BigWorld.Proxy ):
    def __init__( self ):
        BigWorld.Proxy.__init__( self )
        self.count = 0

    def onClientDeath( self ):
        self.destroy()

    def onEntitiesEnabled( self ):
        self.addTimer( 1.0, 1.0 )   # 周期性定时器

    def onTimer( self, timerId, userData ):
        self.count += 1
        self.client.chatMessage( "Hello from the base: " + str(self.count) )
        if self.count == 5:
            self.delTimer( timerId )
            BigWorld.createBaseFromDB( "ClientAvatar", self.character,
                                       self.handleNewCharacter )

    def handleNewCharacter( self, newEntity, dbID, wasActive ):
        if newEntity != None:
            self.giveClientTo( newEntity )
            self.destroy()
```

而客户端脚本 `scripts/client/Account.py` 仅处理 `chatMessage`:

```python
class Account( BigWorld.Entity ):
    def __init__( self ):
        BigWorld.Entity.__init__( self )
        self.tick = 0

    def chatMessage( self, msg ):
        print "Account.chatMessage:", msg
```

注意两点:

1. **同名类**:两份脚本都叫 `Account`,但分别继承 `BigWorld.Proxy` 与 `BigWorld.Entity`。引擎根据当前进程加载对应的脚本。
2. **跨进程透明调用**:Base 侧写 `self.client.chatMessage(msg)` 看起来像是直接调用 Python 方法,但实际上 `self.client` 是一个 `Mailbox`,引擎会把这个调用打包成网络消息发给客户端进程,客户端进程再调用对应的 Python 方法。这就是 6.10 节要讲的"C++/Python 分治"。

### 6.9.3 生命周期钩子

Python 实体类可以重写一组钩子函数,响应引擎事件:

| 钩子 | 触发时机 | 用途 |
|---|---|---|
| `__init__` | 创建实体 | 初始化非持久化字段 |
| `onLoad( self, saver )` | 从数据库加载 | 从 saver 还原状态 |
| `onSave( self, saver )` | 写入数据库 | 把状态写入 saver |
| `onRestore( self )` | 备份恢复 | 恢复临时状态 |
| `onNameSpaceDeallocated` | 命名空间释放 | 清理引用 |
| `onDestroyed` | 销毁前 | 释放资源 |
| `onTimer( self, id, userData )` | 定时器触发 | 周期任务 |
| `onFilterTickStart` / `onFilterTickEnd` | 过滤器 tick | 客户端位置插值 |
| `onWitnessed` / `onEnterAoI` / `onLeaveAoI` | AOI 事件 | 玩家视野变化 |

注意 `onLoad` / `onSave` 接收一个 `saver` 参数——这是引擎传过来的 `ScriptObject`,通过它读写持久化字段。`__init__` 与 `onLoad` 的关系:`__init__` 总是先调用,然后如果是加载场景,引擎再调用 `onLoad` 让脚本恢复持久化字段。

### 6.9.4 字段访问的"自动同步"

Python 中对 `.def` 声明的属性的访问,会自动触发同步。例如:

```python
self.playerName = "Alice"   # 写属性,如果 Flags 是 ALL_CLIENTS,会自动同步给所有客户端
print self.playerName        # 读属性,直接返回当前值
```

这是如何实现的?`DataDescription::callSetterCallback`(`data_description.hpp:161`)就是入口。引擎在 PyObjectPlus 的属性 setter 中拦截,把新值传给 `DataDescription`,后者:

1. 调用 `pDataType_->isSameType` 验证类型。
2. 检查 `dataFlags_`,决定是否要发送给 Ghost / 其他客户端 / 自己客户端。
3. 如果要发送,创建一个 `PropertyChange`,通过 `addCompressedPathToStream` 把变更打包到网络流。
4. 在合适的时候(如下一帧 tick),`RemoteEntityMethod` 把变更发给目标进程。

这种"声明式同步"是 BigWorld 最有特色的设计之一——**Python 端只需要写一行赋值,引擎自动完成网络同步**。代价是每次属性访问都要经过一次 C++ 拦截,所以属性访问比普通 Python 字段慢一些,但对游戏逻辑而言完全可接受。

## 6.10 C++/Python 分治设计

### 6.10.1 分工原则

BigWorld 的设计哲学:**C++ 做性能关键的事,Python 做业务逻辑**。具体分工:

| 层 | 语言 | 负责 |
|---|---|---|
| 网络层 | C++ | Bundle/Channel/Endpoint、可靠 UDP、消息序列化 |
| 空间层 | C++ | Cell/Ghost、AOI、空间分割、BSP |
| 渲染层 | C++ | Moo、Chunk 加载、场景图 |
| 持久化 | C++ | DBApp、SQL/XML、连接池 |
| **游戏逻辑** | **Python** | **规则、AI、事件处理、业务流程** |
| **数据驱动** | **.def** | **属性、方法、同步规则** |

这种分工的核心理由:

1. **Python 易改易热重载**:游戏规则迭代频繁,Python 脚本可以热加载,无需重启进程。
2. **C++ 性能瓶颈在网络与空间**:这些代码每秒执行百万次,必须用 C++。
3. **数据驱动让分工清晰**:策划/美术改 `.def`,程序员改 C++,双方在 `.def` 处对接。

### 6.10.2 Mailbox - 跨进程透明调用

要让 Python 端能"透明"地调用其他进程的实体方法,引擎引入了 Mailbox 概念。`PyEntityMailBox`(`mailbox_base.hpp:55`)是所有 Mailbox 的基类,派生出七种具体 Mailbox:

| Mailbox 类型 | 用途 |
|---|---|
| `CellEntityMailBox` | 指向 Cell 上的实体 |
| `BaseEntityMailBox` | 指向 Base 上的实体 |
| `ClientEntityMailBox` | 指向客户端上的实体 |
| `GhostEntityMailBox` | 指向 Ghost 实体 |
| `BaseEntityMailBoxForCell` | Cell 持有的 Base 引用 |
| `EntityMailBoxToClient` | Base 持有的 Client 引用 |
| `VectorEntityMailBox` | 批量 Mailbox(用于广播) |

每个 Mailbox 内部持有一个 `EntityMailBoxRef`,它包含:

- 目标进程的 `Mercury::Address`(进程地址)
- 实体 ID
- 组件类型(Cell/Base/Client)

当 Python 端写 `self.client.chatMessage("hello")` 时,流程是:

1. `self.client` 是一个 `ClientEntityMailBox`,Python 访问其 `chatMessage` 属性。
2. `pyGetAttribute("chatMessage")`(`mailbox_base.hpp:63`)调用 `findMethod("chatMessage")`,在 `EntityDescription.client()` 中查找方法描述。
3. 找到后,返回一个"远程方法代理"对象(通过 `getStream` 拿到一个 `BinaryOStream`)。
4. Python 调用这个代理对象时,代理对象把参数序列化到流中。
5. `sendStream` 把流打包成 Mercury 消息,发送到目标进程。
6. 目标进程收到消息,根据 `exposedMsgID` 找到 `MethodDescription`,调用 `callMethod(self, data, ...)` 执行 Python 方法。

整个流程对 Python 端完全透明——你写 `self.client.chatMessage("hello")` 与写 `self.local_helper("hello")` 在语法上没有任何区别。这是 BigWorld "分布式对象"魅力的核心。

### 6.10.3 性能权衡

什么时候用 C++,什么时候用 Python?BigWorld 的经验法则:

| 场景 | 选择 | 理由 |
|---|---|---|
| 每帧百万次调用 | C++ | Python 解释开销不可接受 |
| 复杂数值算法 | C++ | 如路径查找、碰撞检测 |
| 网络字节流操作 | C++ | 性能关键 |
| 字符串处理 | C++(用 STL) | Python 字符串操作慢 |
| 游戏规则 | Python | 易改易测 |
| AI 状态机 | Python | 状态多、逻辑分支多 |
| 事件处理 | Python | 频率低、逻辑简单 |
| UI / HUD | Python | 与客户端 Entity 协作 |

对于性能介于两者之间的代码,BigWorld 提供了"混合模式"——用 C++ 实现核心算法,通过 PyObjectPlus 暴露给 Python,Python 端只做高层调度。例如 `Avatar::findPath` 是 C++,但 `Avatar::onArrived` 是 Python。

```cpp
        ScriptErrorPrint( "createEntityDescription("#PROP_NAME"):" ) );
```

它利用 `#PROP_NAME` 字符串化,把 C++ 的 getter 调用结果转换成 Python 字典项。`ScriptObject::createFrom<T>(const T&)` 是模板函数,根据 T 类型自动选择 `Script::getData` 的重载——`bool` 转 `PyBool`、`int` 转 `PyInt`、`string` 转 `PyString`。

### 6.11.2 自动生成的方法分发代码

`ProcessDefs.process`(Python 侧)接收到这个 description 字典后,会做两件事:

1. **生成 `EntityDef.py`**:把所有实体描述以 Python 字典形式保存,供运行时使用。
2. **生成方法分发代码**:对每个暴露方法,生成形如下面的 stub:

```python
class ClientAvatar( BigWorld.Entity ):
    def logOff( self ):
        # 自动生成:调用 C++ 侧的 _logOffExposedBaseMethod
        self._logOffExposedBaseMethod()
```

这样 Python 端调用 `entity.logOff()` 时,实际执行的是 C++ 侧生成的 stub,后者通过 `RemoteEntityMethod` 把调用打包成网络消息发给 Base 进程。Base 进程收到消息后,通过 `exposedMsgID` 找到对应的 `MethodDescription`,再调用真正的 Python 方法 `Account.logOff`。

这种"自动代码生成"避免了手写大量样板代码——每个 `.def` 方法都不需要手写网络调用代码。

### 6.11.3 字段同步的自动机制

我们之前提到过 Python 端 `self.playerName = "Alice"` 会自动触发同步。具体的同步路径:

```
Python: self.playerName = "Alice"
   │
   ▼
PyObjectPlus::_tp_setattro 拦截
   │
   ▼
DataDescription::callSetterCallback(self, oldVal, changePath, isSlice)
   │
   ▼
Entity::onPropertyChange( propName, oldValue, changePath )
   │
   ├── 标记属性已变更(eventStamp 更新)
   ├── 如果 isOtherClientData:生成 PropertyChange,发给所有其他客户端
   ├── 如果 isOwnClientData:发给自己的客户端
   ├── 如果 isGhostedData:发给所有 Ghost
   └── 如果 isPersistent:稍后写回数据库
```

`PropertyChange`(`property_change.hpp:27`)是变更的抽象,它包含:

- `path_`:`vector<pair<int32, int32>>`,从根属性到变更点的路径(用于嵌套属性,如 `myList[3].name`)。
- `rootIndex_`:根属性索引。
- `FLAG_IS_SLICE` / `FLAG_IS_NESTED`:标志位,标识是切片变更还是嵌套变更。

`addCompressedPathToStream`(`property_change.hpp:71`)把路径压缩后写入流,客户端收到后用 `PropertyChangeReader` 还原路径,精确更新对应字段。这种"增量同步"避免了每次属性变更都发送整个实体,大幅节省带宽。

### 6.11.4 Persistent 字段的自动持久化

声明了 `<Persistent>true</Persistent>` 的属性会被定期写入数据库。流程:

1. **属性变更触发**:Python 端改了属性,`DataDescription::callSetterCallback` 检查 `DATA_PERSISTENT` 标志。
2. **标记脏字段**:在 `Entity` 上记录"该属性需要写回数据库"。
3. **定时刷写**:BaseApp 周期性(默认 30 秒)把所有脏字段写入 DBApp。
4. **DBApp 缓冲**:DBApp 收到后缓冲到 `EntityDefs` 队列,按实体类型批量写入。
5. **数据库写入**:DBApp 用 `DataType::addToSection` 把每个属性转成 `DataSection`,再写入 XML 或 SQL。

`DataDescription::fromStreamToSection`(`data_description.hpp:108`)是关键——它把网络字节流转回 `DataSection`,然后 DBApp 把 `DataSection` 写到数据库。这种"流 ↔ DataSection"的双向转换使得同一份 `DataType` 实现可以同时支持"网络序列化"与"数据库存储"。

### 6.11.5 与 DBApp 的协作

DBApp 不直接执行 Python 代码,它只是"数据持久化中心"。BaseApp 与 DBApp 的协作流程:

```
BaseApp                            DBApp
   │                                 │
   │  BigWorld.save( entity, True )  │
   │ ─────────────────────────────► │
   │   实体所有 Persistent 属性        │
   │   通过 EntityDescription::       │
   │   addAttributesToStream          │
   │   写入 DATABASE_ENTITY 流         │
   │                                 │
   │                                 │  写入 MySQL/XML
   │                                 │
   │  ◄───────────────────────────── │
   │  回执:写入成功/失败              │
   │  触发 entity.onSaveComplete()    │
```

加载流程反向:

```
BaseApp                            DBApp
   │                                 │
   │  BigWorld.createBaseFromDB(...) │
   │ ─────────────────────────────► │
   │   查询数据库,返回流              │
   │                                 │
   │  ◄───────────────────────────── │
   │  EntityDescription::             │
   │  readStreamToDict(               │
   │     stream, DATABASE_ENTITY )    │
   │  → 还原所有 Persistent 属性       │
   │  → 创建 Python 实体               │
   │  → 调用 entity.onLoad(saver)     │
   │                                 │
```

`EntityDescription::readStreamToDict`(`entity_description.hpp:174`)把流中的属性读到一个 Python dict,然后实体构造函数可以遍历这个 dict 恢复状态。

### 6.11.6 FailedUnpickle 与版本兼容

之前提到的 `FailedUnpickle` 在这里也发挥作用:如果数据库中存的某个 `PYTHON` 字段引用了已经不存在的类,`unpickle` 会返回一个 `FailedUnpickle` 占位对象。这个对象:

- 可以正常读、正常写(写时直接返回原字节)。
- 不会让加载失败。
- 可以在 Python 端用 `isinstance(x, BigWorld.FailedUnpickle)` 检测并处理。

这种设计让 BigWorld 在做大规模 schema 迁移时不需要"一锤子买卖"——旧字段可以保留为 FailedUnpickle,新字段可以正常使用,迁移可以渐进进行。

### 6.11.7 双向方法(Two-Way Method)

BigWorld 不仅支持"单向调用"(客户端调用服务端方法、不等待返回),还支持"双向方法"——调用方等待被调用方的返回值。

`MethodDescription::hasReturnValues()`(`method_description.hpp:155`)标识一个方法是否有返回值。如果有,调用流程:

1. 调用方创建 `ReplyMessageHandler`,绑定一个 `replyID`。
2. 发送调用消息时附带 `replyID`。
3. 被调用方执行 Python 方法,得到返回值。
4. 被调用方把返回值序列化到流,带 `replyID` 发回去。
5. 调用方收到回执,根据 `replyID` 找到对应的 handler,触发 callback。

如果 Python 方法返回 Twisted `Deferred`,引擎会创建 `PyDeferredResponse`(`method_description.cpp:58`),把 `callback` / `errback` 挂到 Deferred 上,在 Deferred 触发时才发送回执。这是 BigWorld 与 Twisted 框架的深度集成。

### 6.11.8 VIP(Volatile Interest Properties)

`VolatileInfo`(`volatile_info.hpp`)是 BigWorld 节省带宽的关键。它声明"位置、yaw、pitch、roll"四种数据的发送频率:

- `<position/>`:每次都发送(实体的位置变化最频繁)。
- `<yaw/>`:每次都发送。
- `<pitch>20</pitch>`:每 20 个 tick 发送一次。
- `<roll/>`(省略):不发送。

引擎在 Cell 上定期(通常 10 Hz)检查每个有 Witness 的实体,根据 VolatileInfo 决定要不要发送位置/朝向更新。距离 Witness 远的实体发送频率更低(LoD 层级),近的实体发送频率更高。

`appealRadius_`(`entity_description.hpp:197`)是 AOI 半径补偿——大实体(如龙)的"边界"超出 AOI 时,即使中心点不在 AOI 内,玩家也应该看到它。`appealRadius_` 让这种实体的"有效半径"扩大,从而更早进入 AOI。

## 6.12 本章小结

本章我们走完了 BigWorld 脚本系统的完整图景:

1. **pyscript 库**提供了 C++ 与 Python 的双向桥梁——`Script::init`/`fini` 管理解释器,`setData`/`getData` 做类型转换,`PyObjectPtr`/`ScriptObject` 用 RAII 管理引用计数,`PyObjectPlus` 把 C++ 类导出给 Python。
2. **Pickler** 用薄包装复用 Python 标准库的 `cPickle`,并通过 `FailedUnpickle` 提供"反序列化失败的优雅降级"。
3. **entitydef 库**把 `.def` 文件解析为 `EntityDescription`/`DataDescription`/`MethodDescription`,并保存在 `EntityDescriptionMap` 注册表中,提供按名字或按 ID 查询。
4. **.def 文件**用 XML 描述实体的属性与方法,通过 `<Flags>` 决定属性属于哪个进程、`<Persistent>` 决定是否持久化、`<Exposed>` 决定方法是否暴露给客户端。
5. **Python 实体类**继承 `BigWorld.Entity` / `BigWorld.Proxy`,通过重写 `__init__`/`onLoad`/`onSave`/`onTimer` 等钩子参与生命周期;通过 `self.client.method(args)` 风格的 Mailbox 调用实现跨进程透明通信。
6. **C++/Python 分治**:C++ 负责性能关键的网络、空间、渲染,Python 负责游戏逻辑、AI、事件;`.def` 作为契约把两者对接。
7. **自动机制**:`process_defs` 工具把 `.def` 转成 Python 描述,生成方法分发 stub;属性赋值自动触发同步;持久化字段自动写入数据库。

这些设计让 BigWorld 在 2000 年代就实现了"数据驱动的 MMOG 开发"——开发者只需写 `.def` 与 Python,引擎自动处理网络同步、持久化、跨进程调用。理解了这一章,你就掌握了 BigWorld 最具特色的设计理念,可以开始阅读第 7 章的服务器集群架构,看这些"实体"如何在多进程集群中分布与协作。
