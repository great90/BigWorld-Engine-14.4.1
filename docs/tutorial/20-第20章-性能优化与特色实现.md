## 第一部分:可观测性工具

### 20.1 性能优化概述

#### 20.1.1 BigWorld 的性能挑战

MMOG 与单机游戏最大的差异不是"内容多",而是**"规模"**:

- **玩家规模**:同一个服务器集群上同时存在几万名玩家,每一名玩家的位置、状态、技能释放都需要在多个进程之间转发。
- **实体规模**:每个玩家周围可能存在上百个 NPC、怪物、可交互物体,这些都属于"需要同步的实体"。
- **进程规模**:一个生产集群通常包含 1 台 bwmachined、几十台 CellApp、十几台 BaseApp、若干 LoginApp/DBApp/Message Logger,加起来几十个进程协同工作。
- **网络规模**:每秒几万到几十万条消息,跨越进程边界、跨越机器边界,既有可靠 UDP 又有 TCP。
- **资源规模**:几十 GB 的 chunk、模型、贴图、动画,客户端需要边玩边流式加载。

这意味着 BigWorld 不能靠"先写出来再优化",而是从架构第一天起就把性能当成一等公民。优化手段必须渗透到架构、算法、实现、配置四个层次。

#### 20.1.2 优化的四个层次

BigWorld 的优化手段可以按"作用层次"分成四档:

| 层次 | 关注点 | 典型手段 | 本教程章节 |
|---|---|---|---|
| **架构层** | 进程划分、数据归属 | Cell/Ghost 分治、Mailbox 位置透明、AOI 兴趣区域 | 第7/9/18章 |
| **算法层** | 复杂度、数据结构 | 洪水填充+BSP、BVH 包围盒、哈希集群分片 | 第9/17章 |
| **实现层** | 内存、并发、序列化 | 内存池、Bundle 批量、TaskProcessor 多线程 | 第5/15章,本章 |
| **配置层** | 参数调优 | bwmachined.cfg、watcher 在线修改、Cell 负载阈值 | 第8章,本章 |

四个层次自上而下,**架构层的效果最显著但最难改**,实现层最容易调但收益相对小。优化时遵循"先测量后优化"——这就是为什么本章前半部分把 Profiler/Watcher/Logger 放在一起讲。没有测量工具,任何"我觉得这里慢"都是猜。

#### 20.1.3 "先测量后优化"的工作流

BigWorld 推荐的优化工作流:

```
1. 复现场景 → 用 Profiler 抓一帧,定位热点函数
2. 看 Watcher 在线数据 → 确认热点对应的实体数/消息率/内存
3. 看 Message Logger → 排查是否有异常日志路径
4. 改一处(架构/算法/实现/配置四选一)→ 重新测一遍
5. 对比前后 Profiler 数据 → 确认收益再合并
```

下面三节就依次看这三个工具。

### 20.2 Profiler 性能分析系统

#### 20.2.1 三套计时器的关系

BigWorld 的"性能分析"其实是三套独立又互补的计时系统:

| 名称 | 头文件 | 用途 | 开销 |
|---|---|---|---|
| **Profiler** | `lib/cstdmf/profiler.hpp` | Chrome Trace 格式的事件级 profiler,可输出 JSON | 中等,可开关 |
| **ProfileVal** | `lib/server/profile.hpp` | 框架级累计统计,Watcher 可见 | 极低,默认开 |
| **DogWatch** | `lib/cstdmf/dogwatch.hpp` | 帧内分片计时,层次化 manifest | 极低 |

三者针对的场景不同:

- **Profiler** 像 Chrome 的 `chrome://tracing` —— 一帧内每个函数的起止时间都被记录成事件,可以看时间轴、看调用栈、看 CPU/GPU/Python 三类。
- **ProfileVal** 像"统计计数器" —— 累计某个函数被调用了多少次、共耗时多少秒,适合长期监控。
- **DogWatch** 像"watch dog" —— 每帧切片,保留最近 120 帧历史,适合快速发现"卡顿帧"。

新手最容易混淆的是 Profiler 与 ProfileVal:前者是"详细的事件流",后者是"汇总统计"。它们共享 `ENABLE_PROFILER` 编译开关,但运行时是独立的。

#### 20.2.2 Profiler 的核心数据结构

`Profiler` 类(`lib/cstdmf/profiler.hpp` L124-543)是一个单例,通过全局变量 `g_profiler` 访问。它的核心字段:

```cpp
// lib/cstdmf/profiler.hpp L179-191
struct ProfileEntry
{
    EventType       event_;       // START / START_IDLE / END / COUNTER
    EventCategory   category_;    // CPP / GPU / PYTHON
    const char *    name_;        // 函数名/标签
    uint64          time_;        // 时间戳
    bwThreadID      threadIdx_;   // 哪个线程
    int32           value_;       // 计数器值
    int32           frameNumber_; // 第几帧
};
```

每个 `ProfileEntry` 就是一条事件。Profiler 用**双缓冲**收集事件:

```cpp
// lib/cstdmf/profiler.hpp L258-263 + L467-470
struct EntryBuffer
{
    bw_atomic32_t entryCount_;
    uint64        endOfFrameTimeStamp_;
    ProfileEntry * entries_;
};

EntryBuffer profileEntryBuffers_[2];
EntryBuffer * profileEntryBuffer_;       // 当前帧写入
EntryBuffer * finalProfileEntryBuffer_;  // 上一帧供读取
```

主线程在 `tick()` 时切换两个 buffer——新帧写到空 buffer,旧帧由后台线程 `ProcessEntriesTask` 处理。这样写入路径完全无锁,只有切换时需要一次原子交换。

`ProfileEntry` 上限受 `MAXIMUM_NUMBER_OF_THREADS`(96)、`MAX_STACK_DEPTH`(64)、`HISTORY_LENGTH`(512)等常量约束。如果一帧内事件超过 `maxEntryCount_`(动态计算),后续事件被丢弃并打"highWatermark"日志。

#### 20.2.3 ScopedProfiler:RAII 计时

最常用的入口是 `PROFILER_SCOPED` 宏,它展开为 `ScopedProfiler` 对象:

```cpp
// lib/cstdmf/profiler.hpp L43-44 + L638-654
#define PROFILER_SCOPED( name ) \
    ScopedProfiler prof_##name( #name )

class ScopedProfiler
{
public:
    inline ScopedProfiler( const char* text )
    {
        text_ = text;
        g_profiler.addEntry( text, Profiler::EVENT_START, 0 );
    }
    inline ~ScopedProfiler()
    {
        g_profiler.addEntry( text_, Profiler::EVENT_END, 0 );
    }
private:
    const char* text_;
};
```

构造时写一条 `EVENT_START`,析构时写一条 `EVENT_END`,中间这段时间就是这段代码的耗时。这种 RAII 风格的好处是**即使函数提前 return 或抛异常,END 事件也会被记录**。

实际用法:

```cpp
void CellApp::updateCell( float dTime )
{
    PROFILER_SCOPED( updateCell );    // <-- 一行宏
    // ... 一大段业务逻辑
    aoi_.update( dTime );
    physics_.tick( dTime );
    // ... ScopedProfiler 析构自动写 END
}
```

`PROFILER_IDLE_SCOPED` 是变体——标记"空闲时间"。例如 CellApp 主循环空转等待消息时,可以用它把"sleep 等待"与"实际工作"区分开,这样 Profiler 报告里就能看到真实的 CPU 利用率。

#### 20.2.4 计数器与层次计数器

除了"开始/结束"事件,Profiler 还支持**计数器**(counter),用来追踪内存使用量、实体数量等数值变化:

```cpp
// lib/cstdmf/profiler.hpp L49-50
#define PROFILER_COUNTER( name, value ) \
    g_profiler.addEntry( #name, Profiler::EVENT_COUNTER, value );
```

更高级的是 `ProfilerLevelCounter`(`profiler.hpp` L723-738)——专门追踪"水位"类指标(如缓冲区当前长度)。它的特点是**只在变化时输出**,如果水位一直不变,Profiling 数据里就完全没有这个计数器的记录,避免噪音:

```cpp
// lib/cstdmf/profiler.hpp L723-738
class ProfilerLevelCounter
{
public:
    ProfilerLevelCounter( const char *desc )
    {
        desc_ = desc;
        level_ = 0;
    }
    CSTDMF_DLL void increase( int amt );
    CSTDMF_DLL void decrease( int amt );
private:
    bw_atomic32_t level_;   // 原子操作,线程安全
    const char *desc_;
};

#define PROFILER_LEVEL_COUNTER( name ) \
    ProfilerLevelCounter prof_##name( #name )

#define PROFILER_LEVEL_COUNTER_INC( name, amt ) \
    prof_##name.increase( amt )

#define PROFILER_LEVEL_COUNTER_DEC( name, amt ) \
    prof_##name.decrease( amt )
```

使用方式:

```cpp
// 在某个全局对象里声明
PROFILER_LEVEL_COUNTER( bundleQueueSize );

// 入队时增加
PROFILER_LEVEL_COUNTER_INC( bundleQueueSize, 1 );
// 出队时减少
PROFILER_LEVEL_COUNTER_DEC( bundleQueueSize, 1 );
```

Chrome Trace 打开后,水位变化会显示为一条折线,非常直观。

#### 20.2.5 输出格式:Chrome Trace JSON

Profiler 默认输出 **Chrome Trace Format**(JSON 数组),可以直接拖到 `chrome://tracing` 查看。核心字段:

```json
{"traceEvents":[
  {"name":"updateCell","cat":"CPP","ph":"B","ts":1234567,"pid":1,"tid":0},
  {"name":"aoi_.update","cat":"CPP","ph":"B","ts":1234570,"pid":1,"tid":0},
  {"name":"aoi_.update","cat":"CPP","ph":"E","ts":1234590,"pid":1,"tid":0},
  {"name":"updateCell","cat":"CPP","ph":"E","ts":1234600,"pid":1,"tid":0}
]}
```

- `ph:"B"` = Begin(对应 `EVENT_START`)
- `ph:"E"` = End(对应 `EVENT_END`)
- `ph:"C"` = Counter(对应 `EVENT_COUNTER`,带 `args` 字段)
- `cat` = category,可以是 `CPP`/`GPU`/`PYTHON`
- `pid` = process id(进程内不同线程用 `tid` 区分)

Profiler 还支持**模式切换**(`ProfileMode` 枚举,L130-143):

- `HIERARCHICAL`:树形展开,适合看调用栈
- `SORT_BY_TIME`:按耗时排序,找最慢函数
- `SORT_BY_NUMCALLS`:按调用次数排序,找热点函数
- `CPU_GPU`:CPU/GPU 对照视图
- `GRAPHS`:图形化历史数据
- `CORES`(可选):每个 CPU 核独立时间轴

通过 Watcher 字段 `watcherSetSortMode` 可以在线切换模式。

#### 20.2.6 HitchDetector:卡顿检测

服务器对"卡顿"极度敏感——一个 CellApp 一帧卡 100ms,玩家就会感受到技能延迟。`HitchDetector`(`profiler.hpp` L90-114)专门干这事:

```cpp
class HitchDetector
{
public:
    HitchDetector();
    void init( int numSamples, double frameMSLimit, double overAverageFactor );
    bool accumulateTime( double dt );
private:
    double accumulatedTime_;
    double runningAverage_;       // 滑动平均
    double overAverageFactor_;    // 超过平均多少倍才算 hitch
    double lastDTime_;
    double frameMSLimit_;         // 帧时长硬阈值
    int    numTimeSamples_;
};
```

每帧调用 `accumulateTime(dt)`,如果 `dt` 超过 `frameMSLimit_` 或超过 `runningAverage_ * overAverageFactor_`,就会触发 `hitchFreeze`,冻结 Profiler 输出供事后分析。`watcherGetDumpProfile` 字段在 hitch 触发后会被置 true,自动 dump 一帧 JSON 到磁盘。

这就是 `freeze()` 方法的用途——抓到卡顿帧立刻"定格",避免下一帧的事件覆盖掉证据:

```cpp
// lib/cstdmf/profiler.hpp L301-329
void freeze( bool freeze, bool dump )
{
    if (freeze && !freezeProfiling_)
    {
        doJsonDump_ = dump;
    }
    freezeProfiling_ = freeze;
}
// ...
void hitchFreeze( bool hitch )
{
    this->freeze( hitch, (hitch != hitchFreeze_ && hitch) );
    hitchFreeze_ = hitch;
}
```

#### 20.2.7 ProfileVal:框架级累计统计

`ProfileVal`(`lib/server/profile.hpp` L80-242)是另一套计时系统。它和 Profiler 的最大区别是**默认开启、开销极小、只累加不展开**:

```cpp
// lib/server/profile.hpp L83-114
class ProfileVal
{
public:
    CSTDMF_DLL ProfileVal( const BW::string & name = "",
        ProfileGroup * pGroup = NULL );
    void start()
    {
        TimeStamp now = timestamp();
        if (inProgress_ == 0)
            lastTime_ = now;
        ++inProgress_;
        ProfileGroup::Profiles & stack = pGroup_->stack();
        if (!stack.empty())
        {
            ProfileVal & profile = *stack.back();
            profile.lastIntTime_ = now - profile.lastIntTime_;
            profile.sumIntTime_ += profile.lastIntTime_;
        }
        stack.push_back( this );
        lastIntTime_ = now;
    }
    void stop( uint32 qty = 0 );
    // ...
};
```

关键字段:

- `sumTime_`:总耗时(包含子调用)
- `sumIntTime_`:内部时间(扣除子调用,即"自己花的时间")
- `count_`:被调用次数
- `lastQuantity_`/`sumQuantity_`:可选的"数量"统计(如处理了多少实体)

`ProfileGroup` 把多个 `ProfileVal` 关联起来,通过栈维护父子关系——`start` 时把当前 profile 压栈,暂停上一个的内部时间计数;`stop` 时弹栈,恢复上一个的计数。这样**任意时刻只有一个 profile 在累加内部时间**,保证"内部时间"的精确性。

`ProfileVal` 默认通过 `Watcher` 暴露,所以可以在 bwmachined 的 Web 界面看到 `Profile/summaries/...` 路径下的累计耗时。

#### 20.2.8 DogWatch:帧内分片计时

`DogWatch`(`lib/cstdmf/dogwatch.hpp` L36-56)名字里"Dog"取自"watch dog"。它面向的场景是"每帧都跑、需要快速看历史趋势"的代码段:

```cpp
// lib/cstdmf/dogwatch.hpp L36-56
class DogWatch
{
public:
    CSTDMF_DLL DogWatch( const char * title );
    CSTDMF_DLL void start();
    CSTDMF_DLL void stop();
    CSTDMF_DLL uint64 slice() const;
private:
    uint64      started_;
    uint64 *    pSlice_;
    int         id_;
    BW::string  title_;
};
```

`start`/`stop` 的实现(`dogwatch.ipp` L12-47)非常精简——只是抓时间戳并加到对应的 slice 上:

```cpp
inline void DogWatch::start()
{
    pSlice_ = &DogWatchManager::instance().grabSlice( id_ );
    started_ = timestamp();
}
inline void DogWatch::stop()
{
    (*pSlice_) += timestamp() - started_;
    DogWatchManager::instance().giveSlice();
}
```

`DogWatchManager` 维护**120 个切片**(NUM_SLICES),每个切片代表一帧。`tick()` 在每帧结束时把当前 slice 推进一格——超过 120 帧之后,最旧的数据被覆盖。这样始终保留"最近 2 秒(60fps)到 6 秒(20fps)"的历史,正好是发现卡顿所需的时间窗口。

DogWatch 的核心机制是**manifest(显化)**——它会根据当前 DogWatch 的"调用栈"自动组织成层次树。例如:

```
CellApp::tick()
├── aoi_update              (DogWatch "aoi")
│   ├── witness_recalc      (DogWatch "witness")
│   └── ghost_sync         (DogWatch "ghost")
└── physics_step            (DogWatch "physics")
```

同一帧内 `aoi` 调用了多少次、各自花了多少时间,都会按"调用栈位置"分别记录。这就是 `cache_[MAX_WATCHES]` 字段的作用——缓存最近的"栈位置 → slice 指针"映射,避免每次 `start` 都查表。

`BW_SCOPED_DOG_WATCHER` 宏(`dogwatch.hpp` L243-245)是常用入口:

```cpp
#define BW_SCOPED_DOG_WATCHER(name)                  \
    static DogWatch  hidden_dog_watcher(name);      \
    ScopedDogWatch scoped_hidden_dog_watcher(hidden_dog_watcher);
```

注意 `static` 关键字——DogWatch 必须**静态或全局**声明,因为它在 `DogWatchManager` 注册了 id,临时对象会导致 id 重复分配。

#### 20.2.9 三套计时器的协作

实际开发中三者配合使用:

1. **平时**只开 ProfileVal + DogWatch,Watcher 上能看每帧的累计耗时与 120 帧历史。
2. **怀疑某段慢**就临时加 `PROFILER_SCOPED`,本地抓一帧 JSON 用 Chrome 打开。
3. **怀疑内存泄漏**就开 `PROFILER_LEVEL_COUNTER`,水位线变化一目了然。
4. **生产环境偶发卡顿**就开 `HitchDetector`,触发时自动 dump。

它们共享 `ENABLE_PROFILER` 和 `ENABLE_DOG_WATCHERS` 两个编译开关,在 Release 构建里 Profiler 默认关、DogWatch 默认开,避免影响线上性能。

### 20.3 Watcher 运行时监控

#### 20.3.1 Watcher 是什么

**Watcher** 是 BigWorld 的"运行时变量查看与修改系统"。它的作用类似 Linux 的 `/proc` 文件系统——给每个进程内部的状态变量一个路径(如 `components/CellApp01/entities/count`),运维可以随时查看或修改。

Watcher 的设计目标:

- **运行时**:不需要重启进程,通过 HTTP 或自定义协议访问
- **可读可写**:大部分变量可以读取,部分还可以在线修改(改阈值、改开关)
- **树状组织**:用 `/` 分隔路径,类似文件系统
- **类型安全**:支持 int/uint/float/bool/string,以及 tuple、type
- **跨进程**:任何进程都能注册 Watcher,bwmachined 通过 MachineGuard 协议汇聚

这是 BigWorld 在 MMOG 领域的**招牌特色**——把"调试参数"做成生产可观测的标准接口,而不是临时打 log。

#### 20.3.2 核心类层级

`watcher.hpp` 定义了一套完整的 Watcher 类层级:

```
Watcher (抽象基类,L611-855)
├── DirectoryWatcher      (目录,L991-1042,可包含子 Watcher)
├── DataWatcher<T>        (变量,L2460-2586,绑定到具体变量)
├── MemberWatcher<R,O>    (成员,L2136-2299,绑定到对象的 get/set 方法)
├── FunctionWatcher<R>    (函数,L2622-2742,绑定到全局 get/set 函数)
├── SequenceWatcher<SEQ>  (序列,L1056-1413,绑定到 vector 等容器)
├── MapWatcher<MAP>       (映射,L1434-1703,绑定到 map)
├── CallableWatcher       (可调用,L2753-2825,代表一个可远程调用的函数)
├── SafeWatcher           (加锁,L1715-1780,在调用前加 mutex)
├── ReadWriteLockWatcher  (读写锁,L1792-1834)
├── DereferenceWatcher     (解引用,L1844-1890)
└── AbsoluteWatcher       (绝对地址,L3189-3215)
```

每个 Watcher 都有 `Mode`(`watcher.hpp` L618-625):

```cpp
enum Mode
{
    WT_INVALID,        // 错误
    WT_READ_ONLY,      // 只读
    WT_READ_WRITE,    // 可读写
    WT_DIRECTORY,    // 是个目录,有子项
    WT_CALLABLE      // 是个可调用函数
};
```

`Mode` 决定了客户端能对这个 Watcher 做什么操作。

#### 20.3.3 WatcherPath 路径与 DirectoryWatcher

路径用 `/` 分隔(`WATCHER_SEPARATOR = '/'`,`watcher.hpp` L75)。**根 Watcher** 通过 `Watcher::rootWatcher()` 访问,它是一个全局 `DirectoryWatcher`:

```cpp
// lib/cstdmf/watcher.hpp L2893-2915
inline bool Watcher::hasRootWatcher()
{
    if (!hasRootWatcherInternal())
        return false;
    return g_pRootWatcherPath == NULL || g_pRootWatcher != NULL;
}

inline Watcher & Watcher::rootWatcher()
{
    Watcher & watcher = rootWatcherInternal();
    if (g_pRootWatcherPath == NULL)
        return watcher;
    if (g_pRootWatcher == NULL)
    {
        g_pRootWatcher = new DirectoryWatcher();
        watcher.addChild( g_pRootWatcherPath, g_pRootWatcher );
    }
    return *g_pRootWatcher;
}
```

注意 `g_pRootWatcherPath` —— 每个进程(如 CellApp/BaseApp/Message Logger)在初始化时通过 `DECLARE_WATCHER_DATA( name )` 宏把自己的根挂到一个固定的名字下(如 `"components/CellApp"`),这样 bwmachined 汇聚时就能用统一前缀找到每个进程的 Watcher 树。

`DirectoryWatcher`(`watcher.hpp` L991-1042)用 vector 存子项:

```cpp
// lib/cstdmf/watcher.hpp L1031-1041
private:
    struct DirData
    {
        WatcherPtr  watcher;   // 子 Watcher
        void *      base;      // 偏移量(见 20.3.5)
        BW::string  label;     // 子项名
    };
    DirData * findChild( const char * path ) const;
    typedef BW::vector<DirData> Container;
    Container container_;
```

`findChild` 线性查找——大多数 Watcher 子项不多,不需要哈希。

#### 20.3.4 四种基础 Watcher 的使用

**1. DataWatcher:绑定到变量**

```cpp
// 监视一个静态 int
static int s_entityCount = 0;
MF_WATCH( "entities/count", s_entityCount, Watcher::WT_READ_ONLY );
```

`MF_WATCH` 宏展开为 `addWatcher`,内部 `new DataWatcher<int>(rValue, access)`。访问时直接读 `s_entityCount` 的当前值。

**2. MemberWatcher:绑定到 get/set 方法**

```cpp
class CellApp
{
public:
    int  entityCount() const;
    void entityCount( int );
};

CellApp g_cellApp;
MF_WATCH( "entities/count", g_cellApp,
    MF_ACCESSORS( int, CellApp, entityCount ) );
```

`MF_ACCESSORS` 宏展开为两个静态转换后的成员函数指针,分别用于 get 和 set。`MemberWatcher`(`watcher.hpp` L2136-2299)在 `getAsString` 时调用 get 方法,在 `setFromString` 时调用 set 方法。

**3. FunctionWatcher:绑定到全局函数**

```cpp
int  getTickRate();
void setTickRate( int );
MF_WATCH( "tickRate", getTickRate, setTickRate );
```

适用于"值不属于任何对象,只能通过函数获取"的场景。

**4. CallableWatcher:可远程调用**

`CallableWatcher`(`watcher.hpp` L2753-2825)代表一个"可远程调用的函数",用 `setFromStream` 触发。它支持声明参数列表(`addArg`),返回值通过 stream 写回。这是 bwmachined 远程命令的基础——例如"重启某个进程"、"触发一次 chunk 重载"都是 callable watcher。

`ExposeHint`(`watcher.hpp` L2776-2782)决定这个 callable 暴露到哪:

```cpp
enum ExposeHint
{
    WITH_ENTITY,    // 暴露给某个 entity
    ALL,            // 暴露给所有
    WITH_SPACE,     // 暴露给某个 space
    LEAST_LOADED,   // 转发到负载最低的进程
    LOCAL_ONLY      // 只在本进程可调用
};
```

#### 20.3.5 base 指针:容器 Watcher 的关键

`SequenceWatcher` 和 `MapWatcher` 是相对复杂的设计——它们需要**对一个容器内的每个元素**都暴露一个 Watcher。例如,假设 CellApp 有一个 `vector<Entity*>`,运维想看每个 entity 的 hp,就需要在 Watcher 路径里支持 `entities/0/hp`、`entities/1/hp` 这种索引。

BigWorld 的解决方案是**`base` 偏移指针**。每个 Watcher 方法都接受一个 `void * base` 参数:

```cpp
// lib/cstdmf/watcher.hpp L654-658
virtual bool getAsString( const void * base,
    const char * path,
    BW::string & result,
    BW::string & desc,
    Mode & mode ) const = 0;
```

`base` 是"宿主对象的地址"。对于 `DataWatcher<int>`,`base` 指向包含这个 int 的对象,int 的真实地址是 `(uintptr)&rValue_ + (uintptr)base`。

`SequenceWatcher::visitChildren`(`watcher.hpp` L1182-1237)就是遍历整个 vector,对每个元素计算 `subBase_ + (uintptr)&rChild`,再递归调用 `child_->getAsString`:

```cpp
// lib/cstdmf/watcher.hpp L1229-1234
if (!pathRequest.addWatcherPath(
        (void*)(subBase_ + (uintptr)&rChild),
        this->tail( path ), callLabel, *child_ ))
{
    break;
}
```

这种"地址偏移"的设计避免了为每个 entity 单独注册 Watcher 的开销——只需注册一次"vector 里某个元素的 hp 怎么读",运行时根据 base 自动定位。

#### 20.3.6 加锁 Watcher:SafeWatcher 与 ReadWriteLockWatcher

Watcher 可能在多线程被访问(bwmachined 的查询线程 vs 主线程)。两种加锁封装:

- **SafeWatcher**(`watcher.hpp` L1715-1780):包装另一个 Watcher,调用前 `mutex_.grab()`,调用后 `mutex_.give()`。重入计数通过 `grabCount_` 维护。
- **ReadWriteLockWatcher**(`watcher.hpp` L1792-1834):用 `ReadWriteLock`,读操作加读锁,写操作加写锁。适合"读多写少"的场景,如配置项。

```cpp
// 典型用法:把 vector 的 SequenceWatcher 加读锁暴露
rwlock_.beginRead();
SequenceWatcher<vector<Entity*>> * seq = ...;
WatcherPtr safeSeq = new ReadWriteLockWatcher( seq, rwlock_ );
rootWatcher().addChild( "entities", safeSeq );
```

#### 20.3.7 HTTP Watcher 接口

bwmachined 进程内置 HTTP 服务器,把所有进程的 Watcher 树汇聚成一个 HTTP 接口。访问形式:

```
GET http://machined:30000/components/CellApp01/entities/count
PUT http://machined:30000/components/CellApp01/config/maxEntities -d "5000"
```

- `GET` 调用 `getAsString`/`getAsStream`,返回当前值
- `PUT` 调用 `setFromString`/`setFromStream`,在线修改

后端用的是 Watcher 协议 v2(`WatcherPathRequestV2`),支持二进制流传输——`getAsStream` 把值打包成 `[type][mode][data]` 三段式(`watcher.hpp` L860-928),效率比字符串高得多。

`watcherValueToStream` 对每种类型有特化版本:

```cpp

                                  const Watcher::Mode & mode )
{
    result << (uchar)WATCHER_TYPE_INT;
    result << (uchar)mode;
    result.writeStringLength( sizeof(int) );
    result << value;
}
```

类型枚举(`watcher.hpp` L40-54):

```cpp

    WATCHER_TYPE_UNKNOWN = 0,
    WATCHER_TYPE_INT,
    WATCHER_TYPE_UINT,
    WATCHER_TYPE_FLOAT,
    WATCHER_TYPE_BOOL,
    WATCHER_TYPE_STRING,
    WATCHER_TYPE_TUPLE,
    WATCHER_TYPE_TYPE
};
```

`WATCHER_TYPE_TUPLE` 用于 `CallableWatcher` 的多参数调用。

#### 20.3.8 与 bwmachined 集成

第8章讲过 bwmachined 是集群的"看门狗",它通过 MachineGuard 协议与每个进程通信。Watcher 数据也走这条链路:

```
浏览器/运维工具
   │  HTTP
   ▼
bwmachined (MachineGuard)
   │  UDP/Watcher 协议
   ▼
CellApp01 ─── BaseApp01 ─── DBApp01 ─── LoginApp01
   │            │            │            │
   └────────────┴────────────┴────────────┘
                各自的 rootWatcher
```

bwmachined 启动时调用 `addMachineGuardHandler` 注册回调,收到 HTTP 请求时根据路径前缀(`components/CellApp01/...`)路由到对应进程。每个进程启动时通过 `MachineGuardMessage::ADD_BW_LOGGERS` 之类的消息把自己的 Watcher 端点注册到 bwmachined。

### 20.4 日志系统与 Message Logger

#### 20.4.1 为什么需要独立日志进程

MMOG 有几十个进程同时运行,如果每个进程都把日志写到本地文件,会出现这些问题:

- **难以关联**:同一时刻多个进程都有日志,如何串起来?
- **难以搜索**:想找"用户 12345 在 14:30 左右的所有日志",得挨个文件 grep。
- **难以归档**:日志滚动、压缩、过期清理都是麻烦事。
- **难以按级别过滤**:DEBUG 日志只在排查时开,平时关。

BigWorld 的解决方案是 **Message Logger 进程**——一个独立的服务器进程,接收所有其他进程的日志,统一存储、统一查询。所有进程通过 `lib/server/log_msg.hpp` 提供的 `LogMsg` API 发日志,底层通过 UDP 发到 Message Logger。

#### 20.4.2 Logger 进程主结构

`Logger` 类(`server/tools/message_logger/logger.hpp` L27-202)是 Message Logger 进程的主类:

```cpp
// server/tools/message_logger/logger.hpp L27-91

    public TimerHandler
{
public:
    Logger();
    bool init( int argc, char * argv[] );
    bool handleNextMessage();
    // ...
private:
    Endpoint & socket() { return watcherNub_.udpSocket(); }
    WatcherNub watcherNub_;
    Mercury::EventDispatcher dispatcher_;

    LoggerID loggerID_;
    uint logUser_;
    bool logAllUsers_;
    BW::vector< BW::string > logNames_;
    BW::vector< BW::string > doNotLogNames_;
    bool quietMode_;

    bool shouldWriteToStdout_;

    LogStorage *pLogStorage_;
    bool isMongoDBDriverInitialised_;
};
```

字段说明:

- `watcherNub_`:接收 UDP 日志包,同时支持 Watcher 查询
- `dispatcher_`:Mercury 事件循环
- `loggerID_`:本进程服务的 logger id(可过滤只服务某些 process)
- `logUser_`/`logAllUsers_`:按用户过滤
- `pLogStorage_`:存储后端(MLDB 或 MongoDB)
- `shouldRoll_`:是否触发滚动(`SIGHUP` 触发)

#### 20.4.3 main 入口与信号处理

`main.cpp`(`server/tools/message_logger/main.cpp`)的入口非常简短:

```cpp
// server/tools/message_logger/main.cpp L73-98
int BIGWORLD_MAIN( int argc, char * argv[] )
{
    Logger logger;
    gLogger = &logger;

    signal( SIGHUP, sighup );       // 触发日志滚动
    signal( SIGINT, sigint );       // 优雅退出
    signal( SIGTERM, sigint );
    signal( SIGUSR1, sigusr1 );     // 触发主机名校验

    LogMsg::shouldWriteToSyslog( true );
    INFO_MSG( "---- Logger is running ----\n" );

    if (!logger.init( argc, argv ))
        return 1;

    while (!g_finished)
    {
        logger.handleNextMessage();
    }
    return 0;
}
```

三个信号的含义:

- **SIGHUP**:触发 `shouldRoll(true)`,让 Logger 把当前段文件关闭、开新段。日志归档常用。
- **SIGINT/SIGTERM**:优雅退出,把缓冲日志刷盘后退出。
- **SIGUSR1**:触发 `shouldValidateHostnames(true)`,重新校验所有发送方主机名。安全审计用。

#### 20.4.4 LogStorage:存储抽象与双后端

`LogStorage`(`server/tools/message_logger/log_storage.hpp` L21-68)是存储后端的抽象基类:

它定义了所有存储后端必须实现的接口。BigWorld 14.4.1 提供两个具体实现:

**1. MLDB 后端**(`mldb/log_storage.hpp`):BigWorld 自研的本地文件存储,二进制格式,适合小型部署。每个用户一个目录,按段(segment)切分,段大小可配。无需外部依赖,默认选择。

**2. MongoDB 后端**(`mongodb/log_storage.hpp`):用 MongoDB 存储日志,适合大规模部署和复杂查询。需要 MongoDB 服务,但支持任意维度的索引和聚合查询。

两个后端共享同一套抽象接口(`LogStorage`),Logger 进程启动时根据 `storageType_` 配置字段决定实例化哪一个:

```cpp
// 简化伪代码
if (storageType_ == "mldb")
    pLogStorage_ = new LogStorageMLDB( *this );
else if (storageType_ == "mongodb")
    pLogStorage_ = new LogStorageMongoDB( *this );
```

这是典型的**策略模式**——上层逻辑(Logger、查询 API)与底层存储解耦,日后加新后端(如 Elasticsearch)只需再实现一个 `LogStorage` 子类。

#### 20.4.5 日志消息格式与字符串插值

BigWorld 的日志消息不是直接发字符串,而是**格式串 + 参数**:

- 进程启动时,把所有 `LogMsg` 调用点的格式串(如 `"Player %s cast spell %d at %f,%f,%f"`)注册到 Logger,获得一个 `formatStringID`。
- 实际发日志时只发 `formatStringID + 参数值(s/i/f)`,不重复发整个格式串。
- Logger 端用 `LogStringInterpolator` 把格式串与参数重新组合成完整字符串。

这种设计大幅减少了网络传输量——一条"玩家 X 在 位置 Y 释放了技能 Z"的日志,直接发字符串要几十字节,但发"格式串 ID + 3 个参数"可能只要 16 字节。

#### 20.4.6 分类与过滤

`Categories`(`categories.hpp`)管理日志分类。每条日志可以打多个 category 标签,查询时可按 category 过滤。常见的 category 如 `network`、`entity`、`db`、`script` 等。

Logger 进程在 `shouldLogMessagePriority_` 数组里维护优先级过滤:

```cpp

bool shouldLogMessagePriority_[ NUM_MESSAGE_PRIORITY ];
```

通过 Watcher 可以在线开关某个优先级(如临时关闭 DEBUG 日志以减少负载)。

#### 20.4.7 log_view 工具与查询 API

Logger 进程同时提供查询接口,通过 `py_query.hpp`/`py_query_result.hpp` 暴露给 Python。运维可以用 Python 脚本写复杂的查询:

`log_view` 是命令行工具,封装常用查询。它能:

- 实时 tail 模式(持续拉新日志)
- 导出为文本或 JSON

`log_view` 与 Logger 通过 Watcher 协议通信,本质上是 Watcher 的一个特殊客户端。

## 第二部分:优化手段地图

### 20.5 内存优化

#### 20.5.1 内存池与 Allocator

BigWorld 不直接调用系统 `malloc`/`free`,而是经过 `BW::Allocator` 命名空间(`lib/cstdmf/allocator.hpp` L36-188)统一管理:

```cpp
// lib/cstdmf/allocator.hpp L36-52
namespace Allocator
{
    enum SystemStage
    {
        SS_PRE_MAIN,
        SS_MAIN,
        SS_POST_MAIN
    };

    enum InfoFlags
    {
        IF_POOL_ALLOC     = 1,  // 来自固定大小池
        IF_NOTRACK_ALLOC  = 2,  // 不参与内存跟踪
        IF_INTERNAL_ALLOC = 4,  // 内存池内部开销
        IF_DEBUG_ALLOC    = 8   // 调试分配
    };
    // ...
    CSTDMF_DLL void* allocate( size_t size );
    CSTDMF_DLL void  deallocate( void* ptr );
    CSTDMF_DLL void* reallocate( void* ptr, size_t size );
    size_t memorySize( void* ptr );
};
```

`SystemStage` 用来标记"程序生命周期阶段"——`SS_PRE_MAIN` 是静态初始化期,`SS_MAIN` 是 main 函数运行中,`SS_POST_MAIN` 是退出期。区分阶段是为了**判断泄漏是否真的发生**——很多第三方库在 `SS_PRE_MAIN` 阶段分配的内存会"假泄漏"(因为它们析构晚于 main 退出),用阶段标记就能过滤掉。

`InfoFlags` 标记每块内存的来源——`IF_POOL_ALLOC` 说明这块内存来自固定大小池(不走通用堆),统计时单列。`IF_NOTRACK_ALLOC` 用于"已知不会泄漏的第三方分配",跳过跟踪减少开销。

#### 20.5.2 memhook:全局分配函数替换

`lib/memhook/memhook.hpp` + `memhook.cpp` 通过**重载全局 `operator new`/`operator delete`** 把所有 C++ 内存分配劫持到 `Allocator`:

```cpp
// lib/memhook/memhook.cpp L35-48 + L66-71
NOINLINE
void * operator new( size_t sz )
{
    init();
    return (*s_allocFuncs.new_)( sz );
}

NOINLINE
void operator delete( void * p ) throw()
{
    init();
    (*s_allocFuncs.delete_)( p );
}
```

`AllocFuncs`(`memhook.hpp` L34-50)是一个函数指针表,包含 13 个分配相关的函数(new/new[]/delete/delete[]/malloc/free/realloc/_msize 等)。运行时通过 `allocFuncs( const AllocFuncs& )` 替换这个表,就能切换不同的内存后端——比如调试时切换到带堆栈跟踪的版本,生产时切换到 tcmalloc/jemalloc。

注意 `NOINLINE` 宏(`memhook.cpp` L5-9)——服务端是空宏,客户端是 `__declspec(noinline)`。这是为了让调用栈在内存跟踪时能清晰区分"用户代码调用 new"与"Allocator 内部分配"。

#### 20.5.3 固定大小对象池

对于频繁分配/释放的固定大小对象(如 `Entity*`、`Bundle*`),BigWorld 用对象池避免堆碎片。对象池的接口在 `Allocator::heapAllocateAligned` 之上构建,典型用法:

```cpp
// 简化示例:某个高频对象的池
class EntityPool
{
public:
    Entity * acquire()
    {
        if (freeList_.empty())
            return static_cast<Entity*>(
                Allocator::heapAllocateAligned(
                    sizeof(Entity), alignof(Entity),
                    Allocator::IF_POOL_ALLOC ) );
        Entity * e = freeList_.back();
        freeList_.pop_back();
        return e;
    }
    void release( Entity * e )
    {
        freeList_.push_back( e );
    }
private:
    std::vector<Entity*> freeList_;
};
```

池化的对象在 `IF_POOL_ALLOC` 标记下统计,debug 报告里能清晰看到"这部分内存虽然分配量大,但来自池,不需要担心"。

#### 20.5.4 内存跟踪与泄漏检测

`ENABLE_MEMORY_DEBUG` 编译开关打开后,Allocator 会记录每块内存的:

- 分配时间(时间戳)
- 分配点(调用栈,通过 `_CrtCaptureBackStack` 或 `backtrace` 抓取)
- 大小
- 阶段(`SystemStage`)

退出时调用 `debugReport()`(`allocator.hpp` L100)打印未释放的内存列表,可选 `setCrashOnLeak(true)` 在发现泄漏时主动 crash,方便 CI 卡住泄漏提交。

`saveAllocationsToCacheGrindFile`(`allocator.hpp` L109)把分配统计导出为 cachegrind 格式,可以用 KCacheGrind/ QCachegrind 可视化"哪个调用路径分配了多少内存"——这是 BigWorld 内存优化的标准武器。

#### 20.5.5 DataSection 缓存

资源系统(第4章)的 `DataSection` 是 C++/Python 都频繁访问的对象。每次 `XMLSection::readFromFile` 都会触发文件 IO + XML 解析,代价很高。BigWorld 的做法是:

- `DataSectionCache`(`lib/resmgr/data_section_cache.hpp`)缓存最近读过的 DataSection,以文件路径为 key
- 命中缓存直接返回 SmartPointer,不命中才读盘
- 缓存有上限(LRU 淘汰),避免内存无限增长

第15章的 asset_pipeline 进一步用**内容寻址缓存**——同一份资源即使被多次"引用",只在磁盘上存一份,避免重复处理。

#### 20.5.6 资源引用计数

BigWorld 用 `SmartPointer<T>` 模板管理资源生命周期。引用计数到 0 时自动释放,避免手动 `delete` 的泄漏风险。`SmartPointer` 通过 `BW_MEMORYDEBUG_SMARTPOINTER_ASSIGN` 宏(`allocator.hpp` L21-26)在调试构建里把每次赋值记录到全局表,可以反向查询"谁持有这个对象的引用"——排查泄漏时非常有用。

### 20.6 网络优化

#### 20.6.1 Bundle:批量减少 syscall

第5章讲过,Bundle 是 BigWorld 网络层的基本单位。一个 Bundle 可以容纳多条消息,只有 Bundle 满或显式 `send` 时才真正调用 `sendto`。这把"N 条消息 = N 次 syscall"优化成"N 条消息 = 1 次 syscall",在每秒几万条消息的负载下提升明显。

Bundle 内部维护可增长的字节缓冲区:

```
[长度][消息1 ID][消息1 数据][消息2 ID][消息2 数据]...
```

发送时一次性 `sendto`,接收端按格式解包。对于可靠 UDP,还会等 ACK,丢包则重发整个 Bundle。

#### 20.6.2 Channel 滑动窗口

可靠 UDP 用**滑动窗口**控制飞行中的字节数。每个 Channel 维护:

- `sendWindowBytes_`:已发送未确认的字节数
- `maxSendWindowBytes_`:窗口上限

发送时检查 `sendWindowBytes_ < maxSendWindowBytes_`,超了就阻塞或丢包率上升。ACK 到达后窗口向前滑动。窗口大小通过 Watcher 可以在线调整,以适应不同网络环境:

```
GET .../channels/CellApp01/maxSendWindowBytes
PUT .../channels/CellApp01/maxSendWindowBytes -d "1048576"
```

#### 20.6.3 流量控制与优先级消息

BigWorld 的消息有优先级:

- **普通消息**:进入 Bundle 末尾,等下次发送
- **优先级消息**:插到 Bundle 开头,尽快发送
- **紧急消息**:不等 Bundle 满,立刻触发发送

紧急消息用 `Channel::sendUrgent` 接口,典型场景是"玩家登录请求"——这种消息延迟敏感,不能等批量。

流量控制通过 `rateLimit` 字段限制每秒最大字节数,避免某个 Channel 把带宽占满。

#### 20.6.4 紧急消息与非可靠消息

某些消息丢了也无所谓(如位置更新——下一帧又会发新的),用**非可靠消息**避免 ACK 开销。`Mercury::RELIABILITY_UNRELIABLE` 标志位标记。Cell/Ghost 之间的位置同步大量用非可靠消息,在 30% 丢包率下依然能跑——只是位置偶尔抖动一下,不影响游戏。

紧急消息(`URGENT` flag)则相反,它一定要可靠送达,但优先级最高——用单独的 Bundle 或在普通 Bundle 头部插队。

### 20.7 空间优化

#### 20.7.1 AOI:兴趣区域过滤

第9章和第18章讲过 AOI(Area Of Interest)。它的核心思想是:**每个玩家只关心自己周围一定半径内的实体**。如果 CellApp 里有 1000 个实体,但玩家 A 的 AOI 半径只覆盖 50 个,那么 A 只需要接收这 50 个实体的更新。

AOI 实现的关键数据结构是**格子网格(grid)**——把空间切成等大格子,每个格子维护"这个格子内的实体列表"。查询时只看玩家所在格子及周围 8 个格子,从 O(n) 降到 O(1)。

`Witness` 是 AOI 的"观察者"——每个玩家一个 Witness,维护"我能看到的实体集合"。实体进出 AOI 半径时触发 `onEnterAoI`/`onLeaveAoI` 回调,客户端据此增删场景节点。

#### 20.7.2 Cell 分割负载

第9章讲过 Cell 是空间的横向切片。一个 space 可以切多个 Cell,每个 Cell 由不同 CellApp 承载。这样:

- 玩家密集的区域可以切更多 Cell(更小的 cell 面积)分摊负载
- 玩家稀疏的区域合并为大 Cell 节省进程数

负载均衡器(第19章)持续监控每个 Cell 的实体数、消息率,动态调整 Cell 边界——把负载重的 Cell 一分为二,把负载轻的 Cell 合并。

#### 20.7.3 Chunk 流式加载

第14章讲过 Chunk 是客户端世界的分块单位。客户端不会一次性加载整个世界的所有 chunk,而是根据相机位置**只加载周围的 chunk**。具体策略:

- 进入新 chunk 边界时,异步加载该 chunk 及其邻居
- 离开 chunk 一定距离时,卸载
- 加载用后台线程,主线程不阻塞

这样玩家可以在无限大的世界里无缝移动,体验类似"没有加载界面"。

#### 20.7.4 Portal 渲染剔除

Chunk 之间通过 **Portal** 连接(门、窗等开口)。渲染时从相机所在 chunk 出发,通过 Portal 看到"对面的 chunk"。如果 Portal 不在视锥内,对面的 chunk 整体被剔除——这就是 Portal 渲染剔除,可以把渲染负载从"看见多少 chunk"降到"实际可见多少 chunk"。

Portal 还可以嵌套——chunk A 的 Portal 看到 chunk B,chunk B 内部又有 Portal 看到 chunk C。BigWorld 用 BSP 树递归处理这种嵌套可见性。

#### 20.7.5 LOD:细节层次

模型和动画都支持 LOD(Level Of Detail)。离玩家远的实体用低面数模型、低帧率动画,近的用高精度。Moo 渲染层根据距离自动切换 LOD 阶段。

空间层也有 LOD——远处的 entity 可以"休眠"(停止物理模拟,只保留位置同步),进入玩家 AOI 后才唤醒。这把"1000 个 NPC 物理模拟"优化到"只模拟玩家附近的 50 个"。

### 20.8 缓存优化

#### 20.8.1 内容寻址缓存(asset_pipeline)

第15章讲过 asset_pipeline 用**内容哈希**作为缓存 key——同一份资源即使被多个 chunk 引用,只在缓存里存一份。修改资源时哈希变化,自动触发重新编译,避免"修改了源但缓存还是旧的"问题。

#### 20.8.2 DataSection 缓存

第4章讲过 `DataSectionCache`,这里强调它的容量管理——LRU 淘汰策略保证缓存大小不无限增长。典型配置 10000 条,单条平均 4KB,总占用约 40MB,可控。

#### 20.8.3 资源缓存

`ResourceManager`(第4章)维护资源文件的内存缓存——已加载的 `.visual`/`.texture`/`.animation` 在缓存里复用,同一资源被多个 entity 引用时只占一份内存。

#### 20.8.4 Watcher 数据缓存

bwmachined 汇聚所有进程的 Watcher 时,会把"上次查询的值"缓存一段时间(默认 1 秒)。这段时间内重复查询同一路径直接返回缓存,避免每个 HTTP 请求都触发跨进程往返。这对 Web 界面刷新频繁的场景特别有用——一秒内可能刷新几十次,实际只跨进程查询一次。

### 20.9 并发优化

#### 20.9.1 多线程 TaskProcessor

BigWorld 用 `TaskProcessor`(`lib/cstdmf/bgtask_manager.hpp`)管理后台任务。后台任务类型:

- **资源加载**:加载 chunk、模型、贴图
- **JIT 编译**:运行时编译资源
- **网络 IO**:DNS 解析、连接建立
- **日志写入**:Profiler 的 JSON dump、CSV 历史

`TaskManager` 内部维护线程池,任务通过 `addBackgroundTask` 提交。每个任务有优先级,高优先级(如玩家进入新 chunk 触发的加载)插队,低优先级(如预加载远处 chunk)在空闲时跑。

#### 20.9.2 ConverterGuard 读写锁

资源编译器(jit_compiler)与 WorldEditor 之间用 `ReadWriteLock` 同步对资源的访问:

- WorldEditor 写资源时,持有写锁,编译器暂停
- 编译器读资源时,持有读锁,允许其他读者并发
- 多个读者不互斥,大幅提升并发度

`ReadWriteLockWatcher`(20.3.6)就是把这个锁暴露给 Watcher,运维可以查看当前锁的状态——有几个读者、写者在等。

#### 20.9.3 双线程 jit_compiler

第15章讲过 jit_compiler 用"主线程 + 编译线程"双线程模型:

- 主线程:接收客户端请求,加入编译队列
- 编译线程:从队列取任务,调用 asset_pipeline 编译

两线程通过无锁队列通信(单生产者-单消费者),避免锁竞争。编译完成的资源通过 callback 通知主线程,主线程再通知客户端。

#### 20.9.4 事件驱动模型

Mercury 网络库(第5章)用**事件驱动**模型而非线程池。每个进程有一个 `EventDispatcher`,在主线程 select/epoll 等待 IO,IO 就绪后调用对应的 handler。这样:

- 无锁:所有逻辑都在主线程,不需要锁保护共享状态
- 低延迟:IO 到达立刻处理,无需线程切换
- 简单:编程模型比线程池简单

代价是单核处理能力受限——一个进程一个核。BigWorld 通过"多进程"(CellApp/BaseApp 各自独立进程)而非"多线程"扩展,这与传统的"一进程多线程"模型形成鲜明对比。

## 第三部分:特色实现总结与学习路径

### 20.10 十大特色实现总结

教程走到这里,我们终于可以回顾 BigWorld 在 MMOG 领域的十个招牌设计了。它们不是孤立的功能点,而是相互支撑的整体架构。

#### 20.10.1 Cell/Ghost 跨进程实体(第9、19章)

**问题**:一个实体(如 NPC)可能跨越 Cell 边界,需要在两个 CellApp 之间共享。

**方案**:同一个 entity 在不同 Cell 上有 Cell 实体和 Ghost 实体。Cell 实体是真身,Ghost 是投影。Ghost 只读,真身修改时通过 ghost 提案同步。

**意义**:对游戏逻辑完全透明——Python 脚本调 `entity.hp` 不需要知道这个 entity 是不是 ghost。底层自动处理跨进程同步。

#### 20.10.2 Mailbox 7 种类型(第10、18章)

**问题**:实体之间需要互相调用方法,但对方可能在另一个进程,甚至在客户端。

**方案**:`Mailbox` 抽象了 7 种类型:

1. **Client**:发到客户端
2. **Cell**:发到某个 Cell 的 entity
3. **Base**:发到 BaseApp 的 Base 实体
4. **Global**:全局广播
5. **Entity**:某个具体 entity
6. **CellEntity**:同 Cell 内的 entity
7. **BaseEntity**:同 BaseApp 内的 entity

调用方只需要 `mailbox.method(args)`,底层自动路由到正确进程。

**意义**:位置透明——脚本不知道也不需要知道对方在哪。

#### 20.10.3 AOI/Witness 兴趣区域(第9、18章)

**问题**:玩家周围可能有几百个实体,如果都同步给客户端,网络带宽和 CPU 都受不了。

**方案**:

- AOI:服务端按距离过滤,只把玩家附近的实体纳入 Witness
- Witness:每个玩家一个,维护可见实体列表
- 格子网格索引:O(1) 查询附近实体

**意义**:把"全员同步"的 O(n²) 降到 O(n),让万人大世界成为可能。

#### 20.10.4 两层负载均衡(第19章)

**问题**:CellApp 与 BaseApp 是不同维度——CellApp 切空间,BaseApp 切玩家。怎么均衡?

**方案**:

- Cell 层:按空间负载(实体数、消息率)切 Cell
- Base 层:按玩家数切 BaseApp

两层独立均衡,通过 `CellAppGroup`/`BaseAppGroup` 协调。负载重时自动迁移 entity 到轻负载进程。

**意义**:解耦空间负载与玩家负载,各自优化。

#### 20.10.5 主备切换:BackupHash 容错(第12、19章)

**问题**:BaseApp 是单点,挂了所有玩家掉线。

**方案**:每个 BaseApp 有备份,定期把 entity 状态 hash 后存到 BackupHash。BaseApp 挂了,Reviver 选一个备份 BaseApp 接管,从 BackupHash 恢复 entity 状态,客户端重连到新 BaseApp。

**意义**:几秒内恢复,玩家几乎无感知。这是 MMOG "高可用"的硬指标。

#### 20.10.6 bwmachined 进程管理:看门狗(第8章)

**问题**:几十个进程都需要监控、自动重启。

**方案**:bwmachined 是集群的"看门狗",每台机器一个。它启动所有子进程,通过 MachineGuard 协议周期性 ping,无响应就 kill + 重启。所有 Watcher 数据汇聚到 bwmachined,通过 HTTP 暴露。

**意义**:运维不需要登录每台机器操作,所有动作通过 bwmachined 统一编排。

#### 20.10.7 JIT 资源编译:开发时无感(第15章)

**问题**:美术改了 `.visual`,需要手动跑 asset_pipeline 才能看见效果,体验差。

**方案**:`jit_compiler` 监听资源变化,自动触发增量编译。客户端/编辑器请求资源时,如果还没编译好就等编译完再返回。

**意义**:美术"改了立刻能看见",迭代效率大幅提升。

#### 20.10.8 Chunk 流式加载:无缝世界(第14章)

**问题**:世界很大,客户端内存装不下。

**方案**:Chunk 是 200m×200m 的方块,客户端只加载相机周围的 chunk。进出 chunk 边界时异步加载/卸载。

**意义**:玩家在无限大的世界里无缝移动,没有 loading 画面。

#### 20.10.9 .def 实体定义:数据驱动(第6章)

**问题**:每种 entity 都有不同的属性和方法,如果用 C++ 硬编码,改一行要重编译。

**方案**:`.def` XML 文件描述 entity 的属性、方法、Client/Server/Base 分治。运行时 `EntityDef` 解析 .def,生成 Python 类与 C++ 桥接代码。

**意义**:数据驱动,改 .def 不用重编译 C++。Python 写逻辑,C++ 写性能关键路径,分工清晰。

#### 20.10.10 Python 深度集成:逻辑可扩展(第6章)

**问题**:MMOG 逻辑频繁变化,需要快速迭代。C++ 编译慢,不适合频繁改逻辑。

**方案**:BigWorld 把 Python 嵌入 C++ 服务器,entity 逻辑用 Python 写。Python 调 C++ 通过 `Script::Module`/`Script::Object` 桥接。客户端 entity 也是 Python。

**意义**:策划改逻辑不用等程序员——Python 脚本热加载,迭代效率提升一个数量级。

#### 20.10.11 十大特色的共同主题

回顾这十项,你会发现它们的共同主题是**"解耦"**:

- Cell/Ghost 与 Mailbox 解耦"位置"
- AOI 与 LOD 解耦"逻辑范围"与"渲染范围"
- .def 与 Python 解耦"数据"与"逻辑"
- JIT 与 Chunk 流式解耦"开发"与"运行"
- 负载均衡与主备切换解耦"单点"与"可用性"

BigWorld 的整个架构哲学就是:**把复杂问题切成多个正交维度,每个维度独立优化**。这是 MMOG 这种大规模系统必须走的路——一锅烩的架构在万级并发下必然崩溃。

- **代码注释**:`.hpp` 文件头注释比 .cpp 更新,看类说明先看头。
- **Watcher 路径**:`bwmachined` 的 Web 界面是探索 BigWorld 内部状态最好的入口——把所有路径点开看看,能学到很多。
- **Python 控制台**:`bwscript` 工具可以连任意进程跑 Python 脚本,直接访问内部对象。

#### 20.11.5 推荐的练习项目

学完教程,可以尝试这些项目巩固:

1. **加一个新 entity**:写 .def、写 Python、注册到 .entities,跑通"客户端创建 → 服务端 spawn → 双向通信"。
2. **加一个新 Watcher**:选一个内部变量(如 CellApp 的 `tickRate`),用 `MF_WATCH` 暴露,通过 Web 界面修改。
3. **加一个 Profiler 标签**:在某个热点函数加 `PROFILER_SCOPED`,跑一帧,用 Chrome 打开 JSON 看耗时分布。
4. **加一个 callable watcher**:写一个能远程调用的方法(如"重载所有 chunk"),通过 HTTP 触发。
5. **改 Message Logger**:加一个新 category,在某个日志点用它,通过 log_view 过滤查看。
6. **改 bwmachined**:加一个 MachineGuard 消息类型,让 bwmachined 报告一个新的统计字段。

做完这六个练习,你就不仅"看懂"了 BigWorld,而且能"改"它了——这是从读者到贡献者的关键一步。

### 20.12 本章小结

本章是教程的收官,做了三件事:

**可观测性工具**:讲透了 Profiler(事件级)、ProfileVal(累计级)、DogWatch(分片级)三套计时系统的分工与协作;讲透了 Watcher 系统的类层级、base 偏移指针设计、HTTP 接口与 bwmachined 集成;讲透了 Message Logger 进程的 Logger 主类、双存储后端(MLDB/MongoDB)、信号处理与查询接口。这三件是 BigWorld "先测量后优化" 工作流的支柱。

**优化手段地图**:把散落在前 19 章的优化手段统一整理成五个维度——内存(Allocator/memhook/对象池/DataSection 缓存)、网络(Bundle/滑动窗口/优先级消息)、空间(AOI/Cell 分割/Chunk 流式/Portal/LOD)、缓存(内容寻址/DataSection/资源/Watcher)、并发(TaskProcessor/ReadWriteLock/双线程/事件驱动)。每个维度都给出 BigWorld 的具体实现与对应章节引用。

**十大特色实现**:把 Cell/Ghost、Mailbox、AOI、负载均衡、主备切换、bwmachined、JIT、Chunk 流式、.def、Python 集成这十项招牌设计串起来,指出它们的共同主题是"解耦"。BigWorld 的架构哲学是"把复杂问题切成正交维度各自优化",这是 MMOG 大规模系统的必由之路。

最后给了学习路径——本教程覆盖的、未覆盖的、推荐资料、社区入口、六个练习项目。教程到此完结,但 BigWorld 的探索才刚开始。建议读者拿着这份"地图"回到源码,在自己感兴趣的维度上深挖。BigWorld 是一份十几年的工程结晶,任何一处深入下去都能学到东西。
