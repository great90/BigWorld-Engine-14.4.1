## 18.1 为什么需要 Mailbox 与 AOI

### 18.1.1 两个根本难题

MMOG 与单机游戏最大的区别在于:游戏状态被切分在几十台甚至上百台服务器进程上,而玩家只能看到自己周围的一小片世界。这带来两个根本难题:

**难题一:跨进程通信。** 玩家 Alice 在 CellApp#3 上移动,Bob 在 CellApp#7 上交易,Alice 想给 Bob 发一条"你好"。但 Alice 的 Python 脚本里只有一个 `bob` 引用,她不知道也不应该知道 Bob 在哪个进程。如果让脚本去处理"目标在哪个进程、用什么网络通道、按什么格式序列化",那 MMOG 的业务代码将不可维护。

**难题二:可见性筛选。** 一个开放世界 MMOG 同时可能有 10 万个实体在线,但任何一个玩家屏幕上最多显示几百个。如果把所有实体的位置更新广播给所有玩家,带宽和 CPU 都会爆炸。服务器必须为每个玩家维护一个"我能看见谁"的列表,只同步这个列表里的实体。

BigWorld 用两个子系统分别解决这两个难题:

| 子系统 | 解决的问题 | 核心抽象 |
|--------|-----------|---------|
| **Mailbox** | 跨进程透明通信 | "通信地址"——隐藏目标实体在哪个进程 |
| **AOI** | 可见性筛选 | "兴趣区域"——只同步玩家周围的实体 |

### 18.1.2 设计哲学:位置透明

Mailbox 的设计哲学是 **位置透明(Location Transparency)**:调用方不需要知道目标实体物理上位于哪个进程,只需要持有一个"信箱地址",调用方式与本地对象几乎一致。

对比一下:

```python
# 假设没有 Mailbox,脚本要这样写:
if bob_in_my_cellapp:
    bob.onSayHello("Alice")
else:
    addr = lookup_entity_address(bob.id)
    bundle = Mercury.Bundle()
    bundle.writeString("onSayHello")
    bundle.writeString("Alice")
    channel = get_channel(addr)
    channel.send(bundle)
```

```python
# 有了 Mailbox,脚本只需:
bob.cell.onSayHello("Alice")    # bob.cell 就是 Mailbox
```

`bob.cell` 是一个 `CellEntityMailBox` 对象,它封装了"Bob 的 Cell 实体在某台 CellApp 上"这一事实。脚本调用 `onSayHello`,Mailbox 负责把它打包成网络消息发过去。这就是位置透明。

### 18.1.3 设计哲学:基于距离的可见性

AOI 的设计哲学是 **基于距离的可见性**:每个有客户端的实体(Witness)在空间中有一个圆形(实际是矩形,见后文)的"兴趣区域",区域内的实体对它可见,区域外的不可见。

```
                    ┌─────────────────────────────┐
                    │         AOI 半径 R           │
                    │   ┌─────────────────────┐    │
                    │   │  实体 A(可见)       │    │
                    │   │                     │    │
                    │   │      ★ 玩家(Witness)│    │
                    │   │                     │    │
                    │   │  实体 B(可见)       │    │
                    │   └─────────────────────┘    │
                    │                              │
                    │        实体 C(不可见)       │
                    └─────────────────────────────┘
                                  ↑
                            区域外的实体不广播给玩家
```

这套机制让带宽消耗与"玩家周围的实体数"成正比,而不是与"全服实体数"成正比,这是 MMOG 能支撑海量并发的关键。

## 18.2 Mailbox 系统概述

### 18.2.1 Mailbox 是什么

**Mailbox(信箱)** 是一个 Python 对象,它代表"另一个进程里某个实体的通信地址"。你可以把它理解为一个**远程引用**:它不持有目标实体的内存,只持有足够把消息送达的信息——

- **EntityID**:目标实体的 ID
- **Mercury::Address**:目标进程的网络地址(IP + 端口 + salt)
- **Component**:目标在实体上的哪一"层"(Cell / Base / Client)

这三元组被打包成 `EntityMailBoxRef` 结构体,它就是 Mailbox 的"序列化形态":

```cpp
// lib/network/basictypes.hpp:322-364
class EntityMailBoxRef
{
public:
    EntityID            id;       // 实体 ID
    Mercury::Address    addr;     // 进程网络地址

    enum Component
    {
        CELL = 0, BASE = 1, CLIENT = 2,
        BASE_VIA_CELL = 3, CLIENT_VIA_CELL = 4,
        CELL_VIA_BASE = 5, CLIENT_VIA_BASE = 6,
        SERVICE = 7
    };

    Component component() const { return (Component)(addr.salt >> 13); }
    EntityTypeID type() const    { return addr.salt & 0x1FFF; }
};
```

注意一个精巧的位压缩技巧:`salt` 字段同时编码了 `Component`(高 3 位)和 `EntityTypeID`(低 13 位)。这样 `EntityMailBoxRef` 只占 12 字节(EntityID 4 + Address 8),可以廉价地在网络上传送、存进数据库。

### 18.2.2 Mailbox 的类层次

Mailbox 是一个有继承关系的 Python 类型族。其根基类 `PyEntityMailBox` 定义在 `lib/entitydef/mailbox_base.hpp`:

```cpp
// lib/entitydef/mailbox_base.hpp:55-121
class PyEntityMailBox: public PyObjectPlus
{
public:
    virtual const MethodDescription * findMethod( const char * attr ) const = 0;
    virtual BinaryOStream * getStream( const MethodDescription & methodDesc,
            std::auto_ptr< Mercury::ReplyMessageHandler > pHandler ) = 0;
    virtual void sendStream() = 0;

    virtual EntityID id() const = 0;
    virtual const Mercury::Address address() const = 0;

    static PyObject * constructFromRef( const EntityMailBoxRef & ref );
    static bool reduceToRef( PyObject * pObject, EntityMailBoxRef * pRefOutput );
};
```

关键设计点:

1. **`findMethod` 纯虚**:不同 Mailbox 类型(Cell/Base/Client)持有不同的 `MethodDescription` 集合,因为 `.def` 文件里 `Cell`/`Base`/`Client` 段定义的方法不同。
2. **`getStream` 纯虚**:返回一个 `BinaryOStream`,调用方把参数写进去。不同 Mailbox 类型写入的目标 Bundle 不同(直接发给 CellApp?还是经 BaseApp 转发?)。
3. **`sendStream` 纯虚**:把 Bundle 真正发送出去。
4. **`constructFromRef` / `reduceToRef`**:支持 Mailbox 与 `EntityMailBoxRef` 互转,这是序列化(存盘、跨进程传递)的基础。

`PyEntityMailBox` 自身是抽象基类,各进程根据自己的角色实现具体子类。在服务端(CellApp/BaseApp),公共基类是 `ServerEntityMailBox`:

```cpp
// server/cellapp/mailbox.hpp:30-67  (baseapp/mailbox.hpp 同构)
class ServerEntityMailBox: public PyEntityMailBox
{
protected:
    Mercury::Address    addr_;          // 目标进程地址
    EntityID            id_;            // 目标实体 ID
    EntityTypePtr       pLocalType_;    // 目标实体类型
};
```

### 18.2.3 Mailbox 的"魔法"——属性访问

当 Python 脚本写 `entity.cell.onSayHello("Alice")` 时,发生的事情远比看起来复杂。`pyGetAttribute` 被重写,把方法名变成一个 `RemoteEntityMethod` 对象:

```cpp
// lib/entitydef/mailbox_base.cpp:66-79
ScriptObject PyEntityMailBox::pyGetAttribute( const ScriptString & attrObj )
{
    const char * attr = attrObj.c_str();
    const MethodDescription * pDescription = this->findMethod( attr );
    if (pDescription)
    {
        return ScriptObject(
            new RemoteEntityMethod( this, pDescription ),
            ScriptObject::FROM_NEW_REFERENCE );
    }
    return PyObjectPlus::pyGetAttribute( attrObj );
}
```

`RemoteEntityMethod`(见 `lib/entitydef/remote_entity_method.hpp`)是一个轻量代理对象,它持有 `Mailbox*` 和 `MethodDescription*`。当脚本调用这个代理(`proxy("Alice")`)时,才真正触发网络发送:

```cpp
// lib/entitydef/mailbox_base.cpp:141-234 (简化)
PyObject * PyEntityMailBox::callMethod(
    const MethodDescription * pMethodDescription, const ScriptTuple & pArgs )
{
    BinaryOStream * pBOS = this->getStream( *pMethodDescription, ... );
    // 把参数序列化进 pBOS
    if (pMethodDescription->component() == MethodDescription::CLIENT) {
        pMethodDescription->addToClientStream( source, *pBOS, this->id() );
    } else {
        pMethodDescription->addToServerStream( source, *pBOS, sourceEntityID );
    }
    this->sendStream();   // 真正发送
}
```

这就是 Mailbox 的"透明调用"本质:**方法名 → MethodDescription → Bundle → Channel → 网络**。

## 18.3 七种 Mailbox 类型详解

`EntityMailBoxRef::Component` 枚举了 8 个值(7 个实体相关 + 1 个 SERVICE)。理解它们的分类逻辑是掌握 Mailbox 的关键。

### 18.3.1 分类逻辑:进程级 vs 实体级 × 直接 vs 转发

先看一张分类矩阵:

| Component | 目标层 | 发送方式 | 用途 |
|-----------|--------|---------|------|
| `CELL` | Cell 实体 | 直接发给 CellApp | 调用对方 Cell 上的方法 |
| `BASE` | Base 实体 | 直接发给 BaseApp | 调用对方 Base 上的方法 |
| `CLIENT` | Client 实体 | 直接发给客户端(仅 BaseApp 可用) | Base 调用自己的客户端 |
| `BASE_VIA_CELL` | Base 实体 | 经 CellApp 转发 | CellApp 上没有 Base 直连通道时 |
| `CLIENT_VIA_CELL` | Client 实体 | 经 CellApp→BaseApp 转发 | CellApp 想发消息给某实体的客户端 |
| `CELL_VIA_BASE` | Cell 实体 | 经 BaseApp 转发 | BaseApp 想发消息给某实体的 Cell |
| `CLIENT_VIA_BASE` | Client 实体 | 经 BaseApp 转发 | CellApp 想发消息给某实体的客户端 |
| `SERVICE` | 服务 | 直接发给 Service 进程 | 调用命名服务 |

**分类原则一:目标层**。`CELL`/`BASE`/`CLIENT` 是实体的三层(第 6 章讲过 `.def` 文件的 `Client`/`Base`/`Cell` 段)。一个实体在三层各有一个"化身",Mailbox 必须指明调哪一层。

**分类原则二:是否需要转发**。BigWorld 的网络拓扑有约束:
- **CellApp ↔ CellApp**:有直连通道(`CellAppChannel`)
- **BaseApp ↔ BaseApp**:有直连通道
- **CellApp ↔ BaseApp(同一实体的 Base)**:有直连通道
- **CellApp ↔ 客户端**:**无直连**(CellApp 不直接连客户端),必须经 BaseApp 转发
- **BaseApp ↔ 其他实体的 Cell**:BaseApp 通常不直接和别的 CellApp 通信,经该实体的 Base 转发

`_VIA_` 后缀的 Mailbox 就是为绕过这些拓扑限制而生。例如 `CLIENT_VIA_CELL` 表示:"这个消息要发给某实体的客户端,但我(CellApp)没有客户端连接,所以先发给该实体的 Cell,Cell 再转给 Base,Base 再转给客户端"。

### 18.3.2 Cell Mailbox(`CELL`)

**用途**:调用目标实体的 **Cell 方法**(在 CellApp 上执行的方法)。

```python
# 在某实体的 Base 脚本里:
other_entity.cell.bePushed(self.id)   # 让 other 的 Cell 执行 bePushed
```

**实现**:`CellEntityMailBox`(见 `server/cellapp/mailbox.hpp:75` 与 `server/baseapp/mailbox.hpp:110`)。它的 `getStream` 直接往目标 CellApp 的通道上写 Bundle。

```cpp
// server/cellapp/mailbox.hpp:93-100
class CellEntityMailBox: public ServerEntityMailBox
{
    virtual BinaryOStream * getStream( const MethodDescription & methodDesc, ... );
    void sendStream();
    virtual const MethodDescription * findMethod( const char * attr ) const;
    virtual EntityMailBoxRef::Component component() const;
protected:
    Mercury::UDPChannel * pChannel() const;   // 直连目标 CellApp 的通道
};
```

`findMethod` 返回的是该实体类型 `.def` 文件中 `Cell` 段定义的 `MethodDescription`。

### 18.3.3 Base Mailbox(`BASE`)

**用途**:调用目标实体的 **Base 方法**(在 BaseApp 上执行的方法)。

```python
# 在某实体的 Cell 脚本里:
self.base.onCellReady()   # 调用自己的 Base
other.base.trade(item)    # 调用 other 的 Base
```

**实现**:`BaseEntityMailBox`(`server/cellapp/mailbox.hpp:135` / `server/baseapp/mailbox.hpp:142`)。从 CellApp 发往 BaseApp 时,使用 `BaseAppIntInterface` 定义的内部消息接口。

### 18.3.4 Client Mailbox(`CLIENT`)

**用途**:调用目标实体的 **Client 方法**(在客户端上执行的方法)。只有 **BaseApp** 能直接发(因为只有 BaseApp 连着客户端)。

```python
# 在某实体的 Base 脚本里:
self.client.onHealthChanged(50)   # 通知自己的客户端
```

**注意**:在 CellApp 上,脚本一般拿不到 `CLIENT` 直连 Mailbox,只能拿到 `CLIENT_VIA_CELL` 或 `CLIENT_VIA_BASE`(需要转发)。

### 18.3.5 `BASE_VIA_CELL` 与 `CLIENT_VIA_CELL`

这两个 Mailbox 在 **CellApp** 上使用,表示"我没有该实体 Base/Client 的直接通道,但该实体的 Cell 在我这里(或我能找到它的 Cell),通过 Cell 转发"。

```cpp
// server/cellapp/mailbox.cpp:42-113 (节选)
class CellViaBaseMailBox : public CommonBaseEntityMailBox
{
    // 注意:它继承自 CommonBaseEntityMailBox(因为最终会发到 BaseApp)
    virtual BinaryOStream * getStream( const MethodDescription & methodDesc, ... )
    {
        Mercury::Bundle & bundle = this->bundle();
        bundle.startMessage( BaseAppIntInterface::callCellMethod );
        bundle << methodDesc.internalIndex();
        return &bundle;
    }
    EntityMailBoxRef::Component component() const
    { return EntityMailBoxRef::CELL_VIA_BASE; }
};
```

**设计意图**:CellApp 之间有 `CellAppChannel`,但 CellApp 与"别的实体的 BaseApp"不一定有直连。这时把消息先发给该实体的 Cell(本地的或可直达的),由 Cell 所在的 CellApp 转发给 BaseApp。

### 18.3.6 `CELL_VIA_BASE` 与 `CLIENT_VIA_BASE`

镜像对称地,在 **BaseApp** 上,如果想调用某实体的 Cell 方法,但 BaseApp 与该实体所在的 CellApp 没有直连,就经该实体的 Base 转发。`CLIENT_VIA_BASE` 用于 CellApp 想发消息给某实体客户端的场景——所有客户端流量都经 BaseApp 转发(这是 BigWorld 的硬性架构,见第 18.10 节)。

### 18.3.7 DBApp / LoginApp Mailbox

需要澄清:`EntityMailBoxRef::Component` 枚举里 **没有专门的 DBAppMailbox / LoginAppMailbox**。这两类进程的通信不走 Mailbox 抽象,而是走 Mercury 的接口消息(`DBAppInterface`、`LoginAppInterface`)。

DBApp 与 LoginApp 的"进程级 Mailbox"概念体现在 **Service** 机制里:`SERVICE` 类型的 Mailbox 用于调用命名服务(参见 `lib/server/service.hpp`、`lib/server/services_map.hpp`)。这是 BigWorld 14.x 引入的服务发现机制,允许实体通过名字找到某个服务进程并调用其方法。

> **澄清**:本章任务里提到的"7 种 Mailbox 类型",对应的是 `EntityMailBoxRef::Component` 的 7 个实体相关枚举值(`CELL`/`BASE`/`CLIENT`/`BASE_VIA_CELL`/`CLIENT_VIA_CELL`/`CELL_VIA_BASE`/`CLIENT_VIA_BASE`)。`SERVICE` 是第 8 个,用于服务调用,不属于实体层。所谓"CellApp/BaseApp/DBApp/LoginApp 进程级 Mailbox"在 BigWorld 实现中实际是指 `Service` 机制与 Mercury 接口,而非 `PyEntityMailBox` 的子类。

### 18.3.8 Mailbox 的派生关系总览

```
PyEntityMailBox (lib/entitydef/mailbox_base.hpp)
    └── ServerEntityMailBox (server/cellapp/mailbox.hpp, baseapp/mailbox.hpp)
            ├── CellEntityMailBox          → CELL
            ├── CommonBaseEntityMailBox
            │     ├── BaseEntityMailBox     → BASE
            │     └── CellViaBaseMailBox   → CELL_VIA_BASE
            └── (客户端侧 ClientEntityMailBox 在 connection 库)
```

每个具体子类实现三个关键方法:`findMethod`(找方法描述)、`getStream`(拿 Bundle)、`sendStream`(发送)。不同子类的差异就在这三个方法里——它们决定了"消息发往哪里、用什么格式"。

## 18.4 Mailbox 调用流程

### 18.4.1 一次完整的远程调用

让我们跟踪一次 `bob.cell.onSayHello("Alice")` 的完整旅程:

```
[CellApp#3, Alice 的 Cell 脚本]                    [CellApp#7, Bob 的 Cell 脚本]

 1. Python: bob.cell.onSayHello("Alice")
        │
        ▼
 2. PyEntityMailBox::pyGetAttribute("onSayHello")
    → findMethod("onSayHello") 返回 MethodDescription*
    → new RemoteEntityMethod(mailbox, methodDesc)
        │
        ▼
 3. RemoteEntityMethod::__call__("Alice")
    → PyEntityMailBox::callMethod(methodDesc, ("Alice",))
        │
        ▼
 4. CellEntityMailBox::getStream(methodDesc, handler)
    → 取得目标 CellApp#7 的 UDPChannel
    → channel.bundle().startMessage(CELL_METHOD, methodDesc.internalIndex())
    → 返回 &bundle
        │
        ▼
 5. methodDesc.addToServerStream(source, bundle, srcEntityID)
    → 把 "Alice" 字符串序列化进 bundle
        │
        ▼
 6. CellEntityMailBox::sendStream()
    → channel.send()    ←── 网络 UDP 包发出
        │
        ▼  ──── 网络传输 ────►
                                    7. CellApp#7 收到 UDP 包
                                       → Mercury 分发到 CellEntityMessage handler
                                       → 解码出 entityID=Bob, methodIndex=N
                                    8. 在 Bob 的 CellEntity 上调用 Python 方法
                                       bob.onSayHello("Alice")
                                    9. Bob 的脚本执行 onSayHello 逻辑
```

整个过程对 Alice 的脚本完全透明:她只写了 `bob.cell.onSayHello("Alice")`,根本不知道 Bob 在 CellApp#7 上。

### 18.4.2 透明性的三重保障

这套透明性由三层协作实现:

1. **Bundle/Channel 层(第 5 章)**:Mercury 网络层提供"往通道写消息"的原语,Mailbox 只需要拿到正确的 Channel。
2. **MethodDescription 层(第 6 章)**:`.def` 文件定义的方法在编译期生成 `MethodDescription`,它知道方法名、参数类型、如何序列化。Mailbox 用 `internalIndex()` 在 Bundle 里只放一个整数索引,远端用这个索引反查方法——节省带宽。
3. **Mailbox 层**:根据 `Component` 类型选择正确的 Channel 和消息格式。

### 18.4.3 返回值的处理

远程方法可以有返回值,但因为是异步网络调用,返回值不能直接 `return`。BigWorld 用 **Deferred(延迟对象)** 模式:

```cpp
// lib/entitydef/mailbox_base.cpp:150-160
if (pMethodDescription->hasReturnValues())
{
    pReplyHandler = new ReturnValuesHandler( *pMethodDescription );
    pDeferred = pReplyHandler->getDeferred();
}
BinaryOStream * pBOS = this->getStream( *pMethodDescription,
    std::auto_ptr< Mercury::ReplyMessageHandler >( pReplyHandler ) );
```

`getStream` 的第二个参数是一个 `ReplyMessageHandler`——Mercury 的回复处理器。如果方法有返回值,Mailbox 会注册一个 handler,远端处理完会把返回值打包发回,Mercury 收到回复后调用 handler,handler 再触发 deferred。脚本侧拿到的是一个 `PyDeferred` 对象,可以挂回调。

## 18.5 Mailbox 实现剖析

### 18.5.1 与 Bundle/Channel 的协作

`ServerEntityMailBox` 不直接持有 `UDPChannel`,而是通过 `pChannel()` 虚函数动态获取:

```cpp
// server/cellapp/mailbox.hpp:99
class CellEntityMailBox: public CommonBaseEntityMailBox
{
protected:
    Mercury::UDPChannel * pChannel() const;
};
```

`CellEntityMailBox::pChannel()` 的逻辑:根据 `addr_`(目标 CellApp 地址)从 `CellAppChannels` 单例里查找或创建一个 `CellAppChannel`(第 9 章讲过,这是 CellApp 之间的通信通道)。

`BaseEntityMailBox::channel()` 的逻辑:找到该实体 Base 所在 BaseApp 的通道。

这种"按需取通道"的设计让 Mailbox 成为轻量对象——它只存 `(id, addr, type)`,真正的网络连接由全局的 Channel 管理器维护。

## 18.6 AOI 兴趣区域

### 18.6.1 为什么需要 AOI

假设一个 MMOG 有 10 万个实体、1 万个玩家。如果全广播:

- 每个玩家每帧收到 10 万条位置更新 → 带宽爆炸
- 每个实体每帧要给 1 万个玩家发包 → CPU 爆炸

**AOI(Area Of Interest)** 的核心思想:**每个玩家只关心自己周围一小块区域内的实体**。区域外的实体不创建、不更新、不存在于玩家的世界里。

```
   全服 10 万实体                        玩家 A 的视角
   ┌──────────────┐                     ┌──────────────┐
   │ • • • • • • •│                     │              │
   │ • • A • • • •│  ──AOI 过滤──►      │   A ★ • •    │  只剩 ~50 个
   │ • • • • • • •│                     │   • • •      │
   │ • • • • • • •│                     │              │
   └──────────────┘                     └──────────────┘
```

### 18.6.2 AOI 的几何模型

BigWorld 的 AOI 是一个以玩家为中心、边长为 `2 * aoiRadius` 的**正方形**(不是圆)。它按 X 轴和 Z 轴分别判断——只要 `|dx| <= R` 且 `|dz| <= R`,实体就在 AOI 内。

选择方形而非圆形的原因是 **RangeList 的二维链表结构**(见 18.8 节):方形可以拆成两个独立的一维范围判断,X 和 Z 各自在一维链表上扫描,效率是 O(R) 而非 O(N)。

### 18.6.3 `aoiRadius` 配置

AOI 半径在多个层级配置:

```cpp
// server/cellapp/witness.hpp:164-166

// server/cellapp/witness.cpp:136-137 (构造函数默认值)
aoiHyst_( 5.0 ),
aoiRadius_( CellAppConfig::defaultAoIRadius() ),
```

- **全局默认**:`CellAppConfig::defaultAoIRadius()`(来自 `bw.xml` 的 `cellApp/defaultAoIRadius`)
- **全局上限**:`CellAppConfig::maxAoIRadius()`(防止脚本设得过大导致性能问题)
- **每实体覆盖**:脚本可调用 `self.setAoIRadius(100, 5)`

`setAoIRadius` 会把半径钳制到上限内,并触发触发器范围更新:

```cpp

```

当某实体进入/离开玩家的 AOI,会触发回调:

## 18.7 Witness 系统

### 18.7.1 Witness 是什么

**Witness(见证者)** 是 RealEntity 的一个组件,代表"这个实体有客户端在看着"。只有 Real 实体(非 Ghost)才能有 Witness——因为 Ghost 只是镜像,真正的客户端连接在 Real 上。

```cpp
// server/cellapp/witness.hpp:21-26
/**
 *  This class is a witness to the movements and perceptions of a RealEntity.
 *  It is created when a client is attached to this entity. Its main activity
 *  centres around the management of an Area of Interest list.
 */
class Witness : public Updatable
```

Witness 的核心职责:

1. 维护 **AOI 列表**(哪些实体对玩家可见)
2. 每个 tick **挑选**优先级最高的实体变化,打包发给客户端(经 BaseApp 转发)
3. 管理 **IDAlias**(为节省带宽,把 32 位 EntityID 压成 8 位别名)
4. 管理 **LOD**(Level of Detail,远处的实体只发低细节)

### 18.7.2 Witness 的关键成员

### 18.7.4 Witness 的 update 流程(Pull 模型)

Witness 是 `Updatable` 的子类,每 tick 被 `CellApp::updateWitnesses()` 调用一次。它的 `update()` 方法是 BigWorld 最复杂的方法之一(300+ 行),核心是 **pull 模型**:

```
传统 push 模型:实体变化时主动通知所有 Witness → 每个实体要维护"谁在看我"列表
BigWorld pull 模型:Witness 每 tick 主动从 EntityCache 里"拉"变化 → 实体无感知
```

Pull 模型的优势:**实体侧零状态**——实体不需要知道有哪些 Witness 在看它,Witness 通过 `EntityCache` 缓存的变化号(`lastEventNumber_`、`lastVolatileUpdateNumber_`)判断"自上次推送后这个实体有没有变化"。

`update()` 的主循环(简化):

```cpp
// server/cellapp/witness.cpp:1088-1283 (大幅简化)
void Witness::update()
{
    Mercury::Bundle & bundle = this->bundle();
    int desiredPacketSize = int(maxPacketSize_ * throttle) -
            bandwidthDeficit_ + bundle.size();

    // 1. 先发 reference position(供客户端解析相对坐标)
    this->addReferencePosition( bundle );
    // 2. 先发玩家自己的详细位置
    this->addDetailedPlayerPosition( bundle, usePlayerAsReference );
    // 3. 先发载具栈(玩家骑的马、坐的车)
    for (Entity * pVehicle = entity_.pVehicle(); pVehicle; ...) {
        EntityCache * pCache = aoiMap_.find( pVehicle->id() );
        this->sendQueueElement( pCache );
    }

    // 4. 主循环:按优先级从堆里取实体发更新
    EntityCache::Priority maxPriority = entityQueue_.front()->priority() +
            CellAppConfig::witnessUpdateMaxPriorityDelta();
    while (!entityQueue_.empty() &&
           entityQueue_.front()->priority() < maxPriority &&
           bundle.size() < desiredPacketSize - 2)
    {
        EntityCache * pCache = entityQueue_.front();
        std::pop_heap( ..., PriorityCompare() );
        if (!pCache->isUpdatable()) {
            this->handleStateChange( &pCache, queueEnd );
        } else if (!pCache->isPrioritised()) {
            this->sendQueueElement( pCache );   // 发送该实体的增量
            pCache->updatePriority( entity_.position() );  // 重算优先级
        }
    }
    // 5. 记录带宽赤字(本 tick 没发完的)
    bandwidthDeficit_ = (bundle.size() > desiredPacketSize) ?
        bundle.size() - desiredPacketSize : 0;
}
```

**优先级机制**:`EntityCache::priority_` 是一个 `double`,由 `AoIUpdateScheme::apply()` 计算——距离越近优先级越高。`MAX_PRIORITY_DELTA` 限制单 tick 的优先级跨度,避免远处实体抢占带宽。

**带宽赤字**:`bandwidthDeficit_` 记录"本 tick 想发但没发完的字节数",下 tick 从预算里扣——平滑了突发流量。

### 18.7.5 `addToAoI` 与 `removeFromAoI`

这两个方法由 `AoITrigger` 回调触发(见 18.9 节):

```cpp
// server/cellapp/witness.cpp:2202-2295 (节选)
void Witness::addToAoI( Entity * pEntity, bool setManuallyAdded )
{
    if (!pEntity->pType()->description().canBeOnClient()) return;

    EntityCache * pCache = aoiMap_.find( *pEntity );
    if (pCache != NULL) {
        if (pCache->isGone()) {
            pCache->reuse();          // 之前离开过,复用缓存
        } else {
            // 已经在 AoI 里,只更新标志
            if (setManuallyAdded) pCache->setManuallyAdded();
            else pCache->setAddedByTrigger();
            return;
        }
    } else {
        pCache = aoiMap_.add( *pEntity );
        pCache->setEnterPending();     // 标记:待发 createEntity 给客户端
        this->addToSeen( pCache );
    }
    // 触发脚本回调
    this->entity().callback( "onEnteredAoI",
        Py_BuildValue( "(O)", pEntity ), "onEnteredAoI", true );
}
```

**关键设计**:`addToAoI` **不立即发消息给客户端**。它只设 `ENTER_PENDING` 标志,真正发包在下次 `Witness::update()` 时由 `handleEnterPending` 处理。这种延迟批量发送减少了网络包数量。

`removeFromAoI` 类似,设 `GONE` 标志,等下次 update 时发 leave 消息。

## 18.8 RangeList 索引结构

### 18.8.1 为什么需要 RangeList

AOI 触发器要回答一个问题:"当玩家从 (x1,z1) 移动到 (x2,z2) 时,有哪些实体进入了/离开了 AOI 范围?" 

朴素做法是遍历所有实体做距离判断——O(N),N 是 Cell 内实体数。当 N=10000 时每帧成本太高。

**RangeList** 是 BigWorld 的解法:**把所有实体按 X 坐标排成一个双向链表,再按 Z 坐标排成另一个双向链表**。当某实体移动时,只需在链表上局部调整(像插入排序),并在跨越邻居时触发回调——成本 O(移动距离内的邻居数)。

### 18.8.2 RangeListNode 基类

```cpp
// server/cellapp/range_list_node.hpp:34-125
class RangeListNode
{
public:
    enum RangeListFlags
    {
        FLAG_NO_TRIGGERS        = 0,
        FLAG_ENTITY_TRIGGER     = 0x01,
        FLAG_LOWER_AOI_TRIGGER = 0x02,
        FLAG_UPPER_AOI_TRIGGER  = 0x04,
        FLAG_IS_ENTITY          = 0x10,
        FLAG_IS_LOWER_BOUND     = 0x20
    };

    RangeListNode( RangeListFlags wantsFlags, RangeListFlags makesFlags,
            RangeListOrder order );

    void shuffleXThenZ( float oldX, float oldZ );  // 调整位置

    RangeListNode * prevX() const;
    RangeListNode * nextX() const;     // X 链表前后指针
    RangeListNode * prevZ() const;
    RangeListNode * nextZ() const;     // Z 链表前后指针

    bool wantsCrossingWith( RangeListNode * pOther ) const
    { return (wantsFlags_ & pOther->makesFlags_); }

    virtual float x() const = 0;
    virtual float z() const = 0;
    virtual void crossedX( RangeListNode * node, bool positiveCrossing,
        float oldOthX, float oldOthZ ) {}
    virtual void crossedZ( RangeListNode * node, bool positiveCrossing,
        float oldOthX, float oldOthZ ) {}
protected:
    RangeListNode * pPrevX_, * pNextX_, * pPrevZ_, * pNextZ_;
    RangeListFlags  wantsFlags_, makesFlags_;
    RangeListOrder  order_;
};
```

**核心思想**:每个节点维护两个双向链表(X 方向、Z 方向)。当节点移动时,调用 `shuffleXThenZ` 沿链表前后移动到正确位置;每跨越一个邻居节点,就调用双方的 `crossedX`/`crossedZ`——这是触发 enter/leave 检测的时机。

**`wantsFlags` / `makesFlags`**:用位掩码表达"我想知道和谁交叉""我是什么类型"。例如实体节点 `makesFlags = FLAG_IS_ENTITY`,AOI 触发器节点 `wantsFlags = FLAG_ENTITY_TRIGGER | ...`。只有 `wantsFlags & other.makesFlags` 非零时才触发 `crossedX`——避免无意义的回调。

**`order`**:相同坐标时的稳定排序顺序(实体 100,下界 190,上界 200)。这保证触发器边界节点总是在实体节点"外侧",enter/leave 判定方向正确。

### 18.8.3 三种节点类型

RangeList 里有三种节点:

| 类型 | 类 | 作用 |
|------|----|----|
| 实体节点 | `EntityRangeListNode` | 代表一个实体的位置 |
| 触发器节点 | `RangeTriggerNode` | 代表 AOI/范围触发器的边界 |
| 自由节点 | `MobileRangeListNode` | 任意位置、可挂触发器的节点(用于 AoIRoot) |
| 哨兵 | `RangeListTerminator` | 链表头尾,坐标 ±FLT_MAX |

```cpp

{
public:
    EntityRangeListNode( Entity * entity );
    float x() const;     // 取 entity.position.x
    float z() const;     // 取 entity.position.z
    Entity * getEntity() const;
protected:
    Entity * pEntity_;
};
```

### 18.8.4 shuffle 算法

当实体移动时,RangeList 调用 `shuffleXThenZ(oldX, oldZ)`:

```cpp
// server/cellapp/range_list_node.cpp:29-34
void RangeListNode::shuffleXThenZ( float oldX, float oldZ )
{
    this->shuffleX( oldX, oldZ );
    this->shuffleZ( oldX, oldZ );
}
```

`shuffleX` 的核心是"向左/向右冒泡"——很像插入排序的一步:

```cpp
// server/cellapp/range_list_node.cpp:44-128 (简化)
void RangeListNode::shuffleX( float oldX, float oldZ )
{
    float ourPosX = this->x();
    // 向左冒泡:如果前一个节点坐标比我大,交换
    while (pPrevX_ != NULL &&
           (ourPosX < pPrevX_->x() ||
            (isEqual(ourPosX, pPrevX_->x()) && order_ <= pPrevX_->order_)))
    {
        if (this->wantsCrossingWith( pPrevX_ ))
            this->crossedX( pPrevX_, true, pPrevX_->x(), pPrevX_->z() );
        if (pPrevX_->wantsCrossingWith( this ))
            pPrevX_->crossedX( this, false, oldX, oldZ );
        // 交换链表位置
        // ...
    }
    // 向右冒泡:对称
    while (pNextX_ != NULL && ourPosX > pNextX_->x()) { ... }
}
```

**关键**:每次跨越一个邻居,双方的 `crossedX` 都被调用——这就是触发器检测 enter/leave 的时机。先 shuffle X 再 shuffle Z,这样在 `crossedX` 里判断 Z 时用 `oldZ`(因为 Z 还没 shuffle),保证二维判断的正确性。

### 18.8.5 RangeList 容器

```cpp
// server/cellapp/cell_range_list.hpp:12-32
class RangeList
{
public:
    RangeList();

    const RangeListNode * pFirstNode() const { return &first_; }

    }
protected:
    RangeListNode *     pCentralNode_;   // 中心(实体本身)
    RangeTriggerNode    upperBound_;     // 上界节点(x+range)
    RangeTriggerNode    lowerBound_;     // 下界节点(x-range)
    float               oldEntityX_;     // 上一帧实体位置
    float               oldEntityZ_;
};
```

`RangeTriggerNode` 是一个"虚拟节点",它的坐标 = 中心节点坐标 ± range:

```cpp
// server/cellapp/range_trigger.cpp:50-59
float RangeTriggerNode::x() const
{
    volatile float x = pRange_->pCentralNode()->x() + range_;
    return x;
}
```

当中心实体移动时,两个边界节点也跟着移动,在 RangeList 里 shuffle,与经过的实体节点触发 `crossedX`/`crossedZ`。

### 18.9.2 enter/leave 判定算法

当边界节点跨越某实体节点时,`crossedXEntity` 被调用,它要判断这是"进入"还是"离开":

```cpp
// server/cellapp/range_trigger.cpp:170-206 (简化)
void RangeTriggerNode::crossedXEntity( RangeListNode * pNode,
        bool positiveCrossing, float oldOthX, float oldOthZ )
{
    if (pNode == pRange_->pCentralNode()) return;  // 不与自己触发

    // X 先 shuffle,所以用 oldZ 判断 Z 是否在范围内
    const bool wasInZ = pRange_->wasInZRange( oldOthZ, fabsf( oldRange_ ) );
    if (!wasInZ) return;   // Z 不在范围,X 的跨越无意义

    Entity * pOtherEntity = EntityRangeListNode::getEntity( pNode );
    const bool isEntering = (this->isLowerBound() == positiveCrossing);

    if (isEntering) {
        // 检查当前是否真的在范围内
        if (pRange_->isInXRange(pNode->x(), fabsf(range_)) &&
            pRange_->isInZRange(pNode->z(), fabsf(range_)))
        {
            pRange_->triggerEnter( *pOtherEntity );
        }
    } else {
        // 离开:检查过去是否在范围内
        if (pRange_->wasInXRange(oldOthX, fabsf(oldRange_)))
        {
            pRange_->triggerLeave( *pOtherEntity );
        }
    }
}
```

**二维判断的关键**:X 先 shuffle,Z 还没动,所以用 `oldZ` 判断 Z 是否曾InRange。这保证只有"X 跨越 + Z 在范围内"才触发,避免误报。

### 18.9.3 AoITrigger

`AoITrigger` 是 `RangeTrigger` 的具体子类,把 enter/leave 转发给 Witness:

```cpp
// server/cellapp/witness.cpp:73-106
class AoITrigger : public RangeTrigger
{
public:
    AoITrigger( Witness & owner, RangeListNode * pCentralNode, float range ) :
        RangeTrigger( pCentralNode, range,
            RangeListNode::FLAG_LOWER_AOI_TRIGGER,
            RangeListNode::FLAG_UPPER_AOI_TRIGGER,
            RangeListNode::FLAG_NO_TRIGGERS,
            RangeListNode::FLAG_NO_TRIGGERS ),
        owner_( owner )
    {
        // 收集当前在范围内的大型实体
        owner_.entity().space().visitLargeEntities(
            pCentralNode->x(), pCentralNode->z(), *this );
        this->insert();
    }

    virtual void triggerEnter( Entity & entity )
    {
        if (&entity != &owner_.entity() &&
            !entity.pType()->description().isManualAoI())
        {
            owner_.addToAoI( &entity, /* setManuallyAdded */ false );
        }
    }
    virtual void triggerLeave( Entity & entity )
    {
        if (&entity != &owner_.entity() &&
            !entity.pType()->description().isManualAoI())
        {
            owner_.removeFromAoI( &entity, /* clearManuallyAdded */ false );
        }
    }
};
```

**`isManualAoI`**:某些实体类型被标记为"手动 AOI"——它们不自动进入玩家的 AOI,必须脚本主动 `addToManualAoI`。这用于"全屏 boss""公会成员"等特殊可见性逻辑。

### 18.9.4 滞回避免抖动

想象玩家站在 AOI 边界上来回横跳:每跨过边界一次,就触发一次 enter/leave,客户端会疯狂创建/销毁实体——这就是**抖动(jitter)**。

BigWorld 用两层机制对抗抖动:

**机制一:`wasInXRange` / `isInXRange` 的双值检查**。`RangeTrigger` 同时维护 `oldEntityX_`(上一帧位置)和当前位置。判定 enter 用"当前位置是否在范围内",判定 leave 用"上一帧位置是否在范围内"。这两个判断的组合天然带有"迟滞"——只有真正跨过整个边界才触发。

```cpp
// server/cellapp/range_trigger.hpp:98-122
bool wasInXRange( float x, float range ) const
{
    float subX = oldEntityX_;          // 用上一帧位置
    volatile float lowerBound = subX - range;
    volatile float upperBound = subX + range;
    return (lowerBound < x) && (x <= upperBound);
}
bool isInXRange( float x, float range ) const
{
    float subX = pCentralNode_->x();   // 用当前位置
    volatile float lowerBound = subX - range;
    volatile float upperBound = subX + range;
    return (lowerBound < x) && (x <= upperBound);
}
```

> 注意 `volatile` 关键字——这是为了**禁用浮点寄存器扩展精度**。注释解释:如果不加 volatile,CPU 可能在 80 位 FPU 寄存器里做比较,精度高于链表排序时用的 32 位 float,会导致"判定为 InRange 但链表里没触发"或反之的不一致。这是 BigWorld 在工程上踩过坑后留下的细节。

**机制二:`aoiHyst_` 滞回区**。Witness 维护一个 `aoiHyst_`(默认 5 米)概念,代表 AOI 半径之外的"缓冲带"。`setAoIRadius(radius, hyst)` 同时设置两者。这个值被序列化、被 dump,代表"AOI 边界之外还有 hyst 米的滞回区"——可用于扩展的 enter/leave 判定逻辑。

### 18.9.5 AoIUpdateScheme(更新优先级)

`AoIUpdateScheme` 决定"AOI 内某实体的更新频率"——离玩家越近,更新越频繁:

```cpp
// server/cellapp/aoi_update_schemes.hpp:18-54
class AoIUpdateScheme
{
public:
    bool init( const BW::string & name, float minDelta, float maxDelta );

    bool shouldTreatAsCoincident() const
    { return isZero( weighting_ ) && isZero( distanceWeighting_ ); }

    double apply( float distanceSquared ) const
    {
        if (this->shouldTreatAsCoincident()) return 1.0;
        const float distance = sqrtf( distanceSquared );
        return (distance * distanceWeighting_ + 1.f) * weighting_;
    }
private:
    float weighting_;          // 基础权重
    float distanceWeighting_;  // 距离权重
};
```

`apply()` 返回一个"优先级增量":距离越远,增量越大(优先级越低)。Witness 的 update 循环里,优先级低于阈值的实体这 tick 不发更新——这就实现了"远处少更新,近处多更新"。

`shouldTreatAsCoincident()` 表示"无距离衰减"——所有距离一视同仁,适用于需要精确同步的关键实体(如公会战中的队友)。

每个 EntityCache 可以通过 `updateSchemeID` 指定自己的 scheme:

```cpp
// server/cellapp/entity_cache.hpp:98-99
AoIUpdateSchemeID updateSchemeID() const { return updateSchemeID_; }
void updateSchemeID( AoIUpdateSchemeID id ) { updateSchemeID_ = id; }
```

脚本可以为某个实体设置不同的更新策略:

```python
# 在 Witness 实体的 Cell 脚本里
BigWorld.setAoIUpdateScheme( someEntity, "highFreq" )
```

### 18.9.6 EntityCache 的状态机

`EntityCache` 维护每个 AOI 内实体的客户端同步状态:

```cpp
// server/cellapp/entity_cache.hpp:138-162 (节选)
enum
{
    ENTER_PENDING    = 1 << 0, ///< 待发 enterAoI 给客户端
    REQUEST_PENDING  = 1 << 1, ///< 期待客户端的 requestEntityUpdate
    CREATE_PENDING   = 1 << 2, ///< 待发 createEntity 给客户端
    GONE             = 1 << 3, ///< 待从优先级队列移除
    WITHHELD         = 1 << 4, ///< 不发给客户端(脚本主动屏蔽)
    REFRESH          = 1 << 5, ///< 待移除后重新加入 AoI
    PRIORITISED      = 1 << 6, ///< 下次 update 必发
    MANUALLY_ADDED   = 1 << 7, ///< 脚本手动加入的
    ADDED_BY_TRIGGER = 1 << 8, ///< 触发器自动加入的
};
```

典型的状态流转:

```
触发器 enter → ENTER_PENDING →(update 时)→ CREATE_PENDING
    → 发 createEntity → 正常更新
触发器 leave → GONE →(update 时)→ 发 leaveAoI → 移除
```

`WITHHELD` 允许脚本"隐藏"某实体(如隐身单位),`PRIORITISED` 允许强制某实体下 tick 必发(如刚说话的 NPC)。

## 18.10 客户端实体同步

### 18.10.1 CellApp 不直连客户端

这是 BigWorld 架构的关键约束:**CellApp 不直接连接客户端**。所有客户端流量都经 BaseApp 转发:

```
 CellApp ──sendToClient──► BaseApp ──► Client
```

原因:CellApp 是无状态的(可迁移、可死)、负载重;BaseApp 是有状态的(持客户端连接)、负责可靠传输。这种分离让 CellApp 可以自由迁移实体而不影响客户端连接。

### 18.10.2 enter/leave 消息流

当 Witness 决定让某实体进入客户端视野时:

```cpp
// server/cellapp/witness.cpp (sendEnter / sendCreate,简化)
void Witness::sendCreate( Mercury::Bundle & bundle, EntityCache * pCache )
{
    // 1. 在 bundle 里写 createEntity 消息
    // 2. 写实体类型、初始位置、初始属性
    // 3. 分配 IDAlias(8 位,替代 32 位 EntityID)
    pCache->idAlias( this->allocateIDAlias( *pCache->pEntity() ) );
}
```

整个流程:

```
[CellApp]                              [BaseApp]                    [Client]
 Witness::update()
   │
   ├─ sendCreate( bundle, cache )
   │   → 写 createEntity + 实体数据
   ├─ sendQueueElement( cache )  (位置/属性增量)
   │
   ▼ bundle 满
   bundle.startMessage( BaseAppIntInterface::sendToClient )
   bundle << entity_.id();        // 哪个玩家的 Base
   channel->send()  ──────────►  BaseApp 收到
                                  → 转发给客户端 ──────►  Client 收到
                                                            → 创建 Entity
                                                            → 更新位置/属性
```

### 18.10.3 IDAlias 与带宽优化

每个 EntityID 是 32 位,但玩家周围可能同时有几百个实体,频繁引用 EntityID 浪费带宽。Witness 维护一个 **IDAlias** 池(8 位,最多 256 个):

```cpp
// server/cellapp/witness.hpp:286-287
IDAlias freeAliases_[ 256 ];
int     numFreeAliases_;
```

当实体第一次进入 AOI,分配一个未使用的 alias(0-254,255 保留为 NO_ID_ALIAS)。之后所有引用该实体的消息用 alias 代替 EntityID——省 3 字节/次。

当实体离开 AOI,alias 回收:

```cpp
// server/cellapp/witness.cpp (deleteFromClient 简化)
void Witness::deleteFromClient( Mercury::Bundle & bundle, EntityCache * pCache )
{
    bundle.startMessage( BaseAppIntInterface::leaveAoI );
    bundle << pCache->idAlias();   // 客户端按 alias 销毁
    // 回收 alias
}
```

### 18.10.4 位置更新流

位置更新是最高频的消息。BigWorld 用了多层优化:

1. **相对位置**:客户端位置作为 reference,其他实体用相对偏移(可能压成 3 个 uint8)。
2. **Volatile 属性**:位置/朝向标记为 volatile,只发"变化量"而非全量。
3. **LOD**:远处实体只发低精度位置(降低 float 精度)。

```cpp
// server/cellapp/witness.hpp:241-244
#if !VOLATILE_POSITIONS_ARE_ABSOLUTE
bool * addReferencePosition( Mercury::Bundle & bundle );
void calculateReferencePosition();
#endif
```

`VOLATILE_POSITIONS_ARE_ABSOLUTE` 编译开关控制是否用绝对位置。默认不开,用相对位置节省带宽。

### 18.10.5 ManualAoI

脚本可以"强制"把某实体加入玩家 AOI,即使它在范围外:

```python
# 在 Witness 实体的脚本里
self.addToManualAoI( someEntity.id() )   # 强制可见
self.removeFromManualAoI( someEntity.id() )  # 取消强制
```

这用于"望远镜""雷达""公会成员标记"等不依赖物理距离的可见性逻辑。手动加入的实体不会被触发器自动移除(除非显式调用 `removeFromManualAoI`)。

## 18.11 特色实现深度剖析

### 18.11.1 Mailbox 抽象的设计哲学:位置透明

回顾 Mailbox 的设计,它实现了**分布式系统中的位置透明性(Location Transparency)**这一经典理想。对比学术界的标准做法:

| 特性 | 学术 RPC | BigWorld Mailbox |
|------|---------|-----------------|
| 调用语法 | `rpc_call(stub, args)` | `mailbox.method(args)` |
| 类型安全 | IDL 编译生成 stub | `.def` 文件 + `MethodDescription` |
| 返回值 | 阻塞等待 | 异步 Deferred |
| 寻址 | 显式 host:port | 隐藏在 `EntityMailBoxRef` |
| 失败处理 | 抛异常 | 静默丢弃 + Watcher 统计 |

BigWorld 选择异步而非阻塞,因为游戏 tick 不能等网络往返。选择"静默丢弃"而非抛异常,因为游戏世界对瞬时丢包有容忍度——丢一帧位置更新远比卡 tick 可接受。

### 18.11.2 七种 Mailbox 的分类逻辑:网络拓扑的产物

为什么是 7 种而不是 3 种(Cell/Base/Client)?这是 **BigWorld 网络拓扑的产物**。回顾第 7 章的进程拓扑:

```
CellApp ── CellAppChannel ── CellApp     (CellApp 之间直连)
CellApp ── BaseAppInt ── BaseApp(同实体)  (Cell↔Base 直连)
BaseApp ── TCP ── Client                 (Base↔Client 直连)
CellApp ──X── Client                    (CellApp 不直连 Client!)
CellApp ──X── 其他实体的 BaseApp        (CellApp 不一定和别的 BaseApp 直连)
```

`_VIA_` 系列就是为绕过"不直连"的限制。`CLIENT_VIA_CELL` 和 `CLIENT_VIA_BASE` 让 CellApp 能间接发消息给客户端——尽管实际路径是 `CellApp → CellApp(目标实体的) → BaseApp → Client`,但脚本完全无感知。

这种"用转发隐藏拓扑"的设计让上层脚本可以假设"任意两实体可互通",降低了 MMOG 业务代码的复杂度。

### 18.11.3 AOI 的性能优化:分块索引

RangeList 的二维双向链表是一种 **分块索引(Block-based Index)** 思想:

- 不维护全局空间哈希(更新成本高)
- 不维护 KD-Tree(实现复杂、动态更新难)
- 用最简单的链表 + 排序,把"范围查询"转化为"链表局部扫描"

代价是单次查询最坏 O(N),但实际游戏中实体移动是渐进的(每帧只移动几米),shuffle 的实际成本是 O(移动距离内的邻居数)≈ O(1)。这是**利用游戏负载特性做优化**的典范。

### 18.11.4 Witness 的 Pull 模型

传统可见性系统用 push 模型:实体变化时遍历所有 Watcher 推送。BigWorld 反其道而行——Witness 每 tick 主动 pull:

```
Push 模型:
  Entity 变化 → for each Witness watching me: witness.sendUpdate()
  问题:Entity 要维护 watcher 列表,Ghost 同步复杂

Pull 模型:
  Witness::update() → for each EntityCache in aoi: 
      if cache.lastEventNumber < entity.currentEventNumber:
          sendUpdate( entity )
  优势:Entity 无状态,Witness 自治
```

Pull 模型的代价是每个 Witness 每 tick 扫一遍 AOI(O(AoI size))。但 AOI 通常只有几十到几百实体,远小于全服实体数,可接受。

Pull 模型的另一优势:**天然支持优先级调度**。Witness 可以按 `EntityCache::priority_` 决定先发谁、后发谁,在带宽不足时丢弃低优先级更新——push 模型做不到这点(推送方不知道接收方的带宽预算)。

### 18.11.5 滞回避免抖动的工程细节

回顾 18.9.4 节的 `wasInXRange` / `isInXRange` 双值检查。这套机制看似简单,实则解决了两个微妙问题:

**问题一:浮点精度不一致**。链表排序时用 `x()` 返回的 32 位 float,但比较时若用 80 位 FPU 寄存器,可能"判定在范围内"而链表里没触发。`volatile float` 强制截断到 32 位,保证一致。

**问题二:二维移动的顺序**。先 shuffle X 再 shuffle Z。在 `crossedX` 里判断 Z 时,必须用 `oldZ`(因为 Z 还没 shuffle),否则会误判。这是 `RangeTrigger::wasInZRange(oldOthZ, ...)` 用 oldZ 的原因。

**问题三:enter vs leave 的方向**。`isLowerBound == positiveCrossing` 这个看似诡异的布尔表达式,实际编码了"边界类型 × 跨越方向 → enter/leave"的真值表:

| 边界类型 | 跨越方向 | 含义 |
|---------|---------|------|
| LowerBound (x-range) | positiveCrossing (右移) | 实体从左边界外进入 → enter |
| LowerBound | !positiveCrossing (左移) | 实体从左边界内出去 → leave |
| UpperBound (x+range) | positiveCrossing (右移) | 实体从右边界内出去 → leave |
| UpperBound | !positiveCrossing (左移) | 实体从右边界外进入 → enter |

这正是 `const bool isEntering = (this->isLowerBound() == positiveCrossing);` 的逻辑——一个简洁的布尔等价式概括了四种情况。

### 18.11.6 Mailbox 的统计与可观测性

BigWorld 在 Mailbox 层内置了细粒度统计(18.5.4 节)。这不是"附加功能",而是 MMOG 运维的必需品。考虑一个真实场景:

> 玩家反馈"公会战卡顿",但 CPU/带宽都正常。怎么定位?

通过 Watcher 看 `MethodDescription::stats()`:
- `onSayHello` 被调用了 1000 万次?可能是广播风暴
- `onTrade` 字节数异常高?可能是参数没压缩
- 某方法 `countSentToOwnClient` 高?可能是 Base 直接给客户端发包过多

没有这层统计,MMOG 的性能调优几乎不可能。这是 BigWorld 在"开发者体验"上的成熟设计。

### 18.11.7 Mailbox 与容错

`ServerEntityMailBox::s_population_` 维护所有 Mailbox 实例。当 BaseApp 主备切换:

```cpp
// server/cellapp/mailbox.hpp:57-59
static void migrateMailBoxes();
static void adjustForDeadBaseApp( const Mercury::Address & deadAddr,
        const BackupHash & backupHash );
```

遍历所有 Mailbox,把指向死掉的 BaseApp 的地址换成 backup 地址。这是 **位置透明的另一面**:不仅隐藏了"目标在哪",还隐藏了"目标换地方了"。脚本持有的 `bob.base` 引用在 BaseApp 故障后仍然有效——这对 MMOG 的可用性至关重要(详见第 19 章)。

### 18.12.3 设计模式总结

1. **位置透明**:Mailbox 隐藏目标进程,脚本如本地调用。
2. **转发抽象**:`_VIA_` 系列绕过网络拓扑限制。
3. **Pull 模型**:Witness 主动拉,实体无状态。
4. **分块索引**:二维链表把范围查询降到 O(移动距离)。
5. **优先级调度**:带宽不足时按优先级丢弃,保证关键更新。
6. **滞回防抖**:`wasInXRange`/`isInXRange` 双值 + `volatile` 浮点控制。
7. **IDAlias 压缩**:32 位 EntityID → 8 位 alias,省 75% 带宽。
8. **可观测性**:Mailbox 内置字节统计,支持运维定位。

### 18.12.4 与其他章节的联系

- **第 5 章(网络层)**:Mailbox 基于 Mercury 的 Bundle/Channel 实现。
- **第 6 章(脚本系统)**:`.def` 文件定义的方法分治是 Mailbox 类型区分的基础。
- **第 9 章(CellApp)**:Witness 挂在 RealEntity 上,CellApp 维护 RangeList。
- **第 10 章(BaseApp)**:BaseApp 是客户端代理,所有 CellApp→客户端流量经它转发。
- **第 19 章(负载均衡)**:Mailbox 的 `migrateMailBoxes` 支撑 BaseApp 主备切换;实体迁移时 AOI 状态随 offload 数据迁移。
- **第 20 章(性能优化)**:Witness 的带宽预算、优先级调度是性能调优的核心抓手。
