## 2.2 programming/bigworld 核心代码目录

进入 `programming/bigworld/`,你会看到引擎源码的核心组织:

```
programming/bigworld/
├── CMakeLists.txt       # CMake 主入口
├── Makefile             # Make 主入口(包含 build/make/Makefile)
├── Makefile.rules       # Make 规则
├── lib/                 # 50+ 个基础库(核心)
├── client/              # 客户端应用代码
├── server/              # 服务器代码
├── tools/               # 23 个工具
├── common/              # 客户端/工具共享的 Python 绑定(py_chunk/py_network 等)
├── examples/            # 扩展示例(cellapp_extension、client_integration)
├── build/               # 构建脚本(CMake/Make/Docker)
├── third_party/         # 第三方库源码
└── doc/                 # 源码内文档
```

### 2.2.1 lib / client / server / tools 的角色划分

BigWorld 采用"**基础库 + 应用层**"的经典分层:

| 目录 | 角色 | 产物形态 |
|---|---|---|
| `lib/` | 基础库(50+ 个) | 静态库 `.lib` / 动态库 `.dll` |
| `client/` | 客户端可执行 | `client.exe` |
| `server/` | 服务器可执行 | `cellapp`、`baseapp`、`dbapp` 等 |
| `tools/` | 工具可执行 | `worldeditor.exe`、`modeleditor.exe` 等 |

`common/` 目录虽然只有几个文件,但扮演重要角色——它包含客户端与工具共享的 Python 绑定:

```
common/
├── pch.hpp
├── py_chunk.cpp        # 暴露 chunk 系统给 Python
├── py_network.cpp      # 暴露网络层给 Python
├── py_network.hpp
├── py_physics2.cpp     # 暴露物理引擎给 Python
├── py_physics2.hpp
├── py_terrain.cpp      # 暴露地形系统给 Python
├── py_timer.cpp        # 暴露定时器给 Python
└── py_timer.hpp
```

这种"在 `common/` 中集中维护 Python 绑定"的设计,使得客户端与编辑器可以共享同一套脚本接口,避免重复代码。

### 2.2.2 examples 扩展目录

`examples/` 提供两个扩展示例:

- `examples/cellapp_extension/`:演示如何编写 CellApp 扩展(`cellapp_extension` 在 server 配置中作为 binary 项目)。
- `examples/client_integration/python/simple/`:演示如何用 Python 集成客户端(`simple_python_client`)。
- `examples/Makefile` / `Makefile.rules`:Make 构建规则。

新手可以从这里入手,理解 BigWorld 的扩展点机制。

### 2.3.2 子库 CMakeLists.txt 的统一模式

观察 `lib/math/CMakeLists.txt`、`lib/network/CMakeLists.txt`、`lib/cstdmf/CMakeLists.txt` 等,你会发现它们都遵循一个统一模式:

```cmake
CMAKE_MINIMUM_REQUIRED( VERSION 2.8 )
PROJECT( math )

INCLUDE( BWStandardProject )
INCLUDE( BWStandardLibrary )

SET( ALL_SRCS
    vector3.cpp  vector3.hpp  vector3.ipp
    matrix.cpp   matrix.hpp   matrix.ipp
    # ...
)
IF( NOT BW_IS_SERVER )
    LIST( APPEND ALL_SRCS
        colour.hpp
        convex_hull.cpp
        # 客户端/工具才需要的源码
    )
ENDIF()
```

关键点:

1. **`BWStandardProject`**:提供标准 include 路径(`lib/`、`third_party/`、DXSDK)、链接目录、Windows 版本宏等。
2. **`BWStandardLibrary`**:声明这是一个库目标(添加 `_LIB` 宏,工具目标会定义 `CSTDMF_IMPORT` 表示从 DLL 导入 cstdmf)。
3. **`BW_IS_SERVER` 条件编译**:服务器构建时排除客户端/工具专属源码(如 `colour.hpp`),减少体积与依赖。
4. **源码分组**:`SOURCE_GROUP( "Textures" FILES ${TEXTURES_SRCS} )` 用于在 VS 工程中分组显示。

### 2.3.3 跨平台构建文件共存

在 `lib/` 下你会看到多种构建文件并存:

```
lib/cstdmf/
├── CMakeLists.txt    # CMake(主)
├── Makefile          # Linux Make
├── Makefile.rules    # Make 规则
└── Android.mk        # Android NDK 构建
```

- **CMakeLists.txt**:Windows 主用,CMake 生成 VS 工程或 Ninja。
- **Makefile / Makefile.rules**:Linux 服务器构建用,通过 `build/make/Makefile` 统一驱动。
- **Android.mk**:Android 平台构建(主要给 cstdmf、math、network、connection 等核心库)。

这种"多构建系统共存"的设计,反映了 BigWorld 在多平台演进的历史——早期 Windows 用 VS,服务器用 Linux Make,移动端用 Android NDK,后期逐步统一到 CMake。

### 2.3.4 PCH(预编译头)机制

每个子库都有 `pch.hpp` 和 `pch.cpp`:

```
lib/cstdmf/
├── pch.hpp   # 预编译头声明
└── pch.cpp   # 预编译头实现(仅包含 pch.hpp)
```

`BWMacros.cmake` 中的 `BW_PRECOMPILED_HEADER` 函数处理 PCH:

```cmake
FUNCTION( BW_PRECOMPILED_HEADER _PROJNAME _PCHNAME )
    IF( MSVC AND NOT CLANG_CL AND NOT BW_IS_SERVER )
        # 用 /Yc 创建 PCH,用 /Yu 使用 PCH
        SET( _PCHFLAGS "/Yc\"${_PCHNAME}\" /Fp\"${_PCHBIN}\"" )
        # ...
    ENDIF()
ENDFUNCTION()
```

注意:**服务器构建(`BW_IS_SERVER`)不使用 PCH**,因为 Linux GCC/Make 对 PCH 支持不如 MSVC 稳定。

## 2.4 server 目录解析

`server/` 目录包含所有服务器进程的源代码。

### 2.4.1 核心进程

BigWorld 服务器采用分布式多进程架构,共有 5 类核心进程:

| 进程目录 | 进程名 | 角色 | 可实例数 |
|---|---|---|---|
| `cellapp/` | CellApp | 空间实体模拟(AOI、Ghost、Controller) | 多个 |
| `baseapp/` | BaseApp | 玩家代理(Base、Mailbox、客户端连接) | 多个 |
| `dbapp/` | DBApp | 数据持久化(MySQL/XML) | 多个(第一个为 Alpha) |
| `loginapp/` | LoginApp | 登录认证 | 多个 |
| `reviver/` | Reviver | 进程复活器(单次复活后自杀) | 多个 |

每个进程的入口 `main.cpp` 都极简,通过 `BIGWORLD_MAIN` 宏 + `bwMainT<T>` 模板:

```cpp
// server/cellapp/main.cpp
int BIGWORLD_MAIN( int argc, char * argv[] ) {
    return bwMainT< CellApp >( argc, argv );
}
```

这统一了所有服务器的启动流程(详见配套文档 `BigWorld启动流程分析.md` 与本教程第7章)。

### 2.4.2 管理器进程

3 个管理器进程,各自单例:

| 进程目录 | 进程名 | 管理对象 |
|---|---|---|
| `cellappmgr/` | CellAppMgr | 所有 CellApp |
| `baseappmgr/` | BaseAppMgr | 所有 BaseApp |
| `dbappmgr/` | DBAppMgr | 所有 DBApp |

管理器负责负载均衡、进程生死监控、登录条件检查等。

### 2.4.3 dbapp_extensions 数据库扩展

`server/dbapp_extensions/` 提供两种数据库引擎扩展:

```
dbapp_extensions/
├── bwengine_mysql/
│   ├── CMakeLists.txt
│   ├── mysql_engine_creator.cpp    # MySQL 引擎创建器
│   └── Makefile
├── bwengine_xml/
│   ├── CMakeLists.txt
│   ├── xml_engine_creator.cpp      # XML 引擎创建器
│   └── Makefile
└── Makefile
```

这种"扩展点"设计允许在不修改 DBApp 主代码的前提下,添加新的存储后端。`BWConfiguration_server.cmake` 中:

```cmake
# DBMgr MySQL support
bwengine_mysql      server/dbapp_extensions/bwengine_mysql
db_storage_mysql    lib/db_storage_mysql

# DBMgr XML database support
bwengine_xml         server/dbapp_extensions/bwengine_xml
db_storage_xml       lib/db_storage_xml
```

### 2.4.4 服务器工具(server/tools/)

`server/tools/` 包含 9 个服务器端辅助工具:

| 工具目录 | 工具名 | 功能 |
|---|---|---|
| `bwmachined/` | bwmachined | 机器守护进程(每台机器一个,管理进程生死) |
| `bots/` | bots | 压力测试机器人(模拟大量客户端) |
| `message_logger/` | message_logger | 消息日志收集(支持二进制/文本/MongoDB 后端) |
| `consolidate_dbs/` | consolidate_dbs | 数据库合并工具 |
| `sync_db/` | sync_db | 数据库模式同步(MySQL 表结构升级) |
| `transfer_db/` | transfer_db | 数据库迁移(快照+合并) |
| `snapshot_helper/` | snapshot_helper | 快照辅助工具 |
| `clear_auto_load/` | clear_auto_load | 清除自动加载标记 |
| `bw_profile/` | bw_profile | 性能分析工具 |

其中 `bwmachined` 是最特殊的——它使用 `BIGWORLD_MAIN_NO_RESMGR` 宏(不依赖 ResourceManager),是独立可执行进程,负责管理整台机器上的所有 BigWorld 进程。

`message_logger` 内部还包含两个后端实现:

```
message_logger/
├── mldb/        # 自研二进制日志后端
└── mongodb/     # MongoDB 日志后端
    └── tasks/   # 后台任务(flush、roll、reconnect)
```

### 2.4.5 服务器构建目标(BWConfiguration_server.cmake)

`BWConfiguration_server.cmake` 完整列出了服务器构建所需的库与二进制。开头定义服务器编译宏:

```cmake
ADD_DEFINITIONS( -DMF_SERVER )   # 服务器编译宏
```

`BW_LIBRARY_PROJECTS` 按注释分为几个层次(注释即原始 CMake 中的注释):

- **BigWorld Standard libraries**:`network`、`resmgr`、`math`、`cstdmf`、`connection_model`、`memhook`、`build`。
- **All servers**:`server`(`lib/server`,服务器共用基类 ServerApp 等)。
- **DBMgr**:`db`、`db_storage`,以及两套扩展:`bwengine_mysql` + `db_storage_mysql`、`bwengine_xml` + `db_storage_xml`。
- **BaseApp**:`sqlite`(用于 BaseApp 备份)。
- **BaseApp + DBMgr + LoginApp**:`connection`(客户端连接模型)。
- **CellApp**:`waypoint`、`terrain`、`physics2`、`moo`、`chunk_loading`。
- **BaseApp + CellApp**:`delegate_interface`、`entitydef_script`、`scene`。
- **BaseApp + CellApp + DBMgr**:`entitydef`、`pyscript`、`chunk`、`urlrequest`、`script`。
- **Third party**:`libpython`、`zip`、`libpng`。

`BW_BINARY_PROJECTS` 列出全部 8 个核心进程(`baseapp`/`baseappmgr`/`cellapp`/`cellappmgr`/`dbapp`/`dbappmgr`/`loginapp`/`reviver`)+ 9 个工具(`bwmachined`/`bots`/`clear_auto_load`/`consolidate_dbs`/`message_logger`/`_bw_profile`/`snapshot_helper`/`sync_db`/`transfer_db`)+ 1 个扩展示例(`cellapp_extension`)。

注意几个关键点:

1. **`ADD_DEFINITIONS( -DMF_SERVER )`**:所有服务器代码都会有这个宏,用于条件编译排除客户端/工具专属代码。
2. **注释表明库的使用者**:`# BaseApp + CellApp + DBMgr` 这样的注释清晰地标注了每个库被哪些进程使用。
3. **`BW_PCH_SUPPORT OFF`、`BW_FMOD_SUPPORT OFF`** 等:服务器禁用 PCH、音频、Scaleform、Umbra 等客户端/工具特性。
4. **`BW_UNIT_TESTS_ENABLED`**:启用时会构建 22 个单元测试目标(`*_unit_test`),覆盖核心库与所有服务器进程。

### 2.5.2 工具间依赖关系

理解工具间依赖关系,有助于修改一个工具时知道影响范围。以下是关键依赖链:

#### 依赖链 1:asset_pipeline 是资源管线核心

```
asset_pipeline (lib)
  ├─ compiler       (tools/asset_pipeline/compiler)
  ├─ conversion     (tools/asset_pipeline/conversion)
  ├─ dependency     (tools/asset_pipeline/dependency)
  └─ discovery      (tools/asset_pipeline/discovery)

batch_compiler   继承 asset_pipeline
jit_compiler     继承 asset_pipeline
assetprocessor   依赖 asset_pipeline
```

`batch_compiler` 和 `jit_compiler` 都通过继承 `asset_pipeline` 的 compiler/conversion/dependency/discovery 四个子库,获得完整的资源编译能力。区别在于:

- `batch_compiler`:命令行批量编译,适用于离线资源构建。
- `jit_compiler`:运行时即时编译,带系统托盘 UI,适用于开发期热更新。

#### 依赖链 2:exporter_common 被三个导出器链接

```
exporter_common (tools/exporter_common)
  ├─ bsp_generator         BSP 生成
  ├─ node_catalogue_holder 节点目录
  ├─ skin_splitter         蒙皮分割
  └─ vertex_formats        顶点格式

visualexporter       链接 exporter_common
animationexporter    链接 exporter_common
mayavisualexporter   链接 exporter_common
```

这三个导出器都是 DCC 插件(`.dle` / `.mll`),每个都为多个 3ds Max / Maya 版本编译一次:

```
visualexporter/
├── max2009_exporter/  # 3ds Max 2009
├── max2010_exporter/  # 3ds Max 2010
├── max2011_exporter/  # 3ds Max 2011
├── max2012_exporter/  # 3ds Max 2012
├── max2013_exporter/  # 3ds Max 2013
└── visualexporter.def # DLL 导出定义
```

#### 依赖链 3:common + editor_shared 被 worldeditor 链接

```
common (tools/common)
  └─ 相机、属性表、材质编辑器、UndoRedo、bwlockd 连接...

editor_shared (tools/editor_shared)
  ├─ app/         编辑器应用接口
  ├─ cursor/      光标
  ├─ dialogs/     对话框(MFC 后端)
  ├─ gui/         GUI 接口
  ├─ mfc/          MFC 实现
  └─ pages/       标签页内容接口

worldeditor    链接 common + editor_shared + modeleditor_core
modeleditor    链接 common + editor_shared + modeleditor_core
particle_editor 链接 common + editor_shared + modeleditor_core
```

`editor_shared` 的设计尤其值得注意——它通过 `CMakeLists.mfc.txt` 和 `CMakeLists.qt.txt` 提供了 MFC 与 Qt 两种后端,理论上允许编辑器在两种 UI 框架间切换(实际默认使用 MFC)。

#### 依赖链 4:工具配置(BWConfiguration_tools.cmake)

`BWConfiguration_tools.cmake` 列出工具构建所需的全部库,是所有目标中依赖最多的(35+ 个库),因为编辑器需要同时具备客户端渲染能力与编辑能力。其 `BW_LIBRARY_PROJECTS` 主要包含以下几类:

- **BigWorld 核心库**(20+ 个):`appmgr`、`guimanager`、`guitabs`、`ashes`、`asset_pipeline`、`compiled_space_writers`、`controls`、`chunk`、`chunk_scene_adapter`、`duplo`、`entitydef`、`gizmo`、`input`、`math`、`model`、`moo`、`network`、`particle`、`physics2`、`post_processing`、`pyscript`、`resmgr`、`romp`、`scene`、`script`、`space`、`terrain`、`navigation_recast`、`waypoint_generator`、`ual`。
- **Asset Pipeline 子库**(4 个):`compiler`、`conversion`、`dependency`、`discovery`。
- **第三方库**(9 个):`nedalloc`、`libpng`、`nvmeshmender`、`recast`、`detour`、`zip`、`libpython`、`libpython_tools`、`re2`。
- **工具共享库**(3 个):`tools_common`(`tools/common`)、`editor_shared`(`tools/editor_shared`)、`modeleditor_core`(`tools/modeleditor_core`)。

关键宏定义:

```cmake
ADD_DEFINITIONS( -DEDITOR_ENABLED )   # 工具编译宏
```

`EDITOR_ENABLED` 宏会启用 `lib/chunk/`、`lib/terrain/` 等库中的编辑器专属代码(如 `EditorChunk`、`EditorChunkTerrain`),这些代码在纯客户端构建中不会编译。

### 2.5.3 工具独立构建目标

除了 `tools`(主目标),还有 3 个独立的工具构建目标:

| 构建目标 | 配置文件 | 产物 |
|---|---|---|
| `navgen` | `BWConfiguration_navgen.cmake` | 仅 navgen(独立工具) |
| `assetprocessor` | `BWConfiguration_assetprocessor.cmake` | 仅 assetprocessor(作为 Python 模块) |
| `exporters` | `BWConfiguration_exporters.cmake` | 全部 DCC 导出器 |
| `extras` | `BWConfiguration_extras.cmake` | simple_python_client + process_defs + res_packer |

这种"主目标 + 独立小目标"的设计,允许只构建需要的部分,大幅缩短构建时间。

### 2.5.4 Blob 构建(单一可执行)

`BWConfiguration_*_blob.cmake` 是特殊的"blob"构建——它把多个库打包到单一可执行文件中,减少 DLL 地狱:

| Blob 目标 | 内容 |
|---|---|
| `client_blob` | 客户端单一 blob |
| `tools_blob` | 工具单一 blob |
| `exporters_blob` | 导出器单一 blob |

主 `CMakeLists.txt` 中的处理:

```cmake
IF( BW_BLOB_CONFIG )
    ADD_DEFINITIONS( -DBW_BLOB_CONFIG=1 )
    IF( MSVC )
        IF( BW_PLATFORM STREQUAL "win64" )
            SET( CMAKE_CXX_FLAGS_DEBUG "${CMAKE_CXX_FLAGS_DEBUG} /bigobj" )
        ENDIF()
    ENDIF()
ENDIF()
```

`/bigobj` 标志是因为 blob 模式下单个目标文件包含的代码段过多,需要更大的目标文件格式。

## 2.6 构建系统总览

BigWorld 同时支持多种构建系统,这是历史演进的产物。

### 2.6.1 四种构建系统共存

| 构建系统 | 主用平台 | 主用场景 |
|---|---|---|
| **CMake** | Windows、Linux | 主构建系统(推荐) |
| **Makefile** | Linux | 服务器构建(老路径) |
| **Android.mk** | Android | 移动端核心库 |
| **Xcode** | macOS | (已废弃,`process_defs.xcodeproj` 残留) |

> **新手提示**:对于现代构建,**统一使用 CMake** 即可。Makefile 主要给 Linux 服务器运维使用,Android.mk 仅用于移动端核心库。

### 2.6.2 CMake 与 Make 的关系

在 `programming/bigworld/Makefile` 中只有一行:

```makefile
include $(patsubst %/,%,$(dir $(lastword $(MAKEFILE_LIST))))/build/make/Makefile
```

它将所有工作转交给 `build/make/Makefile`。而 `build/make/Makefile` 是完整的 Linux 构建系统:

```makefile
# 顶层 Makefile for BigWorld Technology Server components
# 支持目标:
#   all         - 构建所有源代码组件
#   everything  - 构建一切(包括 RPM)
#   clean       - 清除所有中间文件

BW_ROOT := $(abspath $(patsubst %/,%,$(dir $(lastword $(MAKEFILE_LIST))))/../../../..)

BW_CONFIG_HYBRID := hybrid
BW_CONFIG_DEBUG  := debug

BW_SRC := $(BW_ROOT)/programming/bigworld
BW_ABS_SRC_LIB := $(BW_ABS_SRC)/lib
BW_ABS_SRC_THIRDPARTY := $(BW_ABS_SRC)/third_party
BW_ABS_SRC_SERVER := $(BW_ABS_SRC)/server

BW_CONFIG_DEFAULT := $(BW_CONFIG_HYBRID)
BW_STANDARD_CONFIGS := $(BW_CONFIG_HYBRID) $(BW_CONFIG_DEBUG)

# MF_CONFIG 是兼容性回退
ifdef MF_CONFIG
BW_CONFIG ?= $(MF_CONFIG)
endif
BW_CONFIG ?= $(BW_CONFIG_DEFAULT)
```

注意:

- **配置类型**:`hybrid`(默认,带调试信息的优化构建)和 `debug`。这与 CMake 的 `Debug;Hybrid` 对应。
- **平台检测**:`BW_PLATFORM_PY := $(BW_BLDDIR)/platform_info.py` 用 Python 脚本检测平台。
- **输出目录**:`game/bin/server/<platform>/` 下。

### 2.6.3 构建系统选择建议

| 你的场景 | 推荐构建系统 |
|---|---|
| Windows 开发客户端/工具 | CMake + Visual Studio |
| Windows 开发服务器 | CMake + Visual Studio(remote build 到 Linux) |
| Linux 服务器构建(纯) | Makefile 或 CMake |
| Docker 容器化构建 | CMake(在 CentOS 7 容器内) |
| CI/CD 自动化 | CMake(Ninja 生成器) |

## 2.7 CMake 构建系统深度剖析

CMake 是 BigWorld 的主构建系统,本节深入剖析其工作原理。

### 2.7.1 主 CMakeLists.txt 结构

`programming/bigworld/CMakeLists.txt` 是 CMake 入口,让我们逐段解读:

#### 段 1:基础设置与目标选择

```cmake
CMAKE_MINIMUM_REQUIRED( VERSION 2.8.12 )

# 设置 BigWorld 源目录
SET( BW_SOURCE_DIR ${CMAKE_SOURCE_DIR} )

# CMake 模块查找路径
SET( CMAKE_MODULE_PATH "${BW_SOURCE_DIR}/build/cmake" )

# 必须指定 BW_CMAKE_TARGET
IF( NOT BW_CMAKE_TARGET )
    MESSAGE( FATAL_ERROR "BW_CMAKE_TARGET is not set, either configure CMake by running bigworld/src/build/bigworld_cmake.bat or specify BW_CMAKE_TARGET when invoking CMake." )
ENDIF()
```

**关键点**:

- `BW_CMAKE_TARGET` 是必须的命令行参数,可选值: `client` / `server` / `tools` / `navgen` / `assetprocessor` / `exporters` / `extras` 及对应的 `_blob` 版本。
- CMake 模块统一在 `build/cmake/` 下查找。

#### 段 2:配置类型覆盖

```cmake
# 覆盖默认的 Debug/Release/MinSizeRel/RelWithDebInfo
SET( CMAKE_CONFIGURATION_TYPES Debug;Hybrid
    CACHE STRING "Semicolon separated list of supported configuration types"
    FORCE )
```

BigWorld 自定义了两种配置:

- **Debug**:完全调试,无优化。
- **Hybrid**:带调试信息的优化构建(类似 RelWithDebInfo,但优化级别更高)。

客户端额外有 `Consumer_Release`(面向消费者的发布版,定义 `CODE_INLINE` 与 `CONSUMER_CLIENT_RELEASE`)。

#### 段 3:平台与编译器检测

```cmake
ENABLE_LANGUAGE( C )
ENABLE_LANGUAGE( CXX )

IF( BW_IS_REMOTE_ONLY )
    SET( BW_PLATFORM_LINUX ON )
    SET( BW_PLATFORM ${BW_REMOTE_PLATFORM} )
    SET( BW_ARCH_64 ON )
ELSEIF( WIN32 )
    SET( BW_PLATFORM_WINDOWS ON )
    IF( CMAKE_SIZEOF_VOID_P EQUAL 4 )
        SET( BW_PLATFORM "win32" )
        SET( BW_ARCH_32 ON )
    ELSEIF( CMAKE_SIZEOF_VOID_P EQUAL 8 )
        SET( BW_PLATFORM "win64" )
        SET( BW_ARCH_64 ON )
    ENDIF()
ELSE()
    MESSAGE( FATAL_ERROR "Only Windows builds are currently supported." )
ENDIF()

# 编译器版本检测
IF( MSVC9 )
    SET( BW_COMPILER_TOKEN "vc9" )
ELSEIF( MSVC10 )
    SET( BW_COMPILER_TOKEN "vc10" )
ELSEIF( MSVC14 )
    SET( BW_COMPILER_TOKEN "vc14" )
    SET_PROPERTY( DIRECTORY APPEND PROPERTY
        COMPILE_DEFINITIONS _SILENCE_TR1_NAMESPACE_DEPRECATION_WARNING )
ELSE()
    MESSAGE( FATAL_ERROR "Compiler not currently supported by BigWorld." )
ENDIF()
```

注意:

- `BW_IS_REMOTE_ONLY` 表示 Windows 端配置一个远程 Linux 构建服务器(代码在 Windows 编辑,在 Linux 编译)。
- 通过 `CMAKE_SIZEOF_VOID_P` 区分 32/64 位。
- `BW_COMPILER_TOKEN`(vc9/vc10/vc11/vc12/vc14)用于查找 `third_party/*/lib/<token>/` 下的预编译库。

#### 段 4:特性开关

```cmake
# 默认特性支持,可被目标配置覆盖
SET( BW_PYTHON_AS_SOURCE ON )
SET( BW_PCH_SUPPORT ON )
SET( USE_MEMHOOK OFF )
SET( BW_FMOD_SUPPORT OFF )
SET( BW_SCALEFORM_SUPPORT OFF )
SET( BW_SPEEDTREE_SUPPORT OFF )
SET( BW_UMBRA_SUPPORT OFF )
SET( BW_AWESOMIUM_SUPPORT OFF )

# 包含目标配置
INCLUDE( BWConfiguration_${BW_CMAKE_TARGET} )

# 添加特性宏
IF( BW_FMOD_SUPPORT )
    ADD_DEFINITIONS( -DFMOD_SUPPORT=1 )
    SET( FMOD_INCLUDE_DIRS
        "${BW_SOURCE_DIR}/third_party/fmod/api/inc"
        "${BW_SOURCE_DIR}/third_party/fmod/fmoddesignerapi/api/inc" )
ENDIF()
IF( BW_SCALEFORM_SUPPORT )
    ADD_DEFINITIONS( -DSCALEFORM_SUPPORT=1 )
ENDIF()
IF( BW_SPEEDTREE_SUPPORT )
    ADD_DEFINITIONS( -DSPEEDTREE_SUPPORT=1 )
ENDIF()
```

这些 `BW_*_SUPPORT` 开关控制是否编译可选的第三方集成库。默认全部关闭,需要时在目标配置中开启。

### 2.7.2 BWConfiguration 文件详解

`build/cmake/BWConfiguration_*.cmake` 文件定义了 11 个构建目标。每个文件做三件事:

1. **添加目标专属宏**:`ADD_DEFINITIONS( -DMF_SERVER )` 或 `ADD_DEFINITIONS( -DBW_CLIENT )` 等。
2. **设置 `BW_LIBRARY_PROJECTS`**:列出该目标需要的所有库。
3. **设置 `BW_BINARY_PROJECTS`**:列出该目标需要生成的所有可执行文件。

下表对比 4 个主要目标的特性差异:

| 特性 | client | server | tools | navgen |
|---|---|---|---|---|
| 编译宏 | `BW_CLIENT` | `MF_SERVER` | `EDITOR_ENABLED` | `_NAVGEN` |
| Memhook | ON | OFF | OFF(可配置) | OFF |
| Consumer Release | 是 | 否 | 否 | 否 |
| PCH 支持 | ON | OFF | ON | ON |
| Scaleform/FMOD/SpeedTree | 可选 | 全 OFF | 可选 | 可选 |
| Recast/Detour | 否 | 否 | 是 | 否 |
| 单元测试 | 客户端测试集 | 服务器测试集 | 工具测试集 | 否 |

### 2.7.3 BWStandardProject 与 BWStandardLibrary

这两个模块是所有 BigWorld 子项目的公共配置:

#### BWStandardProject.cmake(对所有目标)

```cmake
# 额外 include 目录
INCLUDE_DIRECTORIES( ${BW_SOURCE_DIR}/lib )
INCLUDE_DIRECTORIES( ${BW_SOURCE_DIR}/third_party )
INCLUDE_DIRECTORIES( $ENV{DXSDK_DIR}/Include )
INCLUDE_DIRECTORIES( ${BW_SOURCE_DIR}/third_party/python/Include )
INCLUDE_DIRECTORIES( ${BW_SOURCE_DIR}/third_party/python/PC )

# 快速浮点
BW_ADD_COMPILE_FLAGS( /fp:fast )

# 平台相关链接目录
IF( BW_PLATFORM_WINDOWS AND BW_ARCH_32 )
    LINK_DIRECTORIES( $ENV{DXSDK_DIR}/Lib/x86 )
    IF( BW_FMOD_SUPPORT )
        LINK_DIRECTORIES( ${BW_SOURCE_DIR}/third_party/fmod/api/lib )
    ENDIF()
ELSEIF( BW_PLATFORM_WINDOWS AND BW_ARCH_64 )
    LINK_DIRECTORIES( ${BW_SOURCE_DIR}/lib )
    LINK_DIRECTORIES( $ENV{DXSDK_DIR}/Lib/x64 )
ENDIF()

# Windows 版本定义(目标 Windows XP)
ADD_DEFINITIONS(
    -DNTDDI_VERSION=0x05010000
    -D_WIN32_WINNT=0x0501
    -D_WIN32_WINDOWS=0x0501
    -D_WIN32_IE=0x0600
)

# CRT 安全警告抑制
ADD_DEFINITIONS(
    -D_CRT_SECURE_NO_WARNINGS
    -D_CRT_NONSTDC_NO_DEPRECATE
)
```

注意 BigWorld 14.4.1 仍然目标 Windows XP(`_WIN32_WINNT=0x0501`),这是为了兼容老客户端。现代构建可能需要更新此宏。

#### BWStandardLibrary.cmake(仅对库目标)

```cmake
ADD_DEFINITIONS( -D_LIB )

IF( BW_IS_TOOLS OR BW_IS_OFFLINEPROCESSOR )
    SET( BW_USE_CSTDMF_DLL ON )
    SET( BW_USE_CSTDMF_IN_DLL ON )
    ADD_DEFINITIONS( -DCSTDMF_IMPORT )
ENDIF()
```

**关键设计**:工具目标使用 `cstdmf` 的 DLL 版本(通过 `CSTDMF_IMPORT` 宏声明从 DLL 导入),而服务器/客户端使用静态库版本。这避免了工具之间 `cstdmf` 全局状态冲突。

def writeCMakeRunBat( cmd, outputDir, batchenv = "", configs = [] ):
    # 写 rerun_cmake.bat

    if batchenv:
        out.write( batchenv )
    cmdstr = ' '.join( cmd )

### 2.8.3 库间依赖关系

BigWorld 的库之间存在明确的依赖关系。从 `BWConfiguration_server.cmake` 的注释可以看出大致层次:

```
层次 1(基础设施,无依赖):
    cstdmf  math  memhook  build

层次 2(基础库,依赖层次 1):
    network       → cstdmf
    resmgr        → cstdmf
    pyscript      → cstdmf (Python)

层次 3(数据/存储):
    db            → network, cstdmf
    db_storage    → db
    db_storage_xml    → db_storage
    db_storage_mysql  → db_storage

层次 4(游戏逻辑):
    entitydef     → network, resmgr, pyscript
    entitydef_script  → entitydef
    chunk          → resmgr, cstdmf
    connection     → network, cstdmf
    delegate_interface  → cstdmf

层次 5(渲染/物理,仅客户端/工具):
    moo            → math, resmgr
    model          → moo
    terrain        → moo, chunk
    physics2       → math, cstdmf
    waypoint       → math, cstdmf

层次 6(应用):
    server         → 所有服务器库
    client         → 所有客户端库
    tools          → 所有库
```

这种层次化设计的好处是:修改底层库(如 `cstdmf`)会触发上层所有库重新编译,而修改上层库(如 `worldeditor`)只影响自身。

### 2.9.4 远程构建(Windows 编辑 + Linux 编译)

BigWorld 支持"在 Windows 上编辑源码、在 Linux 上编译服务器"的工作流:

#### 步骤 1:配置远程服务器

运行 `bigworld_cmake_with_server.bat` 或在 `bigworld_cmake.py` 中选择远程构建。需要提供:

- **Hostname**:Linux 服务器主机名。
- **Linux source path**:服务器上 `programming/bigworld` 的路径。
- **Connection type**:PuTTY SSH(默认)。
- **Private key path**:SSH 私钥路径(可选,可用 pageant)。
- **Compile Flags**:额外编译标志。
- **Replace Paths in Output**:是否将错误信息中的 Linux 路径替换为 Windows 路径(便于 VS 跳转)。

#### 步骤 2:工作流

1. 在 Windows VS 中编辑代码。
2. CMake 通过 `RemoteBuildConverter.py` 将构建请求推送到 Linux。
3. Linux 端 rsync 同步代码并执行 Make。
4. 错误信息回传,路径转换为 Windows 格式后显示在 VS 错误列表中。

这种方式让团队可以共享一台强力 Linux 构建服务器,而开发者各自在 Windows 上工作。

### 2.9.5 单元测试

BigWorld 内置完整的单元测试,通过 CTest 管理。如 2.4.5 节所示,服务器目标启用单元测试时会构建 22 个测试可执行(`cstdmf_unit_test`、`math_unit_test`、`cellapp_unit_test` 等),客户端与工具目标也有各自的测试集(分别约 16 个和 2 个)。

每个测试目标对应一个 `unit_test/` 子目录,使用 CppUnitLite2 框架(位于 `third_party/CppUnitLite2`)。运行测试:

```bash
# Linux:运行所有测试(继续执行不停止)
make -C programming bw-run-all-unit-tests

# Linux:运行测试,遇到首个失败即停止
make -C programming bw-run-unit-tests

# Windows (VS):右键 RUN_TESTS 项目 -> Build
# 或命令行
ctest -C Hybrid --output-on-failure
```

测试结果会输出每个测试用例的通过/失败状态,失败时打印期望值与实际值对比,便于定位问题。

## 2.10 常见构建问题与排查

### 2.10.1 缺少 DirectX SDK

**症状**:`Cannot open include file: 'd3d9.h'`

**原因**:Windows 构建需要 DirectX SDK,环境变量 `DXSDK_DIR` 未设置。

**解决**:
1. 安装 DirectX SDK(June 2010)。
2. 设置环境变量:`setx DXSDK_DIR "C:\Program Files (x86)\Microsoft DirectX SDK (June 2010)"`。
3. 重启 VS 或终端。

> **注意**:VS 2012+ 自带的 Windows SDK 已包含部分 DirectX 头文件,但 BigWorld 仍依赖旧版 DirectX SDK 的某些组件(如 D3DX)。

### 2.10.2 BW_CMAKE_TARGET 未设置

**症状**:`BW_CMAKE_TARGET is not set`

**原因**:CMake 必须通过 `-D` 参数指定构建目标。

**解决**:
```bash
cmake -DBW_CMAKE_TARGET=client ..
# 或
cmake -DBW_CMAKE_TARGET=server ..
```

### 2.10.3 Python 版本不匹配

**症状**:构建时 Python 相关错误,或运行时 `import bw` 失败。

**原因**:BigWorld 14.4.1 使用 Python 2.x(`third_party/python/`),系统 Python 版本冲突。

**解决**:
- CMake 默认从 `third_party/python/` 源码自构建 Python(`BW_PYTHON_AS_SOURCE ON`)。
- 若改为系统 Python,需保证版本兼容。

### 2.10.4 Windows XP 工具集缺失

**症状**:`The build tools for v141_xp cannot be found`

**原因**:VS 2017+ 的 v141_xp 工具集是可选组件,默认未安装。

**解决**:在 VS Installer 中勾选"使用 C++ 的 Windows XP 支持"组件。

### 2.10.5 Linux 第三方库首次并行构建失败

**症状**:`make -j64` 首次构建第三方库时报错。

**原因**:`build/make/Makefile` 注释中明确提到:"initial third party library builds may not like parallel jobs"。

**解决**:首次构建第三方库时用单线程:
```bash
make -j1 -C programming
# 之后的完整构建可以用 -j64
make -j64 -C programming
```

### 2.10.6 Docker 构建需要运行两次

**症状**:Docker 内 `make` 首次运行提前停止。

**原因**:`Dockerfile` 注释:"May need to run it twice, sometimes it gets confused and stops early due to Python build-system output confusion"。

**解决**:简单再运行一次 `make` 即可。

### 2.10.7 CMake 生成器选择困难

**建议**:

| 场景 | 推荐生成器 |
|---|---|
| Windows 日常开发(需调试) | `Visual Studio 2022 Win32`(多配置,IDE 友好) |
| Windows CI/CD(求速度) | `Ninja with MSVC14 Win64`(单配置,更快) |
| Linux 开发 | `Unix Makefiles` 或 `Ninja` |
| Linux CI/CD | `Ninja`(最快) |

### 2.10.8 PCH 相关错误

**症状**:PCH 相关编译错误。

**原因**:服务器构建(`BW_IS_SERVER`)禁用 PCH,某些代码可能依赖 PCH 中的包含。

**解决**:确保每个 `.cpp` 显式包含所需头文件,不依赖 PCH 间接包含。

## 2.11 本章小结

### 2.11.1 关键知识点回顾

1. **目录结构**:
   - `programming/bigworld/lib/` 是 50+ 个基础库的集合,分为基础设施、数据存储、渲染、游戏逻辑、工具 UI、第三方集成六大类。
   - `client/`、`server/`、`tools/` 三个应用目录基于 `lib/` 构建可执行文件。
   - `build/` 是构建系统控制中心,包含 CMake 模块、Make 脚本、Docker 配置。

2. **构建系统**:
   - CMake 是主构建系统,通过 `BW_CMAKE_TARGET` 选择 11 种构建目标。
   - Makefile 是 Linux 服务器构建的传统路径,与 CMake 等价但不共享配置。
   - Android.mk 用于移动端核心库。
   - 通过 `bigworld_cmake.py` 交互式配置生成 VS 工程。

3. **依赖管理**:
   - `third_party/` 自包含全部依赖,支持离线构建。
   - 商业 SDK(FMOD/Scaleform/SpeedTree/Umbra)需自行获取,默认关闭。
   - 库间依赖层次清晰,底层库变动影响上层。

4. **构建流程**:
