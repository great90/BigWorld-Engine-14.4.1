## 7.1 为什么要分布式集群

**为什么 MMOG 服务器必须是分布式集群,而不能是单进程?** MMOG 与普通多人游戏(如 FPS 房间战)有本质差异:单局人数从几十到数千~数万,世界状态从几分钟一局到数月~数年不关服,玩家穿越从战局间无关联到无缝穿越不同区域,数据持久化从战局结束即丢到必须可靠存档。

单进程方案在 MMOG 场景下有四大硬伤:

1. **CPU 上限**:单核 10Hz tick 下,一万人同时移动连 tick 都跑不完;
2. **内存上限**:每个实体数 KB,加上 AOI 索引、ghost 缓存,单机内存动辄上百 GB;
3. **单点故障**:一个进程崩溃=全服宕机,运营上不可接受;
4. **不可独立扩缩容**:临时加机器抗峰值在单进程架构下无法实现。

分布式集群的解法是:**把世界按空间切分到多个 CellApp,把玩家代理按哈希分布到多个 BaseApp,把数据库写入分散到多个 DBApp,把登录请求负载均衡到多个 LoginApp,用控制平面(Manager)统一调度,数据平面(Worker)水平扩展**。这正是 BigWorld 的设计思路。

### 7.2.2 三大通信路径

整个集群的进程间通信可以归纳为三条主路径:

#### 路径一:控制平面内部互连(Manager ↔ Manager)

DBAppMgr、BaseAppMgr、CellAppMgr 三个单例管理器之间互为 `Mercury::ChannelOwner`(参见 `cellappmgr.hpp:35` 的 `typedef Mercury::ChannelOwner BaseAppMgr;`)。任何一方诞生(`handleCellAppMgrBirth` / `handleBaseAppMgrBirth` / `handleDBAppMgrBirth`)都会通知其他两方,以建立双向信道。**CellAppMgr 持有 TimeKeeper 的"主时钟"角色**,BaseAppMgr、CellApp、BaseApp 都向它对时。

#### 路径二:控制平面 ↔ 数据平面(Manager ↔ Worker)

Manager 通过 Mercury 消息向 Worker 下发命令,Worker 反向上报状态:

| Manager | 下发 | 上报 |
|---------|------|------|
| CellAppMgr | `addCell`、`startup`、`shouldOffload`、`controlledShutDown` | `informOfLoad`、`gameTimeReading`、`recoverCellApp` |
| BaseAppMgr | `startup`、`setBackupBaseApps`、`startBaseEntitiesBackup`、`createBaseWithCellData` | `informOfLoad`、`useNewBackupHash`、`addGlobalBase/delGlobalBase` |
| DBAppMgr | `setDBAppAlpha`(经 BaseAppMgr/CellAppMgr 转发)、`recoverDBApp` | `serverHasStarted`、`addDBApp` |

#### 路径三:数据平面内部(Worker ↔ Worker)

- **CellApp ↔ CellApp**:`CellAppChannels` 集合,用于 ghost 同步、实体迁移、跨 cell 调用(见 `server/cellapp/cell_app_channels.hpp`)。
- **BaseApp ↔ BaseApp**:备份链路,每个 BaseApp 通过 `BackupSender` 把一部分 base 实体状态备份到哈希到的"备份 BaseApp"(见 `server/baseapp/backup_sender.cpp`)。
- **BaseApp ↔ CellApp**:BaseApp 持有 base 实体的"真实状态",CellApp 持有对应 cell 实体的"模拟状态",两者经 `BaseEntityMailBox` / `CellEntityMailBox` 互通。
- **DBApp ↔ BaseApp/CellApp**:BaseApp 通过 `DBAppsGateway` 写库;CellApp 通过 `dbAppAlpha_`(Alpha DBApp)申请实体 ID 段。

### 7.2.3 客户端接入路径

```
Client
  │  1. TCP/UDP 登录请求
  ▼
LoginApp  ─── 2. 向 DBApp Alpha 查询账号 ───► DBApp Alpha
                                                  │
                                                  │ 3. 校验密码 + 加载实体数据
                                                  ▼
LoginApp  ◄── 4. 返回 BaseApp 地址 + session key ─── DBApp Alpha
  │
  │ 5. 把 BaseApp 地址告诉 Client
  ▼
Client  ─── 6. 直连 BaseApp 外部接口 ───► BaseApp
                                          │
                                          │ 7. 创建 Proxy,经 BaseAppMgr 让 CellApp 创建 cell entity
                                          ▼
                                       CellApp(实体进入世界)
```

**关键设计**:Client **从不直连 CellApp**,CellApp 是"纯内部进程",所有客户端流量都经 BaseApp 中转。这保证了:

- **安全**:CellApp 不暴露公网,杜绝客户端伪造坐标;
- **容错**:CellApp 崩溃时 BaseApp 可重新创建 cell entity,客户端无感;
- **限流**:BaseApp 可对每个客户端做 rate-limit,避免恶意客户端冲击 CellApp。

## 7.3 进程分类与职责

BigWorld 的进程可分为三大类:**管理类**(单例控制平面)、**工作类**(可水平扩展的数据平面)、**辅助类**(运维工具)。

### 7.3.1 管理类进程(单例)

管理类进程在整个集群中**只有一个实例**,负责全局调度。它们**不持有任何游戏实体状态**,因此即使重启也不会丢失玩家数据。

#### CellAppMgr — 空间管理总控

- **源码位置**:`server/cellappmgr/cellappmgr.{hpp,cpp}`
- **类继承**:`ManagerApp → ServerApp`(见 `cellappmgr.hpp:45`)
- **核心职责**:
  - 管理 CellApp 生命周期(`addApp`、`recoverCellApp`、`handleCellAppDeath`);
  - 创建与划分 Space / Cell(基于 BSP 树,见 `server/cellappmgr/bsp_node.hpp`);
  - 两层负载均衡:`loadBalance`(Space 内 Cell 边界重分,默认 1s 周期)+ `metaLoadBalance`(跨 CellAppGroup 加/退役 Cell,默认 3s 周期);
  - **持有 TimeKeeper 主时钟**:整个集群的游戏时间以 CellAppMgr 为权威源,BaseAppMgr、CellApp、BaseApp 都向它对时;
  - Space 持久化:`writeSpacesToDB()`、`writeGameTimeToDB()` 周期写到 DBApp。
- **不持有实体**:CellAppMgr 完全不存储 Entity,只存储 `CellData`(BSP 节点的元数据:边界矩形、所在 CellApp 地址),真正的 Entity 在 CellApp 上。

#### BaseAppMgr — Base 实体总控

- **源码位置**:`server/baseappmgr/baseappmgr.{hpp,cpp}`
- **类继承**:`ManagerApp → ServerApp`
- **核心职责**:
  - 管理 BaseApp + ServiceApp 生命周期(用 `ManagedAppSubSet` 抽象,共享同一个 `baseAndServiceApps_` 容器,通过 `isServiceApp` 谓词区分);
  - 客户端登录分配:`findLeastLoadedApp()` 选出最闲 BaseApp,把 `createBaseWithCellData` 转发过去;
  - 备份拓扑管理:`adjustBackupLocations` 在 BaseApp 增减时重新计算哈希,`BackupHashChain` 维护备份链;
  - 全局 base 邮箱注册表:`globalBases_`,跨进程的全局单例实体名 → Base 邮箱映射;
  - 共享数据:`sharedBaseAppData_`、`sharedGlobalData_`,经 Mercury 广播给所有 BaseApp。

#### DBAppMgr — 数据库总控

- **源码位置**:`server/dbappmgr/dbappmgr.{hpp,cpp}`
- **类继承**:`ManagerApp → ServerApp`(见 `dbappmgr.hpp:35`)
- **核心职责**:
  - 管理 DBApp 生命周期,跟踪 DBApp Alpha(`dbApps_.smallest().second` 即为 Alpha,见 `dbappmgr.hpp:62-64`);
  - 维护 DBApp 哈希表:DBApp 按 entityID 哈希分片,`sendDBAppHashUpdate` 在 Alpha 切换或新增 DBApp 时广播给 BaseAppMgr / CellAppMgr;
  - 管理 LoginApp:DBAppMgr 同时是 LoginApp 的注册中心,`addLoginApp` / `recoverLoginApp` 处理 LoginApp 注册;
  - 启动状态机:`STARTUP_STATE_NOT_STARTED → STARTUP_STATE_STARTED → STARTUP_STATE_INDETERMINATE`,`serverHasStarted` 通知 BaseAppMgr;
  - **不直接读写数据库**:DBAppMgr 只做调度,真正的 SQL/IO 在 DBApp 上。

#### bwmachined — 机器守护进程

- **源码位置**:`server/tools/bwmachined/`
- **运行方式**:每台物理机一个,以 daemon 方式运行(见 `linux_machine_guard.cpp` 的 `daemon(0,0)`)
- **核心职责**(详见第 8 章):
  - 子进程 spawn / kill(`CREATE_MESSAGE`、`SIGNAL_MESSAGE`);
  - 进程 birth / death 监听与广播(`LISTENER_MESSAGE`、`NOTIFY_BIRTH`、`NOTIFY_DEATH`);
  - 集群成员发现:环形 buddy 拓扑(`cluster.cpp`),周期 flood 探测;
  - **端口服务**:仅 UDP,绑定 `PORT_MACHINED`,以及一个本地 + 一个广播端点;
  - `findInterface` / `queryForInternalInterface`:新进程启动时向它查询本机内网 IP。
- **特殊性**:
  - 不依赖 `BWResource`,使用 `BIGWORLD_MAIN_NO_RESMGR` 宏(见 `bwservice.hpp:156`);
  - **唯一不继承 ServerApp 的进程**(直接是 `BWMachined` 类);
  - 通过 `fork + exec` 启动子进程,使用"状态管道"机制异步检测 exec 是否成功(详见第 8 章)。

#### Reviver — 故障恢复

- **源码位置**:`server/reviver/reviver.{hpp,cpp}`
- **类继承**:`ServerApp`(注意:不继承 `ManagerApp`,但与 Manager 协同)
- **核心职责**:
  - 监听 bwmachined 的 death 通知,在 Manager 进程意外死亡时启动新的;
  - **单次复活后自杀**:Reviver 完成一次恢复任务后进程退出,等待下次被 bwmachined 重新拉起;
  - 通过 `ComponentReviver`(见 `server/reviver/component_reviver.hpp`)针对不同组件类型(CellAppMgr / BaseAppMgr / DBAppMgr)做特定恢复动作。
- **设计哲学**:Reviver 是"被动式看门狗",不长期驻留,避免自己成为单点故障。

### 7.3.2 工作类进程(多实例)

工作类进程**可水平扩展**,通过增加实例数量来承载更多负载。

#### CellApp — 空间计算

- **源码位置**:`server/cellapp/cellapp.{hpp,cpp}`
- **类继承**:`EntityApp → ScriptApp → ServerApp`(见 `cellapp.hpp:68`)
- **核心职责**:
  - 持有多个 `Cell`(每个 Cell 对应一个 Space 在本进程上的一个分区);
  - 模拟所有"有空间位置"的实体:玩家、NPC、掉落物、AOE 法术等;
  - **Ghost 机制**:每个实体在它附近的 CellApp 上都有一个"幽灵副本"(属性快照,无真实状态),用于 AOI 跨进程可见性;
  - **Witness / AOI**:玩家观察世界的代理,管理可见实体集合,触发 client tick 数据下发;
  - **两层容错备份**:周期把部分实体状态备份到对应 BaseApp(`tickBackup()`);
  - **负载上报**:每 tick 计算并上报 `persistentLoad_` 给 CellAppMgr。
- **关键成员**(见 `cellapp.hpp:315-385`):
  - `cells_`(`Cells` 集合)
  - `pSpaces_`(`Spaces *`,空间对象)
  - `cellAppMgr_`(`CellAppMgrGateway`)
  - `dbAppAlpha_`(`typedef Mercury::ChannelOwner DBApp`,用于 ID 申请)
  - `pBufferedGhostMessages_`、`pBufferedEntityMessages_`、`pBufferedInputMessages_`(三类消息缓冲,在 finishInit 之前积压消息)
  - `witnesses_`(`Updatables`,所有有 Witness 的实体)

#### BaseApp — 玩家代理

- **源码位置**:`server/baseapp/baseapp.{hpp,cpp}`
- **类继承**:`EntityApp → ScriptApp → ServerApp` + `Mercury::ChannelListener`(见 `baseapp.hpp:71`)
- **核心职责**:
  - 持有 Base 实体(玩家代理 + 服务端业务对象),管理其生命周期;
  - **双接口架构**:`intInterface_`(内部 UDP,与 CellApp/Mgr 通信)+ `extInterface_`(外部 UDP,与客户端通信)+ `tcpServer_`(外部 TCP,登录首包);
  - **客户端连接管理**:`baseAppLogin` → `LoginHandler` → `authenticate` 三段式握手;
  - **两级容错备份**:
    - 一级:`backup()` 哈希到备份 BaseApp(秒级,内存到内存);
    - 二级:`archive()` 写 DBApp/SQLite(分钟级,内存到磁盘);
  - **ServiceApp 模式**:`isServiceApp_=true` 时,BaseApp 不接客户端,只跑服务端业务实体(全局服务、跨区服务等);
  - **Proxy**:每个登录玩家的代理对象,持有客户端 channel 与限流状态。
- **关键成员**(见 `baseapp.hpp:380-463`):
  - `bases_`(`Bases`,所有 base 实体集合)
  - `proxies_`(`map<Address, Proxy *>`,客户端 → Proxy 映射)
  - `extInterface_`、`tcpServer_`、`pExternalInterfaceFilter_`
  - `pBackupSender_`、`pArchiver_`、`pBackupHashChain_`
  - `pEntityCreator_`(内含 IDClient,实体 ID 分配)

#### DBApp — 数据持久化

- **源码位置**:`server/dbapp/dbapp.{hpp,cpp}`
- **类继承**:`ScriptApp → ServerApp`(注意:不继承 `EntityApp`,因为不模拟实体;但持有 EntityDefs 用于序列化)
- **核心职责**:
  - 数据库读写:支持 MySQL(生产)与 XML(演示)双引擎,通过 `DatabaseEngineCreator` 工厂模式注册(见 `lib/db_storage/db_engine_creator.hpp`);
  - 实体持久化:`loadEntity`、`saveEntity`、`deleteEntity`;
  - **DBApp Alpha**:第一个 DBApp 实例为 Alpha,负责实体 ID 段分配(`IDClient::pullIDs` 批量取号)、服务器启动状态机;
  - 账号认证:`authenticateAccountHandler`、`relogonAttemptHandler`;
  - 二级数据库:`initSecondaryDB` 创建 SQLite 文件,作为 Archiver 的本地缓冲;
  - **多 DBApp 分片**:DBApp 按 entityID 哈希分片,`DBHashSchemes` 定义哈希方案,Alpha 切换时通过 `sendDBAppHashUpdate` 通知所有 BaseApp。

#### LoginApp — 登录服务

- **源码位置**:`server/loginapp/loginapp.{hpp,cpp}`
- **类继承**:`ServerApp` + `TimerHandler`(注意:不继承 `ScriptApp`,因为 LoginApp 跑 Python 但不持有 EntityDefs)
- **核心职责**:
  - 接收客户端登录请求(TCP/UDP);
  - 与 DBApp Alpha 通信查询账号、获取实体数据;
  - 返回 BaseApp 地址 + session key 给客户端;
  - **登录挑战**:支持 `LoginChallenge` 机制(如基于密码的 challenge-response),避免明文传密码;
  - **限流与封禁**:`IPAddressBanMap` IP 黑名单,`numAllowedLoginsLeft_` 限流计数,`LoginStats` 统计;
  - **可水平扩展**:多 LoginApp 共存,DBAppMgr 通过 `addLoginApp` 注册。

### 7.3.3 辅助进程

辅助进程不在生产环境的"实时游戏循环"中,但服务于开发、运维、测试。

#### message_logger — 日志收集

- **源码位置**:`server/tools/message_logger/`
- **职责**:
  - 接收所有服务端进程的日志消息(经 `BW_MESSAGE_FORWARDER3` 转发);
  - 存储到文件 / MongoDB / MLDB(三种后端,见 `message_logger/file_handler.cpp`、`mongodb/`、`mldb/`);
  - 提供查询接口:`py_query.cpp` 暴露 Python 查询接口。
- **运行方式**:集群中通常一个实例,可与 `log_view` 工具配合查询历史日志。

#### bots — 压测机器人

- **源码位置**:`server/tools/bots/`
- **职责**:
  - 模拟大量客户端登录并执行预设行为(`beeline_controller`、`patrol_graph`、`zigzag_patrol_graph` 等控制器);
  - 压测登录流程、CellApp 负载、网络吞吐;
  - 通过 watcher 接口动态增减机器人(`add_bots_callable_watcher`、`del_bots_callable_watcher`)。
- **运行方式**:独立进程,每个进程可模拟数千个机器人。

#### consolidate_dbs — 数据库合并

- **源码位置**:`server/tools/consolidate_dbs/`

### 7.4.2 ServerApp 基类:进程主循环

`ServerApp`(`lib/server/server_app.hpp:54`)是所有服务端进程的根基类,持有 `mainDispatcher_`(事件循环)、`interface_`(网络接口)、`time_`(游戏时间)、`updatables_`(可更新对象集合)等核心成员,并提供统一的 `runApp` 启动入口与 `advanceTime` tick 推进。

#### 统一启动序列(`runApp`)

`ServerApp::runApp`(`lib/server/server_app.cpp:253-279`)是所有进程的统一启动入口,采用模板方法模式:

```cpp
bool ServerApp::runApp( int argc, char * argv[] )
{
    stampsPerSecond();                  // 1. 时钟校准
    if (this->init( argc, argv )) {     // 2. 虚函数 init(子类 override)
        result = this->run();            // 3. 虚函数 run,进入主循环
    }
    this->fini();                       // 4. 虚函数 fini(清理)
    interface_.prepareForShutdown();
    return result;
}
```

`run()` 的默认实现是 `mainDispatcher_.processUntilBreak()`——一个**永不退出的事件循环**,直到某处调用 `breakProcessing()` 才结束。

#### Tick 推进钩子

`ServerApp::advanceTime`(`server_app.cpp:311-335`)按固定顺序触发 6 个阶段钩子,这是 BigWorld 服务器"每 tick 做什么"的核心骨架:

```
onTickPeriod( tickPeriod )    // 1. 卡顿告警 / hitch 检测
onEndOfTick()                 // 2. tick 收尾(时间未 +1)
++time_                       // 3. 游戏时间 +1
onStartOfTick()               // 4. tick 开始(时间已 +1)
callUpdatables()              // 5. 调用所有 Updatable::update()
onTickProcessingComplete()    // 6. EntityApp 在此 callTimers()
```

**为什么这么设计**:把 tick 拆成 6 个有序钩子,让子类按需 override,基类不关心子类具体做什么。这是典型的**模板方法模式**(Template Method Pattern)。

### 7.4.3 ScriptApp:Python 脚本支持

## 7.5 启动序列详解

BigWorld 集群的启动顺序严格遵循依赖关系,**任何一步失败都会阻塞后续**。完整启动序列如下:

### 7.5.1 启动顺序总览

```
[1] bwmachined 启动(每台机器)
    └─► 集群成员发现(环形 buddy 拓扑完成)

[2] DBAppMgr 启动(单例,任意一台机器)
    └─► 向 bwmachined 注册,等待 DBApp

[3] DBApp 启动(多个,第一个为 Alpha)
    └─► 向 DBAppMgr 注册(addDBApp)
    └─► Alpha 执行一次性初始化(loadEntityDefs / 数据库引擎创建)
    └─► Alpha 调 serverHasStarted 通知 DBAppMgr

[4] BaseAppMgr 启动(单例)
    └─► 向 bwmachined 注册
    └─► 查找 CellAppMgr、DBAppMgr
    └─► 接收 DBAppMgr 转发的 startup 消息

[5] CellAppMgr 启动(单例)
    └─► 查找 BaseAppMgr、DBAppMgr
    └─► ready(READY_BASE_APP_MGR | READY_BASE_APP)

[6] BaseApp 启动(多个,第一个非 ServiceApp 为 bootstrap)
    └─► 向 BaseAppMgr 注册(addApp)
    └─► finishInit:更新 DBApp 哈希、创建 EntityCreator
    └─► 接收 BaseAppMgr 的 startup(bootstrap=true)
    └─► bootstrap BaseApp 自动从 DB 加载 _BigWorldInfo/AutoLoad 实体

[7] CellApp 启动(多个)
    └─► 向 CellAppMgr 注册(addApp)
    └─► finishInit:接收 id、time、baseAppAddr、dbAppAlphaAddr
    └─► 接收 addCell,创建第一个 Cell

[8] LoginApp 启动(多个)
    └─► 向 DBAppMgr 注册(addLoginApp)
    └─► 获取 DBApp Alpha 地址

[9] Reviver 启动(可多个,被动触发)
    └─► 监听 death 通知
    └─► 单次复活后自杀

→ 集群就绪,接受客户端登录
```

### 7.5.2 启动依赖关系图

```
bwmachined ─────► DBAppMgr ─────► DBApp(Alpha)
                                    │
                                    │ serverHasStarted
                                    ▼
                                 BaseAppMgr ─────► CellAppMgr
                                    │                  │
                                    │ startup          │ startup
                                    ▼                  ▼
                                 BaseApp(bootstrap)  CellApp
                                    │                  │
                                    │ createBase       │ addCell
                                    ▼                  ▼
                                 CellApp ◄────────── CellApp(实体进入世界)
                                    │
                                    │
                                    ▼
                                LoginApp(允许客户端登录)
```

### 7.5.3 关键依赖解释

**为什么 DBAppMgr 必须先于 BaseAppMgr?**
- BaseAppMgr 在 `addApp` 时需要把 DBApp 哈希表下发给新 BaseApp;
- BaseApp 的 `EntityCreator` 需要从 DBApp Alpha 申请实体 ID 段;
- 数据库不就绪就无法登录验证。

**为什么 CellAppMgr 在 BaseAppMgr 之后?**
- CellAppMgr 是 TimeKeeper 主时钟,需要 BaseAppMgr 配合对时;
- BaseApp 启动时需要 CellAppMgr 地址来构造自己的 TimeKeeper;
- CellAppMgr 的 `ready(READY_ALL)` 需要 BaseAppMgr 与 CellApp 都就绪。

**为什么 BaseApp 在 CellApp 之前?**
- BaseApp 的 `createBaseWithCellData` 流程会通过 BaseAppMgr → CellAppMgr → CellApp 创建对应的 cell entity;
- 如果没有 CellApp,这个流程无法完成,但 BaseApp 本身可以先启动并加载持久化实体。

**为什么 LoginApp 在最后?**
- LoginApp 在 DBApp Alpha 之前不能查询账号;
- 客户端登录流程的最终一步是返回 BaseApp 地址,所以 BaseApp 必须先就绪。

### 7.5.4 通用入口链路

每个进程的 `main.cpp` 极简,通过 `BIGWORLD_MAIN` 宏 + `bwMainT<T>` 模板:

```cpp
// server/cellapp/main.cpp
int BIGWORLD_MAIN( int argc, char * argv[] )
{
    return bwMainT< CellApp >( argc, argv );
}
```

`BIGWORLD_MAIN` 宏(`lib/server/bwservice.hpp:143-154`)展开后顺序执行:

1. `BW_SYSTEMSTAGE_MAIN()`:设置系统阶段标识;
2. `BWResource::init(argc, argv)`:初始化资源管理器(查找 respaths);
3. `BWConfig::init(argc, argv)`:加载并解析 `bw.xml` 配置链;
4. `bwParseCommandLine(argc, argv)`:处理 `-machined` 等通用命令行参数;
5. 调用 `bwMain(argc, argv)`,即 `bwMainT< CellApp >(argc, argv)`。

`bwMainT<SERVER_APP>` 模板(`bwservice.hpp:97-138`)统一执行:

| 顺序 | 操作 |
|------|------|
| 1 | 创建 `Mercury::EventDispatcher dispatcher` |
| 2 | `MachineDaemon::queryForInternalInterface` 向 bwmachined 查询内网 IP |
| 3 | 构造 `Mercury::NetworkInterface`(端口 0,内部接口) |
| 4 | 安装 `SignalProcessor`(作为 FrequentTask 挂载到 dispatcher) |
| 5 | 创建日志转发器 `BW_MESSAGE_FORWARDER3` |
| 6 | `START_MSG(appName)` 打印启动横幅 |
| 7 | `ServerAppConfig::init(postInit)` 加载所有 `BW_OPTION` 配置 |
| 8 | 栈上构造 App 实例 `SERVER_APP serverApp(dispatcher, interface)` |
| 9 | 调用 `serverApp.runApp(argc, argv)` |

注意:**只有 bwmachined 例外**——它使用 `BIGWORLD_MAIN_NO_RESMGR` 宏(`bwservice.hpp:156`),跳过 `BWResource::init` 与 `BWConfig::init`,因为它是 daemon,需要尽可能早地绑定端口,且不依赖资源系统。

## 7.6 进程间通信总览

BigWorld 的进程间通信(IPC)完全建立在 **Mercury 消息系统** 之上,这是一个基于 UDP 的可靠消息传输层(详见第 5 章)。

### 7.6.1 Mercury 消息系统概览

Mercury 的核心抽象:

| 概念 | 说明 | 源码位置 |
|------|------|---------|
| `Mercury::NetworkInterface` | 网络接口,绑定 UDP 端口,管理收发 | `lib/network/network_interface.hpp` |
| `Mercury::EventDispatcher` | 事件循环引擎,管理定时器与 IO | `lib/network/event_dispatcher.hpp` |

### 7.6.3 Mailbox 七种类型

Mailbox 是 BigWorld 的"实体级跨进程引用",它把"在远端进程的某个实体"抽象成本地可调用的对象。共有七种 Mailbox,详见第 18 章,本节先建立总览:

| # | Mailbox 类型 | 级别 | 用途 | 源码 |
|---|--------------|------|------|------|
| 1 | CellApp Mailbox | 进程级 | CellApp 之间的 ghost 信道 | `lib/entitydef/cell_app_mailbox.hpp` |
| 2 | BaseApp Mailbox | 进程级 | BaseApp 之间的备份、转发 | `lib/entitydef/base_app_mailbox.hpp` |
| 3 | Cell Mailbox | 实体级 | Base → Cell 调用、Ghost → Real 调用 | `lib/entitydef/cell_entity_mailbox.hpp` |
| 4 | Base Mailbox | 实体级 | Cell → Base 调用、跨 BaseApp 实体调用 | `lib/entitydef/base_entity_mailbox.hpp` |
| 5 | Client Mailbox | 实体级 | Server → Client 下发(经 BaseApp 转发) | `lib/entitydef/client_entity_mailbox.hpp` |
| 6 | DBApp Mailbox | 进程级 | BaseApp → DBApp 持久化调用 | `lib/entitydef/dbapp_mailbox.hpp` |
| 7 | LoginApp Mailbox | 进程级 | DBAppMgr → LoginApp 控制 | `typedef Mercury::ChannelOwner LoginApp` |

#### Mailbox 的关键设计:透明跨进程调用

无论 Mailbox 指向的是本进程还是远端进程,**Python 脚本层的调用语法完全一致**:

```python
# 假设 entity 是某个 base 实体,它有一个 cell mailbox
entity.cell.someMethod(arg1, arg2)   # 调用 cell 上的方法
entity.base.otherMethod(arg)         # 调用 base 上的方法
entity.client.clientMethod()         # 调用客户端的方法
```

底层 Mailbox 自动处理:
- **本地调用**:直接转 C++ 函数调用;
- **远端调用**:序列化参数到 Bundle,通过 Mercury 发送;
- **跨 BaseApp 转发**:如果目标 base 已被 offload 到其他 BaseApp,自动转发。

这种"位置透明"是 BigWorld 最大的设计亮点之一——业务脚本无需关心实体在哪个进程上。

```xml
        <password>...</password>
    </db>

    <!-- 父配置(支持配置链继承) -->
    <parentFile>server/bw_production.xml</parentFile>
</root>
```

### 7.7.2 配置链继承

`bw.xml` 支持 `<parentFile>` 节点,形成配置链:

```
bw.xml
  └─ parentFile → bw_production.xml
                    └─ parentFile → bw_base.xml
```

查找配置时,`BWConfig::getSection` 从当前文件开始找,找不到则沿 `parentFile` 链向上追溯,子配置覆盖父配置。

此外,`BWConfig::init`(`lib/server/bwconfig.cpp:176-241`)还支持:
- **用户级覆盖**:优先尝试 `server/bw_<username>.xml`,便于开发者各自维护私有配置;
- **命令行覆盖**:`+key value` 形式参数会写入最前面的配置 section,优先级最高。

### 7.7.3 分进程配置

每个进程的配置位于 `bw.xml` 中以其 `configPath` 命名的节点:

| 进程 | configPath | 主要配置项(节选) |

| BaseAppMgr | `baseAppMgr/` | `baseAppTimeout`、`updateCreateBaseInfoPeriod`、`maxDestinationsInCreateBaseInfo` |
| DBApp | `dbApp/` | `numDBLockRetries`、`secondaryDB.enable`、`isProduction` |
| LoginApp | `loginApp/` | `challengeType`、`maxErrRepliesPerSec`、`maxRate` |

### 7.7.5 ServerAppOption:运行时可调配置

`ServerAppOption<T>`(`lib/server/server_app_option.hpp`)是 BigWorld 配置系统的精髓之一,它把"配置项"与"Watcher 暴露"绑定在一起:

```cpp
// 配置声明(在 *_config.cpp 中)
// lib/server/server_app_option_macros.hpp:20
#define BW_OPTION( TYPE, NAME, VALUE )
    ServerAppOption< TYPE > BW_CONFIG_CLASS::NAME( VALUE,
        BW_CONFIG_PREFIX BW_COMMON_PREFIX #NAME,
        BW_OPTION_WATCHER_DIR #NAME );
```

每个 `BW_OPTION` 同时做两件事:
1. **启动时**从 `bw.xml` 的 `BW_CONFIG_PREFIX/NAME` 路径读值;
2. **运行时**通过 watcher 在 `config/BW_CONFIG_PREFIX/NAME` 路径暴露,可读写。

例如 `cellapp_config.cpp` 中:

```cpp
BW_OPTION( float, maxCellAppLoad, 1.0f );     // 启动从 cellApp/maxCellAppLoad 读
BW_OPTION( bool,  shouldOffload, true );        // 启动从 cellApp/shouldOffload 读
BW_OPTION( float, cellAppTimeout, 3.f );       // cellAppMgr 用
```

读取时直接当变量用(`Config::maxCellAppLoad()`),写入时通过 watcher 工具改值后立即生效——**这是 BigWorld 实现"运行时热调参"的核心机制**。

### 7.7.6 Watcher 运行时配置

`Watcher` 系统(详见 7.8 节)在每个进程上暴露一棵"变量树",路径形如:

```
/
├─ config/
│  ├─ cellApp/
│  │  ├─ updateHertz          (可读写)
│  │  ├─ maxCellAppLoad       (可读写)
│  │  └─ ...
│  ├─ baseApp/
│  └─ ...
├─ components/
│  ├─ CellApps/
│  │  ├─ 0/                    (各 CellApp 实例)
│  │  │  ├─ numEntities
│  │  │  ├─ load
│  │  │  └─ ...
│  └─ BaseApps/
└─ ...
```

运维通过 `bw_auth` 或 HTTP 接口可读写 watcher 节点,实现:
- 实时观察进程负载;
- 动态调整限流阈值;
- 触发 graceful shutdown;
- 强制实体迁移。

## 7.8 监控与运维

BigWorld 提供一套完整的运维工具链,核心是 **Watcher 系统** + **message_logger** + **bwmachined 管理接口**。

### 7.8.1 Watcher 系统

Watcher(`lib/cstdmf/watcher.hpp`)是 BigWorld 的"运行时反射系统",它把 C++ 进程内的关键变量以"路径字符串"的形式暴露出来,支持远程读写。

#### Watcher 注册

每个进程在 `addWatchers()` 中注册自己的 watcher 节点。以 CellApp 为例(`server/cellapp/cellapp.cpp` 的 `CellApp::addWatchers`):

```cpp
void CellApp::addWatchers()
{
    // 注册根 watcher
    Watcher & root = Watcher::rootWatcher();

    // 暴露进程级统计
    root.addChild( "numRealEntities", makeWatcher( &CellApp::numRealEntities ) );
    root.addChild( "load",            makeWatcher( &CellApp::getLoad ) );
    root.addChild( "uptime",          makeWatcher( &CellApp::uptime ) );

    // 暴露 cells / spaces 统计
    root.addChild( "spaces/numSpaces", ... );

    // 通过 ServerAppOption 自动暴露的配置项位于 config/ 下
}
```

#### BW_REGISTER_WATCHER 宏

每个进程向 bwmachined 注册自己的 watcher 端口:

```cpp
// lib/server/bwconfig.hpp:219
#define BW_REGISTER_WATCHER( ID, ABRV, CONFIG_PATH, DISPATCHER, ADDR )
{
    BW::string interfaceName = BWConfig::get(
        CONFIG_PATH "/monitoringInterface",
        BWConfig::get( "monitoringInterface", ADDR.ipAsString() ) );

    WatcherNub::instance().registerWatcher( ID, ABRV, interfaceName.c_str(), 0 );
    WatcherNub::instance().attachTo( DISPATCHER );
}
```

调用方式(`server/cellapp/cellapp.cpp` 的 `finishInit`):

```cpp
BW_REGISTER_WATCHER( id_, "cellappNN", "cellApp", mainDispatcher_, interface_.address() );
```

`ABRV` 是 watcher 节点的前缀,`NN` 会自动替换为 `id` 的两位数字。运维查询时,通过 `cellapp00`、`cellapp01` 这样的名字定位具体实例。

### 7.8.2 HTTP Watcher 接口

除了原生 watcher 协议(UDP),BigWorld 还提供 HTTP watcher 接口,便于集成到 Web 监控面板。HTTP 接口支持:

- `GET /watcher/<path>`:读取 watcher 节点值;
- `POST /watcher/<path>`:写入 watcher 节点值;
- `GET /components`:列出所有已注册进程;
- `GET /status`:返回进程状态 JSON。

Manager 进程还提供 **ForwardingWatcher**(`lib/server/watcher_forwarding.hpp:19`),它把对 Manager 的 watcher 请求**转发给被管理的 Worker**:

```cpp
// lib/server/watcher_forwarding.hpp:28
enum ExposeHints
{
    WITH_ENTITY,      // 拥有特定实体的 component
    CELL_APPS,         // 所有 CellApps
    WITH_SPACE,        // 拥有特定 space 的 component
    LEAST_LOADED,     // 最闲的 component
    BASE_APPS,         // 所有 BaseApps
    SERVICE_APPS,      // 所有 ServiceApps
    BASE_SERVICE_APPS, // 所有 Base + Service Apps
};
```

例如查询 `CellAppMgr/components/CellApps/*/numEntities` 时,CellAppMgr 会把请求转发给所有 CellApp,聚合结果后返回——**运维无需关心每个 CellApp 在哪台机器上**。

### 7.8.3 message_logger 日志收集

所有服务端进程通过 `BW_MESSAGE_FORWARDER3` 宏(`bwservice.hpp:119`)在启动时创建日志转发器,把本地 `INFO_MSG`、`WARNING_MSG`、`ERROR_MSG`、`DEBUG_MSG` 等日志消息异步转发到 message_logger 进程。

message_logger(`server/tools/message_logger/`)支持三种存储后端:

| 后端 | 文件 | 适用场景 |
|------|------|---------|
| 文件(二进制 + 索引) | `message_logger/file_handler.cpp` | 单机部署、轻量 |
| MongoDB | `message_logger/mongodb/` | 生产环境、海量日志 |
| MLDB(自定义格式) | `message_logger/mldb/` | 紧凑存储、快速查询 |

日志条目结构(`message_logger/log_entry.hpp`):

```cpp
struct LogEntry {
    LogTime     timestamp;
    LogEntryAddress  source;     // 进程地址 + 组件名 + appid
    uint8       category;        // 消息类别(网络/实体/脚本等)
    uint8       severity;        // INFO/WARNING/ERROR/DEBUG
    uint16      formatStringId;  // 格式串 ID(节省空间)
    BW::string  args;            // 参数(已序列化)
};
```

通过把"格式串"与"参数"分离存储,message_logger 显著节省了日志磁盘占用——同一条 `INFO_MSG("Entity %d created", id)` 的格式串只存一次,每次记录只需存参数。

### 7.8.4 log_view 工具

`log_view` 是查询 message_logger 的命令行工具(在 `server/tools/message_logger/` 目录,基于 `py_query.cpp` 暴露的 Python 接口)。常用查询:

```bash
# 查询最近 10 分钟所有 ERROR
log_view --severity=ERROR --last=10m

# 查询特定进程的日志
log_view --component=cellapp --appid=3 --last=1h

# 按格式串过滤
log_view --format="Entity * created"
```

### 7.8.5 bwmachined 的管理接口

bwmachined 暴露的管理消息(详见第 8 章):

| 消息类型 | 作用 |
|---------|------|
| `LISTENER_MESSAGE` | 注册 birth/death listener |
| `PROCESS_MESSAGE` | 进程注册/注销/通知 |
| `PROCESS_STATS_MESSAGE` | 查询某进程 CPU/内存 |
| `CREATE_MESSAGE` | 启动子进程 |
| `SIGNAL_MESSAGE` | 向匹配进程发信号(kill) |
| `TAGS_MESSAGE` | 查询配置中的 tag |
| `QUERY_INTERFACE_MESSAGE` | 查询本机内网接口地址 |

通过这些消息,运维可以:
- 查看集群中所有进程的实时状态;
- 远程启动 / 停止 / 重启任何进程;
- 触发 controlled shutdown(优雅关停)。

### 7.8.6 controlled shutdown 两阶段关停

`ShutDownStage`(`lib/server/common.hpp:28-53`)定义了关停的各个阶段:

```cpp
enum ShutDownStage
{
    SHUTDOWN_NONE,                  // 未关停
    SHUTDOWN_REQUEST,               // 请求开始关停
    SHUTDOWN_INFORM,                 // 通知父进程
    SHUTDOWN_DISCONNECT_PROXIES,     // BaseApp 断开所有客户端
    SHUTDOWN_PERFORM,                // 立即关停
    SHUTDOWN_TRIGGER                 // 从最 senior 进程触发(LoginApp → DBApp → BaseAppMgr)
};
```

典型的优雅关停流程:
1. 运维对 LoginApp 发 `SHUTDOWN_TRIGGER`;
2. LoginApp 停止接受新登录,等当前登录处理完,转 `SHUTDOWN_REQUEST` 给 DBApp;
3. DBApp 把待写数据全部落盘,转 `SHUTDOWN_REQUEST` 给 BaseAppMgr;
4. BaseAppMgr 通知所有 BaseApp 进入 `SHUTDOWN_DISCONNECT_PROXIES`,断开所有客户端;
5. BaseApp 把 base 实体全部 archive 到 DBApp,转 `SHUTDOWN_PERFORM`;
6. BaseAppMgr → CellAppMgr → CellApp 依次 `SHUTDOWN_PERFORM`;
7. 最后 bwmachined 退出。

## 7.9 典型场景流程

理解架构的最佳方式是跟踪具体场景。下面分析四个典型场景的进程协同流程。

### 7.9.1 玩家登录流程

```
[1]  Client → LoginApp: login(用户名 + 密码 + challenge response)
[2]  LoginApp → DBApp Alpha: authenticateAccount(账号, 密码)
       DBApp: 校验密码 + 加载实体数据 + 检查 LogOnRecords 是否已有 Base 在线
[3]  DBApp → BaseAppMgr: createBaseWithCellData(实体数据)
       BaseAppMgr: findLeastLoadedApp() 选最闲 BaseApp,检查 areBaseAppsOverloaded
[4]  BaseAppMgr → BaseApp: createBaseWithCellData(实体流)
       BaseApp: 反序列化 → 创建 Base + Proxy → onLogOnAttempt 脚本 → 经 BaseAppMgr 让 CellAppMgr 选 CellApp
[5]  BaseApp → CellAppMgr: createEntity(cell 数据, 位置)
       CellAppMgr: findSpace → findCell(pos) → 选定 CellApp
[6]  CellAppMgr → CellApp: createEntity(cell entity 流)
       CellApp: 在 Cell 中创建 Entity + RealEntity(因有 Witness)→ 注册 range list → 通知 BaseApp
[7]  CellApp → BaseApp: onCellCreated(cell entity id)
       BaseApp: 把 cell mailbox 指向新 cell entity → onCellCreated 脚本 → 准备接受客户端
[8]  BaseApp → BaseAppMgr → DBApp: 更新 LogOnRecord(标记已登录)
[9]  LoginApp ← DBApp: 返回 BaseApp 地址 + session key
[10] Client ← LoginApp: 收到 BaseApp 地址
[11] Client → BaseApp: baseAppLogin(session key)
       BaseApp: session key 找 Proxy → 绑定 client channel → onClientLogOn 脚本 → 下发 tick
[12] Client ← BaseApp: 收到首个 client tick(初始世界状态),玩家正式进入游戏
```

### 7.9.2 玩家移动流程

玩家的位置移动是 MMOG 最频繁的操作,设计直接影响服务器吞吐:

```
[1] Client → BaseApp: 上报玩家位置(position, direction, velocity)
       │
       │  BaseApp 的 Proxy 收到后:
       │  - 限流检查(rate limit filter)
       │  - 校验合理性(防作弊)
       │  - 更新本地 base 实体的位置缓存
       │  - 转发给对应的 CellApp
       │
       ▼
[2] BaseApp → CellApp: CellEntityMailbox.playerMove(position, direction, ...)
       │
       │  CellApp 的 cell entity:
       │  - 更新位置
       │  - 通知 range list 重新索引
       │  - 触发 AOI 更新(若有 Witness 在视野内)
       │  - 检查是否跨越 cell 边界
       │
       ▼
[3] CellApp(若跨越边界):
       │  - 通知 CellAppMgr 调整 cell 边界(loadBalance)
       │  - 或触发实体迁移到相邻 CellApp
       │
       ▼
[4] CellApp → BaseApp(经 witness 系统决定):
       │  - 若玩家在某个 Witness 的视野内,触发"实体进入视野"事件
       │  - BaseApp 把事件累积到 client tick buffer
       │
       ▼
[5] 每个 client tick 周期:
       CellApp → BaseApp: 把所有有 Witness 的玩家的可见实体变化打包
       BaseApp → Client:  下发打包后的 tick 数据
```

**关键设计**:CellApp 不直接给客户端发消息,而是经 BaseApp 中转。这样:
- 客户端只需连接一个 BaseApp,简化网络拓扑;
- BaseApp 可做合并、限流、压缩;
- CellApp 崩溃时 BaseApp 可重新创建 cell entity,客户端无感。

### 7.9.3 跨区域移动(实体迁移)

当玩家从 CellApp A 管辖的区域移动到 CellApp B 管辖的区域时,需要"实体迁移":

```
[1] 玩家位置接近 CellApp A 的 cell 边界
       │
       ▼
[2] CellApp A → CellAppMgr: 通知即将跨边界
       │  CellAppMgr: 查找目标 cell 所属的 CellApp B;若不存在则 addCell 创建
       ▼
[3] CellAppMgr → CellApp B: createEntity(实体数据)
       │  CellApp B 在目标 cell 创建新 entity,但 real_=NULL(标记为 ghost)
       ▼
[4] CellAppMgr → CellApp A: offloadEntity(entity id, 目标 CellApp B 地址)
       │  CellApp A: 序列化 real entity 完整状态 → 发给 CellApp B;本地降级为 ghost
       ▼
[5] CellApp A → CellApp B: 迁移 entity 状态
       │  CellApp B: 把 entity 升级为 real,应用状态,通知 BaseApp 更新 cell mailbox
       ▼
[6] 后续消息:BaseApp → CellApp B(新地址)
```

**关键点**:迁移过程中 entity 始终"存在",只是 real 状态在不同 CellApp 之间转移。客户端完全无感,只看到位置平滑移动。这是 BigWorld 实现"无缝大世界"的核心机制。

### 7.9.4 断线重连

玩家网络断开后,服务器不会立即销毁 base 实体,而是保留一段时间等待重连:

```
[1] Client 与 BaseApp 网络断开
       │
       ▼
[2] BaseApp 的 Proxy:
       - client channel 超时 → Proxy::onClientDeath(CLIENT_DISCONNECT_TIMEOUT)
       - base 实体不立即销毁,进入"等待重连"状态
       - LogOnRecord 标记为 "pending relogon",启动定时器(默认数十秒)
       │
       ▼
[3] Client 重新连接 → LoginApp:login(用户名, 密码)
       │
       ▼
[4] LoginApp → DBApp: authenticateAccount
       │  DBApp: 查 LogOnRecord 发现 base 还在线 → 调用 BaseApp::relogonAttempt
       ▼
[5] DBApp → BaseApp(原 base 所在): relogonAttempt
       │  BaseApp: 找原 base,调 Proxy::onLogOnAttempt 脚本,允许则返回新 session key + 原 base 地址
       ▼
[6] BaseApp → DBApp → LoginApp → Client: 返回原 BaseApp 地址
       │
       ▼
[7] Client → BaseApp: 用新 session key 重新登录
       │  BaseApp: 复用原 Proxy,绑定新 client channel,触发 onClientLogOn 脚本,下发当前世界状态
       ▼
[8] 玩家继续游戏,无数据丢失
```

**关键点**:重连不需要重新加载实体数据(base 仍在内存中);CellApp 上的 cell entity 也未受影响,只在 BaseApp 层切换 client channel。这种"代理保持 + 客户端切换"设计大幅降低断线重连的服务器开销。

## 7.10 容错与高可用

BigWorld 的容错体系建立在**多层冗余**之上,从秒级内存备份到分钟级磁盘归档,从主备切换到自动复活。

### 7.10.1 主备切换(Primary/Backup)

#### DBApp Alpha 切换

DBApp 集群中**第一个 DBApp 实例为 Alpha**,持有特殊职责:实体 ID 段分配(`IDClient::pullIDs`)、服务器启动状态机(`serverHasStarted`)、LoginApp 注册中心。

Alpha 故障时的切换流程:

```
[1] bwmachined 检测到 DBApp Alpha 进程死亡(NOTIFY_DEATH)
[2] bwmachined → DBAppMgr: handleDBAppDeath(Alpha 地址)
      - DBAppMgr 从 dbApps_ 中移除 Alpha
      - 新 Alpha = dbApps_.smallest().second(下一个 ID 最小的 DBApp)
      - sendDBAppHashUpdate(true) 通知所有 BaseApp/CellApp
[3] DBAppMgr → BaseAppMgr/CellAppMgr: setDBAppAlpha(新 Alpha 地址)
[4] BaseApp/CellApp 切换 dbAppAlpha_.addr,后续 IDClient::pullIDs 走新 Alpha
```

#### BaseAppMgr / CellAppMgr 主备

BaseAppMgr、CellAppMgr、DBAppMgr 都是单例,故障时由 Reviver 拉起新实例:

```
[1] Manager 进程死亡 → bwmachined NOTIFY_DEATH
[2] Reviver 监听到 death 通知
      - ComponentReviver::revive("BaseAppMgr")
      - 通过 bwmachined spawn 新 Manager 进程(-recover 参数)
[3] 新 Manager 启动,带 -recover 参数
      - 跳过正常 startup 流程,进入恢复模式
      - 向其他进程查询状态(例如 CellAppMgr 向所有 CellApp 发 recoverCellApp,
        CellApp 上报地址、id、time、所有 space 描述),重建 Space/Cell 拓扑
[4] Reviver 进程自杀(单次复活后退出)
```

### 7.10.2 Reviver 监控机制

Reviver(`server/reviver/reviver.hpp:28`)的设计很特别:

```cpp
class Reviver : public ServerApp, public TimerHandler,
    public Singleton< Reviver >
{
    // ...
    void revive( const char * createComponent );
    bool hasEnabledComponents() const;
};
```

它的特点:
- **被动触发**:不主动轮询,而是订阅 bwmachined 的 death listener;
- **单次复活后自杀**:Reviver 完成一次恢复任务就 `shutDown()`,避免长期驻留占用资源;
- **bwmachined 重启它**:下次有进程死亡时,bwmachined 自动 spawn 新的 Reviver。

这种设计避免了 Reviver 自身成为单点——如果 Reviver 也死了,只需 bwmachined 在下次需要时拉起一个新的。

### 7.10.3 bwmachined 重启策略

bwmachined 本身不自动重启——它由 init.d / systemd / supervisord 等系统级守护拉起。但它会:
- **保存进程表**:`/var/run/bwmachined.state`,SIGTERM 时 `save()`;
- **重启后恢复进程表**:知道集群中原本有哪些进程,以便其他进程重新连接;
- **不主动重启子进程**:子进程死亡只通知 listener,由 Reviver 决定是否拉起。

### 7.10.4 实体备份(Base backup)

BaseApp 的实体有两级备份,确保 BaseApp 故障时不丢数据:

#### 一级:BaseApp → BaseApp 内存备份(秒级)

每个 BaseApp 上都有一份其他 BaseApp 上 base 实体的"备份副本"。`backup()` tick 触发时,`BackupSender` 遍历本地 base,按 hash 选定备份目标 BaseApp,通过 `backupBaseEntity` 消息把状态流发送过去。目标 BaseApp 把它存到 `offloadedBackups_`(若实体不在本地)或更新本地副本(若已是本地实体的备份)。

故障切换:BaseApp B 死亡时,bwmachined → BaseAppMgr::handleBaseAppDeath,BaseAppMgr 调用 `adjustBackupLocations(OP_CRASH)` 重新计算备份哈希,通知所有 BaseApp "B 上的实体的备份在哪",备份持有方把备份升级为 real。CellApp 上的 cell entity 不变(通过新 base mailbox 联系),客户端重连后通过 LoginApp 找到新 BaseApp 地址。

#### 二级:BaseApp → DBApp/SQLite 归档(分钟级)

`archive()` tick(默认 1 分钟周期)触发时,`Archiver` 选择一批 base 实体,通过 `saveEntity` 消息发送给 DBApp,DBApp 写入数据库(MySQL / XML)并更新 LogOnRecord。同时 BaseApp 写本地 SQLite(若启用 secondaryDB),作为 DBApp 故障时的本地缓存。

### 7.10.5 Cell 迁移

CellApp 故障的处理与 BaseApp 不同——Cell 上的实体状态可以从 BaseApp 重新创建(因为 Base 持有真实状态):

```
[1] CellApp A 死亡
[2] bwmachined → CellAppMgr: handleCellAppDeath(A 地址)
      - sendSignalViaMachined(A, SIGQUIT) 确保进程真的退出
      - 新建 CellAppDeathHandler,等待所有 CellApp ack
      - 通知 BaseApp: handleCellAppDeath,把 base 的 cell mailbox 失效
      - 把 A 上的 cells 重新分配给其他 CellApp
[3] CellAppMgr → 其他 CellApp: addCell(原 A 上的 space)
[4] BaseApp → CellAppMgr: 重新创建 cell entity
      - Base::onCellAppDeath 触发,自动调 Base::createCellEntity,经 CellAppMgr 重建
[5] cell entity 在新 CellApp 上恢复(玩家可能瞬移到附近位置,但 base 状态完整,无数据丢失)
```

**关键差异**:
- BaseApp 故障 → 从备份 BaseApp **恢复 base 实体**;
- CellApp 故障 → 从 BaseApp **重新创建 cell entity**(因为 cell entity 是 base 的"投影")。

这种"Base 是真理源,Cell 是缓存"的设计,使 CellApp 的容错成本远低于 BaseApp。

## 7.11 特色实现深度剖析

### 7.11.1 进程拓扑的解耦设计:Manager 与 Worker 分离

BigWorld 把"控制平面"(Manager)与"数据平面"(Worker)显式分离:

| 维度 | Manager(CellAppMgr/BaseAppMgr/DBAppMgr) | Worker(CellApp/BaseApp/DBApp) |
|------|------|------|
| 实例数 | 单例 | 可水平扩展 |
| 持有实体 | **无** | 有 |
| 状态持久化 | 仅拓扑信息(Space/Cell 边界) | 实体数据 |
| 故障影响 | 集群暂停,但不丢实体 | 仅本机实体受影响 |
| 重启速度 | 快(无状态需加载) | 慢(需从 DB 加载) |

**好处**:
1. **扩缩容简单**:增加 Worker 不影响 Manager,Manager 不需要知道 Worker 在哪台机器;
2. **故障隔离**:Worker 故障不影响其他 Worker,Manager 故障只导致集群暂停(不丢数据);
3. **职责清晰**:Manager 只做调度,Worker 只做执行,代码复杂度可控。

### 7.11.2 统一启动框架:模板方法模式

`ServerApp` 的 `runApp` + 一系列 `on*` 钩子是经典的**模板方法模式**:

```cpp
bool ServerApp::runApp( int argc, char * argv[] )
{
    if (this->init( argc, argv )) {        // 模板:固定调用顺序
        result = this->run();              // 子类可 override
    }
    this->fini();                          // 子类可 override
}

void ServerApp::advanceTime()              // 模板:固定 tick 顺序
{
    this->onTickPeriod( tickPeriod );      // 子类 hook
    this->onEndOfTick();                   // 子类 hook
    ++time_;
    this->onStartOfTick();                 // 子类 hook
    this->callUpdatables();
    this->onTickProcessingComplete();      // 子类 hook(EntityApp 在此 callTimers)
}
```

**好处**:
- 基类控制全局流程,保证一致性(所有进程的 tick 顺序一致);
- 子类按需 override 个别钩子,代码局部化;
- 新增进程类型时,只需继承合适的基类,大部分基础设施复用。

### 7.11.3 Mailbox 抽象:透明跨进程调用

Mailbox 把"调用远端实体的方法"抽象成"调用本地对象的方法":

```python
# Python 脚本中,无论 entity 在本进程还是远端
entity.cell.someMethod(arg)        # 调用 cell 上的方法
entity.base.otherMethod(arg)      # 调用 base 上的方法
entity.client.clientMethod(arg)   # 调用客户端的方法
```

底层 Mailbox 自动处理:
- **本地调用** → 直接 C++ 函数调用;
- **远端调用** → Mercury 消息序列化 + UDP 发送;
- **跨 BaseApp 转发** → 自动通过 forwarding 机制转给目标 BaseApp;
- **客户端调用** → 经 BaseApp 中转打包到 client tick。

这种"位置透明"让业务脚本无需关心进程拓扑,大幅简化 MMOG 开发。后续第 18 章会详细剖析 7 种 Mailbox 的实现。

### 7.11.4 配置驱动的运行时调整

`ServerAppOption<T>` 把"配置项"与"watcher 暴露"绑定:

```cpp
// 声明:启动时从 bw.xml 读,运行时通过 watcher 改
BW_OPTION( float, maxCellAppLoad, 1.0f );
```

这实现了:
- **启动时配置**:从 `bw.xml` 加载默认值;
- **运行时热调**:通过 watcher 工具改值,立即生效,无需重启;
- **持久化**:运维改的值不写回 `bw.xml`,但可通过其他配置机制(如运维脚本)记录。

这种"配置即运行时变量"的设计,让 BigWorld 在生产环境可不停服调整大量参数——从限流阈值到负载均衡周期,从 ghost 距离到 AOI 半径,几乎一切可调。

### 7.11.5 与典型 MMOG 架构的对比

#### 与 SmartFoxServer 对比

| 维度 | BigWorld | SmartFoxServer |
|------|---------|----------------|
| 架构 | 多进程分布式 | 单进程 + Room 分片 |
| 扩展性 | 进程级水平扩展 | 单机扩容,跨机需自实现 |
| 空间管理 | Cell + Ghost + AOI(原生) | Room 抽象,无空间概念 |
| 持久化 | DBApp + MySQL(原生) | 需自实现 |
| 客户端 | 自有 Client + Moo 渲染 | 仅服务器,客户端无关 |
| 适用场景 | 大世界 MMOG | 房间制多人游戏 |

#### 与 Photon 对比

| 维度 | BigWorld | Photon |
|------|---------|--------|
| 架构 | 自有 Mercury(UDP 可靠) | Photon 自有协议 |
| 实体模型 | Cell/Base 分离 + Ghost | PhotonRoom 单一实体 |
| 跨区无缝 | 原生支持(实体迁移) | 需自实现 |
| 语言 | C++ + Python | C# / C++ |
| 部署 | Linux 集群 | Windows / Linux |
| 适用场景 | 大世界 MMOG | FPS / MOBA 房间 |

#### BigWorld 独有特色

1. **Cell/Base 实体分离**:Cell 持有空间状态(可丢),Base 持有持久状态(必保),容错成本极低;
2. **Ghost 机制**:跨 cell 实体的"幽灵副本",实现 AOI 跨进程可见性,无需广播;
3. **Mercury 可靠 UDP**:比 TCP 更适合游戏流量(突发 + 实时),比原生 UDP 多了重传与流控;
4. **TimeKeeper 主从对时**:整个集群游戏时间严格同步,避免"卡顿"现象;
5. **Manager/Worker 解耦**:控制平面与数据平面分离,扩缩容无需重启 Manager。

## 7.12 小结

本章我们建立了对 BigWorld 服务器集群的整体认知:

1. **整体架构**:9 类进程构成的分布式集群,分为控制平面(Manager 单例)、数据平面(Worker 可扩展)、辅助进程(运维工具)。进程拓扑清晰,通信路径分三类:Manager 内部、Manager↔Worker、Worker 内部。

2. **进程职责**:
   - 管理类:CellAppMgr(空间)、BaseAppMgr(Base)、DBAppMgr(DB)、bwmachined(守护)、Reviver(复活);
   - 工作类:CellApp(空间计算)、BaseApp(玩家代理)、DBApp(持久化)、LoginApp(登录);
   - 辅助类:message_logger、bots、consolidate_dbs 等。

3. **统一启动框架**:`ServerApp → ScriptApp → EntityApp / ManagerApp` 类层次,通过 `runApp` 模板方法统一启动流程,通过 `advanceTime` 钩子统一 tick 顺序。`SERVER_APP_HEADER` 宏提供进程名与配置路径。

4. **启动序列**:bwmachined → DBAppMgr → DBApp → BaseAppMgr → CellAppMgr → BaseApp → CellApp → LoginApp → Reviver。每一步都依赖前一步,任何失败都会阻塞后续。

5. **进程间通信**:基于 Mercury 消息系统,8 个主要 Interface(CellAppMgrInterface 等),7 种 Mailbox 类型实现透明跨进程调用。Client 从不直连 CellApp,所有流量经 BaseApp 中转。

6. **配置系统**:`bw.xml` 主配置 + 配置链继承 + `BWConfig` 单例访问 + `ServerAppOption<T>` 运行时可调。几乎所有的运行参数都可热改。

7. **监控运维**:Watcher 系统暴露进程内变量树,支持 HTTP 接口与 ForwardingWatcher 转发;message_logger 收集所有进程日志,支持文件 / MongoDB / MLDB 三种后端;bwmachined 提供进程管理接口;controlled shutdown 实现优雅关停。

8. **典型场景**:玩家登录(11 步,涉及 Client/LoginApp/DBApp/BaseAppMgr/BaseApp/CellAppMgr/CellApp 七个进程)、玩家移动(经 BaseApp 中转 CellApp 处理)、跨区移动(实体迁移,客户端无感)、断线重连(代理保持 + 重连复用)。

9. **容错高可用**:DBApp Alpha 主备切换、Manager 由 Reviver 拉起、BaseApp 两级备份(秒级内存 + 分钟级磁盘)、CellApp 故障从 BaseApp 重建。Base 是真理源,Cell 是缓存,容错成本不对等。

10. **特色实现**:Manager/Worker 解耦、模板方法启动框架、Mailbox 位置透明、配置即运行时变量。与 SmartFoxServer、Photon 等典型 MMOG 架构相比,BigWorld 原生为大世界 MMOG 设计,在跨区无缝、容错、扩展性上有独到优势。
