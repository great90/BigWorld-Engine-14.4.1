## 第一部分:负载均衡概述

### 19.1 为什么需要负载均衡

#### 19.1.1 MMOG 的规模困境

想象一下,你要在一个服务器上同时跑 10000 名玩家、50000 个 NPC、再加上各种可交互物体——加起来几万到十几万个实体。每个实体都要按 tick 推进状态、同步位置、处理消息。一台机器再强,也扛不住这样的负载。

更糟糕的是,MMOG 的负载是**不均匀**的:

- **空间不均**:主城人满为患,野外空无一人。同一个世界地图上,有的区域每平方米 10 个玩家,有的区域几乎没人。
- **时间不均**:晚上 8 点高峰期全员在线,凌晨 4 点只有几十个挂机玩家。
- **行为不均**:Boss 战时所有玩家挤在一片小区域释放技能,AOI 范围内的消息量爆炸;和平采集时分散在整个地图,几乎没消息。

如果用"一台机器扛所有"的思路,你只能服务几百人。BigWorld 的解法是:**把空间切开,把代理分散,让几十台机器分摊负载,并且能动态调整边界**。

#### 19.1.2 负载均衡的两个目标

BigWorld 的负载均衡要同时满足两个目标:

1. **横向扩展**:增加机器就能提升容量,理论上没有上限。
2. **动态调整**:负载变化时,自动迁移实体,不需要停服。

第一点靠"进程划分"——CellApp 负责空间,BaseApp 负责代理,各进程独立。第二点靠"迁移机制"——Cell 之间可以切分边界,Base 之间可以 offload 实体。这正是 BigWorld 三大特色之一(另两个是 Cell/Ghost 实体分治和 Mailbox 位置透明)。

### 19.2 两层负载均衡的分工

BigWorld 的负载均衡分成两层,分别对应两类实体:

| 层次 | 管理者 | 被管理对象 | 均衡方式 | 触发频率 |
|---|---|---|---|---|
| **Cell 层** | CellAppMgr | Cell(空间分区) | 移动 BSP 切分线 | 每 200ms 一次 |
| **Base 层** | BaseAppMgr | Base 实体(代理) | offload 迁移 + 哈希重平衡 | 退休时触发 |

这两层是**完全独立**的——Cell 在哪台机器上跑,跟 Base 在哪台机器上跑,没有任何绑定关系。它们各自追求负载均衡,通过 Mailbox 互相寻址。这是 BigWorld 设计的关键洞察:**空间数据(实体在哪儿)和代理数据(谁负责这个实体)是两个正交问题,应该分开解决**。

- **Cell 层**关注的是"空间局部性"——同一片区域内的实体应该在同一台机器上,这样它们之间的交互不需要跨进程。
- **Base 层**关注的是"代理负载"——每个玩家的 Base 实体占用多少内存和 CPU,需要在不同 BaseApp 之间均匀分布。

### 19.3 动态迁移的本质

负载均衡的核心动作是"迁移"——把实体从一个进程搬到另一个进程。但"迁移"这件事,在分布式系统里非常难做,因为:

1. **状态不能丢**:实体有位置、血量、Buff、技能冷却等状态,迁移过程中不能丢一个字节。
2. **消息不能错序**:迁移期间,如果还有消息发往旧进程,必须转发到新进程,不能丢失或重复。
3. **客户端不能断**:玩家不会感觉到"我刚才迁移了一下",必须完全透明。

BigWorld 的解法是:

- **Cell 迁移**:通过 Real/Ghost 切换实现。源 Cell 的 Real 实体先变成 Ghost,目标 Cell 的 Ghost 变成 Real。实体状态由 Real 持有,Ghost 只有副本数据,切换时通过 Backup 同步。
- **Base 迁移**:通过 offload 机制实现。源 BaseApp 把 Base 实体的完整状态序列化,发给目标 BaseApp,目标 BaseApp 重建实体后,源 BaseApp 在消息转发器里登记映射,后续消息自动转发。
- **客户端透明**:Mailbox 的地址是动态的,迁移完成后 BaseApp 会通知所有持有该 Mailbox 的实体更新地址。客户端只通过 BaseApp 与服务器通信,BaseApp 迁移由 BaseAppMgr 协调,客户端无感知。

## 第二部分:Cell 层负载均衡

### 19.4 CellAppMgr 的角色

#### 19.4.1 控制平面 vs 数据平面

CellAppMgr 是**控制平面**,它自己不持有任何游戏实体,只管理 CellApp 进程的元数据:

- 哪些 CellApp 进程在线(注册/注销)
- 每个 Space 被划分成哪些 Cell(BSP 树结构)
- 每个 Cell 由哪个 CellApp 承载
- 每个 CellApp 的当前负载是多少

真正的游戏逻辑(实体 tick、AOI、物理)都在 CellApp(数据平面)上跑。CellAppMgr 通过 Mercury 消息与 CellApp 通信,告诉它"你负责的 Cell 边界变成了 X",CellApp 据此调整自己的实体归属。

源码位置:`programming/bigworld/server/cellappmgr/cellappmgr.hpp`

```cpp
class CellAppMgr : public ManagerApp,
    public TimerHandler,
    public Singleton< CellAppMgr >
{
    // ...
    Spaces spaces_;        // 所有 Space(SpaceID -> Space*)
    CellApps cellApps_;    // 所有 CellApp(Address -> CellApp*)
    // ...
};
```

#### 19.4.2 关键数据结构

- **`Spaces`**:`BW::map<int, Space*>`,所有 Space 的集合。每个 Space 内部维护一棵 BSP 树,描述自己的 Cell 划分。
- **`CellApps`**:`BW::map<Address, CellApp*>`,所有 CellApp 进程的集合。每个 CellApp 记录自己的负载、cells 列表、所属的元负载均衡分组。
- **`Space`**:持有 `pRoot_`(BSP 树根节点),`cells_`(CellData 列表),`preferredIP_`(优先 IP,用于同机亲和)。
- **`CellApp`**:持有 `cells_`(CellData 列表),`currLoad_`/`smoothedLoad_`/`estimatedLoad_`(三种负载统计),`pGroup_`(元负载均衡分组)。

注意 CellAppMgr 上有两套"Cell 抽象":

- **`CellData`**(在 `cellappmgr` 侧):BSP 树的叶子节点,记录 Cell 的边界、所属 CellApp、实体数量等元数据。
- **`Cell`**(在 `cellapp` 侧):真正的 Cell 运行时,持有实体、Ghost、Witness。

CellAppMgr 只关心 `CellData`,它操作的就是这些元数据。真正的 Cell 运行时在 CellApp 内部,通过消息同步。

### 19.5 Cell 分配算法

当一个 Space 需要新建一个 Cell(因为负载过重、空间太大、Chunk 还没加载完),CellAppMgr 要决定:**这个新 Cell 应该放在哪个 CellApp 上?**

这就是 `CellApps::findBestCellApp` 做的事。源码在 `cellapps.cpp`:

```cpp
CellApp * CellApps::findBestCellApp( const Space * pSpace,
        const CellAppGroup * pExcludedGroup ) const
{
    MF_ASSERT( pSpace );
    CellApp * pBest = NULL;
    Map::const_iterator iter = map_.begin();

    while (iter != map_.end())
    {
        CellApp * pApp = iter->second;

        if (((pExcludedGroup == NULL) || (pApp->pGroup() != pExcludedGroup)) &&
                !pApp->isRetiring())
        {
            if (cellAppComparer_.isValidApp( pApp, pSpace ) &&
                cellAppComparer_.isABetterCellApp( pBest, pApp, pSpace ))
            {
                pBest = pApp;
            }
        }
        ++iter;
    }
    return pBest;
}
```

可以看到,选择算法是**线性扫描 + 多维度打分**:

1. 跳过正在退休(`isRetiring()`)的 CellApp——这些进程马上要关,不能再加新 Cell。
2. 跳过与 `pExcludedGroup` 同组的 CellApp——这是为了避免在同一元负载均衡组内重复加 Cell(新 Cell 应该开在新组,扩大均衡空间)。
3. 用 `CellAppComparer` 多维度比较,选出最优的。

#### 19.5.1 CellAppComparer 多维度评分

`CellAppComparer` 是一个**可配置的评分器链**,在 `cellapp_comparer.cpp` 中实现。它从配置文件 `cellAppMgr/metaLoadBalancePriority` 读取评分器列表,按优先级顺序逐个比较:

```cpp
bool CellAppComparer::isABetterCellApp(
        const CellApp * pOld, const CellApp * pNew, const Space * pSpace ) const
{
    if (pOld == NULL) return true;

    Scorers::const_iterator iter = attributes_.begin();
    while (iter != attributes_.end())
    {
        const CellAppScorer & attribute = **iter;
        float result = attribute.compareCellApps( pOld, pNew, pSpace );

        if (result < 0.f) return false;
        else if (result > 0.f) return true;
        ++iter;
    }
    return false;
}
```

每个评分器返回一个 float,大于 0 表示 `pNew` 更好,小于 0 表示 `pOld` 更好,等于 0 表示平局(进入下一个评分器)。这就是**字典序比较**——先按最重要的指标比,平了再按次要指标比。

BigWorld 提供了 5 个内置评分器:

| 评分器 | 评分逻辑 | 适用场景 |
|---|---|---|
| `CellAppLoadScorer` | `-pApp->estimatedLoad()`,负载越低分越高 | 默认,优先选最闲的机器 |
| `CellAppGroupLoadScorer` | `-pGroup->avgLoad()`,考虑整组负载 | 避免给已经过载的组加重 |
| `CellCellTrafficScorer` | `pSpace->numCellAppsOnIP(pApp->addr().ip)`,同机 CellApp 数 | 减少跨机通信 |
| `BaseCellTrafficScorer` | 1 如果 CellApp 在 preferredIP 上,否则 0 | 让 Cell 跟它的 BaseApp 同机 |
| `LimitedSpacesScorer` | 限制每个 CellApp 上的 Space 数 | 隔离不同 Space |

`CellCellTrafficScorer` 和 `BaseCellTrafficScorer` 都体现了"同机亲和"思想——如果两个进程在同一台物理机上,它们之间的消息走本地环回,几乎零开销。BigWorld 主动把相关的 Cell 和 BaseApp 调度到同一台机器,能显著降低网络开销。

### 19.6 BSP 空间分割

#### 19.6.1 为什么用 BSP 树

Space 是一个 2D 矩形区域(用 `BW::Rect` 表示)。如果整个 Space 都在一个 CellApp 上跑,那个 CellApp 会成为瓶颈。我们需要把 Space 切成多块,每块由不同的 CellApp 承载。

最简单的切法是**网格切分**——把 Space 切成 N×N 个等大小的格子。但网格有两个问题:

1. **负载不均**:主城一个格子挤了 1000 人,野外一个格子只有 1 人,但格子大小一样,主城所在的 CellApp 会过载。
2. **难以动态调整**:要加一个 Cell,必须重新切整个网格,所有 Cell 都要重新分配。

BigWorld 选择了 **BSP 树**(Binary Space Partitioning)切分。BSP 树是一棵二叉树,每个内部节点表示一条切分线(水平或垂直),叶子节点表示一个 Cell。它的优点是:

- **自适应负载**:Cell 的边界可以任意移动,根据负载动态调整。负载重的区域可以多切几刀,负载轻的区域可以少切几刀。
- **增量调整**:加一个 Cell 只需要分裂一个叶子,不影响其他 Cell。删一个 Cell 只需要合并一个内部节点。
- **空间局部性**:BSP 树的叶子是矩形,一个 Cell 内的实体都在同一片连续区域,交互不需要跨进程。

#### 19.6.2 BSPNode 抽象基类

源码在 `bsp_node.hpp`:

```cpp
enum BSPNodeType
{
    BSP_NODE_HORIZONTAL,
    BSP_NODE_VERTICAL,
    BSP_NODE_LEAF
};

class BSPNode : public WatcherProvider
{
public:
    BSPNode( const BW::Rect & range );
    virtual ~BSPNode() {};

    virtual BSPNode * addCell( CellData * pCell, bool isHorizontal = true ) = 0;
    virtual BSPNode * addCellTo( CellData * pNewCell, CellData * pCellToSplit,
           bool isHorizontal = true ) = 0;
    virtual CM::BSPNode * removeCell( CellData * pCell ) = 0;

    virtual void visit( CellVisitor & visitor ) const = 0;
    virtual CellData * pCellAt( float x, float y ) const = 0;

    virtual float updateLoad() = 0;
    virtual float avgLoad() const = 0;
    virtual float avgSmoothedLoad() const = 0;
    virtual float totalSmoothedLoad() const = 0;

    virtual void balance( const BW::Rect & range,
            float loadSafetyBound,
            bool isShrinking = false ) = 0;
    virtual void updateRanges( const BW::Rect & range ) = 0;
    // ...
};
```

`BSPNode` 有两个具体子类:

- **`InternalNode`**(在 `internal_node.hpp`):内部节点,表示一条切分线。持有 `pLeft_`、`pRight_` 两个子节点,以及切分方向(`isHorizontal_`)和位置(`position_`)。
- **`CellData`**(在 `cell_data.hpp`):叶子节点,表示一个 Cell。持有指向 `CellApp` 的指针。

#### 19.6.3 InternalNode 内部节点

```cpp
class InternalNode : public BSPNode
{
    // ...
private:
    BSPNode * pLeft_;
    BSPNode * pRight_;

    int leftCount_;       // 左子树的 Cell 数量
    int rightCount_;      // 右子树的 Cell 数量

    bool isHorizontal_;   // true:水平切分(y=position_),false:垂直切分(x=position_)
    float position_;      // 切分线位置

    float balanceAggression_;  // 平衡激进程度(0~1)
    BalanceDirection prevBalanceDir_;  // 上一次平衡方向

    float totalLoad_;           // 子树总负载
    float totalSmoothedLoad_;   // 子树平滑总负载
    float minLoad_;             // 子树最小负载
    float maxLoad_;             // 子树最大负载
};
```

切分线的方向交替进行——根节点水平切,下一层垂直切,再下一层水平切……这样能避免一个方向上切得太细,形成"意大利面条"状的细长 Cell。

#### 19.6.4 切分示例

假设一个 Space 一开始只有一个 Cell,覆盖整个矩形 `[-1000, -1000] ~ [1000, 1000]`。负载上升后,需要分裂:

1. **第一次分裂**:水平切,`position = 0`,得到上下两个 Cell。
2. **上侧 Cell 负载过重**:再垂直切,`position = 200`,得到左上、右上两个 Cell。
3. **左上 Cell 仍过重**:再水平切,得到左上上、左上下两个 Cell。

最终 BSP 树结构:

```
                    [根:水平 y=0]
                   /              \
              [上:垂直 x=200]     [下:Cell D]
              /          \
        [左上:水平 y=200] [右上:Cell C]
        /        \
     [Cell A]   [Cell B]
```

四个 Cell 的边界:

- Cell A:`[-1000, 200] ~ [200, 1000]`(左上角小块)
- Cell B:`[-1000, 0] ~ [200, 200]`(左中块)
- Cell C:`[200, 0] ~ [1000, 1000]`(右上大块)
- Cell D:`[-1000, -1000] ~ [1000, 0]`(下方大块)

注意 Cell 的大小是不均匀的——主城区域被切得细,野外区域保持大块。这正是 BSP 的优势。

#### 19.6.5 pCellAt:定位一个点属于哪个 Cell

BSP 树最常见的查询是"给定坐标 (x, y),返回它属于哪个 Cell"。这是个递归下降过程:

```cpp
CellData * InternalNode::pCellAt( float x, float y ) const
{
    bool isLeft = isHorizontal_ ? (y < position_) : (x < position_);
    return isLeft ? pLeft_->pCellAt( x, y ) : pRight_->pCellAt( x, y );
}
```

非常简单——根据切分方向判断点在切分线的左侧还是右侧,递归下降到叶子。查询复杂度是 O(log N),N 是 Cell 数量。CellApp 收到实体位置更新时,就用这个方法判断"这个实体应该属于哪个 Cell"。

### 19.7 Cell 间的实体迁移

#### 19.7.1 边界移动触发迁移

Cell 间的实体迁移不是显式调用"迁移函数",而是**边界移动的自然结果**。当 `InternalNode::balance` 调整切分线位置后:

- 原本属于左 Cell 的某些点,现在坐标大于新的 `position_`,变成属于右 Cell。
- CellApp 在下一次 tick 时,检查每个实体的位置,发现它"跨过"了边界,就触发迁移。

迁移的本质是 **Real/Ghost 切换**:

- 源 Cell 上的 Real 实体降级为 Ghost(只保留位置等少量数据)。
- 目标 Cell 上的 Ghost 升级为 Real(获得完整状态)。
- 状态转移通过 Backup 通道完成(参见 19.16)。

这个过程的细节在 `cellapp` 侧的 `entity.cpp` 里实现,CellAppMgr 只负责"通知边界变了",不参与具体的实体搬运。

#### 19.7.2 informCellAppsOfGeometry:通知边界变化

`Space::loadBalance` 完成 BSP 树调整后,会调用 `informCellAppsOfGeometry` 把新的 BSP 树结构序列化发给所有相关的 CellApp:

```cpp
// Space::loadBalance 末尾

```

每个 CellApp 收到后,会更新自己内部的 `CellInfo` 结构(BSP 树的本地副本),并据此判断哪些实体需要迁移。

### 19.8 Cell 分裂与合并

#### 19.8.1 Cell 分裂:addCellTo

当某个 Cell 负载过重,需要分裂成两个时,调用 `Space::addCellTo(pCellToSplit)`。源码在 `space.cpp`:

```cpp
CellData * Space::addCellTo( CellData * pCellToSplit )
{
    // ...
    CellApp * pCellApp = cellApps.findBestCellApp( this, pGroup );
    return pCellApp != NULL ? this->addCell( *pCellApp, pCellToSplit ) : NULL;
}
```

`addCell` 会创建一个新的 `CellData`,然后在 BSP 树上调用 `addCellTo`:

```cpp
// CellData::addCellTo
CM::BSPNode * CellData::addCellTo( CellData * pNewCell, CellData * pCellToSplit,
        bool isHorizontal )
{
    if (pCellToSplit == this)
    {
        return this->addCell( pNewCell, isHorizontal );
    }
    return NULL;
}

// CellData::addCell - 把新 Cell 加到自己旁边,返回新的 InternalNode
CM::BSPNode * CellData::addCell( CellData * pCell, bool isHorizontal )
{
    const float partitionPt = range_.range1D( isHorizontal ).max_;
    BW::Rect newRange = range_;
    newRange.range1D( isHorizontal ).min_ = partitionPt;
    newRange.range1D( isHorizontal ).max_ = partitionPt;
    pCell->setRange( newRange );

    return new CM::InternalNode( this, pCell,
            isHorizontal, range_, partitionPt );
}
```

分裂的过程是:

1. 选一个目标 CellApp(用 `findBestCellApp`)。
2. 创建新的 `CellData`,初始范围与原 Cell 相同。
3. 在 BSP 树上找到原 Cell 所在的叶子,用新的 `InternalNode` 替换它,左右子分别是原 Cell 和新 Cell。
4. 新 Cell 的初始范围是"零宽度"——`min_ == max_`,然后由后续的 `balance` 调整边界,逐渐"长出来"。

#### 19.8.2 Cell 合并:removeCell

当某个 Cell 负载过轻,需要合并到邻居时,调用 `InternalNode::removeCell`:

```cpp
CM::BSPNode * InternalNode::removeCell( CellData * pCell )
{
    CM::BSPNode * pResult = this;

    if (pLeft_ == pCell)
    {
        pResult = pRight_;    // 返回兄弟节点
        pLeft_ = pRight_ = NULL;
        delete this;           // 删除自己(内部节点)
    }
    else if (pRight_ == pCell)
    {
        pResult = pLeft_;
        pLeft_ = pRight_ = NULL;
        delete this;
    }
    else
    {
        // 递归在子树中删除
        pLeft_ = pLeft_->removeCell( pCell );
        pRight_ = pRight_->removeCell( pCell );
    }
    return pResult;
}
```

合并的逻辑很优雅——如果删除的 Cell 是当前节点的直接子节点,就把兄弟节点"提升"上来,替代当前节点。这个过程递归进行,直到根节点。这就是 BSP 树的"合并"——其实是删除一个叶子,顺便清理冗余的内部节点。

#### 19.8.3 退休机制:startRetiring

实际生产中,Cell 不会突然被删除(那会导致实体丢失),而是走**退休(retire)**流程:

1. `CellData::startRetiring()` 设置 `numRetiring_ = 1`,标记为退休中。
2. BSP 树的 `balance` 会在每次 tick 时把退休 Cell 的边界往里缩,逐渐把实体"挤"到邻居 Cell。
3. 当退休 Cell 的实体数量降到 0,且面积为 0 时,`Space::addCellToDelete` 把它加入删除队列。
4. 下一次 `loadBalance` 末尾,`removeSelf` 真正删除 CellData。

源码在 `cell_data.cpp`:

```cpp
void CellData::balance( const BW::Rect & range,
        float loadSafetyBound, bool isShrinking )
{
    range_ = range;
    isOverloaded_ = (this->cellApp().smoothedLoad() > loadSafetyBound);

    bool hasArea = (range.xMin() < range.xMax()) &&
            (range.yMin() < range.yMax());

    // 当 Cell 没有面积,且正在被缩小或退休,且没有实体时,加入删除队列
    if (!hasArea && (isShrinking || numRetiring_) && (this->numEntities() == 0))
    {
        Space::addCellToDelete( this );
    }
}
```

这种"渐进式退休"是 BigWorld 的设计特色——**任何变更都不会瞬间发生,而是通过多次 tick 逐渐完成**。这避免了突发性抖动,让系统始终处于"准稳态"。

### 19.9 两层负载均衡:loadBalance 与 metaLoadBalance

CellAppMgr 有**两层负载均衡**,通过两个独立定时器触发:

#### 19.9.1 第一层:loadBalance(空间内均衡)

源码在 `cellappmgr.cpp`:

```cpp
void CellAppMgr::loadBalance()
{
    Spaces::iterator iter = spaces_.begin();
    while (iter != spaces_.end())
    {
        if (g_shouldLoadBalance)
        {
            iter->second->loadBalance();   // 每个 Space 内部做 BSP 平衡
        }
        // ...
        iter++;
    }
    cellApps_.sendToAll();    // 把所有 CellApp 的消息一次性发出
}
```

`Space::loadBalance` 的核心是调用 BSP 根节点的 `balance`:

```cpp
void Space::loadBalance()
{
    pRoot_->updateLoad();    // 更新负载统计

    BW::Rect rect(/* 全屏范围 */);
    float loadSafetyBound = std::max( CellAppLoadConfig::safetyBound(),
            pRoot_->avgSmoothedLoad() * CellAppLoadConfig::safetyRatio() );

    pRoot_->balance( rect, loadSafetyBound );   // 递归平衡
    pRoot_->updateLoad();
    // ...
}
```

`InternalNode::balance` 是核心算法,它的工作流程是:

1. **比较左右子树负载**:计算 `loadDiff`,大于 0 表示左重右轻,小于 0 表示左轻右重。
2. **决定移动方向**:`dirFromLoadDiff` 返回 `BALANCE_LEFT`(右移边界,缩小左树)、`BALANCE_RIGHT`(左移边界,缩小右树)或 `BALANCE_NONE`(不动)。
3. **计算新位置**:结合"实体边界"(`entityLimitInDirection`,根据实体分布确定能移动多远)和"Chunk 边界"(`chunkLimitInDirection`,根据已加载 Chunk 限制),取较保守的那个。
4. **更新 `position_`**。
5. **递归平衡子树**:`balanceChildren`。

这个算法的关键是 `balanceAggression_`——一个 0~1 之间的"激进程度"系数。每次方向反转时乘以 `aggressionDecrease`(< 1,变保守),方向不变时乘以 `aggressionIncrease`(> 1,变激进)。这是一种**惯性算法**——避免在平衡点附近来回震荡,让平衡过程逐渐稳定下来。

源码:

```cpp
void InternalNode::adjustAggression( BalanceDirection balanceDir )
{
    const int hasReversedDirection =
        ((balanceDir == BALANCE_LEFT) && (prevBalanceDir_ == BALANCE_RIGHT)) ||
        ((balanceDir == BALANCE_RIGHT) && (prevBalanceDir_ == BALANCE_LEFT));

    if (hasReversedDirection)
    {
        balanceAggression_ *= BalanceConfig::aggressionDecrease();
    }
    else
    {
        balanceAggression_ *= BalanceConfig::aggressionIncrease();
    }
    balanceAggression_ = BalanceConfig::clampedAggression( balanceAggression_ );
    prevBalanceDir_ = balanceDir;
}
```

#### 19.9.2 第二层:metaLoadBalance(跨组均衡)

`loadBalance` 只在 Space 内部调整边界,**不能跨 Space 加减 Cell**。如果一个 CellApp 上的所有 Space 都很忙,光调整边界是不够的——需要**新建 Cell**,把工作分摊到其他 CellApp。

这就是 `metaLoadBalance` 做的事,源码在 `cellappmgr.cpp`:

```cpp
void CellAppMgr::metaLoadBalance()
{
    CellAppGroups appGroups( cellApps_ );   // 识别 CellApp 分组

    const float mergeThreshold =
        this->avgCellAppLoad() + CellAppMgrConfig::metaLoadBalanceTolerance();

    // 检查是否有 Group 过载,过载则加 Cell
    appGroups.checkForOverloaded( mergeThreshold );

    // 是否有 Space 还在加载 Chunk,需要更多 Cell 帮忙
    bool hasLoadingSpaces = this->checkLoadingSpaces();

    if (!hasLoadingSpaces)
    {
        // 检查是否有 Group 负载过低,过低则退役 Cell
        appGroups.checkForUnderloaded( CellAppLoadConfig::lowerBound() );
    }
}
```

**CellAppGroup** 是元负载均衡的核心概念。它是一组"通过多 Cell Space 互相连接"的 CellApp。只有同 Space 的 Cell 之间才能做边界平衡,所以一个 CellAppGroup 内的所有 CellApp 必须共享至少一个多 Cell Space。

`CellApps::identifyGroups` 用**洪水填充**算法识别 Group:

```cpp
void CellApps::identifyGroups( BW::list< CellAppGroup > & groups ) const
{
    Map::const_iterator iter = map_.begin();
    while (iter != map_.end())
    {
        CellApp * pApp = iter->second;
        if (!pApp->isEmpty())
        {
            if (pApp->pGroup() == NULL)
            {
                groups.push_back( CellAppGroup() );
                pApp->markGroup( &groups.back() );   // 递归标记同组 CellApp
            }
        }
        ++iter;
    }
}
```

`markGroup` 递归遍历当前 CellApp 的所有 Space 的所有邻居 CellApp,把没有分组的加入当前组。最终结果是:**每个连通的 CellApp 集合形成一个 Group**。

`metaLoadBalance` 的策略:

- **过载检测**:`checkForOverloaded` 检查每个 Group 的平均负载,如果超过 `avgCellAppLoad + tolerance`,就在最忙的 Group 中加一个 Cell(分裂到新 CellApp)。
- **退役检测**:`checkForUnderloaded` 检查每个 Group 的平均负载,如果低于 `lowerBound`,就退役一个 Cell(让那个 CellApp 上的 Cell 退休,实体迁移到邻居)。
- **加载辅助**:`checkLoadingSpaces` 检查是否有 Space 还在加载 Chunk,如果有就给它加更多 Cell,加速加载。

### 19.11 Base 分配算法

当有新的 Base 实体要创建时,BaseAppMgr 要决定:**这个 Base 应该放在哪个 BaseApp 上?**

这就是 `ManagedAppSubSet::findLeastLoadedApp` 做的事,源码在 `baseappmgr.cpp`:

```cpp
BaseApp * ManagedAppSubSet::findLeastLoadedApp() const
{
    BaseApp * pBest = NULL;
    float lowestLoad = 0.f;
    BaseAppsIterator iter = this->iterator();

    while (BaseApp * pCurr = iter.next().get())
    {
        const float currLoad = pCurr->load();
        if (!pCurr->isRetiring())
        {
            if (!pBest || (currLoad < lowestLoad))
            {
                lowestLoad = currLoad;
                pBest = pCurr;
            }
        }
    }
    return pBest;
}
```

非常简单——遍历所有非退休 BaseApp,选负载最低的。这与 CellAppMgr 的 `findBestCellApp` 形成对比:

- **Cell 层**:多维度评分(负载、组负载、Cell-Cell 通信、Base-Cell 通信、Space 限制)。
- **Base 层**:只看负载。

为什么 Base 层不需要考虑通信亲和?因为 Base 实体之间的通信量远少于 Cell 内实体之间的通信量——Base 主要是玩家代理,代理之间很少直接交互。而 Cell 内实体之间有密集的 AOI、物理碰撞、技能效果等。所以 Base 层只追求负载均衡,不需要考虑空间局部性。

#### 19.11.1 bestBaseApp:createBaseAnywhere 的目标

BaseAppMgr 维护一个 `bestBaseAppAddr_`,代表"当前推荐用于创建新 Base 的 BaseApp"。这个值会被 BaseAppMgr 主动推给 CellAppMgr:

```cpp
void BaseAppSubSet::updateBestBaseApp()
{
    BaseApp * pBest = this->findLeastLoadedApp();
    if ((pBest != NULL) &&
            (bestBaseAppAddr_ != pBest->addr()) &&
            cellAppMgr_.channel().isEstablished())
    {
        bestBaseAppAddr_ = pBest->addr();
        Mercury::Bundle & bundle = cellAppMgr_.bundle();
        CellAppMgrInterface::setBaseAppArgs & rSetBaseApp =
            CellAppMgrInterface::setBaseAppArgs::start( bundle );
        rSetBaseApp.addr = bestBaseAppAddr_;
        cellAppMgr_.send();
    }
}
```

当 CellApp 调用 `createBaseAnywhere` 时,会用这个 `bestBaseApp` 作为目标。这是一种**简单的负载感知路由**——CellAppMgr 把"最闲的 BaseApp 地址"广播给所有 CellApp,CellApp 创建新实体时就用这个地址。

### 19.12 Base 迁移(offload)机制

#### 19.12.1 什么是 offload

当一个 BaseApp 要退休(比如运维要重启它),它持有的所有 Base 实体必须迁移到其他 BaseApp。这个迁移过程叫 **offload**——"卸载"。

源码在 `baseapp/backup_sender.hpp`:

```cpp
class BackupSender
{
public:
    void startOffloading() { isOffloading_ = true; }
    bool isOffloading() const { return isOffloading_; }
    // ...
private:
    bool isOffloading_;
    int offloadPerTick_;    // 每 tick offload 多少个
    int ticksSinceLastSuccessfulOffload_;
};
```

#### 19.12.2 offload 的流程

offload 不是"复制 + 删除",而是**"提升备份 + 转发消息"**:

1. **触发**:BaseApp 收到 retireApp 消息,设置 `isRetiring_ = true`,启动 offload。
2. **选实体**:每个 tick,`BackupSender::tick` 选若干个 Base 实体(默认是备份周期到期的)。
3. **发送备份**:把 Base 实体的完整状态序列化,发给目标 BaseApp(目标通过 BackupHash 决定)。
4. **目标 BaseApp 接收**:`createBaseFromStream` 重建 Base 实体,接管它的所有 Mailbox。
5. **源 BaseApp 转发**:在 `BaseMessageForwarder` 中登记映射 `<旧地址, 新地址>`,后续发给旧地址的消息自动转发。
6. **完成**:所有 Base 迁移完后,源 BaseApp 通知 BaseAppMgr,可以安全关闭。

源码在 `backup_sender.cpp`:

```cpp
void BackupSender::tick( const Bases & bases,
                         Mercury::NetworkInterface & networkInterface )
{
    int periodInTicks = BaseAppConfig::backupPeriodInTicks();
    if (periodInTicks == 0) return;

    Mercury::BundleSendingMap bundles( networkInterface );

    // 计算本 tick 要备份的实体数(浮点余数保证周期正确)
    float numToBackUpFloat =
        float(bases.size())/periodInTicks + backupRemainder_;
    int numToBackUp = int(numToBackUpFloat);
    backupRemainder_ = numToBackUpFloat - numToBackUp;

    if (isOffloading_)
    {
        // offload 时提高速率,尽快卸载
        if (offloadPerTick_ < numToBackUp)
        {
            offloadPerTick_ = numToBackUp;
            INFO_MSG( "BackupSender::tick: "
                    "BaseApp is retiring, offloading at %d entities per tick\n",
                offloadPerTick_ );
        }
        else
        {
            numToBackUp = offloadPerTick_;
        }
    }
    // ... 真正的备份/offload 逻辑
}
```

注意 offload 会**自适应加速**——`offloadPerTick_` 会逐渐增大,确保在合理时间内完成。这是一种"软实时"设计——不强制限定时间,但保证不会无限拖延。

#### 19.12.3 OffloadedBackups:退休 BaseApp 也当备份

退休的 BaseApp 不是"什么都搬走就关掉",它会保留一份"已 offload 实体的备份",以防目标 BaseApp 也崩溃。这就是 `OffloadedBackups`:

## 第四部分:实体备份机制

### 19.13 Primary/Backup 模型

BigWorld 的 Base 实体采用 **Primary/Backup** 模型:

- **Primary**:Base 实体的"主人",持有完整状态,处理所有消息。每个 Base 实体只有一个 Primary。
- **Backup**:Base 实体的"备份",持有完整状态的副本(可能略滞后)。每个 Base 实体有一个或多个 Backup。

Primary 崩溃时,某个 Backup 升级为新的 Primary,继续提供服务。这是分布式系统里常见的"主备复制"模式。

但 BigWorld 的实现有一个独特之处——**Backup 不是固定指向某个 BaseApp,而是通过哈希函数动态决定**。这意味着:

- 同一个 Base 实体,在不同时刻,可能由不同的 BaseApp 备份。
- 哪个 BaseApp 备份哪个 Base 实体,由全局的 `BackupHash` 决定,所有 BaseApp 都知道。
- 当 BaseApp 集合变化(加减机器)时,只需调整 `BackupHash`,系统自动重新分布备份。

### 19.14 BackupHash 哈希

#### 19.14.1 哈希函数的设计


`addressFor(EntityID)` 的逻辑:

1. 用 `hashFor(id)` 计算一个哈希值 `h = (id * prime_)`。
2. 把 `h` 折叠到 `virtualSize_` 范围内(用位运算 `h & (virtualSize_ - 1)`,因为 `virtualSize_` 是 2 的幂)。
3. 如果结果 `< size_`,返回 `addrs_[result]`;否则"折叠"——`result = hashFor(result)`,重试。

这种"虚拟大小 + 折叠"的设计是**一致性哈希**的变体,目的有两个:

- **变更最小**:增加或减少一个 BaseApp 时,只有约 `1/size` 的 Base 实体需要重新备份,而不是全部。
- **均匀分布**:即使 EntityID 不均匀,哈希后也能均匀分布到各 BaseApp。

`prime_` 是一个**随机质数**,每个 BackupHash 实例的 prime 都不同。注释说:

> A random prime is chosen so that the hash functions are different for different BaseApps. If we did not do this, we could get bad distribution once a few BaseApps have died.

如果所有 BaseApp 用相同的 prime,那么一个 BaseApp 死亡后,它上面的所有 Base 实体会按相同的哈希函数重新分配,可能集中到某个 BaseApp。用不同的 prime 可以避免这种"哈希聚集"。

#### 19.14.2 备份切换的过渡:newBackupHash

当一个 BaseApp 加入或退出时,`BackupHash` 需要更新。但直接替换会导致**短时间内没有备份**——新哈希还没建立,旧哈希已经失效。

BigWorld 的解法是**双哈希过渡**:

```cpp
class BaseApp
{
    BackupHash  backupHash_;       // 当前生效的
    BackupHash  newBackupHash_;    // 过渡中的新哈希
};
```

切换流程:

1. **BaseAppMgr 决定切换**:比如有新 BaseApp 加入,调用 `BaseApp::adjustBackupLocations`。
2. **设置 newBackupHash_**:`newBackupHash_ = this->backupHash()` 然后修改(增加/删除地址)。
3. **通知所有 BaseApp**:用 `BaseAppIntInterface::setBackupBaseApps` 把 `newBackupHash_` 发给当前 BaseApp。
4. **BaseApp 启动新备份**:`StartSetBackupDiffVisitor::onAdd` 通知目标 BaseApp 开始接收新备份。
5. **数据迁移**:`BackupSender::tick` 按 `newBackupHash_` 把需要迁移的 Base 实体发过去。
6. **完成切换**:BaseApp 完成后回复 `useNewBackupHash`,`backupHash_` 替换为 `newBackupHash_`。

源码在 `baseappmgr/baseapp.cpp`:

```cpp
void BaseApp::adjustBackupLocations( const Mercury::Address & newAddr,
        BaseAppsIterator baseApps,
        AdjustBackupLocationsOp op,
        bool hadIdealBackup, bool hasIdealBackup )
{
    if (newBackupHash_.empty())
    {
        newBackupHash_ = this->backupHash();   // 复制当前哈希
    }

    // 修改 newBackupHash_(根据 op 增加/删除地址)
    switch (op)
    {
    case ADJUST_BACKUP_LOCATIONS_OP_ADD:
        newBackupHash_.push_back( newAddr );
        break;
    case ADJUST_BACKUP_LOCATIONS_OP_CRASH:
        if (this->backupHash().erase( newAddr ))
        {
            this->backupHash().clear();   // 当前哈希失效
        }
        // fall through
    case ADJUST_BACKUP_LOCATIONS_OP_RETIRE:
        newBackupHash_.erase( newAddr );
        break;
    }

    // 把新哈希发给当前 BaseApp
    Mercury::Bundle & bundle = this->bundle();
    bundle.startMessage( BaseAppIntInterface::setBackupBaseApps );
    bundle << newBackupHash_;
    this->send();
}
```

### 19.15 BackupHashChain 双哈希链

#### 19.15.1 问题:多个 BaseApp 连环崩溃

`BackupHash` 解决了"单次变更"的平滑过渡。但如果**多个 BaseApp 连环崩溃**呢?

假设 BaseApp A 崩溃,它的 Base 实体按 `BackupHash_A` 重新分配到 B、C、D。还没等 B 上的新备份建立完成,B 也崩溃了。这时 B 上的实体(包括从 A 迁过来的)需要再次重新分配。

问题是:**A 崩溃时建立的 `BackupHash` 已经丢失了**——它存在 A 上,A 已经死了。如果没有特殊处理,我们就不知道"哪些实体本来是从 A 迁到 B 的",也就无法把它们正确地再次迁移。

#### 19.15.2 解法:哈希链

`BackupHashChain` 解决了这个问题。它维护一个**历史哈希映射**:

```cpp
class BackupHashChain
{
public:
    void adjustForDeadBaseApp( const Mercury::Address & deadApp, 
                               const BackupHash & hash );
    Mercury::Address addressFor( const Mercury::Address & address,
                                 EntityID entityID ) const;
private:
    typedef BW::map< Mercury::Address, BackupHash > History;
    History history_;
};
```

`history_` 是一个 `map<Address, BackupHash>`,记录"每个已死 BaseApp 死亡时的 BackupHash"。每次有 BaseApp 死亡,就调用 `adjustForDeadBaseApp` 把它的 `BackupHash` 存起来。

`addressFor` 解析一个地址(可能是已死的)到当前活的 BaseApp:

```cpp
Mercury::Address BackupHashChain::addressFor( const Mercury::Address & address,
                                             EntityID entityID ) const
{
    History::const_iterator firstMatch = history_.find( address );
    if (firstMatch == history_.end())
    {
        return address;   // 这个地址没死,直接返回
    }

    BW::set< Mercury::Address > visited;
    History::const_iterator match = firstMatch;
    Mercury::Address position = address;

    while (match != history_.end())
    {
        if (visited.count( position ))
        {
            WARNING_MSG( "BackupHashChain::addressFor: Infinite loop\n" );
            return address;
        }
        visited.insert( position );

        // 用死去 BaseApp 的哈希,重新算出该实体的目标地址
        position = match->second.addressFor( entityID );
        match = history_.find( position );
    }
    return position;   // 找到一个没死的 BaseApp
}
```

这是个**链式查找**过程:

1. 给定地址 `A`(假设已死),在 `history_` 中找到 `A` 死亡时的 `BackupHash`。
2. 用那个 `BackupHash` 重新算 `entityID` 的目标地址,得到 `B`。
3. 如果 `B` 也在 `history_` 中(说明 B 也死了),继续用 B 的哈希算,得到 `C`。
4. 重复,直到找到一个不在 `history_` 中的地址(活的 BaseApp)。

`visited` 集合防止无限循环——如果链中出现环(理论上不应该发生,但容错总要考虑),就停止并返回原地址。

这种"双哈希链"是 BigWorld 容错性的精髓——**即使所有备份都连环崩溃,只要还有一个 BaseApp 存活,实体的目标地址就能被解析出来**。

#### 19.15.3 主备切换的触发

源码在 `baseappmgr.cpp`:

```cpp
bool BaseAppMgr::onBaseAppDeath( const Mercury::Address & addr )
{
    // ...
    BaseAppPtr pBaseApp = iter->second;
    const bool controlledShutDown =
        this->getSubSet( *pBaseApp ).onBaseAppDeath( *pBaseApp );
    if (!controlledShutDown)
    {
        // 关键:把死去的 BaseApp 的 backupHash 加入哈希链
        pBackupHashChain_->adjustForDeadBaseApp( pBaseApp->addr(),
            pBaseApp->backupHash() );
        this->sendBaseAppDeathNotifications( *pBaseApp );
        this->redirectGlobalBases( *pBaseApp );
    }
    // ...
}
```

`adjustForDeadBaseApp` 把死去的 BaseApp 的 `backupHash` 存入哈希链,从此所有发往该地址的消息都可以通过哈希链解析到新的目标。

### 19.16 BackupSender 周期备份

#### 19.16.1 备份的触发

备份不是"一次完成"的,而是**周期性滚动**进行。源码在 `backup_sender.cpp`:

```cpp
void BackupSender::tick( const Bases & bases,
                         Mercury::NetworkInterface & networkInterface )
{
    int periodInTicks = BaseAppConfig::backupPeriodInTicks();
    if (periodInTicks == 0) return;   // 备份关闭

    if (!isUsingNewBackup_ && entityToAppHash_.empty())
        return;

    Mercury::BundleSendingMap bundles( networkInterface );

    // 计算本 tick 要备份多少个实体
    float numToBackUpFloat =
        float(bases.size())/periodInTicks + backupRemainder_;
    int numToBackUp = int(numToBackUpFloat);
    backupRemainder_ = numToBackUpFloat - numToBackUp;
    // ...
}
```

`periodInTicks` 是"完整备份一轮"所需的 tick 数(由配置决定,通常是几分钟)。每个 tick 备份 `bases.size() / periodInTicks` 个实体,加上一点浮点余数(避免取整误差累积)。

这种"滚动备份"的好处:

- **平滑负载**:不会一次性产生大量备份流量,均匀分散到每个 tick。
- **持续保护**:任何时刻,所有 Base 实体的备份都不超过 `periodInTicks` 之前的旧版本,崩溃时损失最小。

#### 19.16.2 备份的接收

目标 BaseApp 收到备份消息后,通过 `createBaseFromStream` 重建 Base 实体(但标记为 backup,不激活)。源码在 `baseapp/base.cpp`,流程:

1. 反序列化实体类型、位置、状态。
2. 调用 `Base::onLoaded` 完成初始化。
3. 加入 `backedUpBaseApps_` 集合(记录"我正在为谁做备份")。

如果 Primary 后续崩溃,BackupSender 会通过 `BackupHashChain::addressFor` 找到新的目标,把备份激活为 Primary。

## 第五部分:故障恢复

### 19.17 Reviver 与 bwmachined 双重守护

BigWorld 的故障检测不是单点,而是**双重守护**:

#### 19.17.1 bwmachined:机器级守护

bwmachined(详见第8章)运行在每台物理机上,负责:

- **fork/exec 进程**:根据 `bwmachined.conf` 启动 CellApp、BaseApp 等子进程。
- **心跳检测**:每秒检查子进程是否存活,如果子进程崩溃,根据 `restart=true` 配置决定是否重启。
- **死亡通知**:向 Reviver 报告进程死亡事件(通过 `MachineGuard` 协议)。

但 bwmachined 只能看到"进程死了",不能看到"进程僵死了但没退出"——比如死锁、内存耗尽、网络断开但进程还在。这就需要 Reviver。

#### 19.17.2 Reviver:集群级守护

Reviver(详见第12章)运行在独立的机器上,负责:

- **5 类进程监控**:CellAppMgr、BaseAppMgr、DBAppMgr、LoginApp、CellApp(可配),其他如 BaseApp 由 BaseAppMgr 自己处理。
- **双死亡检测**:既听 bwmachined 的死亡通知,也自己 ping 目标进程。两边都确认死了,才判定为真死亡。
- **主备切换**:对 CellAppMgr、BaseAppMgr、DBAppMgr 这类"单点"管理进程,Reviver 启动备用实例,通过 `shutDownOnRevive` 标志让旧实例退出,新实例接管。

Reviver 的关键源码在 `server/reviver/`,5 个 `ComponentReviver` 子类分别处理 5 类进程。

#### 19.17.3 双重检测的意义

为什么需要双重检测?因为每种检测都有盲区:

- **bwmachined 检测**:能看到进程崩溃,但看不到进程死锁(进程还活着但不响应)。
- **Reviver ping**:能看到进程死锁,但如果 Reviver 自己网络出问题,会误判所有进程都死了。

只有两边都报告死亡,才真正死亡。这避免了"假阳性"导致的误重启。源码在 `reviver.cpp::handleFailure`:

```cpp
// 简化逻辑
if (bwmachinedReportedDead && reviverPingFailed)
{
    triggerRevive(componentName, addr);
}
```

### 19.18 故障切换流程详解

我们以 **BaseApp 崩溃**为例,完整走一遍故障切换流程。这是最复杂的场景,涉及实体恢复、消息重定向、客户端重连。

#### 19.18.1 阶段一:检测

1. **bwmachined 检测到**:BaseApp 进程退出(SIGSEGV、SIGABRT 或正常退出)。
2. **bwmachined 通知 Reviver**:通过 MachineGuard 协议发送 `handleCellAppDeath`/`handleBaseAppDeath` 类似消息。
3. **Reviver ping 确认**:Reviver 直接 ping 死亡地址,如果连续 N 次失败,判定为真死亡。
4. **BaseAppMgr 心跳超时**:`CellApps::checkForDeadCellApps` 也会检测到 BaseApp 长时间无心跳,触发 `handleBaseAppDeath`。

#### 19.18.2 阶段二:决策

BaseAppMgr 收到死亡通知,调用 `onBaseAppDeath`:

```cpp
bool BaseAppMgr::onBaseAppDeath( const Mercury::Address & addr )
{
    BaseApps::const_iterator iter = baseAndServiceApps_.find( addr );
    // ...
    BaseAppPtr pBaseApp = iter->second;
    const bool controlledShutDown =
        this->getSubSet( *pBaseApp ).onBaseAppDeath( *pBaseApp );
    if (!controlledShutDown)
    {
        // 1. 更新哈希链
        pBackupHashChain_->adjustForDeadBaseApp( pBaseApp->addr(),
            pBaseApp->backupHash() );
        // 2. 通知 CellAppMgr 和其他 BaseApp
        this->sendBaseAppDeathNotifications( *pBaseApp );
        // 3. 重定向 GlobalBases(全局服务)
        this->redirectGlobalBases( *pBaseApp );
    }
    return true;
}
```

`ManagedAppSubSet::onBaseAppDeath` 内部做几件事:

1. **检查是否有备份**:`if (baseApp.backupHash().empty())` 如果没有备份,记录错误日志。
2. **检查存活数**:`if (numAppsAlive < this->minimumRequiredApps())` 如果剩余 BaseApp 少于最低要求,触发 controlled shutdown。
3. **调整备份位置**:`adjustBackupLocations( baseApp, ADJUST_BACKUP_LOCATIONS_OP_CRASH )` 让所有 BaseApp 重新计算 `newBackupHash_`。
4. **停止备份**:停止向死亡 BaseApp 发送备份。

#### 19.18.3 阶段三:恢复

死亡的 BaseApp 上的 Base 实体,需要由它的 Backup 接管。流程:

1. **其他 BaseApp 收到死亡通知**:`sendBaseAppDeathNotifications` 把死亡地址广播给所有 BaseApp。
2. **Backup Hash Chain 解析**:每个 BaseApp 检查自己持有的 backup 实体,如果它们的 Primary 在死亡的 BaseApp 上,就升级为 Primary。
3. **激活 Backup**:BaseApp 调用 `Base::onRestoreComplete` 把 backup 实体转为 active,开始接受消息。
4. **重新备份**:由于丢失了一个 BaseApp,整体备份拓扑变化,BaseAppMgr 触发 `newBackupHash_` 切换,所有 BaseApp 重新建立备份。

具体细节在 `baseapp/backed_up_base_apps.cpp` 等文件中。

#### 19.18.4 阶段四:客户端重连

对于 Proxy(玩家代理)实体,客户端连接需要切换到新的 BaseApp。流程:

1. **客户端检测断线**:BaseApp 不响应,客户端 Connection 检测到断开。
2. **客户端重连**:客户端用登录时获得的备用 LoginApp 地址,重新走登录流程。
3. **DBApp 找到新 BaseApp**:DBApp 通过 `BackupHashChain` 找到 Proxy 的新地址(升级为 Primary 的 Backup 所在的 BaseApp)。
4. **客户端重连到新 BaseApp**:登录成功后,客户端连接到新的 BaseApp,继续游戏。

这个过程对玩家是**几乎无感**的——可能感觉到几秒卡顿,然后游戏继续。这是 BigWorld 设计的核心目标之一:**故障对玩家透明**。

### 19.19 客户端透明与重连

#### 19.19.1 Mailbox 重定向

故障恢复期间,可能有消息已经发往死亡的 BaseApp(还在路上)。这些消息不能丢,需要重定向到新的 Primary。

BigWorld 的解法是 `BaseMessageForwarder`(在 `baseapp/base_message_forwarder.hpp`):每个 BaseApp 维护一个"转发映射表",记录 `<旧地址, 新地址>`。收到发给旧地址的消息时,自动转发到新地址。

这个机制在 offload 期间也使用——offload 完成后,源 BaseApp 上的 forwarder 记录 `<自己, 目标 BaseApp>`,确保过渡期间的消息不丢。

#### 19.19.2 BaseBackupSwitchMailBoxVisitor

源码在 `lib/server/base_backup_switch_mailbox_visitor.hpp`:

```cpp
class BaseBackupSwitchMailBoxVisitor : public PyEntityMailBoxVisitor
{
public:
    BaseBackupSwitchMailBoxVisitor( const BackupHashChain & hashChain,
            const Mercury::Address & deadAddr );
    // ...
};
```

当 BaseApp 死亡时,所有持有指向该 BaseApp 上实体的 Mailbox 都需要更新。这个 Visitor 遍历所有 Mailbox,用 `BackupHashChain::addressFor` 解析新地址,把 Mailbox 重定向过去。

这种"自动重定向"是客户端透明的核心——**Mailbox 的地址是动态的,系统会在故障后自动更新**。

## 第六部分:特色实现深度剖析

### 19.20 两层负载均衡的分工哲学

BigWorld 的负载均衡之所以分成两层,是因为它把"空间"和"代理"看作两个正交问题。

#### 19.20.1 Cell 层:空间局部性优先

Cell 层负载均衡的核心目标是**空间局部性**——同一片区域内的实体应该在同一台机器上,这样它们之间的交互不需要跨进程。

举例:一个 Boss 战,100 个玩家聚集在 50×50 的小区域。如果用网格切分,可能切成 4 个 25×25 的格子,4 个 CellApp 各处理 25 个玩家。但玩家之间的技能效果、AOE 伤害、位置同步都需要跨 4 个 CellApp 通信,网络开销巨大。

BSP 树可以更精细地切这片小区域——切 8 刀、16 刀,每刀负责一小片。但更关键的是,BSP 树可以根据负载**自适应调整**——主城区域切得密,野外区域保持大块。这是网格做不到的。

#### 19.20.2 Base 层:负载均衡优先

Base 层负载均衡的核心目标是**负载均衡**——每个 BaseApp 上的 Base 实体数量大致相等。

Base 实体之间的通信量很少(玩家代理之间不直接交互,都是通过 Cell 实体中转),所以不需要考虑空间局部性。只要负载均匀,就足够了。

这就是为什么 Base 层用简单的 `findLeastLoadedApp`,而 Cell 层用复杂的 `CellAppComparer` 多维度评分——**它们优化的目标不同**。

#### 19.20.3 两层的独立性

这两层是**完全独立**的:

- 一个 BaseApp 上的 Base 实体,可以指向任何 CellApp 上的 Cell 实体。
- 一个 CellApp 上的 Cell 实体,可以由任何 BaseApp 上的 Base 实体代理。

这种独立性让系统可以**分别扩展**——加机器给 CellApp 时,只影响 Cell 层;加机器给 BaseApp 时,只影响 Base 层。这是 BigWorld 设计的关键优势。

### 19.21 BSP 分割的空间局部性

BSP 树的一个常被忽视的优势是**空间局部性**——每个 Cell 都是矩形,且矩形的边平行于坐标轴。

这意味着:

- **AOI 计算高效**:给定一个实体的位置和 AOI 半径,AOI 范围是个圆。判断哪些 Cell 与这个圆相交,只需要 BSP 树的几次比较——O(log N)。
- **Ghost 边界清晰**:Ghost 距离是配置项(`CellAppMgrConfig::ghostDistance()`),Cell 边界周围的实体会被复制为 Ghost 到邻居 Cell。由于 Cell 是矩形,Ghost 边界也是矩形,复制判断很简单。
- **Chunk 加载对齐**:BigWorld 的 Chunk 系统也是基于矩形分块的(详见第14章)。BSP 切分线可以与 Chunk 边界对齐(通过 `shouldLimitBalanceToChunks` 配置),避免一个 Cell 跨越 Chunk 边界,简化加载逻辑。

源码在 `cell_data.cpp::calculateAreaNotLoaded`:

```cpp

}
```

可以看到,Cell 的边界、Ghost 距离、Chunk 边界都是矩形运算,非常高效。

### 19.22 BackupHashChain 的容错性

`BackupHashChain` 是 BigWorld 容错性的精髓,我们来深度剖析它。

#### 19.22.1 设计动机

普通的 `BackupHash` 只能处理"单次变更"——加一个 BaseApp 或减一个 BaseApp。但生产环境中,**多个 BaseApp 可能在短时间内连环崩溃**:

- 网络分区导致一组 BaseApp 同时失联。
- 同一批次的硬件故障(比如硬盘坏道)导致多个 BaseApp 同时崩溃。
- 运维误操作批量重启。

如果只用 `BackupHash`,每次崩溃后哈希就被覆盖了,之前的备份映射丢失。`BackupHashChain` 用"链式历史"解决了这个问题。

#### 19.22.2 哈希链的结构

`BackupHashChain::history_` 是一个 `map<Address, BackupHash>`:

- **Key**:已死 BaseApp 的地址。
- **Value**:该 BaseApp 死亡时的 `BackupHash`。

每次有 BaseApp 死亡,就把 `(dead_addr, dead_app's_backup_hash)` 加入 history。**从不删除**——理论上这个链可以无限增长。

`addressFor` 方法沿着链查找,直到找到一个活的 BaseApp:

```cpp
while (match != history_.end())
{
    if (visited.count( position ))  // 防止环
    {
        return address;  // 异常情况,返回原地址
    }
    visited.insert( position );

    position = match->second.addressFor( entityID );
    match = history_.find( position );
}
return position;
```

#### 19.22.3 容错性分析

考虑一个极端场景:

1. BaseApp A 持有实体 E,备份到 B(按 `Hash_A` 算)。
2. A 崩溃,BackupHashChain 加入 `(A, Hash_A)`。E 的 Primary 现在是 B(用 `Hash_A` 解析 `E → B`)。
3. B 还没把 E 的备份建立完,B 也崩溃了。BackupHashChain 加入 `(B, Hash_B)`。E 的 Primary 现在是?
4. `addressFor(A, E)`:用 `Hash_A` 算,得到 B。B 在 history 中,继续。用 `Hash_B` 算,得到 C。C 不在 history 中,返回 C。

但问题是:**C 上还没有 E 的备份**!B 在建立备份前就死了。

BigWorld 的处理:这种情况只能靠 DBApp 持久化的数据恢复——E 的最后状态在 DBApp 上有副本(详见第11章),DBApp 重新创建 E。这是"最后兜底",虽然有少量数据丢失(自上次 archive 以来的变更),但实体不会丢失。

这种"层层兜底"的容错设计——Primary → Backup → HashChain → DBApp——是 BigWorld 高可用的基石。

### 19.23 与其他 MMOG 的对比

#### 19.23.1 与 sharded 架构对比

很多 MMOG(如早期魔兽世界、EVE Online 早期)采用 **sharded(分服)** 架构:

- 一个服务器(shard)服务一个独立的世界,几千玩家。
- 不同 shard 之间完全隔离,玩家不能跨 shard。
- 单个 shard 内部可能有多台机器,但负载固定分配。

这种架构简单,但扩展性差——单 shard 容量有上限,加机器不能提升单 shard 的容量。

BigWorld 的架构是 **seamless(无缝)单世界**:

- 所有玩家在同一个世界,可以互相交互。
- 加机器就能提升容量,理论上没有上限。
- 但实现复杂——需要 Cell/Ghost、Mailbox、负载均衡、故障恢复等一整套机制。

#### 19.23.2 与 static partitioning 对比

有些 MMOG 用**静态分区**:

- 把世界地图预先切成 N 块,每块固定由一个服务器处理。
- 玩家跨区时,触发"区切换"(zone transition),通常有短暂卡顿。
- 单区过载时,只能靠升级硬件解决,不能动态扩展。

BigWorld 的 BSP 树是**动态分区**:

- Cell 边界可以随时移动,适应负载变化。
- 玩家跨 Cell 时,通过 Real/Ghost 切换实现,完全透明,无卡顿。
- 单区过载时,自动分裂,把工作分摊到更多机器。

#### 19.23.3 与 actor model 对比

有些现代 MMOG(如某些用 Akka 实现的)用 **actor model**:

- 每个实体是一个 actor,有自己的状态和消息队列。
- actor 可以在任意机器上,通过 actor 地址寻址。
- 负载均衡通过 actor 迁移实现。

BigWorld 的 Base 实体本质也是 actor 模型——每个 Base 实体有状态、有 Mailbox(地址)、可以迁移。但 BigWorld 的特色在于:

- **Cell 层不是 actor**——Cell 实体是空间感知的,绑定在 BSP 树的叶子上。这避免了"actor 不知道自己邻居在哪"的问题,空间局部性更强。
- **Base 层是 actor**——Base 实体确实可以看作 actor,迁移通过 offload 实现。
- **两层分离**——空间逻辑(Cell)和代理逻辑(Base)解耦,各自优化。

这种"混合架构"兼具 actor 模型的灵活性和空间数据结构的高效性,是 BigWorld 的独特贡献。

#### 19.23.4 与 modern serverless 对比

现代 serverless 游戏(如某些基于 Agones 的)用**进程级 scaling**:

- 每个游戏 session 是一个独立进程,Kubernetes 自动伸缩。
- 适合 match-based 游戏(如 FPS、MOBA),不适合 persistent world MMOG。

BigWorld 的设计假设是**持久化单世界**,所以选择了"长运行进程 + 内部负载均衡"的架构,而不是 serverless 的"短进程 + 外部调度"。这两种架构适用于不同类型的游戏。

### 19.24 本章小结

本章深入剖析了 BigWorld 的三大特色之一——**负载均衡与故障恢复**。核心要点:

1. **两层负载均衡的分工**:Cell 层基于 BSP 树做空间分割,追求空间局部性;Base 层基于哈希做实体分配,追求负载均衡。两层独立运行,各自优化。

2. **BSP 空间分割**:用 BSP 树自适应切分 Space,Cell 边界可以动态调整。`InternalNode::balance` 用"惯性算法"避免震荡,通过 `balanceAggression_` 调整激进程度。

3. **两层负载均衡触发**:`loadBalance` 每 200ms 在 Space 内部调整 BSP 边界;`metaLoadBalance` 每 3s 跨 CellAppGroup 加减 Cell。前者频繁微调,后者偶尔大动作。

4. **Base offload 机制**:BaseApp 退休时通过 offload 把 Base 实体迁移到其他 BaseApp,源 BaseApp 保留 OffloadedBackups 防止目标也崩溃。

5. **BackupHash 一致性哈希**:用虚拟大小 + 折叠实现一致性,加机器时只有约 1/size 的实体需要重新备份。随机 prime 避免哈希聚集。

6. **BackupHashChain 双哈希链**:用历史哈希映射解决连环崩溃问题,即使所有 Primary 都死了,只要还有一个 Backup 存活,就能解析出实体目标地址。

7. **双重故障检测**:bwmachined 看进程退出,Reviver 看进程死锁,两边都报告才真正判定死亡,避免假阳性。

8. **故障切换流程**:检测 → 决策(更新哈希链)→ 恢复(Backup 升级为 Primary)→ 客户端重连。整个流程对玩家几乎透明。

9. **客户端透明**:通过 Mailbox 自动重定向、BaseMessageForwarder 消息转发、BaseBackupSwitchMailBoxVisitor 邮箱切换,实现故障对玩家无感知。

10. **与其他架构对比**:相比 sharded(分服)、static partitioning(静态分区)、actor model、serverless,BigWorld 的"seamless 单世界 + 两层负载均衡 + BSP 空间分割 + 双哈希链容错"组合,是针对持久化 MMOG 的深度优化。
