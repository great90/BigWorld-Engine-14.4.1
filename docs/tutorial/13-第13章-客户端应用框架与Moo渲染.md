# 第13章 客户端应用框架与 Moo 渲染

> 前几章我们走的都是"服务器侧"——CellApp 怎么切空间、BaseApp 怎么代理玩家、DBApp 怎么落地、LoginApp 怎么放人进来。从本章开始,我们跨过网线,看看玩家面前那台机器上跑的东西:**客户端**。
>
> BigWorld 的客户端不是"画一个窗口,渲染几个模型"那么简单。它要在 Windows 上撑起一个进程,把网络包、Python 脚本、D3D 渲染、场景图、UI、相机、声音……全部串成一个稳定的 60FPS 主循环。这套骨架由两层抽象构成:**App/Module 框架**(`lib/appmgr/`)负责"主循环与可切换功能模块"的拆分,**Moo 渲染引擎**(`lib/moo/`)负责把 Direct3D 9 包成一套跨未来 API 的资源/场景/材质系统。本章就带你拆开这两层,看清客户端是怎么"立起来"的。

## 第一部分:客户端应用框架概述

### 13.1 客户端在哪里

BigWorld 的客户端源码位于 `programming/bigworld/client/`。和 `server/` 下按进程切分的目录(BaseApp、CellApp、LoginApp、DBApp)不同,客户端只有一个可执行文件,目录下所有的 `.cpp/.hpp` 都最终编译链接到这一个 exe(或者在 DLL 模式下,一个 dll + 一个启动器)。

打开 `client/` 目录,你会看到几十个文件,大致分四类:

| 分类 | 代表文件 | 职责 |
|------|---------|------|
| **应用骨架** | `app.hpp/cpp/ipp`、`bw_winmain.cpp`、`winmain.cpp` | 进程入口、主循环、App 单例 |
| **MainLoopTask** | `world_app.hpp`、`device_app.hpp`、`script_app.hpp`、`camera_app.hpp`、`gui_app.hpp`、`canvas_app.hpp`、`facade_app.hpp`、`lens_app.hpp`、`debug_app.hpp`、`finale_app.hpp`、`profiler_app.hpp` | 主循环里负责某个子系统的任务 |
| **实体与过滤** | `entity.hpp/ipp`、`filter.hpp`、`avatar_filter.hpp`、`boids_filter.hpp`、`dumb_filter.hpp`、`py_entity.hpp`、`py_filter.hpp`、`entity_factory.hpp` | 客户端实体表现与位置插值 |
| **杂项** | `physics.hpp`、`minimap.hpp`、`bwvoip.hpp`、`server_discovery.hpp`、`version_info.hpp` | 物理、小地图、语音、版本 |

需要特别提醒的一点:**这个目录里有两个 App 概念,不要混了**。

- `lib/appmgr/app.hpp` 里的 `class App` 是**框架基类**,代表"一个跑在 Windows 上的应用程序",它管 HWND、InputManager、Module 栈,只负责最朴素的主循环。
- `client/app.hpp` 里的 `class App` 是**客户端的实际 App 单例**,继承自 `InputHandler`、`DebugMessageCallback`,内部用 `MainLoopTask` 链管理十几个子系统。它不继承 `appmgr::App`,而是"取代"了后者——历史上 BigWorld 用过 `appmgr::App` 那套 Module 栈模式,后来演进到 `MainLoopTask` 链模式,`appmgr` 库被保留下来主要供 WorldEditor 这类工具使用。

本章会先讲 `appmgr` 框架(它是理解客户端演化与工具架构的钥匙),再回到客户端自己的 `App`。

### 13.2 客户端与 lib 的协作模型

客户端链接了 `lib/` 下的一大堆库,典型依赖如下:

```
                      ┌──────────────────────────┐
                      │      client.exe          │
                      │  (BigWorld Client)       │
                      └────────────┬─────────────┘
                                   │
        ┌──────────────┬──────────┼──────────┬──────────────┐
        ▼              ▼          ▼          ▼              ▼
   ┌─────────┐   ┌─────────┐  ┌────────┐  ┌────────┐   ┌─────────┐
   │ appmgr  │   │  moo    │  │ chunk  │  │  romp  │   │  duplo  │
   │ (框架)  │   │ (渲染)  │  │ (空间) │  │ (环境) │   │ (模型) │
   └────┬────┘   └────┬────┘  └────┬───┘  └────┬───┘   └────┬────┘
        │             │            │           │            │
        └──────┬──────┴─────┬──────┴───────────┴────────────┘
               ▼            ▼
          ┌────────┐    ┌────────┐    ┌────────┐    ┌────────┐
```

其中两个最关键的库就是本章的两个主角:

- **`lib/appmgr/`**:应用与模块管理框架,提供 `App`/`Module`/`ModuleManager`/`Factory`/`Options`/`DevMenu` 等通用骨架。
- **`lib/moo/`**:Direct3D 9 渲染抽象层,提供 `RenderContext`、`Visual`、`Material`、`Node`、`Light`、`TextureManager` 等资源/场景类。

下面我们分别拆开看。

## 第二部分:App/Module 框架

### 13.3 appmgr 库全貌

打开 `lib/appmgr/` 目录,你会看到一组职责清晰的文件:

| 文件 | 角色 |
|------|------|
| `app.hpp/cpp/ipp` | `App` 抽象基类,管理 HWND、InputManager、Module 栈与主循环 |
| `module.hpp/ipp` | `Module` 抽象基类与 `FrameworkModule` 渲染辅助 |
| `module_manager.hpp/ipp` | `ModuleManager`:模块栈的 push/pop/当前模块 |
| `factory.hpp/ipp` | `Factory<TYPE>`:模板工厂,从 XML 数据节创建对象 |
| `scripted_module.hpp/ipp` | `ScriptedModule`:把所有事件转交给 Python 脚本对象 |
| `options.hpp/ipp` | `Options`:全局选项(类似配置中心) |
| `dev_menu.hpp/ipp` | `DevMenu`:开发菜单模块 |
| `application_input.hpp/ipp` | `ApplicationInput`:应用层输入 |
| `input_manager.hpp/ipp` | `InputManager`:输入分发 |
| `script_instance.hpp/ipp` | `ScriptInstance`:脚本实例包装 |
| `commentary.hpp/ipp` | `Commentary`:旁白系统 |
| `closed_captions.hpp/ipp` | `ClosedCaptions`:字幕 |

这套库的核心理念是:**进程是一个 tick 驱动的 App,内部维护一个 Module 栈,栈顶的 Module 接收每帧的 update/render 调用,并独占输入**。这让我们可以做出"主菜单 → 进入游戏 → 暂停菜单 → 设置"这种状态切换,每个状态都是独立 Module,互不耦合。

### 13.4 App 抽象基类

`lib/appmgr/app.hpp` 里的 `App` 类(我们记作 **appmgr::App** 以免混淆)是这套框架的核心:

```cpp
// programming/bigworld/lib/appmgr/app.hpp  L18-60
class App
{
public:
    App();
    ~App();

    bool init( HINSTANCE hInstance, HWND hWndApp, HWND hwndGraphics,
         IMainFrame * mainFrame,
         bool ( *userInit )( HINSTANCE, HWND, HWND ) );
    void fini( void (*userFini)() = NULL );
    void updateFrame( bool tick = true );
    void consumeInput();

    HWND hwndApp();

    // Windows messages
    void resizeWindow( );
    void handleSetFocus( bool focusState );

    // Application Tasks
    float calculateFrameTime();
    void pause(bool paused);
    bool isPaused() const;

    // State changes for subclasses to override
    virtual void presenting( bool isPresenting ) {};

private:
    HWND                hWndApp_;
    uint64              lastTime_;
    bool                paused_;
    InputManager        inputHandler_;
    bool                bInputFocusLastFrame_;
    float               maxTimeDelta_;
    float               timeScale_;
};
```

它做了三件事:

#### 13.4.1 主循环驱动

`App::updateFrame(bool tick)` 是主循环的"一帧"。看 `app.cpp` 的实现:

```cpp
// programming/bigworld/lib/appmgr/app.cpp  L316-412 (节选)
void App::updateFrame( bool tick )
{
    BWResource::instance().flushModificationMonitor();

    float dTime = this->calculateFrameTime();
    if (!tick) dTime = 0.f;

    if ( InputDevices::hasFocus() )
    {
        // 把队列里的输入事件分发给 inputHandler_
        InputDevices::processEvents( this->inputHandler_ );
    }

    EngineStatistics::instance().tick( dTime );
    Moo::AnimatingTexture::tick( dTime );
    Moo::Material::tick( dTime );
    Moo::rc().effectVisualContext().tick( dTime );

    ModulePtr pModule = ModuleManager::instance().currentModule();
    if (pModule)
    {
        if (!Moo::rc().checkDevice()) {  // 设备丢失时直接 sleep
            Sleep(100);
            return;
        }

        pModule->updateFrame( dTime );

        HRESULT hr = Moo::rc().beginScene();
        if (SUCCEEDED(hr))
        {
            Moo::rc().nextFrame();
            pModule->updateAnimations();
            pModule->render( dTime );

            if (ConsoleManager::instance().pActiveConsole() != NULL)
                ConsoleManager::instance().draw( dTime );

            Moo::rc().endScene();
        }

        presenting( true );
        Moo::rc().present();
        presenting( false );
    }
}
```

注意这个流程里**框架做了哪些、留给 Module 做哪些**:

- 框架做:**算时间差**、**dispatch 输入**、**tick 全局静态对象**(纹理动画、材质等)、**取栈顶 Module**、**checkDevice**、**beginScene/endScene**、**present**。
- Module 做:`updateFrame`(逻辑)、`updateAnimations`(动画)、`render`(绘制)。

这就是典型的**模板方法模式**——固定骨架在基类,可变步骤在子类。

#### 13.4.2 时间管理

`calculateFrameTime` 算的是这一帧距离上一帧的时间差,单位秒:

```cpp
// programming/bigworld/lib/appmgr/app.cpp  L263-281
float App::calculateFrameTime()
{
    uint64 thisTime = timestamp();
    float dTime = (float)(((int64)(thisTime - lastTime_)) / stampsPerSecondD());

    if (dTime > maxTimeDelta_)   // 防止断点恢复后大跳变
        dTime = maxTimeDelta_;

    dTime *= timeScale_;          // 调试用的时间缩放
    lastTime_ = thisTime;

    if (paused_) dTime = 0.0f;
    return dTime;
}
```

`maxTimeDelta_` 默认 0.5 秒。当你在断点停了几秒后继续,`dTime` 不会被允许超过这个上限,否则实体位置会一下子跳很远,角色穿墙,客户端崩。`timeScale_` 是给开发者调慢动作用的(例如 0.2 倍速看动画细节)。

#### 13.4.3 输入与窗口

`InputManager inputHandler_` 持有一个输入分发器,把 Windows 的键盘/鼠标事件转换成 BigWorld 的 `KeyEvent`/`MouseEvent`/`AxisEvent`,然后派发给当前焦点对象。`handleSetFocus` 处理 WM_ACTIVATE 的激活/失焦,失焦时会把输入队列清空,避免窗口重新激活后涌入一堆积压事件。

### 13.5 Module 抽象基类

`Module` 是 App 主循环里"当前做什么"的抽象:

```cpp
// programming/bigworld/lib/appmgr/module.hpp  L15-45
class Module : public InputHandler, public ReferenceCount
{
public:
    Module() {};
    virtual ~Module();

    // 模块被工厂创建时调用
    virtual bool init( DataSectionPtr pSection );

    // 模块入栈/出栈
    virtual void onStart();
    virtual int  onStop();

    // 栈顶模块被新模块覆盖/恢复
    virtual void onPause();
    virtual void onResume( int exitCode );

    // 每帧调用(栈顶模块)
    virtual void updateFrame( float dTime ) = 0;
    virtual void updateAnimations() = 0;
    virtual void render( float dTime ) = 0;

    virtual void setApp( App * app ) = 0;
    virtual void setMainFrame( IMainFrame * mainFrame ) = 0;
};
```

要点:

1. **Module 继承 `InputHandler`**:这意味着模块本身就是一个输入处理器,栈顶模块自动获得键盘鼠标事件的处理权。
2. **Module 继承 `ReferenceCount`**:用智能指针 `ModulePtr` 管理,栈里存的是 `SmartPointer<Module>`,引用计数归零自动销毁。
3. **生命周期回调**:四个 `onStart/onStop/onPause/onResume` 让模块知道"我现在在栈顶/被压下去了/恢复了"。
4. **三个纯虚方法**:`updateFrame`/`updateAnimations`/`render` 是模块每帧必须做的事,与 App 主循环的三段对应。

框架还提供了 `FrameworkModule`,它在 `Module` 之上加了"渲染骨架":

```cpp
// programming/bigworld/lib/appmgr/module.hpp  L52-66
class FrameworkModule : public Module
{
protected:
    virtual void updateFrame( float dTime );      // 实现了:调用 updateState
    virtual bool updateState( float dTime );      // 子类实现:返回 false 退出模块
    virtual void setApp( App * app ) = 0;
    virtual void setMainFrame( IMainFrame * mainFrame ) = 0;
private:
    uint32 backgroundColour_;
};
```

`FrameworkModule::updateFrame` 默认实现里会调用 `updateState`,如果 `updateState` 返回 false,模块自动 pop 出栈。这给"按 ESC 返回上一级菜单"这种交互提供了简洁写法。

### 13.6 ModuleManager:模块栈

```cpp
// programming/bigworld/lib/appmgr/module_manager.hpp  L20-44
class ModuleManager : public Factory<Module>
{
public:
    static ModuleManager& instance();
    static void fini();
    void popAll();

    bool push( const BW::string & moduleIdentifier );
    void push( ModulePtr module );
    ModulePtr currentModule();
    void pop();

private:
    typedef std::stack< ModulePtr > ModuleStack;
    ModuleStack modules_;
};
```

`ModuleManager` 是单例,内部维护一个 `std::stack<ModulePtr>`。注意它**多重继承自 `Factory<Module>`**——也就是说,模块管理器本身就是一个模块工厂,可以根据字符串 ID 创建模块。

`push(const BW::string& moduleIdentifier)` 是最常用的入口:传入一个模块名(例如 `"Game"`、`"MainMenu"`),它会调用 `Factory<Module>::create(name)` 找到对应的 `Creator`,创建模块实例并压栈。`pop()` 弹出栈顶并触发 `onStop`。这套设计让 Python 脚本可以通过一个字符串就启动新模块,不需要写 C++ 代码注册。

### 13.7 Factory:从数据到对象

`Factory<TYPE>` 是 BigWorld 的模板工厂:

```cpp
// programming/bigworld/lib/appmgr/factory.hpp  L32-55 (节选)
template <class TYPE>
class Factory
{
public:
    void add( const char * name, Creator<TYPE> & creator );
    TYPE * create( const char * name, DataSectionPtr pSection = NULL ) const;
protected:
    typedef typename StringHashMap< Creator<TYPE> *> Creators;
    Creators creators_;
    DataSectionPtr pExtensions_;
};
```

它通过 `add(name, creator)` 注册"名字→Creator",通过 `create(name, pSection)` 创建对象。`Creator<TYPE>` 是个抽象基类,子类必须实现 `create(DataSectionPtr)`:

```cpp
// programming/bigworld/lib/appmgr/factory.hpp  L13-24
template <class TYPE>
class Creator
{
public:
    virtual bool init( DataSectionPtr pSection );
    virtual TYPE * create( DataSectionPtr pSection ) = 0;
};
```

为了少写样板代码,头文件里提供了一个 `IMPLEMENT_CREATOR` 宏:

```cpp
// programming/bigworld/lib/appmgr/factory.hpp  L79-101 (节选)
#define IMPLEMENT_CREATOR( NAME, TYPE )                 \
class NAME##Creator : public StandardCreator<TYPE>     \
{                                                       \
public:                                                 \
    NAME##Creator() : StandardCreator<TYPE>(            \
        #NAME, TYPE##Factory::instance() ) {}           \
private:                                                \
    virtual TYPE * create( DataSectionPtr pSection )    \
    {                                                   \
        return this->createHelper( pSection, new NAME() ); \
    }                                                   \
};                                                      \
static NAME##Creator s_##NAME##Creator;
```

这样某个具体模块类(比如 `GameModule`)只要在 cpp 里写一行 `IMPLEMENT_CREATOR( GameModule, Module )`,就会自动注册到 `ModuleFactory::instance()`,之后 Python 或 XML 数据都可以通过 `"GameModule"` 这个字符串创建它。

### 13.8 ScriptedModule:Python 模块

`ScriptedModule` 是个特别有用的内置模块,它把所有 Module 的虚函数都转交给一个 Python 脚本对象:

```cpp
// programming/bigworld/lib/appmgr/scripted_module.hpp  L23-52
class ScriptedModule : public FrameworkModule
{
public:
    ScriptedModule();
    ~ScriptedModule();

    bool init( DataSectionPtr pSection );
    virtual void onStart();
    virtual int  onStop();
    virtual void onPause();
    virtual void onResume( int exitCode );
    virtual bool updateState( float dTime );
    virtual void updateAnimations();
    virtual void render( float dTime );
    virtual bool handleKeyEvent( const KeyEvent & /*event*/ );
    virtual bool handleMouseEvent( const MouseEvent & /*event*/ );
    virtual void setApp( App * app ) {};
    virtual void setMainFrame( IMainFrame * mainFrame ) {};
private:
    PyObject * pScriptObject_;
};
```

这意味着**策划/脚本工程师可以完全用 Python 实现一个新模块**,不需要改 C++ 代码、不需要重新编译客户端。这正是 BigWorld 工具链(WorldEditor 等)插件机制的基石。

## 第三部分:winmain.cpp 入口

讲完 appmgr 框架,我们回头看客户端进程是怎么起来的。入口文件 `client/winmain.cpp` 只有 200 多行,但承担了三件事:

### 13.9.1 Windows 入口点

```cpp
// programming/bigworld/client/winmain.cpp  L179-201 (节选)
int PASCAL wWinMain(HINSTANCE hInstance,
                    HINSTANCE hPrevInstance,
                    LPWSTR lpCmdLine,
                    int nCmdShow )
{
    BW::CStdMf::checkUnattended();

    HCURSOR cursor = LoadCursor( hInstance, MAKEINTRESOURCE(IDC_NULL) );
    WNDCLASS wc = { CS_HREDRAW | CS_VREDRAW, WndProc, 0, 0, hInstance,
                    LoadIcon( hInstance, MAKEINTRESOURCE(IDI_CLIENT_ICON)),
                    cursor, NULL, NULL, s_className.c_str() };

    if( !RegisterClass( &wc ) )
        return FALSE;

    int ret = CallWithExceptionFilter( BWWinMain, hInstance,
                (LPCTSTR)lpCmdLine, nCmdShow, s_className.c_str(), APP_TITLE );

    BOOL success = UnregisterClass( s_className.c_str(), hInstance );
    return ret;
}

LRESULT CALLBACK WndProc(HWND hWnd, UINT msg, WPARAM wParam, LPARAM lParam)
{
    return BWWndProc( hWnd, msg, wParam, lParam );
}
```

注意三点:

1. **`wWinMain` 是 Unicode 版本的 WinMain**。BigWorld 在 Windows 上要求 Unicode。
2. **`RegisterClass` + `WndProc`**:标准 Win32 窗口注册,窗口类名 `s_className`(默认是 `"App"`,DLL 模式下会带时间戳)。
3. **`CallWithExceptionFilter`**:不直接调用 `BWWinMain`,而是包一层结构化异常过滤器,这样崩溃时能 dump 出调用栈。

`WndProc` 本身只是转交给 `BWWndProc`,后者实现在 `bw_winmain.cpp`。

### 13.9.3 BWWinMain:真正的启动流程

`bw_winmain.cpp::BWWinMain` 是 BigWorld 的"实际 WinMain",它做完了所有真正的初始化工作:

```cpp
// programming/bigworld/client/bw_winmain.cpp  L78-266 (节选)
int BWWinMain( HINSTANCE hInstance, LPCTSTR lpCmdLine, int nCmdShow,
               LPCTSTR lpClassName, LPCTSTR lpWindowName )
{
    BWResource bwresource;

    if (!parseCommandLine( lpCmdLine ))      // 1. 解析命令行
        return FALSE;

    ExternalProfiler::initialize();

    // 创建主窗口的位置和尺寸,默认 1024x768
    const int DefaultWidth = 1024;
    const int DefaultHeight = 768;

    // 2. 创建客户端 App 单例
    App app( configFilename, compileTimeString );

    // 3. 读 preferences.xml,提取用户偏好
    DataSectionPtr preferences;
    DataResource dataRes;
    if (dataRes.load( preferencesFilename.resolveName() ) == DataHandle::DHE_NoError)
        preferences = dataRes.getRootSection();

    // 4. 初始化 Moo(D3D)
    if ( !Moo::init( (exInterface == 0) ) )
        return FALSE;

    // 5. 创建主窗口
    hWnd = CreateWindow( lpClassName, windowName.c_str(),
                         WS_OVERLAPPEDWINDOW, xPos, yPos, width, height,
                         NULL, NULL, hInstance, 0 );
    ShowWindow( hWnd, nCmdShow );

    // 6. 调用 App::init
    if( !app.init( hInstance, hWnd ) )
        app.setQuiting( true );

    Automation::parseCommandLine( lpCmdLine );

    // 7. 主循环
    bool running = !app.isQuiting();
    while(running)
    {
        if( PeekMessage( &msg, NULL, 0, 0, PM_REMOVE ) )
        {
            if( msg.message == WM_QUIT )
                running = false;
            TranslateMessage( &msg );
            DispatchMessage( &msg );
        }
        else
        {
            if (!app.updateFrame(g_bActive))
                app.quit(false);
        }
    }

    Moo::fini();
    DestroyWindow( hWnd );
    return static_cast<int>( msg.wParam );
}
```

整个启动流程可以概括为 7 步:

```
        WinMain
          │
          ▼
   RegisterClass
          │
          ▼
     BWWinMain ◀── CallWithExceptionFilter(崩溃兜底)
          │
          ├── parseCommandLine         (BW_RES_PATH 等环境)
          ├── new App(configFilename)  (客户端 App 单例)
          ├── Moo::init()              (D3D 初始化)
          ├── CreateWindow             (主窗口)
          ├── app.init(hInstance, hWnd)(装载所有子系统)
          └── while !quit:
                  PeekMessage → DispatchMessage
                  app.updateFrame(active)
          ▼
       Moo::fini() + DestroyWindow
```

注意主循环使用的是 `PeekMessage`(非阻塞),不是 `GetMessage`(阻塞)。这意味着即使没有 Windows 消息,主循环也会持续调用 `app.updateFrame`,这是游戏循环的标准写法——必须保持每帧主动 tick,而不是被动等消息。

### 13.10 MainLoopTask 主循环任务链

客户端 App 不再用 Module 栈,而是用 `MainLoopTasks` —— 一个**有序的任务链**。每个任务是一个 `MainLoopTask` 子类,实现 `init/fini/tick/updateAnimations/draw/inactiveTick`。任务之间通过依赖字符串声明顺序:

```
">Device"  表示"在 Device 之后"
```

`App::init` 里这样注册任务链:

```cpp

MainLoopTasks::root().add( NULL, "VOIP",   ">Device", NULL );
MainLoopTasks::root().add( NULL, "Web",    ">VOIP", NULL );
MainLoopTasks::root().add( NULL, "Script", ">Web",   NULL );
MainLoopTasks::root().add( NULL, "Camera", ">Script", NULL );
MainLoopTasks::root().add( NULL, "Canvas", ">Camera", NULL );
MainLoopTasks::root().add( NULL, "World",  ">Canvas", NULL );
MainLoopTasks::root().add( NULL, "Flora",  ">World",  NULL );
MainLoopTasks::root().add( NULL, "Facade", ">Flora",  NULL );
MainLoopTasks::root().add( NULL, "Lens",   ">Facade", NULL );
MainLoopTasks::root().add( NULL, "GUI",    ">Lens",   NULL );
```

任务链的顺序如下:

```

   → Facade → Lens → GUI → Debug → Finale
```

含义:

| 任务 | 职责 |
|------|------|
| **Device** | D3D 设备维护、字体、纹理 feeds、镜头特效、后处理管理器 |
| **VOIP** | 语音通话 |
| **Web** | Web 嵌入(Esper/Scaleform 等) |
| **Script** | Python tick(Personality.tick 等) |
| **Camera** | 相机更新、自动瞄准、目标选取 |
| **Canvas** | 画布/UI 根 |
| **World** | 空间、地形、实体、物理 |
| **Flora** | 草地植被 |
| **Facade** | 远景 facade |
| **Lens** | 镜头光晕 |
| **GUI** | UI 组件 |
| **Debug** | 调试覆盖层 |
| **Finale** | 帧尾收尾(最后一帧才渲染的东西) |

每帧的 tick/updateAnimations/draw 都按这个顺序触发,**反过来 fini 时按逆序**。这种"声明依赖,框架拓扑排序"的模式比 Module 栈灵活:模块可以并行、可以重入、可以替换。

### 13.11 updateFrame 一帧

```cpp
// programming/bigworld/client/app.cpp  L1406-1462 (节选)
bool App::updateFrame(bool active)
{
    g_profiler.tick();
    this->calculateFrameTime();              // 算 dRenderTime_/dGameTime_
    MouseCursor::updateMouseClipping();
    BWResource::instance().flushModificationMonitor();

    if (dRenderTime_ > 0.f)
    {
        if (active)
        {
            // 1) tick 所有 MainLoopTask(逻辑)
            MainLoopTasks::root().tick( dGameTime_, dRenderTime_ );

            if (Moo::rc().checkDevice())
            {
                // 2) 更新动画
                MainLoopTasks::root().updateAnimations( dGameTime_ );

                // 3) 绘制
                MainLoopTasks::root().draw();
            }
        }
        else
        {
            // 失焦时只跑 inactiveTick(暂停逻辑,但不渲染)
            MainLoopTasks::root().inactiveTick( dGameTime_, dRenderTime_ );
        }

        // 4) 帧率限制(可选)
        ...
    }
    return !quiting_;
}
```

每帧分三阶段:**tick → updateAnimations → draw**。三阶段都按依赖顺序遍历所有 `MainLoopTask`。这种"逻辑/动画/绘制"分离让 BigWorld 客户端在多线程友好度上比"一锅端"的游戏循环好得多。

## 第六部分:Moo 渲染引擎概述

讲完应用框架,我们看渲染。

BigWorld 的渲染库叫 **Moo**,源码在 `lib/moo/`。命名来源已不可考,推测是 "MOO" = "M**y** O**bject** O**riented**" 或就是某只牛的哞声(项目里到处是 `Moo::` 前缀,既好认又好笑)。

Moo 的职责是把 **Direct3D 9** 这套 COM API 封装成一套**面向对象、资源管理友好、能跨未来图形 API** 的渲染抽象层。它的核心目标:

1. **资源生命周期**:D3D9 设备丢失(alt+tab 全屏切换、显存压力)时,所有 default-pool 资源要重建。Moo 用 `DeviceCallback` 自动处理。
2. **场景图**:Node 树 + Visual + Material + Light,让美术导出的 `.visual`/`.primitive`/`.animation`/`.mfm` 文件能被加载与绘制。
3. **材质系统**:既支持固定管线 `Material`,也支持可编程 `EffectMaterial`(D3DX Effect)。
4. **渲染管线抽象**:`IRendererPipeline` 提供 deferred/forward 两条管线,统一接口。
5. **辅助系统**:纹理管理、渲染目标、雾效、动画、阴影、贴花、自发光、SSAO、HDR、TAA……整套现代 MMOG 需要的渲染特性。

### 13.14 DeviceCallback:设备丢失通知

D3D9 的 default-pool 资源(默认资源)在设备丢失时必须释放、设备恢复后必须重建。Moo 用观察者模式统一处理:

```cpp
// programming/bigworld/lib/moo/device_callback.hpp  L19-45
class DeviceCallback
{
public:
    typedef BW::list< DeviceCallback * > CallbackList;

    DeviceCallback();
    virtual ~DeviceCallback();

    virtual void deleteUnmanagedObjects( );
    virtual void createUnmanagedObjects( );
    virtual void deleteManagedObjects( );
    virtual void createManagedObjects( );

    virtual bool recreateForD3DExDevice() const;

    static void deleteAllUnmanaged( bool forceRelease = false );
    static void createAllUnmanaged( bool forceCreate = false );
    static void deleteAllManaged( );
    static void createAllManaged( );

    static void fini();
};
```

任何持有 D3D 资源的类(纹理、render target、vertex buffer 等)都继承 `DeviceCallback`,实现四个虚函数,在构造时自动加入全局观察者列表。设备丢失/恢复时,框架调用 `deleteAllUnmanaged/createAllUnmanaged/deleteAllManaged/createAllManaged`,所有资源类被批量通知,各自重建自己的 D3D 资源。这就避免了"100 个类各自监听设备事件"的混乱。

`GenericUnmanagedCallback` 是个泛型包装,允许把两个 C 函数指针注册成回调,方便临时资源管理。

1. **父节点用裸指针 `Node* parent_`**——注释里写得很清楚:"to ensure that the whole tree will be destructed if the parent's reference count reaches 0"。如果父也用智能指针,会形成循环引用,树永远不被释放。

3. **`traverse()`**:从根开始递归,把 `transform_`(局部)乘上 parent 的 `worldTransform_` 算出自己的 `worldTransform_`。这就是经典的场景图遍历。
4. **`identifier_`**:骨骼节点的名字(例如 "Bip01 Spine1"),动画 channel 通过名字找到节点。

- **`Channel` 枚举**把材质按渲染通道分类:不透明物体走 `SOLID` 通道,半透明物体走 `SORTED` 通道(按距离排序),光晕走 `FLARE`,水波扰动走 `SHIMMER`。这让渲染管线可以按通道分批绘制,避免状态切换。

### 13.20 Light 系统

Moo 提供多种灯光类型:

## 第八部分:场景图与渲染流程

### 13.24 Node 树结构

Moo 的场景图由 `Node` 树构成。每个 `Visual` 拥有一个根 `Node`,根的 children 形成骨骼层级。一帧的渲染流程大致是:

```
1. 客户端 MainLoopTask tick:更新实体位置、动画状态、相机
2. updateAnimations:遍历每个 Visual
   ├── 动画 channel 把变换写入 Node::blendTransform_
   └── Node::traverse() 递归计算每个节点的 worldTransform_
3. draw:
   ├── Visual::draw 被调用
   ├── 遍历 RenderSet
   │     ├── EffectVisualContextSetter 把 transformNodes_ 的世界变换
   │     │   塞进 shader 常量(矩阵 palette)
   │     └── 遍历 Geometry
   │           └── 遍历 PrimitiveGroup
   │                 ├── Material::set() 设备状态
   │                 └── Primitive::drawPrimitiveGroup(i) 画三角形
   └── 把渲染指令塞进 DrawContext,统一 flush
```

注意步骤 3——BigWorld 14.x 是**延迟绘制提交**的:Visual 不立即调用 `DrawIndexedPrimitive`,而是把"什么时候画、用什么材质、什么变换"塞进 `DrawContext` 队列,最后由渲染管线(`IRendererPipeline`)按材质排序、按通道分组统一 flush。这是现代渲染引擎的标准做法,能大幅减少状态切换。

两条管线的语义:

- **`TYPE_DEFERRED_SHADING`(延迟着色)**:先把几何的 GBuffer(位置、法线、材质 ID 等)画到多个 render target,然后在屏幕空间应用所有光源。优点是大量光源开销恒定,缺点是半透明物体不能走延迟管线(必须再用 forward pass 画)。
- **`TYPE_FORWARD_SHADING`(前向着色)**:每个物体绘制时直接计算光照,光源越多开销越大,但半透明物体友好,适合低端机器。

`IRendererPipeline` 的接口把一帧拆成清晰阶段:

```
begin
  ├── beginCastShadows  → 画阴影贴图
  ├── endCastShadows
  ├── beginOpaqueDraw   → 画不透明几何
  │     (Deferred 在此步写 GBuffer)
  ├── endOpaqueDraw
  ├── applyLighting     → 应用光照(Deferred 在此步做全屏光照)
  ├── beginSemitransparentDraw → 画半透明
  ├── endSemitransparentDraw
  ├── beginGUIDraw      → 画 GUI
  └── endGUIDraw
end
```

注意 **stencil usage**:用 stencil buffer 的 4 个高位标记每个像素属于什么类型(地形/SpeedTree/植被/其他不透明),这样后续光照 pass 可以针对不同类型用不同 shader,降低 shader 复杂度。

`Renderer` 是 `Singleton<Renderer>`,持有当前 pipeline 实例 `m_pipeline`。`rp()` 全局函数返回当前 pipeline 引用,业务代码到处是 `rp().beginOpaqueDraw()` 这种调用。

6. **物理**:`pPhysics_` 持有客户端物理对象,`physicsMovement` 是物理驱动移动入口(载具等)。

### 13.27 Filter 平滑插值

#### 13.27.1 为什么需要 Filter

MMOG 网络是"尽力而为"的——服务器不会每帧发实体位置,而是按一定频率(典型 10Hz,即每秒 10 次)发送,且根据距离衰减。如果客户端直接把收到位置"啪"地设到实体上,会出现:

1. **抖动**:网络包到达时间不均匀,实体忽快忽慢。
2. **跳跃**:相邻两个位置点之间相隔几米,实体瞬移。
3. **穿墙**:插值不连续时,实体可能短暂穿墙。

Filter 就是解决这个问题的:它接收服务器位置输入,经过算法处理后输出平滑位置给实体。这就是 `MovementFilter` 接口:

```cpp
// programming/bigworld/client/filter.hpp  L30-45
class Filter : public MovementFilter
{
public:
    Filter( PyFilter * pOwner );
    virtual ~Filter();
protected:
    const PyFilter * pOwner() const { return wpOwner_.get(); }
private:
    WeakPyFilterPtr wpOwner_;
};
```

`Filter` 继承自 `MovementFilter`(在 `lib/connection/` 里),持有 `PyFilter` 弱引用(让 Python 端能配置 C++ Filter)。三个核心方法(在基类定义):

- **`reset(time)`**:重置到某个时间点。
- **`input(time, spaceID, vehicleID, pos, posError, dir)`**:接收一个位置输入。
- **`output(time, target)`**:输出当前时间应有的位置到 target(实体)。

#### 13.27.3 AvatarFilter:标准玩家 Filter

```cpp
// programming/bigworld/client/avatar_filter.hpp  L24-76 (节选)
class AvatarFilter : public Filter
{
public:
    static const uint NUM_STORED_INPUTS = AvatarFilterHelper::NUM_STORED_INPUTS;

    AvatarFilter( PyAvatarFilter * pOwner );
    ~AvatarFilter();

    float latency() const;
    void  latency( float v );

    void addCallback( AvatarFilterCallback * pCallback );

    const AvatarFilterHelper::StoredInput & getStoredInput( uint index ) const
    { return helper_.getStoredInput( index ); }

    void reset( double time );

    virtual void input( double time, SpaceID spaceID, EntityID vehicleID,
                        const Position3D & pos, const Vector3 & posError,
                        const Direction3D & dir );

    virtual void output( double time, MovementFilterTarget & target );
protected:
    virtual bool tryCopyState( const MovementFilter & rOtherFilter );
private:
    virtual void onEntityPositionUpdated( Entity & entity ) {}
    AvatarFilterHelper helper_;
    ListNode callbackListHead_;
};
```

`AvatarFilter` 是**绝大多数生物实体**用的 Filter,核心思想是:

> **存一个输入历史,把"现在时间"往前偏移一段 latency,在历史区间内插值输出。**

`AvatarFilterHelper` 维护 `NUM_STORED_INPUTS` 个历史输入(典型 4 个)。`output(time, target)` 时:

1. 算出 `outputTime = time - latency`。
2. 在历史输入中找到 `outputTime` 落在哪两个输入之间。
3. 在这两个输入之间做位置插值(典型 Catmull-Rom 样条,平滑且经过控制点)和方向插值(球面插值 slerp)。
4. 调用 `target.set(...)` 把插值结果写到实体。

**关键点**:`latency` 是关键参数——它代表"客户端故意把实体位置滞后多少秒显示"。这个滞后换来的是平滑性:即使网络抖动 100ms,实体也不会卡顿,因为显示的是 100ms 前的位置,客户端有 100ms 的"缓冲"来吸收抖动。代价是玩家看到的实体位置比"真实"位置滞后 latency 秒。

`AvatarFilter` 还支持 callback 列表(`addCallback`),当实体经过某个输入点时回调——用于脚步声、动画事件等"按时触发"的逻辑。

## 第十部分:特色实现深度剖析

讲完各组件,我们看几个特别值得学习的设计。

### 13.29.1 App/Module 的模板方法模式

appmgr 的 `App::updateFrame` 是教科书级的模板方法:

```cpp
// 固定骨架(基类)
void App::updateFrame( bool tick )
{
    calculateFrameTime();             // 1. 算 dTime
    InputDevices::processEvents(...); // 2. 处理输入
    EngineStatistics::tick(dTime);    // 3. 全局 tick
    Moo::AnimatingTexture::tick(dTime);
    Moo::Material::tick(dTime);
    Moo::rc().effectVisualContext().tick(dTime);

    ModulePtr pModule = ModuleManager::instance().currentModule();
    if (pModule)
    {
        if (!Moo::rc().checkDevice()) { Sleep(100); return; }   // 设备丢失

        pModule->updateFrame( dTime );          // 4a. 子类实现
        Moo::rc().beginScene();
        Moo::rc().nextFrame();
        pModule->updateAnimations();            // 4b. 子类实现
        pModule->render( dTime );               // 4c. 子类实现
        ConsoleManager::instance().draw( dTime );
        Moo::rc().endScene();
        Moo::rc().present();
    }
}
```

骨架规定了:**输入 → tick → checkDevice → updateFrame → beginScene → updateAnimations → render → endScene → present** 这个固定顺序。Module 子类只关心 `updateFrame/updateAnimations/render` 三个虚函数的实现,不用担心"什么时候 beginScene"。

**演化的轨迹**:客户端 14.x 不再使用 Module 栈,而是 `MainLoopTask` 链。但**模板方法没变**——`App::updateFrame` 的骨架还是这个,只是把 `pModule->xxx()` 换成 `MainLoopTasks::root().xxx()`,按依赖顺序遍历每个 task。这就是良好抽象的力量:**当需求从"单模块状态机"演化到"多任务链"时,骨架完全不变,只是把"调用哪个对象"换了一种遍历方式**。

### 13.29.2 Moo 封装 D3D 的设计

Moo 的封装分三层:

```
应用代码           Moo::rc().beginScene() / Visual::draw() / ...
                       │
                       ▼
业务抽象层         RenderContext / Visual / Material / Node / Light
                       │                       (类型/语义)
                       ▼
设备抽象层         DX::Device / DX::Texture / DX::VertexBuffer
                       │                       (类型别名)
                       ▼
原生 API          IDirect3DDevice9 / IDirect3DTexture9 / ...
```

**关键决策**:

1. **`DX::` 命名空间只做 typedef**:不做行为封装。这让"未来换 API"成本最低——只改别名定义,业务代码不动。
2. **业务抽象层不直接暴露原生接口**:`Visual::draw` 返回 HRESULT,但内部调用的是 `DX::Device::DrawIndexedPrimitive`。如果未来要换 D3D11,只需要在 `Visual::draw` 内部把 DrawIndexedPrimitive 换成 DrawIndexed,业务调用方不变。
3. **`RenderContext` 持有"当前状态"**:矩阵、相机、灯光、帧时间。这让"绘制函数不需要传一堆参数",而是直接从 `Moo::rc()` 取。
4. **`DeviceCallback` 自动设备管理**:任何持有 D3D 资源的类继承它,自动被通知设备丢失/恢复。这是"观察者模式"对 D3D9 设备丢失问题的标准解。

**这种分层在 D3D9→D3D9Ex 演化时确实发挥了作用**——`DX::Interface`/`InterfaceEx` 双别名让代码同时支持两种接口,只需要在 init 时根据可用性选择。未来如果 BigWorld 要迁到 D3D11,虽然工作量仍然巨大(深度依赖固定管线的 Material 要重写),但**核心架构是支持的**。

### 13.29.3 Filter 系统的插值平滑

Filter 系统解决"网络抖动下的视觉平滑"问题,本质是**用延迟换取平滑**:

```
服务器发送位置:        P0 ──────── P1 ──────── P2 ──────── P3
                       10Hz       10Hz        10Hz        10Hz
                       t=0.0      t=0.1       t=0.2       t=0.3

客户端收到时间:        P0          P1            P2          P3
                       t=0.05      t=0.18       t=0.27      t=0.42
                       (网络延迟50ms, 抖动30ms)

AvatarFilter 输出:    ▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓
                     (在 P0/P1 之间插值,显示 t-latency 的位置)
                     latency = 100ms
```

关键点:

1. **历史存储**:`NUM_STORED_INPUTS` 个历史输入,典型 4 个,覆盖约 400ms。
2. **延迟参数 `latency`**:控制"显示比真实滞后多少"。太短(<网络抖动)会抖动,太长(>500ms)会让操作反馈迟钝。典型 100-200ms。
3. **样条插值**:不是线性插值,而是 Catmull-Rom 样条——经过控制点且 C1 连续,曲线更自然。
4. **方向 slerp**:方向用四元数球面插值,避免欧拉角的 Gimbal Lock。
5. **错误修正 `posError`**:服务器发的位置可能和客户端预测不一致,Filter 会渐进修正(每帧拉近一点),而不是瞬移。

这个设计在 MMOG 领域是经典——QUake/Source/UE 都有类似机制。BigWorld 的特色是把它做成可配置的 `Filter` 类层次(Dumb/Avatar/Boids/PlayerAvatar/AvatarDrop),不同实体类型用不同 Filter,且 Python 端可以通过 `PyFilter` 配置参数(例如 `setLatency`)。

### 13.29.4 客户端/服务器实体的一致性

客户端 Entity 和服务器 Entity 是两个不同的类,但它们**共享同一份 def 文件**:

```xml
<!-- 我的实体定义 my_entity.def -->
<Entity>
    <Client>...</Client>     <!-- 客户端字段/方法 -->
    <Cell>...</Cell>          <!-- CellApp 字段/方法 -->
    <Base>...</Base>          <!-- BaseApp 字段/方法 -->
</Entity>
```

每个 `<Property>` 在三处都可以有定义,定义内容一致(类型、长度)。这保证:

- 服务器 CellApp/CellApp 修改实体位置 → 序列化为二进制 → 网络发送 → 客户端 `Entity::onProperty` 接收 → 反序列化 → 通过 `PyEntity` 转发给 Python `BigWorld.Entity` 实例。
- 客户端调用 `BigWorld.Entity.cell.<method>(args)` → 经由 PyEntity → BaseApp/CellApp 远程方法调用 → 服务器执行。

**`EntityType` 与 `EntityTypeManager`** 在客户端加载 def 文件,生成字段表,让二进制流反序列化按字段 ID 找到正确的 setter。这是 BigWorld 跨进程一致性的关键——**def 是 Single Source of Truth**。

`Entity::tick` 在客户端每帧被调用,负责驱动 Filter 输出新位置、tick Python 端的实体逻辑。服务器实体没有"渲染",所以 tick 只关心业务逻辑;客户端实体 tick 既关心业务(脚本)又关心表现(模型、动画、Filter)。这种"双 tick"机制让客户端和服务器能跑不同的代码,但通过同一份 def 共享数据契约。

## 13.30 本章小结

我们从两个维度看完了客户端的核心:

- **应用框架维度**:`appmgr` 提供了 App/Module/ModuleManager 的模板方法 + 工厂 + 栈式状态机;客户端 `App` 演化为基于 `MainLoopTask` 链的多任务架构,但模板方法的骨架没变——`updateFrame` 一帧的"输入→tick→updateAnimations→render→present"流程依然清晰。
- **渲染框架维度**:`Moo` 用三层封装(DX 别名 / 业务抽象 / 应用代码)隔离了 D3D9 的细节,通过 `DeviceCallback` 处理设备丢失,通过 `Node` 树管理场景图,通过 `Visual/Material/Primitive/Vertices` 组织网格资源,通过 `IRendererPipeline` 支持 deferred/forward 两条管线,通过 `TextureManager`/`RenderTarget`/`FogHelper` 管理纹理/目标/雾效。

加上客户端实体系统——`Entity` 继承 `BWEntity`,通过 `Filter`(Dumb/Avatar/Boids)做位置平滑插值,通过 `PyEntity` 桥接 Python,既保持了与服务器实体的数据契约(共享 def),又能驱动客户端表现(模型、动画、Trap)。

下一章我们会进入 BigWorld 的另一个客户端侧核心:**`chunk` 系统**(空间分块、室内外无缝、传送门)和 `space`(空间管理),看客户端是怎么把"无穷大世界"切成可管理的块的。
